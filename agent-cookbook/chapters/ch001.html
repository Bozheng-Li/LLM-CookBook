前言：为什么是 Agent，为什么是现在

2022 年 ChatGPT 让机器学会了「说话」，2023 年之后，业界真正关心的问题变成了：机器什么时候能「办事」？本章回答三个问题：Agent 到底是什么、它为什么恰好在此时爆发、以及这本书打算怎样把你从旁观者变成构建者。

从「聊天」到「办事」：一次范式迁移

先看两个真实到近乎平淡的场景。场景一：你问客服机器人「我的订单为什么还没到」，它用 300 字解释了物流流程——每句话都对，但没有一句解决问题。场景二：你把同样的问题交给一个 Agent，它查询了订单系统，发现包裹卡在中转仓，对比了承运商的时效承诺，直接发起了催件工单，并在两分钟后回复你：「包裹延误 18 小时，已催件，预计明天 14:00 前送达，若再次延误将自动升级处理并补偿运费。」——两者的差距不是模型智力，而是系统能力：能不能查、能不能做、能不能对结果负责。

把大语言模型（Large Language Model, LLM）放进产品，你很快会撞上同一堵墙：模型只能输出文本，而现实世界的任务需要动作。用户要的不是「如何退货的说明」，而是「帮我把这单退了」。这个落差，就是 Agent（智能体）存在的全部理由——让模型不仅可以说，还可以做：调用工具、检索资料、执行代码、操作浏览器，并在每一步之后观察结果、修正方向，直到任务完成。

用一句话定义这本书的主角：

Agent = LLM + 工具 + 记忆 + 循环。LLM 负责决策「下一步做什么」，工具负责「真正去做」，记忆负责「记住做过什么」，而循环把三者串成一个可以持续运行、自我修正的系统。

这个定义看起来平淡，但它的含义深远：一旦「决策」由模型完成而不是由开发者预先编排，软件的形态就从「确定性的流程图」变成了「目标驱动的开放系统」。工程师的工作重心，从「写清楚每一步怎么走」转变为「设计好目标和约束，然后信任（并验证）模型的选择」。第 14 章会把这种转变拆解成可操作的工程语言。

📘 术语约定

本书中的 Agent、智能体、AI Agent 是同义词；在需要区分时，「Workflow（工作流）」指由开发者预先编排好每一步的系统，「Agent」指由模型自主决定下一步的系统。这个区分来自 Anthropic 的工程实践文章《Building Effective Agents》（2024），我们将在第 14 章正式采用它。

为什么是现在：三个条件同时成熟

「能感知环境并采取行动以达成目标」的 Agent 定义，在人工智能教科书里至少存在了三十年（Russell & Norvig《人工智能：现代方法》第一版 1995 年就已把 Agent 作为中心组织概念）。真正的问题从来不是「想不想做」，而是「凭什么现在能做成」。答案是三个条件在 2022-2024 年间同时成熟：

第一，模型智力跨过了可用性阈值。GPT-4（2023）之后的旗舰模型在代码生成、指令遵循、长上下文理解上达到了「能当助手」的水平；2024 年 9 月 OpenAI o1 与 2025 年 1 月 DeepSeek-R1 相继验证了「推理时多花算力换正确率」的强化学习范式（第 43 章），模型第一次能在行动前进行长链条的规划与自查——而这正是 Agent 可靠性的瓶颈所在。

第二，工具生态完成了标准化。2023 年 6 月 OpenAI 把 Function Calling 做成正式 API 能力，工具调用从「解析正则表达式的技巧」变成「稳定的接口约定」；2024 年 11 月 Anthropic 发布 MCP（Model Context Protocol），并在此后一年内被 OpenAI、Google 等主要厂商采纳，工具生态第一次出现了「写一次、处处可用」的 USB-C 式标准（第 36 章）。

第三，成本与延迟降到了产品临界点以下。与 2023 年初相比，同等能力模型的推理价格下降了两个数量级左右（以 MMLU 等基准上持平性能的价格衡量），加上批处理、缓存与级联路由（第 78 章），「让模型跑几十步循环」从奢侈行为变成了可以计入成本的工程决策。

三个条件缺一不可，这条判断有反例支撑：2023 年 AutoGPT 手握工具循环却因模型推理太弱而沦为玩具；同期不少学术原型证明了可行性，却因数十美元的单任务成本无法商用；而工具生态不标准化时，每个 Agent 都要为每个工具写一遍胶水代码，生态繁衍不起来。当三者同时就位，增长就不是线性的，而是网络效应式的：工具越多 → Agent 越有用 → 更多人为 Agent 建工具（MCP 服务器数量在发布后一年内从个位数增长到数千个的量级）。

这是一本什么书

市场不缺 Agent 教程，缺的是一本既讲清楚「为什么」，又给得出「怎么做」，还标明「边界在哪」的完整参考。这本书的写作遵循四条原则：

  • 全景但不失焦。从 Transformer 的注意力机制到 Agent 强化学习（RLVR、Agent RL），从 Prompt 注入防御到生产级可观测性，13 个部分 113 章覆盖了截至 2026 年的主要版图——但每章都收敛到一个明确的问题，不为了全而堆料。
  • 可运行优先。凡是能写成代码的，就给出能跑的代码。第 27 章会在 200 行 Python 里写完一个最小 Agent，后续所有机制（规划、记忆、反思）都在这个骨架上生长。我们不希望你「理解了」却写不出来。
  • 文献支撑。每个关键论断都尽量回溯到论文或一手工程资料（附 arXiv 编号），100 篇核心论文的地图与精读见第 99-104 章。这让你有能力辨别：哪些是经过验证的知识，哪些是社区流行但未经检验的说法。
  • 诚实的边界。Agent 领域充斥着宣传。本书会在每一处标明「实验室数字」与「生产现实」的差距——比如多 Agent 系统的通信成本（第 24 章）、基准分数与实际效用的偏离（第 50 章）。

这本书写给谁

三条主线读者，对应三条学习路径（详见第 2 章）：

  • 开发者 / 学生：你会 Python（或 TS），想进入这个领域。路径：第 14-17 章建立直觉 → 第 27 章手写最小 Agent → 第 81-88 章做完八个实战项目。
  • 工程师 / 架构师：你要把 Agent 做成可靠的产品。路径：机制篇全读 → 框架与协议篇（第 26-37 章）选型 → 评测篇（第 50-57 章）与安全篇（第 58-65 章）建立质量与安全体系。
  • 研究者 / 算法工程师：你关心模型为什么能做到这些、下一步怎么变得更强。路径：训练与强化篇（第 38-49 章）→ 理论篇（第 91-98 章）→ 论文库篇（第 99-104 章）。

与 Agent 相关的三种职业角色

如果你正在规划职业方向，Agent 浪潮创造了三种需求曲线完全不同的岗位，本书对三者的训练侧重也不同：Agent 应用工程师（本书最大受众）负责把模型能力组装成产品，核心竞争力是机制理解 + 系统工程 + 评测素养，对应路径 B；Agent 算法工程师 / 研究员负责让模型本身更会做事——工具调用训练、Agent RL、过程奖励设计，核心竞争力是强化学习功底 + 实验能力，对应路径 C；AI 产品经理 / 技术管理者负责决定「该不该做、做到什么程度」，核心竞争力是能力边界感 + 成本风险测算 + 验收设计，对应路径 A + 第 5、6、8 部分的选读。三种角色的面试考察差异与题库见第 110-112 章。

一个来自招聘市场的观察（截至 2026 年中）：应用工程师岗位数量最多但竞争在加剧，算法岗位集中在头部实验室与少数自研企业，而「既懂机制又能管预算」的技术管理者是三者中最稀缺的——因为 Agent 项目死于管理失误（不设验收、盲目追新、预算失控）的比例不亚于死于技术失误。本书因此把「诚实的边界」当作贯穿立场，而不仅仅是技术态度。

不需要机器学习背景也能读完全书的前半部分；训练篇需要基础的深度学习概念（梯度、损失函数），我们会在入口处给出最小补充。

⚠️ 给决策者的提醒：投资回报的时间刻度

如果你是带着「采购或立项」目的来的，先校准预期：把一个 Agent 从 Demo 做到生产，机制实现通常只占工期的三成左右，其余消耗在评测集建设、护栏与权限设计、可观测性与灰度机制上——本书用整整三个部分（第 5、6、8 部分）讲这些「不性感但决定生死」的环节。行业里常见的时间感是：一周做出演示，一季度做到可用，一年做到省心。预算与耐心按这个刻度分配，项目存活率会高得多。

先尝一口：20 行的 Agent 循环

在展开理论之前，先给你看这本书反复出现的核心结构。下面这段 Python 代码是一个真正能运行的最小 Agent（依赖 openai SDK，模型可替换为任何兼容接口）：它让模型在「调用工具」与「给出答案」之间自主选择，循环往复直到任务完成。

python最小 Agent 循环（完整版见第 15/27 章） 
from openai import OpenAI
import json

client = OpenAI()  # 需设置环境变量 OPENAI_API_KEY

def search(query: str) -> str:
    """示例工具:真实场景可换成任意检索/数据库/HTTP 调用"""
    return f"《寄生虫》获得2020年第92届奥斯卡最佳影片(2019年上映)"

tools = [{
    "type": "function",
    "function": {
        "name": "search",
        "description": "搜索外部信息",
        "parameters": {
            "type": "object",
            "properties": {"query": {"type": "string"}},
            "required": ["query"],
        },
    },
}]

messages = [{"role": "user", "content": "2020年奥斯卡最佳影片是哪部?上映年份是?"}]

for step in range(10):                      # 刹车一:步数上限
    r = client.chat.completions.create(
        model="gpt-4o-mini", messages=messages, tools=tools)
    msg = r.choices[0].message
    messages.append(msg)
    if not msg.tool_calls:                  # 模型决定不再调用工具 → 任务完成
        print(msg.content)
        break
    for tc in msg.tool_calls:               # 执行每个工具调用
        args = json.loads(tc.function.arguments)
        result = search(**args)
        messages.append({"role": "tool", "tool_call_id": tc.id,
                         "content": result})  # 观察结果回填上下文

亲手运行它，你会看到三次关键交互：第一轮，模型不直接回答（它不确定自己的知识），而是输出一个 search 工具调用，参数是它自己拟的查询词；你的代码执行工具，把结果作为 role 为 tool 的消息追加进对话；第二轮，模型读到搜索结果，综合出最终答案并停止调用工具。整个过程没有一行 if-else 在判断「用户意图」——所有分支决策都发生在模型内部，这就是「模型驱动决策」判据（第 3 章）的代码级含义。

同时请留意这段代码刻意「没做」的事：没有重试与限流（第 12 章）、没有记忆持久化（第 19 章）、没有步数之外的任何刹车（第 15 章）、没有注入防护（第 59 章）、没有 trace 记录（第 79 章）。这些「没做」就是全书剩余 112 章的目录——每章都会回到这段代码，为它增加一层生产级能力。到第 89 章结束时，你会得到一个与 2026 年商业 Agent 产品同构的完整系统，而它的每一行你都亲手写过或理解过。

💡 阅读建议

如果你现在就想动手：把上面的代码跑起来，然后试着把 search 换成一个真实可用的工具（比如调用 Wikipedia API），观察模型行为的变化。这种「改一下、跑一遍」的节奏，是读这本书最有效的方式。

附记：这本书是怎么写出来的

作为一本 2026 年的书，它的诞生方式本身就是本书方法论的演示：全书由一个「多智能体协作流水线」写成——统一的目录规划（toc.json 作为唯一事实来源）、统一的写作规范（STYLE_GUIDE.md）、十余个专职「写作智能体」按章分工，每一章完成后都要通过自动质检脚本（字数、结构、插图、引用、链接有效性等硬指标），再经过多轮「评审智能体」从文字质量、图示准确性、阅读观感等维度独立盲审并打回修改。这个流水线的工程细节，与你在第 24 章（多智能体系统）和第 57 章（LLM-as-Judge）读到的机制同源——我们用本书所教的技术写了这本书，全部脚本开源在仓库 tools/ 目录，欢迎审计与复用。

这也解释了本书的一个立场：对 AI 生成内容，「是否有严谨的验证流程」比「是否由 AI 写作」更重要。人写的百科全书有错误，经过多轮独立评审与引用核查的机器辅助写作可以更可靠——关键在于流程而非出身。我们在安全篇（第 64-65 章）讨论治理时，会回到这个立场。

本书的承诺与不承诺

我们承诺：读完后，你能独立设计、实现、评测并上线一个生产级 Agent 系统；能读懂该领域的主流论文；能对「要不要上多 Agent」「用不用框架」「怎么防注入」这类问题给出有依据的判断。这三个承诺分别对应三重检验：拿一个真实需求，你能在两周内交付一个带评测的可用系统（检验工程能力）；拿到一篇新论文，你能在两小时内判断它的贡献成色与可复现性（检验理论素养）；拿到一份「Agent 转型」的汇报或提案，你能问出五个让对方露出思考表情的问题（检验判断力）。

我们也不回避失败案例：书中专设「常见坑」与排错手册（附录 B），收录了实践中最高频的 30 种故障模式——从「模型无限重试同一个失败调用」到「评测集被训练数据污染导致的虚假高分」。在 Agent 领域，知道什么会坏，往往比知道什么能跑更值钱。

我们不承诺：不承诺任何「一夜暴富式」的方法论——Agent 领域没有银弹；不承诺每个数字都精确到个位——对快速演化的领域，我们更愿意给你量级和出处，而不是虚假的精确；不承诺内容永远不过时——但我们把「哪些思想是稳定的、哪些细节是易变的」在每章中明确区分，思想的生命周期远长于框架 API。

最后一个阅读心态的建议。Agent 领域的舆论场昼夜颠倒：上午「Agent 将取代所有软件」，下午「Agent 都是套壳玩具」。这本书请你在两极之间保持第三种姿态——把宣言换成机制，把惊叹换成评测。任何让你兴奋或愤怒的说法，都可以拆解成可检验的工程命题：它声称的环节由谁决策？观察从哪来？失败如何被度量？这套拆解习惯，就是本书要教给你的最重要的元技能。

本章小结

  • Agent = LLM + 工具 + 记忆 + 循环；它把软件从「确定性流程」变成「目标驱动的开放系统」。
  • Agent 在 2022-2024 年爆发，是模型能力、工具标准化（Function Calling、MCP）、成本下降三个条件同时成熟的结果。
  • 本书覆盖 13 部分 113 章：机制、框架、训练与强化、评测、安全、多模态、前沿、实战、理论、论文与项目库。
  • 30 行代码即可写出一个最小 Agent；所有框架都是这个内核的工程增强。
  • 本书由多智能体协作流水线写成，全部构建脚本开源；对 AI 生成内容，重要的是验证流程而非出身。
  • 最重要的元技能：把任何说法拆解成「谁决策、观察从哪来、失败如何度量」的工程命题。
  • Agent 创造三种职业角色：应用工程师、算法研究员、技术管理者——本书用不同路径训练三者，而「诚实的边界」是共同的职业素养。
  • 第 1 章的 30 行代码是全书的「基准点」：后续每章为它补一层生产能力，读完书 = 亲手造出一个完整系统。
