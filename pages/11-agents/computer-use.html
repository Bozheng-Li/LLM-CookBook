Computer Use 与 GUI Agent

当 Agent 不再局限于「调 API」，而是直接「用你的电脑」——看屏幕、点按钮、填表单——人机交互的形态就变了。但这条路远比想象中难：OSWorld 上的成功率至今离「可靠」很远。这一页拆解屏幕理解、坐标定位与操作序列生成的技术栈，以及真实差距到底在哪。

一图看懂

GUI Agent 的循环：截屏（或读取可访问性树）→ 模型理解界面 → 决定下一步操作（点哪里、输入什么）→ 执行 → 观察新状态，循环直到任务完成。与 API Agent 最大的区别是：它面对的是「人看的界面」，而不是「机器读的接口」。

一、GUI Agent 与 API Agent 的本质区别

很多人以为 GUI Agent 只是「会截图的多模态 Agent」，实际上它和 API Agent 是两种完全不同的范式。API Agent 面对的是结构化的接口：参数明确、返回值确定、错误可捕获。GUI Agent 面对的是「为人类设计的界面」：像素、坐标、布局、视觉层级——这些信息天然是模糊的、高噪声的。

维度API AgentGUI Agent
交互对象结构化接口人类界面（像素）
反馈信号明确返回值屏幕变化（模糊）
错误处理异常捕获视觉状态判断
成功率高低（OSWorld ~20-40%）
通用性受接口覆盖限制任意应用可用
典型场景云服务、数据库、工具调用遗留系统、桌面应用、浏览器自动化
一句话直觉 API Agent 是「机器对机器」，GUI Agent 是「机器假装成人」——假装会看、会点、会判断界面状态。后者要处理的信息噪声大得多，这也是成功率差距的根本来源。

这个「假装成人」的比喻值得再展开一层，因为它揭示了 GUI Agent 的核心矛盾：人类界面的一切设计都是为「人的感知和动作」优化的，而不是为「机器的感知和动作」优化的。按钮要做成多大，取决于人的手指和鼠标能不能点中；界面布局要清晰，取决于人的注意力；操作反馈要直观，取决于人能不能一眼看出发生了什么。而机器面对的是一堆像素——没有「语义层级」，没有「焦点概念」，连「这个按钮现在能不能点」都只能从灰度和状态推断。这就是为什么一个人类三秒钟就能完成的操作，GUI Agent 往往需要好几步外加出错重试。

「用人类的方式操作手机 App」这个方向，有一篇被广泛引用的论文可以当第一手教材——AppAgent。它展示了 LLM 驱动的多模态 Agent 如何在完全不接入系统后端的情况下，靠「看屏幕 + 点/滑」操作真实的手机应用。看它的论文原图：

手把手读这张图。图是若干个小分镜拼成的「多应用巡礼」——每个分镜里是一个真实的手机界面截图，配上 Agent 的动作标注（点击哪、滑向哪）。要抓住的不是「它认识很多 App」，而是每个分镜里的动作形态：全部是 tap（点）和 swipe（滑）这类极简动作。这正是 AppAgent 的核心设计——把动作空间压缩成「人怎么用手操作」的少数几种，模型不需要输出精确到像素的坐标，只需要在「界面元素编号」或「网格」上选择目标。对比你会在本页后面看到的「直接输出 (x,y) 坐标」方案，这种「元素级动作」牺牲了一点通用性，换来了可验证性和成功率。

另一个值得注意的细节：AppAgent 不是「上来就点」，而是先有一个探索阶段——Agent 先在 App 里自主乱点、观察每个界面长什么样，把「这个 App 有哪些页面、每个按钮做什么」记成一份文档；到了部署阶段，它查这份文档再决定怎么操作。这其实就是本页「页面状态跟踪」和「屏幕记忆」两个概念的雏形：把「每帧屏幕」升级成「对界面结构的持续理解」。这篇论文在 50 个任务上验证了可行性——但请注意，这些任务大多是单个 App 内的操作，和 OSWorld 那种跨应用长任务的成功率（20-40%）不在一个难度量级。读到这篇论文时，把它当成「GUI 交互可行性的证明」，而不是「GUI Agent 已经可靠」的证据。

另一个常被低估的差异是「接口的稳定性」。API 的字段名和格式由文档定义，版本之间有明确契约；而 GUI 的布局、文案、控件在每个版本里都可能变——按钮从一个位置挪到另一个位置，弹窗文案换了个说法，这些对人是无感的改变，对 GUI Agent 却是「界面完全变了」。这意味着 GUI Agent 需要持续的「界面漂移检测」：定期用回归任务集跑一遍，一旦成功率显著下降，就说明上游应用改版了，模型需要重新适配。这个维护成本在规划 GUI Agent 项目时就要算进去，它不像 API Agent 那样「接一次就能稳定跑很久」。

二、感知：截图、可访问性树，还是两者混合

GUI Agent 感知界面的方式直接决定能力上限，三种方案各有取舍：

感知方式原理优点局限
纯截图 + 视觉模型多模态模型直接看图通用、不看实现细节坐标定位精度差、token 贵、小元素看不清
可访问性树读 DOM / a11y 结构精确、便宜、元素语义全依赖应用暴露结构，游戏/视频等场景拿不到
混合截图给视觉 + 树给语义取长补短，当前主流两路要对齐，实现复杂度高

工程现实：浏览器内用 DOM 树最可靠；操作系统级（桌面应用）则更依赖截图 + 辅助功能接口；纯视觉方案是「最后的通用手段」，也是当前成功率最低的。

3.2 一个 GUI Agent 循环的最小实现

import pyautogui
from PIL import ImageGrab

class GUIAgent:
    """最小 GUI Agent：截屏 → 理解 → 操作 → 再截屏"""

    def __init__(self, vlm, max_steps=20, screenshot_dir="./screens"):
        self.vlm = vlm          # 视觉语言模型
        self.max_steps = max_steps
        self.screenshot_dir = screenshot_dir

    def act(self, task):
        """执行一个 GUI 任务，直到完成或达到步数上限"""
        history = []
        for step in range(self.max_steps):
            # 1. 截取当前屏幕
            img = ImageGrab.grab()  # 全屏截图
            img.save(f"{self.screenshot_dir}/step_{step}.png")

            # 2. 让 VLM 理解界面并决策
            decision = self.vlm(
                image=img,
                prompt=(
                    f"任务：{task}\n"
                    f"历史操作：{history}\n\n"
                    "请输出 JSON："
                    '{"thought": "你的思考", "action": "click|type|scroll|done", '
                    '"args": {...}}'
                )
            )

            # 3. 解析并执行操作
            act = decision["action"]
            if act == "done":
                return {"status": "success", "steps": step,
                        "answer": decision.get("answer")}

            self._execute(act, decision["args"])
            history.append({"step": step, "action": act,
                            "args": decision["args"]})

        return {"status": "max_steps", "steps": self.max_steps}

    def _execute(self, action, args):
        """把决策变成真实操作"""
        if action == "click":
            x, y = args["x"], args["y"]
            pyautogui.click(x, y)
        elif action == "type":
            pyautogui.typewrite(args["text"])
        elif action == "scroll":
            pyautogui.scroll(args.get("clicks", -3))
        # ... 更多动作类型

上面的实现刻意保持了最小，它缺少一个对成功率影响最大的环节——执行后的校验。生产级的 GUI Agent 循环不是「截屏→操作→再截屏」的裸循环，而是「操作 → 等待 → 验证预期变化 → 确认或修正」的闭环。把一步操作放大看，真实时序是这样的：

引入校验后，成功率曲线完全不同。设单步操作的错误率为 5%，20 步任务若不做校验，最终成功率约 \((0.95)^{20} \approx 36\%\)，错误全部累积；做了执行后校验，假设校验能发现并修正 80% 的错误，那么每一步的「有效错误率」降到约 1%，20 步后成功率提升到约 82%。这不是理论推演——几乎所有把 GUI Agent 成功率从个位数推到 30-50% 的工程实践，核心都落在「校验与纠错」上。

四、为什么成功率上不去：OSWorld 的教训

OSWorld 是目前最权威的 GUI Agent 基准之一：模型需要在真实的操作系统（Windows/Ubuntu/macOS）上完成 369 个真实任务（文件操作、浏览器、办公软件等），评估最终屏幕状态而非中间动作。到 2025 年，最好的模型成功率也只有 20-40%——远低于 API Agent 的 90%+。

  • 视觉理解不足：模型能认出「大按钮」，但认不出「图标含义」「禁用状态」「hover 提示」这些精细语义；
  • 坐标精度差：VLM 输出的坐标普遍有 5-10px 偏差，小按钮直接点不中；
  • 状态追踪弱：点击后页面可能异步加载（弹窗、转圈、变灰），模型难以判断「现在是什么状态」；
  • 长序列误差累积：每一步有 5% 错误率，20 步之后成功率掉到 $(0.95)^{20} \approx 36\%$——错误像滚雪球。

还有一个不在四大瓶颈之列、但同样致命的问题：评测基准本身偏向「简单任务」。OSWorld 的 369 个任务虽然真实，但大多是「打开文件另存为」「在浏览器里搜索并收藏」这类单个应用内的操作；跨应用协作（比如「把邮件附件里的表格填进另一个应用的表单」）的占比很小，而这恰恰是真实办公场景里最耗时的部分。所以当你看到某个模型的 OSWorld 分数时，要意识到这个数字代表的是「单应用内任务的完成率」，离「替人类完成一整天的工作」还有很大距离。

理解这些瓶颈的具体成因，也就能理解为什么「换一个更强的视觉模型」往往不是灵丹妙药。坐标精度差不是模型变笨了，而是「从像素到坐标」这个映射本身存在不确定性——一个 30px 宽的小按钮，5-10px 的偏差就是「点没点中」的差别；状态追踪弱也不是模型不懂界面，而是异步加载产生的「中间状态」信息密度极低，模型从一帧静态图里根本看不出来。这些问题的解法不在模型端，而在系统端：用可访问性树拿精确坐标、用状态机判定页面状态、用执行后校验拦截错误。这也印证了本页反复强调的观点——GUI Agent 的工程问题，靠的是架构设计而不是模型堆料。

关键结论 GUI Agent 目前适合「人工监督的半自动场景」——用户盯着它干活，出错时人工纠正。完全无人值守的 GUI 自动化，在绝大多数业务场景里还不现实。

五、一步操作要多久：延迟预算拆解

GUI Agent 的另一个现实问题是慢。一个「点击几下、填个表单」的简单任务，跑起来往往要一两分钟，用户很难等得起。要理解为什么慢，就得把一步操作的耗时拆开看。一步完整操作由四个串行环节组成：截屏、模型理解、执行操作、等待界面稳定。把典型耗时列出来：

环节典型耗时优化空间
截屏（全屏 PNG）50-200 ms裁剪感兴趣区域、降低分辨率
VLM 理解 + 决策1-4 秒小模型路由、缓存相似界面
执行操作10-100 ms基本无优化空间
等待界面稳定0.5-3 秒轮询停止条件代替固定延迟

加总起来，一步操作约 2-6 秒，一个 15 步的任务就是 30-90 秒。瓶颈一目了然：VLM 决策占了大头。这解释了为什么「动作空间约束」和「执行后校验」能显著提效——它们都能减少不必要的决策轮次。比如动作白名单限制了模型只能在「点击/输入/滚动」里选，模型就不用反复纠结要不要做复杂操作；执行后校验把「一次做错、五次重来」的浪费压到「发现即修正」。还有一个立竿见影的优化是等待策略：很多实现用固定延迟（比如每次操作后固定等 2 秒），但真实界面有时 0.5 秒就稳定、有时要 5 秒。改成轮询——每 200ms 截一次图，对比界面状态变化，直到「不再变化」或超时——平均每步能省下 1 秒以上。

展开：延迟预算的完整算例

假设一个表单填写任务需要 12 步操作。方案 A（固定延迟 2 秒、无校验、VLM 每次全屏决策）的耗时估算：12 步 × (1.5 秒截屏决策 + 0.05 秒执行 + 2 秒固定等待) ≈ 12 × 3.55 ≈ 43 秒。

方案 B（轮询等待平均 0.8 秒、动作白名单、执行后校验，假设 20% 的步骤需要修正重做一次）的耗时估算：12 步中约 10 步一次通过、2 步需要重做，共约 14 步有效操作 × (1.0 秒裁剪决策 + 0.05 秒执行 + 0.8 秒轮询) ≈ 14 × 1.85 ≈ 26 秒。

同样是完成任务，方案 B 比方案 A 快约 40%，而且成功率更高。这个例子说明：GUI Agent 的「性能优化」和「成功率优化」经常是同一种手段的两面——减少决策轮次、缩短无效等待、尽早发现错误，对延迟和成功率同时有益。

以上数字是工程经验参考值，不同模型和界面差异较大，建议在自己的环境里实测「一步决策耗时」和「界面稳定时间」两个基准数据，再代入上面的框架计算。

六、提高成功率的工程手段

尽管整体成功率不高，业界已经沉淀出一套「工程提分」的手段，把成功率从个位数推到 30-50%：

手段具体做法提升效果
高分辨率输入裁剪目标区域放大后识别小元素识别率 +30%

七、页面状态跟踪：从「看一帧」到「看懂状态机」

GUI Agent 的一大痛点不是「看不见」，而是「不知道当前处于什么状态」。网页和桌面应用大多是异步的：点击按钮后，可能出现转圈、按钮变灰、内容局部刷新、弹窗覆盖——这些状态变化在截图里都能看到，但模型很难从「上一帧 vs 这一帧」的差异里准确推断「系统正在做什么、还要不要等」。这正是「状态追踪弱」这个瓶颈的根源。

工程上把界面建模成状态机，比让模型每次都从头理解一帧截图可靠得多。一个典型的交互页面有四个状态：空闲、加载中、有弹窗、出错。模型每执行一个动作，就预测「应该转移到哪个状态」，然后和截图观察到的实际状态比对——对不上就说明动作没生效或者出现了预期外的情况，需要等待、重试或回退：

状态机的收益是双重的。一是等待策略更聪明：传统做法是固定延迟，状态机则让 Agent 在「加载中」状态持续轮询，直到观察到「空闲」或「出错」——界面 0.5 秒稳定就 0.5 秒继续，5 秒稳定就等 5 秒，不浪费也不过早。二是错误定位更准：当 Agent 预期「空闲」却观察到「出错」时，错误被精确定位到「上一次动作」，可以当场重试该动作或换个方式，而不是让错误悄悄滚进后续步骤。

实现状态机不需要复杂的框架。做法是给模型一个固定的「状态标签集合」以及「当前状态下允许的动作」约束，让模型在输出 JSON 时同时输出 {"predicted_next_state": "加载中", "action": "click", ...}，宿主代码负责「执行动作 → 轮询截图 → 判定实际状态 → 与预测比对」。宿主侧的判定可以是一个轻量的视觉模型或者干脆用 DOM/a11y 树的变化事件（浏览器场景），这样状态判定从「模型主观判断」变成了「代码确定性判断」，可靠性完全不同。

新手最容易搞错 新手最容易把 GUI Agent 当成「会截图的多模态 Agent」，以为核心是「让视觉模型看图更准」。实际上 GUI Agent 的成功率瓶颈大半在系统侧：坐标怎么定（元素引用 vs 裸坐标）、动作怎么约束（白名单）、界面状态怎么判（状态机 vs 猜）、错误怎么纠（执行后校验）。「换一个更强的视觉模型」通常只能提升一点识别率，而「加上执行后校验 + 状态机」能把成功率从个位数推到 30-50%。另一个常见误解是把 OSWorld 的分数当成「整体能力」——OSWorld 的 369 个任务大多单应用操作，跨应用长任务占比很小，看到某个模型 40% 的分数时，要清楚这离「替人干一整天活」还差很远。

八、安全与风险：GUI Agent 的放大效应

GUI Agent 拥有「操作真实系统」的能力，这意味着它的安全风险比只输出文本的模型大一个量级——一个错误的点击可能是删除文件、购买商品、发送邮件。安全设计是上线前的必修课。

防御层做法拦截目标
动作白名单只允许点击/输入/滚动删除、格式化等危险动作
人工确认破坏性操作弹窗确认删除文件、支付等不可逆操作
沙箱隔离在虚拟机/容器内运行系统级破坏
审计日志记录每一步操作事后追溯与取证
权限最小化按任务授予最小权限越权访问

工程建议：未验证的 GUI Agent 只能在沙箱中运行；任何不可逆操作必须有人工确认环节；全程保留审计日志。这是 GUI Agent 从「演示」走向「生产」的硬门槛。

十、从单步操作到完整任务：规划层是成功率的放大器

前面讨论的校验、状态机、动作白名单，都是在「单步操作」这个尺度上做文章。但真实任务几乎都不是「点一下」——而是「把下载文件夹里的文件按类型分类整理」这种十几步的序列。当任务超过四五步，只靠「走一步看一步」的贪心策略，模型很容易在局部细节里迷失：每一步都对，但整体目标悄悄丢了。这引出了 GUI Agent 的第二个关键组件——规划层。

规划层的工作可以拆成三段：任务拆解、子任务执行、动态重规划。拆解阶段，规划器把「整理下载文件夹」拆成「列出所有文件 → 按类型分组 → 建立分类子目录 → 移动文件 → 检查残留」五个子任务；执行阶段，Agent 逐个推进，每个子任务内部仍然是「感知—决策—执行—校验」的微循环；重规划阶段最关键——当某个子任务连续失败，或环境出现预期外的变化（比如文件夹里多了一个加密压缩包），Agent 要能停下当前的拆解方案、重新拆解，而不是硬着头皮把原计划走完。很多翻车现场，问题恰恰出在「规划之后不再回头看」。

规划层带来的收益有一个直观的算例。设单步成功率为 95%、执行后校验能发现并修正 80% 的错误（即单步「有效失败率」约 1%），一个 15 步的任务直接贪心执行，最终成功率约为 86%；而如果任务被拆成 3 个子任务、每个子任务结束后做一次「结果是否符合子目标」的检查，一次检查能拦下后续所有步骤的连带错误，那么只要子任务层不跑偏，最终成功率可以压到 95% 附近。差别不在单步，而在「错误有没有机会滚雪球」——规划层的检查点相当于把 15 次相乘的失败率，压缩成 3 段相乘的失败率。

但规划层不是免费的午餐。它的代价主要是 token 与延迟：每个子任务开始前，都要把目标、进度、已观察到的环境重新打包给模型；规划器自己的输出也要花时间。粗略估算：一个 5 子任务的任务，规划层额外消耗约 1-2 次模型调用、2-4 秒；如果拆成 20 个子任务，开销就涨到 4-8 次调用、8-16 秒——对一个总时长 30-90 秒的任务来说，这已经不能忽略。所以工程上的取舍是：规划粒度要和任务复杂度匹配——简单任务给「粗计划 + 自动续完」，复杂任务才需要「细计划 + 关键节点人工确认」。常见的失败模式也源于此：拆得太细，模型在计划上反复推演、迟迟不行动；拆得太粗，规划层形同虚设。实践里比较可靠的做法是「先粗后细」的两级规划，并用「子任务完成率」这个指标动态调整粒度：连续两个子任务一次通过，就放宽粒度；连续失败，就切细。

展开：坐标偏差 5 像素是怎么毁掉一次点击的

很多人觉得「坐标偏移 5px 没什么大不了」——直到亲眼看到它怎么毁掉任务。以 1080p 屏幕上的一个小按钮为例：假设「保存」按钮是 30px × 20px，VLM 输出的坐标 (540, 400) 恰好命中中心。但 VLM 的坐标误差普遍在 5-10px 量级——如果实际落点是 (548, 400)，就偏出按钮右边界 8px，这一下点到了按钮旁边的空白区域，界面没有任何反应。

这还不是最糟的。如果按钮旁边正好是「删除」按钮，一次 6px 的偏移可能直接点错对象——而且 Agent 往往察觉不到，因为它「看到」屏幕发生了变化，却不知道变化不是它想要的那个。这正是本页强调「执行后校验」的原因：

# 错误恢复的简化逻辑：操作后验证预期变化
def safe_click(x, y, expected_change):
    pyautogui.click(x, y)
    before = screenshot()
    ok = wait_until(lambda: has_expected_change(before, expected_change), timeout=3)
    if not ok:
        # 没发生预期变化 → 认为点错了，回退或改用元素引用重试
        revert()  # 或换成 a11y 树里的元素定位
        return retry_with_element_reference()

对抗坐标误差的三板斧：① 优先用元素引用（a11y 树编号）代替裸坐标；② 必要时对目标区域裁剪放大后再让 VLM 精确定位；③ 永远在操作后校验「预期变化是否发生」。前两条减少误差，第三条拦截误差——缺一不可。

要点速查

  • 本质：GUI Agent 让模型「假装成人」操作界面，感知像素、输出坐标、判断状态；与 API Agent 是两种范式。
  • 感知三方案：纯截图（通用但精度差）、a11y 树（精确但覆盖窄）、混合（主流）。
  • 定位三方式：直接坐标（简单易错）、元素引用（精准）、网格坐标（粗粒度稳定）。
  • 成功率瓶颈：视觉理解不足、坐标偏差 5-10px、状态追踪弱、长序列误差累积（$0.95^{20} \approx 36\%$）。
  • 提分手段：高分辨率裁剪、动作白名单、执行后校验、错误恢复、屏幕记忆。
  • 当前定位：人机协同的半自动场景，不适合无人值守关键业务。
  • 常见坑：期望 GUI Agent 达到 API Agent 的可靠性；忽略异步加载状态；不做执行后校验让错误滚雪球。
