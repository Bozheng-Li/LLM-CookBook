Agent 算法：从反应式循环到可验证执行

把 Agent 理解为一个带工具、状态和失败恢复的闭环系统，而不是“会调用函数的聊天机器人”。

本页结论：Agent 的核心算法是状态估计、动作选择、环境反馈和终止判定。提示词只定义了策略的一部分，工具契约、权限、轨迹和评测决定系统是否可靠。

1. 形式化：Agent 到底在优化什么

将一次任务表示为部分可观测决策过程。环境状态为 s_t，模型只能看到观测 o_t，历史轨迹为 h_t=(o_0,a_0,...,o_t)。策略 pi(a_t|h_t) 选择自然语言回复或工具动作，工具执行后返回新的观测。一个有副作用的 Agent 还必须维护权限状态 p_t 和预算 b_t。

while not terminal(state) and budget > 0:
    context = compose(goal, state, memory, tool_schemas)
    action = policy(context)
    action = validate_schema_permission_idempotency(action)
    observation = execute(action, timeout=deadline)
    state = update(state, action, observation)
return answer_or_handoff(state)

与普通生成不同，动作会改变外部世界。因此正确性至少包含任务结果、工具参数、状态转移和副作用四层。失败时优先修复状态或工具输入，不能让模型凭空补全工具结果。

2. 算法谱系：ReAct、规划与反思

范式控制流优势典型失败
ReActThought -> Action -> Observation 交替短链探索、工具反馈及时循环、重复搜索、把猜测当观察
Plan-and-Execute先生成步骤图，再逐步执行长任务可视化、易于审批计划过时，局部错误传播到后续步骤
ReWOO/无思考执行预先绑定变量与工具结果减少模型调用和 token无法适应动态环境
Reflexion失败后生成可检索的反思记忆能把失败转成下一次策略提示反思内容空泛，记忆污染后续任务

工程上通常采用混合结构：确定性编排器负责权限、重试、并行和终止，模型只在需要语义判断的节点选择动作。规划器输出的不是不可验证的自然语言，而应是带依赖、输入和验收条件的结构化计划。

3. 工具调用：契约比提示词更重要

工具 schema 至少需要名称、参数类型、必填字段、权限范围、超时、幂等键、错误码和结果大小上限。执行前做参数校验和越权检查，执行后把原始结果、摘要和可信度分开保存，避免把未经处理的网页内容直接拼进系统提示。

{
  "name": "create_ticket",
  "input": {"title": "string", "priority": "enum(low,high)"},
  "auth": {"scope": "ticket:write", "approval": "required"},
  "runtime": {"timeout_ms": 5000, "idempotency_key": "required"}
}

MCP 统一了工具发现、资源和提示的协议边界，但不替应用承担最小权限、审计和提示注入防护。对写操作应设置预览/审批节点；对读操作也要限制返回字段和数据租户范围。

4. 轨迹学习与 Agentic RL

一条可训练轨迹应包含目标、环境快照、模型消息、工具调用、真实结果、错误、最终状态和人工/程序评分。只保留成功答案会丢失恢复策略；只保留模型思考会掩盖工具和环境因素。常见训练顺序是行为克隆或 SFT 打底，再用成功/失败轨迹做偏好优化，最后在可验证环境中做 RFT/RLVR。

终局奖励可写成 R = success - lambda_cost * cost - lambda_risk * risk。工具调用次数、输出长度和格式都可能成为捷径，因此奖励必须按工具、任务和轨迹长度分层归一化，并用独立 verifier 检查真正目标。

5. 评测与故障模式

至少报告：任务成功率、步骤成功率、工具参数准确率、重试次数、token、p50/p95 延迟、成本、越权率和人工接管率。故障注入应覆盖超时、空结果、错误 schema、部分成功、重复写入、提示注入和环境状态变化。

实践检查：实现一个最多 8 步的 Agent，给写工具加入幂等键和人工审批；保存完整轨迹，分别统计“答对但越权”“工具正确但任务失败”“重试后恢复”三类结果。
