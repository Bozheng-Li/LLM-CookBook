MoE 混合专家

如何让模型拥有几千亿参数的「知识容量」，却只花几百亿参数的「推理成本」？答案是稀疏激活：每个 token 只唤醒一小撮相关的「专家」。MoE 已从研究概念变成 2026 前沿模型的默认架构。这一节从路由机制讲到负载均衡，从训练稳定性讲到推理部署，配上完整代码和 DeepSeek 架构剖析。

一图看懂

把 Transformer 里那个稠密的前馈网络（FFN）拆成许多个小 FFN（专家），再加一个路由器（Router）。每个 token 进来，路由器只挑选 Top-K 个最相关的专家去处理，其余专家完全不激活。于是总参数量巨大（能力强），但单次实际计算量很小（成本低）。

稠密 vs 稀疏：核心区别

理解 MoE，先分清两个关键的参数概念。这两个概念的解耦是 MoE 的全部价值所在：

总参数量 Total Params

模型拥有的全部参数，决定知识容量的上限。MoE 可以做到极大（如 DeepSeek-V3 达 671B）。

激活参数量 Active Params

处理单个 token 实际参与计算的参数，决定推理成本与速度。DeepSeek-V3 每次仅激活 37B。

维度稠密模型 Dense稀疏模型 MoE

显存占用较低高（所有专家都要驻留显存）
训练稳定性成熟稳定需处理负载均衡等难题

一句话直觉 MoE 用「显存换算力」——参数都存着（占显存），但每次只算一部分（省算力），换来「大模型能力、小模型成本」。代价是显存需求暴增：671B 参数的模型即使量化后也需要多卡才能装载。

算一笔账：Mixtral 8×7B 的参数从哪来

"8×7B 却只有 46.7B 而不是 56B"是很多人第一次看到 Mixtral 时的疑惑。把参数拆开数一遍，MoE 的账就彻底清楚了。Mixtral 8×7B 的配置是 $d_{model} = 4096$、FFN 中间维度 $d_{ff} = 14336$、32 层、8 个专家、每 token 选 2 个。它用的是 SwiGLU，一个 FFN 里有三个大矩阵（gate、up、down），所以：

$$\text{单个专家参数} = 3 \times d_{model} \times d_{ff} = 3 \times 4096 \times 14336 \approx 1.76\times10^8$$

也就是每个专家约 1.76 亿参数。一层有 8 个专家，32 层共 $8 \times 1.76\text{亿} \times 32 \approx 451$ 亿。再加上注意力层、词嵌入和输出头约 16 亿，总计约 467 亿（46.7B）——和官方数字对上了。之所以不是 $8 \times 7 = 56$B，是因为注意力层和词表在 8 个"7B"之间是共享的，没有复制 8 份，重复计算了才会得出 56B。

激活参数同理：每个 token 只走 2 个专家，$2 \times 1.76\text{亿} \times 32 \approx 113$ 亿，加上共享的注意力和嵌入约 16 亿，得到约 129 亿（12.9B）。于是这个模型的性格就出来了：推理时的算力开销接近一个 13B 稠密模型，但知识容量对标 47B 级别；显存却要按 47B 准备。

"稀疏比"这一列是 MoE 设计里最有信息量的指标。早期 MoE（Mixtral 一代）只有 3.6×，因为专家数少（8 个）、每次选得多（2 个）。DeepSeek-V3 把稀疏比推到 18×，靠的是专家切得更细（256 个）而每次仍只选 8 个。稀疏比越高，"用小算力买大容量"的杠杆就越大——但显存代价和路由难度也同步上升。DeepSeek-V3 的 1342 GB BF16 权重意味着最少要 17 张 80 GB 卡才装得下，这不是普通团队能承担的部署。

MoE 的经济学：省的是算力，花的是显存和带宽 如果你的瓶颈是训练/推理算力（有卡但每张卡算不快，或者按 FLOPs 计费），MoE 极其划算。如果你的瓶颈是显存容量（比如只有一两张卡、要做端侧部署），MoE 是纯粹的负担——同样 16 GB 显存，稠密模型能跑 8B，MoE 只能跑一个激活参数 2B 左右的小模型。选型前先想清楚自己卡在哪一头。

路由机制：怎么选专家

路由器是 MoE 的大脑，通常就是一个小小的线性层。它为每个 token 计算对所有专家的亲和度分数，再选出得分最高的 K 个：

MoE 的路由机制最早被画进论文，是从 Switch Transformer 那张著名的「编码器块」示意图开始的。它也是理解「MoE 到底改了什么」的最直观一页：在普通 Transformer 编码器里，前馈网络（FFN）是一整个稠密模块；Switch Transformer 把它替换成一个「路由器 + 多个小 FFN 专家」的稀疏结构。

这张图是 MoE 新手的第一张地图，逐块看有四件事：① 大块的蓝色区域是「稀疏 Switch FFN 层」，它整体替换了原来的稠密 FFN——层数、输入输出维度都不变，接缝处无需改动；② 图里画了两个 token（x₁="More"、x₂="Parameters"），用实线表示它们被路由器分别派往不同的专家——注意每个 token 是「独立」路由的，这正是稀疏激活与稠密 FFN「所有 token 过所有参数」的分水岭；③ 路由器的输出不是硬开关——专家输出还要乘以一个门控权重（图上虚线表示的 gate value），这个权重让路由器可微、能训练；④ 图里只画了 4 个专家、每个 token 去 1 个——对应 Switch 的 Top-1 简化，而 GShard / Mixtral 的 Top-2 只是「选 2 个专家再加权」的推广。

需要特别指出：Switch Transformer 论文里用的是 Top-1 路由（每个 token 只去一个专家），这是它比 GShard 更「激进」的简化——训练更快、通信更少，但路由决策也更脆弱。今天的 MoE 模型大多回到 Top-2 或细粒度 Top-8，但「路由器打分 → 门控加权 → 只算选中专家」这个骨架，全部源自这张图。

$$g = \text{Softmax}(x \cdot W_g), \qquad y = \sum_{i \in \text{Top-}K(g)} g_i \cdot E_i(x)$$

其中 $W_g$ 是路由器权重，$g_i$ 是第 $i$ 个专家的门控权重，$E_i(x)$ 是第 $i$ 个专家的输出。只有进入 Top-K 的专家才会被计算和加权。

一个容易踩的实现细节：Softmax 在 Top-K 之前还是之后

上面的公式写的是"先 softmax 再取 Top-K"，但工程实现里有两种常见写法，结果并不等价：

  • 先 Softmax 后 Top-K：在全部 $N$ 个专家上做归一化，再挑出最大的 $K$ 个，保留它们各自的概率值。此时被选中的 $K$ 个权重加起来不等于 1（剩下的概率质量被丢掉了）。好处是权重的绝对大小反映了"路由器有多确信"——如果 Top-1 只拿到 0.15，说明模型很犹豫，这个信号会传递到输出的幅度上。
  • 先 Top-K 后 Softmax：先按原始 logits 选出 $K$ 个，再只在这 $K$ 个上做归一化。权重严格加和为 1，输出幅度稳定，训练更平滑。Mixtral 用的就是这种。

这个选择会实打实影响训练稳定性。前者在路由器不确定时输出幅度会缩水，相当于给残差流注入了一个随机缩放，早期训练容易震荡；后者则丢失了"确信度"信息，但换来了稳定。绝大多数现代实现选后者，因为幅度稳定对深层网络太重要了。上一节代码里的 weights = F.softmax(weights, dim=-1) 正是在 topk 之后做的，就是这个道理。

Top-K 里的 K 该取几

$K=1$（Switch Transformer 的做法）是最省算力的极端：每个 token 只过一个专家，通信量和计算量都减半。但它有一个理论上的麻烦——路由决策是离散的，$K=1$ 时门控权重 $g_i$ 是唯一一个能给路由器传梯度的通道。如果某个专家从来没被选中，它的路由权重就永远收不到梯度，只能靠辅助损失硬推。

$K=2$ 是长期以来的默认值（GShard、Mixtral 都是），因为它提供了"比较"：两个专家的输出被加权混合，路由器能通过调整权重比例学到"谁更合适"，梯度信号明显更好。代价是算力和通信翻倍。

$K \geq 8$ 只在细粒度专家的设定下才合理。DeepSeek 的思路是：既然要激活 8 个，那就把每个专家做小 8 倍，总激活算力不变，但"从 256 个里选 8 个"的组合数（约 $4\times10^{14}$）远远大于"从 8 个里选 2 个"（28 种）。组合空间的爆炸式增长，就是细粒度专家带来表达力提升的根本原因。

展开：DeepSeek 的细粒度 + 共享专家设计

DeepSeek-V3 采用了两项关键设计，成为 2025-2026 MoE 的标杆：

  • 细粒度专家（Fine-Grained）：把专家切得更小更多（如 256 个路由专家），每次激活 8 个。更细的粒度让专家能学到更专精的知识，组合空间也更大。
  • 共享专家（Shared Expert）：设置 1 个始终激活的共享专家，负责处理所有 token 都需要的通用知识，让路由专家能专注于差异化的专业知识，避免知识冗余。

这套「1 共享 + 256 路由、每次激活 8 个」的配置，是 DeepSeek 实现 671B 总参数 / 37B 激活的关键。

负载均衡：MoE 的头号难题

如果放任路由器自由学习，它会倾向于把大多数 token 都发给少数几个「明星专家」——这些专家越练越强、越强越被选中，形成马太效应。结果是大部分专家闲置，模型容量白白浪费，还可能训练崩溃。

常见的解决方案：

  • 辅助负载均衡损失（Auxiliary Loss）：在训练目标里加一项惩罚，鼓励 token 均匀分配到各专家。
  • 无辅助损失均衡（Aux-Loss-Free）：DeepSeek-V3 采用为每个专家维护一个可动态调整的偏置项，避免辅助损失干扰主任务的梯度。
  • 专家容量（Capacity Factor）：给每个专家设一个 token 处理上限，超出的 token 被丢弃或转发。

容量因子与丢 token：一个必须算清楚的数

"专家容量"这个概念之所以存在，是因为 GPU 上的专家计算必须写成固定形状的张量运算。你不能让专家 3 这一步处理 1800 个 token、下一步处理 200 个——那样每一步都要重新分配缓冲区、核函数无法预编译，效率崩溃。所以工程实现要求：每个专家的输入缓冲区大小是提前固定好的，装不下的 token 只能溢出。

容量的计算公式很简单：

$$\text{capacity} = \left\lceil \text{CF} \times \frac{T \times K}{N} \right\rceil$$

其中 $T$ 是这一批的 token 总数，$K$ 是每 token 选中的专家数，$N$ 是专家数，$\text{CF}$ 是容量因子（capacity factor）。分式部分 $T\cdot K/N$ 是"完全均匀分配时每个专家该拿多少"，CF 是留出的余量。

代入具体数字：一批 $T = 4096$ 个 token，$N = 8$ 个专家，$K = 2$。均匀情况下每个专家该拿 $4096 \times 2 / 8 = 1024$ 个。取 CF = 1.25，容量就是 1280。现在假设路由器学偏了，某个热门专家被分到 1800 个 token——超出容量的 520 个 token 会被丢弃，占该专家 token 的 29%，占整批的约 6%。这些 token 在这一层什么都没算，直接靠残差连接穿过去（这就是所谓的"残差转发"，token 至少不会变成零向量），但它们在这一层确确实实没有获得任何 FFN 变换。

这里有一个反直觉但很重要的现象：丢 token 在训练时反而有一点"正则化"作用——它逼着路由器不要过度集中，因为集中的代价是自己选的 token 被扔掉。但在推理时丢 token 是不可接受的，因为它会造成输出的不确定性：同一句话，因为和它同批的其他请求不同，被丢弃的 token 也不同，结果就不可复现了。所以生产推理引擎普遍采用 dropless 方案——用分组 GEMM（grouped GEMM）或稀疏矩阵核函数支持变长的专家输入，代价是核函数实现复杂得多。MegaBlocks 就是把 MoE 计算改写成块稀疏矩阵乘来实现无丢弃训练的代表工作。

调试线索 如果你训练 MoE 时发现 loss 曲线有规律的锯齿、或者验证集指标显著低于训练集，先查丢弃率。很多框架会输出每层的 tokens_dropped 或 capacity_overflow 指标。丢弃率长期高于 5% 基本可以断定负载均衡出了问题，先把 CF 临时提到 2.0 观察，再回头调均衡机制。

无辅助损失均衡是 2025 年最被推崇的做法。它不在损失函数里加惩罚项（那会损害主任务），而是给路由分数额外加一个可学习的偏置 $b_e$：过载的专家偏置自动下降、少被选中，闲置的专家偏置上升、多被选中。这个偏置按"本步各专家实际负载"在线更新，不进入反向传播的主梯度。下面这段伪代码展示了它的更新逻辑：

# 无辅助损失均衡：为每个专家维护可更新的偏置 b_e
# 路由分数 = softmax(x · W_g + b)，偏置 b 按负载在线调整，不进主梯度
def update_bias(bias, expert_counts, target, lr=1e-3):
    # bias: [num_experts]；expert_counts: 本步各专家被选中的 token 数
    imbalance = expert_counts - target        # > 0 表示该专家过载
    return bias - lr * imbalance               # 过载专家偏置下降，少被选中
负载不均不只是效率问题 如果 80% 的 token 都去 2 个专家，这 2 个专家成为训练瓶颈（梯度更新集中在它们身上），而其他专家几乎不被训练——等于你花了几百亿参数的钱，实际只用了几十亿参数的能力。更严重的是，未被充分训练的专家在推理时可能产生不可预测的输出。
新手最容易搞错 很多新手把「总参数 671B」和「显存 671B」混为一谈，或者反过来以为「只激活 37B 就不用装下 671B」。正确的账是这样：MoE 省的是算力（FLOPs），一分钱都没省显存。所有专家权重必须全部驻留在显存里（哪怕这次推理只用到其中 8 个），因为下一次推理可能用到任何一个。所以 MoE 的部署账本永远是「按总参数算显存、按激活参数算速度」——这也是为什么 MoE 模型几乎必然配量化、多卡和张量并行，纯靠单卡根本装不下。还有个常见误区：路由器的 Top-K 不是「投票后取众数」，而是所有被选中专家的输出按门控权重加权求和——是「混合」，不是「挑选一个」。

专家并行：MoE 的分布式训练与推理

MoE 的一个核心工程挑战是：所有专家都要驻留显存，但 671B 参数的模型单卡装不下。解决方案是专家并行（Expert Parallelism）——把不同的专家放到不同的 GPU 上。

专家并行引入了一个新的通信模式：All-to-All——每张 GPU 都可能需要把 token 发送到其他 GPU 上的专家，也要接收其他 GPU 发来的 token。这个通信量比普通数据并行的 All-Reduce 大得多，是 MoE 训练效率的主要瓶颈。

正因为每次跨卡都要两轮 All-to-All（发出去、收回来），MoE 训练对网络带宽极度敏感。这也是为什么 DeepSeek 这类超大 MoE 通常部署在 IB（InfiniBand）网络、甚至采用"专家并行 + 通信计算重叠"来隐藏延迟。

通信量估个数量级

抽象地讲，一次 MoE 层的 All-to-All 通信量大约是：每张卡上有 $T$ 个 token，每个 token 要发往 $K$ 个专家，每份数据是 $d_{model}$ 维的隐状态。所以单卡发出的字节数约为 $T \times K \times d_{model} \times \text{dtype\_bytes}$，收回来的结果同样大小，一层共两轮。

代入 $T = 4096$、$K = 8$、$d_{model} = 7168$、BF16：单卡单层单向约 $4096 \times 8 \times 7168 \times 2 \approx 470$ MB。一个有 58 个 MoE 层的模型，一次前向就要搬 $58 \times 470\text{MB} \times 2 \approx 54$ GB。反向传播还要再来一遍。这就是为什么 MoE 训练必须上 InfiniBand 或 NVLink——普通以太网的带宽会让 GPU 大部分时间在等网络。

手段做法效果限制
通信-计算重叠把一批 token 切成若干微批，第 $i$ 批在通信时第 $i+1$ 批在算注意力理想情况能把通信时间几乎完全藏起来需要精细的流水线编排，微批太小会让 GEMM 效率下降
限制跨节点路由约束每个 token 最多只能路由到有限个节点（如 DeepSeek 的节点受限路由）把昂贵的跨节点通信压到可控范围轻微限制了路由自由度，需要与均衡机制配合
降低通信精度All-to-All 传输时用 FP8 甚至更低精度通信量直接减半需要硬件支持与数值验证

还有一个容易忽略的点：All-to-All 的耗时由最慢的那张卡决定。如果负载不均，某张卡上的专家收到了两倍的 token，其他所有卡都要等它算完才能进入下一步。所以在分布式场景下，负载均衡不只是"容量利用率"的问题，它直接决定了整个集群的墙钟时间。这两个原本看起来独立的话题——路由均衡与通信效率——在超大规模训练里是同一个问题的两面。

推理时的挑战 推理时所有专家都要驻留显存——即使每次只激活 37B 参数，671B 参数的模型权重仍然需要全部加载。这意味着 MoE 模型的推理显存需求远大于同等激活参数的稠密模型。这也是为什么 MoE 模型的量化（见 量化）和 KV 缓存管理（见 KV 缓存）格外重要。

训练稳定性：MoE 特有的坑

MoE 训练比稠密模型更容易出问题，因为路由器的引入带来了新的不稳定性来源：

路由崩塌：最危险的失败模式

训练初期，路由器还没学好，可能把所有 token 都路由到同一个专家。这个专家被反复训练，越来越强；其他专家从未被激活，权重停留在初始化。一旦发生，模型等于退化成了一个只用了 1/N 容量的小模型——而且很难自我恢复。

防御方法：(1) 训练初期用较大的辅助损失权重强制均衡；(2) 路由器初始化时加入噪声打破对称性；(3) 监控专家利用率，如果发现崩塌趋势及时介入。

怎么判断路由是否健康

路由崩塌不是突然发生的，它有清晰的前兆。训练 MoE 时应该把下面几个指标和 loss 一起打到监控面板上，任何一个越界都值得停下来看：

指标怎么算健康区间越界意味着
负载变异系数 CV各专家 token 数的标准差 ÷ 均值< 0.3持续 > 1.0 说明少数专家在吃掉大部分流量
零激活专家数整个 epoch 内一次都没被选中的专家个数0> 0 就是实打实的容量浪费，这部分参数白存了
token 丢弃率溢出容量的 token ÷ 总 token< 1%> 5% 说明容量因子或均衡机制需要调整
路由熵门控分布的平均信息熵接近但低于 $\ln N$骤降表示路由器变得过度确信，是崩塌的早期信号
Top-1 权重均值最高分专家的门控权重的批平均0.4–0.8持续接近 1.0 说明退化为硬路由，梯度信号变差

其中路由熵是最灵敏的先行指标。健康的路由器应该保持一定的"犹豫"——熵接近均匀分布的上界 $\ln N$，说明它还在探索不同专家的组合。一旦熵在几百步内快速下降，往往意味着路由器找到了一条"偷懒捷径"：把所有 token 都塞给同几个专家，短期内 loss 也能降，但长期看整个模型的容量就被锁死了。这时候把辅助损失权重临时调大、或者给路由 logits 加一点高斯噪声，通常能把它拽回来。

另一个实践经验是不要在训练中途大幅改变专家数或 Top-K。路由器的权重是针对特定专家数训练出来的，改变 $N$ 相当于把它的输出维度换掉，需要重新学习整个路由空间。如果确实要扩容，业界的做法是"专家复制 + 加噪"：把已有专家复制一份、加上小扰动作为新专家，让路由器在此基础上继续分化，比随机初始化收敛快得多。

展开：MoE 层最小实现（PyTorch 风格） 
import torch
import torch.nn as nn
import torch.nn.functional as F

class MoELayer(nn.Module):
    def __init__(self, d_model, num_experts=8, top_k=2):
        super().__init__()
        self.top_k = top_k
        self.gate = nn.Linear(d_model, num_experts)          # 路由器
        self.experts = nn.ModuleList([
            nn.Sequential(nn.Linear(d_model, 4 * d_model),
                          nn.GELU(),
                          nn.Linear(4 * d_model, d_model))
            for _ in range(num_experts)
        ])

    def forward(self, x):                                    # x: (tokens, d_model)
        logits = self.gate(x)                                # (tokens, num_experts)
        weights, idx = torch.topk(logits, self.top_k, dim=-1)
        weights = F.softmax(weights, dim=-1)                 # 只对选中的专家归一化

        out = torch.zeros_like(x)
        for k in range(self.top_k):
            for e in range(len(self.experts)):
                mask = (idx[:, k] == e)                      # 选中专家 e 的 token
                if mask.any():
                    out[mask] += weights[mask, k:k+1] * self.experts[e](x[mask])
        return out

真实实现会用更高效的分组 gather/scatter 和专家并行（Expert Parallelism）来跨 GPU 分布专家，但核心逻辑就是「路由 → 选 Top-K → 加权求和」。

要点速查

  • 本质：把稠密 FFN 拆成多个专家 + 路由器，每 token 只激活 Top-K 个。总参数（容量）与激活参数（成本）解耦。
  • 收益：「大能力、小开销」——671B 参数的模型只花 37B 的推理成本。
  • 代价：所有专家占显存（显存需求暴增）；训练需解决负载均衡；All-to-All 通信开销大。
  • 路由公式：$g = \text{Softmax}(x \cdot W_g)$，选 Top-K，加权求和 $y = \sum g_i \cdot E_i(x)$。
  • 负载均衡：辅助损失 / 无辅助损失偏置调节（DeepSeek 路线）/ 专家容量限制。不解决会马太效应→路由崩塌。
  • 路由崩塌：最危险的失败模式——所有 token 只去少数专家，模型退化成小模型。防御：初期大辅助损失 + 噪声初始化 + 利用率监控。
  • 专家并行：不同专家放不同 GPU，All-to-All 通信是主要开销。
  • 前沿配置：细粒度专家 + 共享专家 + 无辅助损失均衡（DeepSeek 路线）。
  • 2026 现状：新架构中约七成采用 MoE，稠密模型在端侧仍有不可替代的地位。

关键问题与边界

Q1：MoE 节省的是算力还是显存？

标准回答：MoE 主要节省每个 token 的激活计算量，不直接节省总权重显存。总参数量决定模型容量，激活参数量决定单 token 的 FLOPs；部署时通常仍要让全部专家权重可访问，还要承担路由和通信开销。

常见误区：“37B 激活参数”不等于“只需要加载 37B 参数”。如果专家权重没有卸载或按专家分片，显存仍接近总参数量。

Q2：Top-K 路由为什么会导致专家负载不均？

标准回答：路由器会根据 token 表示选择专家，早期稍占优势的专家可能获得更多 token，训练后形成“越忙越被选”的反馈，导致其他专家闲置、热门专家溢出，甚至出现路由崩塌。

追问：如何监控和缓解？

训练中应记录每个专家的 token 占比、容量溢出率、丢 token 数量和路由熵。缓解方法包括辅助负载均衡损失、容量因子、路由噪声、专家偏置调节、Expert-Choice，以及 DeepSeek 风格的无辅助损失均衡。不能只看总 loss，因为总 loss 下降并不代表专家使用健康。

Q3：为什么 MoE 会引入 All-to-All 通信？

标准回答：在 Expert Parallelism 中，不同 GPU 放置不同专家。一个 batch 的 token 先在本地生成路由结果，然后需要把 token 发送到承载目标专家的 GPU，专家计算后再把结果发送回原设备，这两次跨卡重排通常就是 All-to-All 通信。

工程取舍：增加专家并行度可以装下更大的总参数，但会放大通信和负载不均问题；实际系统要结合互联拓扑、micro-batch、容量因子和专家放置共同设计。

Q4：Fine-Grained Experts 和 Shared Experts 解决什么问题？

标准回答：细粒度专家把 FFN 切得更细，让 Top-K 组合具有更灵活的容量分配；共享专家则为所有 token 提供一条稳定的公共知识路径，避免所有信息都依赖动态路由。两者可以在保持稀疏激活的同时改善专家专门化和训练稳定性。

常见误区：专家数量越多不一定越好。专家切得越细，路由选择空间、通信调度和负载均衡难度也会增加，必须用实际吞吐和质量评测验证收益。
