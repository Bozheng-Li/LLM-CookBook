混合推理与思考预算

推理模型对每个问题都"想很久"，但"法国首都是哪"这种问题不需要想。混合推理的目标是让模型自己判断：这个问题该快回答还是慢思考？该想 100 token 还是 10000 token？这就是思考预算（thinking budget）——推理算力的旋钮。问题在于，OpenAI、Anthropic、Google、Qwen 四家都做了这个旋钮，但接口设计互不兼容，参数名、控制粒度、行为语义全不一样。应用层要同时支持四家，就得做统一封装——而封装的复杂度本身就是一笔持续的技术债。

前置知识 本页假定你已理解推理模型的行为特征和训练范式，见 推理模型；并了解推理时扩展的基本概念，见 推理时扩展。如果你还不清楚 temperature 这类参数在推理模型上为什么常常无效，先看 解码策略。
一图看懂

混合推理的核心是快慢思考路由：简单问题走快通道（不思考或最少思考），困难问题走慢通道（长思维链）。思考预算控制慢通道"想多久"。理想状态下模型自主路由，但现实中用户/应用也需要能通过 API 参数手动控制。四家厂商的接口互不兼容是最大的工程痛点——同一个"调低思考量"的意图，在四家 API 上要写四套完全不同的参数。

先说清楚这一页在解决什么问题

推理模型带来的能力提升是真实的，但它有一个所有人在上生产之前都会低估的副作用：成本和延迟不再由输出长度决定，而是由「模型自己决定想多久」决定。

传统模型的成本模型很好算：输入 token 数 × 单价 + 输出 token 数 × 单价，输出长度还可以用 max_tokens 卡死。推理模型不一样——思维链也是要计费的 token，而且这部分长度由模型自己决定。同一个 API 调用，有时候思维链 200 token，有时候 8000 token，成本差 40 倍。对一个日请求量百万级的服务来说，这个方差是不可接受的：你没法给财务一个可靠的预算数字，也没法给用户一个可靠的延迟承诺。

混合推理就是为了把这个方差重新拿回控制之下。它包含两件事：

  • 路由：判断这个问题该不该思考，该走哪条通道。
  • 预算：如果要思考，允许它想多久。

这两件事在概念上很简单，但在工程上非常麻烦——麻烦不在算法，而在四家厂商把同一个概念做成了四套互不兼容的接口。本页的一半篇幅是在处理这个「接口税」。

Overthinking：想太多反而是问题

推理模型有一个违反直觉的失效模式：想太多反而答错。这叫 overthinking——模型对简单问题生成了不必要的冗长思维链，在过度推理中引入了错误。

要理解 overthinking 为什么是「训练出来的」，看一张论文原图最直观。下图是 DeepSeek-R1-Zero 在纯 RL 训练过程中，在 AIME 2024 数学竞赛题上的准确率曲线——它一路向上，最终超过 70%。这证明「答对」这个奖励确实被模型吃透并强化了。

把这张图和 overthinking 放在一起读，你会看到问题的根源：训练的奖励函数只有「答案对不对」这一项，没有「答得快」「别多想」「预算内完成」这些维度。于是 RL 发现「想得越久、答对的概率越高」这条捷径之后，就沿着它一路走下去——准确率曲线爬升的同时，思维链长度也在同步膨胀（这正是上一页 推理模型 里那张长度曲线展示的）。训练数据以竞赛级难题为主时，模型甚至完全没见过「简单题」，根本无从学会「简单题要快速收手」。overthinking 不是模型故意偷懒或犯傻，它是奖励函数设计缺失的必然产物——而思考预算，就是应用层在奖励函数之外补上的那个「别想太久」的旋钮。

Overthinking 的几种典型表现：

  • 简单问题复杂化："2+3=?"模型想了 2000 token，中间怀疑自己是不是理解对了题意，最后反而算错了。研究表明，在简单算术上，推理模型的错误率有时随思维链长度增加而上升。
  • 过度自我怀疑：模型已经得出了正确答案，但思维链继续"让我再检查一下"，在检查过程中把正确的改成了错误的。
  • 成本浪费：即使最终答案是对的，用 5000 token 思维链回答一个 50 token 就能搞定的问题，是纯粹的算力浪费。

Overthinking 的根源在于推理模型的训练信号：RLVR 奖励的是"答对"，不惩罚"想太久"。模型在训练中学会的是"多想更容易对"，但没有学会"什么时候该停"。这个偏差在训练数据全是困难问题（数学竞赛、代码竞赛）时尤其严重——模型从来没见过简单问题，不知道简单问题不需要多想。

怎么在日志里识别 overthinking

Overthinking 不会主动报错，它表现为「服务变慢变贵，但没人说得清哪里出了问题」。要把它抓出来，需要在观测层面盯几个信号：

这五个信号里最有实操价值的是翻转率。它是唯一能直接回答「多想到底有没有用」的指标，而且计算成本可控——只需要在一批离线样本上跑两遍。很多团队直到跑了这个实验才意识到：自己业务里有相当一部分题目，思考预算给多了反而掉点。

新手最容易搞错 "推理模型一定比普通模型好"——不对。在简单任务上，推理模型因为 overthinking 可能更慢、更贵、甚至更不准确。推理模型的价值在困难推理任务上，把它用在所有场景是典型的"用大炮打蚊子"。更麻烦的是，这种浪费在小流量测试时几乎看不出来，等到放量才会集中爆发成账单问题。另一个与之配套的误解是「预算给得越大越稳」——预算是上限不是目标值，给 32000 token 不代表模型会用满，但一旦遇到发散型题目，它就会实打实地烧满这 32000 token 再给你一个可能并不更准的答案。

思考预算：推理算力的旋钮

思考预算（thinking budget）是控制推理模型"想多久"的参数。它的物理含义是限制思维链的 token 数量——预算越大，模型可以想得越久，精度越高但延迟和成本也越高；预算越小，模型快速给出答案，成本低但可能精度不够。

理想情况下，思考预算应该由模型自主决定——模型自己判断问题难度，分配适当的思考量。实际上，推理模型在推理时确实有一定的自主判断能力（RLVR 训练让它学会了"难问题多想"）。但自主判断不完美——它会 overthinking 简单问题，也会在困难问题上偶尔过早收敛。所以厂商都提供了外部控制接口，让用户/应用可以覆盖模型的自主判断。

思考预算的设计有一个根本性的权衡：自主 vs 可控。

  • 完全自主（不给用户控制接口）：简单，但无法应对模型 overthinking 或 underthinking 的场景。
  • 完全可控（用户精确指定 token 数）：可控，但把难度判断的负担转嫁给了用户——用户怎么知道这个问题该想 500 还是 5000 token？

四家厂商在这条权衡线上选择了不同的位置，导致接口设计互不兼容。

预算是上限，不是配额

一个容易搞错的语义细节：思考预算通常是上限（cap）而不是目标值（target）。给 8192 的预算，不代表模型会想满 8192 token；简单问题它可能想 300 token 就收手了。预算的作用是「封顶」，防止发散。

这个语义差别在成本估算时非常关键。如果你按「预算 × 请求数」估算账单，几乎一定会大幅高估；实际成本取决于思考长度的真实分布，而这个分布通常是重尾的——大部分请求想得很短，少数请求顶到上限。所以正确的做法是：用 P50 估平均成本，用 P99 和预算上限估最坏延迟，两个数分开看。

预算耗尽时会发生什么

这是文档里往往一笔带过、线上却经常踩到的地方。当思考 token 撞上预算上限，理论上有四种可能的行为：

行为表现对调用方的影响应对
强制收敛停止思考，立刻基于当前进展给出答案答案质量下降但结构完整可接受；记录该请求「顶到上限」用于后续调参
返回空答案预算全部消耗在思考上，正文部分为空下游解析直接崩溃必须在客户端判空并重试，且重试时提高预算
报错返回一个明确的超限错误相对友好，至少不会静默出错按错误码分支处理
截断在思考中返回的内容里能看到半截思维链可能把内部推理泄露给终端用户输出前必须剥离思考段，见下文可见性一节

具体是哪一种，取决于厂商实现和模型版本，务必以各家官方文档和实测为准，不要假设。写封装层时最稳妥的姿势是：把这四种情况全部当成可能发生的，统一在一个地方判空、判错、判残缺，然后决定是降级返回还是提预算重试。

别让重试变成成本炸弹 「预算不够就提高预算重试」听起来很自然，但如果没有次数上限，一个持续失败的请求可能触发指数级的算力消耗——第一次 2048、第二次 8192、第三次 32000，加起来是原计划的 20 倍。重试必须设最大次数（通常 1 次就够）和总预算上限，超过就降级到非推理模型或直接返回失败。

来逐一拆解四套接口的设计逻辑和差异来源。

OpenAI：离散档位，抽象等级

OpenAI 的 o1/o3 系列用 reasoning_effort 参数，取值为 low、medium、high。用户不需要指定 token 数，只需要选一个"努力程度"等级，模型内部决定具体想多久。思维链不完整公开——用户只能看到摘要（reasoning summary），看不到完整推理过程。

这个设计的取向是最抽象、最用户友好：用户不需要理解"思考 token"是什么，只需要选"多想想"还是"少想想"。代价是控制粒度最粗——只有三档，无法精确控制成本。而且不能完全关闭思考（最低是 low），对简单问题场景不友好。

思维链不公开这件事，官方给出的理由通常包含两方面：一是安全与对齐考虑，未经润饰的原始思维链可能包含不适合直接展示的内容；二是竞争考虑，完整思维链是极高质量的蒸馏数据。对应用层的直接影响是：任何依赖读取完整思维链的功能（推理过程审计、把中间步骤展示给用户、用思维链做二次判断）在这条路线上都做不了。

Anthropic：token 级连续预算

Anthropic 的 Claude 系列用 thinking 参数，需要指定 type: "enabled" 和 budget_tokens（一个整数，表示思考的 token 上限）。思维链完整公开，在响应中以独立的 thinking block 返回。

这个设计的取向是最精确、最透明：用户可以精确控制思考 token 数，可以审计完整的思维链。代价是用户需要理解"token 数"的含义——一个不熟悉 LLM 的用户很难判断"这个问题该给 1024 还是 8192 token 的预算"。而且同样不能完全关闭思考（必须给一个最低预算值）。

「独立 thinking block」这个返回结构是个不小的便利：思考内容和最终答案在数据结构层面就是分开的，客户端不需要自己解析分隔符去切。相比之下，一些开源模型把思考包在特殊标记里混在正文流中，客户端就得自己做状态机来剥离——一旦标记没配对（比如被 max_tokens 截断），剥离逻辑就会出错，把内部推理直接漏给用户。

Google Gemini：连续预算 + 可关闭

Google 的 Gemini 2.5 系列用 thinkingConfig.thinkingBudget，同样是一个整数 token 上限。但 Gemini 的独特之处是可以设为 0 完全关闭思考——这是四家中唯一允许在 API 层面彻底关闭思考的。Gemini 也支持 thinkingLevel（none/low/medium/high）作为更高层的抽象，但两种模式的行为细节可能不同。

Gemini 的设计在灵活性上最强——既能精确控制（token 数），又能完全关闭，还有高层抽象（level）。但灵活性也意味着复杂性：同一参数的不同取值范围行为差异大，文档需要仔细读。特别要注意的是，「同时提供两套控制方式」本身就是一个隐患——当 thinkingBudget 和 thinkingLevel 同时被设置时的优先级规则，是封装层最容易写错的地方之一。

Qwen3：布尔开关

Qwen3 系列用 enable_thinking 布尔参数——要么开要么关，没有中间档。这是四家中最简单的接口，但也是最粗粒度的。部分 Qwen3 模型后续也加入了 thinking_budget 参数做更细粒度控制，但核心控制仍然是布尔开关。

开源模型还有一个闭源模型没有的变量：同一个权重在不同推理引擎下的参数名可能不一样。同样是关闭思考，在 vLLM、SGLang、Ollama、以及厂商自己的云服务上，暴露的字段名和传参位置都可能不同（有的在请求体顶层，有的在 chat_template_kwargs 里）。自建部署时这一层要单独测，不能照抄云 API 的写法。

Qwen3 的简单设计与其"先合后拆"的挫折直接相关——下一节详述。

思考 token 的计费与上下文占用

比参数名更容易被忽略的，是思考 token 在计费和上下文窗口两个维度上的行为。这两件事直接决定了你的账单和你的多轮对话能撑多久。

  • 计费：思考 token 一般按输出 token 计价，也就是说它们和最终答案一样贵。一次「思考 6000 token、答案 200 token」的调用，成本几乎全在思考上。所以看账单时不能只看用户可见的输出长度，必须把思考 token 单独统计成一个指标。
  • 上下文占用：思考内容是否会留在后续轮次的上下文里，各家处理不同。如果留着，多轮对话的上下文会以极快的速度膨胀；如果不留，模型在下一轮就「忘了」自己上一轮是怎么想的。两种设计各有代价，需要按你的场景确认。
  • 是否计入 max_tokens：思考 token 和答案 token 是否共享同一个输出上限，也是各家不一致的地方。共享时，一个大预算会挤占答案的空间，导致答案被截断。

这三点的具体行为都以各家官方文档为准，但无论哪家，落地时都要做同一件事：在观测系统里把「思考 token」和「答案 token」拆成两个独立指标。合在一起看，你永远搞不清成本涨了是因为回答变长了还是因为模型想多了，也就无从优化。

一个便宜的止损开关 在正式接推理模型之前，先在网关层加一条硬规则：单请求思考 token 超过某个阈值就记一条告警日志。这条规则几乎零成本，却能在放量当天就把「哪些场景在过度思考」暴露出来，比事后翻账单快得多。
展开：思考预算到底值多少钱——手算一张日账单

光说「思考 token 很贵」太抽象，拿一个真实的量级算一遍。假设你的服务日请求量 100 万次，普通模型的平均输出是 300 token。

第一步：全量切到推理模型，不做任何控制。推理模型平均「思考 3000 token + 回答 300 token」，单次 3300 token。日输出量 = 100 万 × 3300 = 33 亿 token，是普通模型的 11 倍。账单直接爆炸——这是很多团队第一次接推理模型后的真实经历。

第二步：加思考预算上限 4096，并利用「预算是上限不是目标值」的性质。大量简单题在想 300～500 token 时就自己收手了，平均思考量从 3000 压到约 800。日输出 = 100 万 × 1100 = 11 亿 token，降到约 3.7 倍。这一步几乎零工程成本，收益主要来自「让模型自己知道什么时候该停」。

第三步：加难度路由。假设 60% 的请求是简单题，路由到普通模型（300 token），40% 走推理模型（1100 token）。日输出 = 60 万 × 300 + 40 万 × 1100 = 1.8 亿 + 4.4 亿 = 6.2 亿 token，约是普通模型的 2 倍。这一步的收益来自「别让推理模型碰简单题」。

三步合计：从 11 倍压到 2 倍，质量指标基本不动。这个例子里的数字是示意量级，真实数值取决于你的题型分布，但「先加预算上限、再做难度路由」的优化顺序是普适的——预算上限的收益零成本且立竿见影，路由的收益更大但需要准确率作为前提。

Qwen3 的"先合后拆"挫折：统一模型为什么退回分开

Qwen3 在设计之初做了一个雄心勃勃的决策：把思考模式和非思考模式合并到一个模型里。理想状态下，一个模型既能做推理（开思考），也能做快速问答（关思考），通过 enable_thinking 参数切换。这比维护两个独立模型（一个推理版一个通用版）更简洁，也避免了模型选择的路由逻辑。

但实践证明这个"合"带来了意想不到的问题：

  • 模式串扰：关闭思考时，模型仍然偶尔输出思维链内容；开启思考时，模型对简单问题过度推理。两种模式在同一个权重空间里互相干扰——你无法在同一组权重上同时最优化"会想"和"不会想"两种行为。
  • 训练信号冲突：推理 RLVR 鼓励"多想再答"，通用 SFT 鼓励"直接回答"。在一个模型里同时优化这两个目标，梯度方向是冲突的——强化推理能力的同时，快速回答的能力在退化。
  • 评测困难：同一个模型在思考开/关两种模式下的能力曲线不一致，难以建立稳定的评测基准——一个 mode 切换 bug 可能导致评测结果大幅波动。

最终 Qwen3 团队不得不在后续版本中部分"拆"回去——为不同用途提供不同的模型变体或更明确的模式分离机制，而不是纯粹依赖一个布尔参数在同一个权重上切换。这个挫折揭示了一个深刻的教训：推理能力和快速回答能力在权重层面是竞争关系，不是一个旋钮能调和的。

值得注意的是，这个教训并不否定「一个模型两种模式」这个方向本身，只是说明它比想象中难得多。从系统设计的角度看，「合」的收益（少维护一套权重、少一层路由）是确定的，「合」的代价（两种能力互相拉扯）是随训练强度增长的。当推理能力被推得越强，非推理模式受到的挤压就越大——这是一个此消彼长的关系，而不是一个可以靠调参消除的 bug。

一句话直觉 想让一个人既是百米冲刺冠军又是马拉松冠军，不是靠"切换模式"就能做到的——两件事练的肌肉不一样。推理模型也一样，"快思考"和"慢思考"竞争同一组权重，合并比分开难得多。

统一封装策略：应用层怎么应对四套接口

应用层要同时支持四家厂商的推理模型，就必须做一个统一封装层，把四套不同的参数映射到一套内部接口上。这不是一次性的工作——厂商的接口在持续演进，封装层需要跟着更新。

封装的核心是设计一个内部抽象，能覆盖四家的能力交集：

# 统一思考预算接口的设计
class ThinkingConfig:
    """统一的思考预算控制，映射到各家 API。"""
    OFF = "off"        # 完全关闭思考
    LOW = "low"        # 最少思考
    MEDIUM = "medium"  # 适中思考
    HIGH = "high"      # 最大思考

    def to_openai(self):
        # OpenAI 不支持 OFF，最低是 LOW
        mapping = {
            self.OFF: "low",      # 降级处理
            self.LOW: "low",
            self.MEDIUM: "medium",
            self.HIGH: "high",
        }
        return {"reasoning_effort": mapping[self.value]}

    def to_anthropic(self):
        # Anthropic 不支持 OFF，需给最低预算
        budget_map = {
            self.OFF: 1024,       # 最低允许值
            self.LOW: 2048,
            self.MEDIUM: 8192,
            self.HIGH: 32000,
        }
        return {"thinking": {"type": "enabled",
                             "budget_tokens": budget_map[self.value]}}

    def to_gemini(self):
        # Gemini 支持 OFF（设为 0）
        budget_map = {
            self.OFF: 0,
            self.LOW: 1024,
            self.MEDIUM: 8192,
            self.HIGH: 24576,
        }
        return {"thinking_config": {"thinking_budget": budget_map[self.value]}}

    def to_qwen(self):
        # Qwen3 只有布尔开关
        return {"enable_thinking": self.value != self.OFF}

这个封装暴露了四个关键的设计决策：

  • 抽象层级选择：用离散档位（OFF/LOW/MEDIUM/HIGH）而不是连续 token 数，因为四家的交集是离散的——OpenAI 只有三档，Qwen 只有开/关，用连续值做统一接口无法覆盖这两家。
  • 降级处理：OpenAI 和 Anthropic 不支持完全关闭思考，当用户请求 OFF 时只能降级到最低档。封装层必须记录这个降级行为，否则用户会误以为思考被完全关闭了。
  • token 预算映射：同一个"MEDIUM"档位在 Anthropic 上是 8192 token，在 Gemini 上可能也是 8192——但两家的 token 定义不同（tokenizer 不同），实际"思考量"并不对等。封装层只能做近似映射，不能保证语义完全一致。
  • 思维链可见性差异：OpenAI 只给摘要，其他三家给完整思维链。如果应用逻辑依赖检查完整思维链（如审计或调试），在 OpenAI 上会失败。封装层需要标注这个能力差异。

把「能力差异」显式化，而不是藏起来

上面的封装还缺一样最重要的东西：告诉调用方「你要的东西我没能完全给你」。一个只会把参数翻译过去的封装层，会把降级、截断、能力缺失全部静默吞掉，最后变成线上难以定位的诡异行为。

更稳妥的做法是让封装层返回一个包含「实际生效配置」和「能力标志」的结果对象：

from dataclasses import dataclass, field

@dataclass
class ThinkingResult:
    """统一封装的返回结果，显式暴露降级与能力差异。"""
    answer: str
    thinking_text: str | None      # 完整思维链，拿不到时为 None
    thinking_tokens: int | None    # 思考 token 数，拿不到时为 None
    requested_level: str           # 调用方要的档位
    effective_level: str           # 实际生效的档位
    hit_budget_cap: bool = False   # 是否顶到了预算上限
    warnings: list = field(default_factory=list)

    @property
    def degraded(self) -> bool:
        return self.requested_level != self.effective_level


def call_with_thinking(provider, prompt, level, max_retry=1):
    """带降级记录与一次性重试的统一调用。"""
    result = provider.invoke(prompt, level)

    if result.degraded:
        result.warnings.append(
            f"请求 {result.requested_level} 但实际为 {result.effective_level}"
        )

    # 关键防御：预算耗尽导致答案为空时，提一档重试一次
    if not result.answer.strip() and max_retry > 0:
        higher = {"off": "low", "low": "medium", "medium": "high"}.get(level)
        if higher:
            result.warnings.append(f"答案为空，提档到 {higher} 重试")
            return call_with_thinking(provider, prompt, higher, max_retry - 1)

    # 观测：思考与答案 token 必须分开上报，否则无法归因成本
    emit_metric("thinking_tokens", result.thinking_tokens or 0,
                tags={"provider": provider.name, "level": level})
    emit_metric("hit_budget_cap", int(result.hit_budget_cap),
                tags={"provider": provider.name, "level": level})
    return result

这段代码的重点不在语法，而在三条原则：降级要留痕、空答案要兜底、思考 token 要单独上报。这三条在真实项目里的价值，远高于把四家参数名映射对。

工程提醒 统一封装的最大风险不是初始实现，而是持续维护。四家厂商的 API 在持续演进——参数名可能变（Gemini 从 thinkingBudget 到 thinkingLevel）、取值范围可能变（Anthropic 的最低预算可能调整）、新功能可能加（OpenAI 可能增加更多档位）。封装层的测试必须覆盖各家 API 的版本差异，否则一次厂商 API 更新就会导致线上故障。建议为每家各留一组「金丝雀用例」，定时跑，参数语义一变就能立刻发现。

模型路由：更根本的解决方案

思考预算控制的是"同一个模型想多久"，模型路由（model routing）解决的是"不同问题用不同模型"。这是比思考预算更根本的方案——与其让一个推理模型对简单问题"少想"，不如直接把简单问题路由到一个快速的非推理模型。

一个典型的路由策略：

问题类型路由目标典型延迟成本
事实性问答、翻译、格式转换小模型（非推理）< 1s最低
中等推理、代码补全、摘要大模型（非推理）或推理模型低预算1-3s中
数学证明、复杂代码、多步推理推理模型（高预算）5-30s最高

路由可以由一个轻量分类器实现（对小模型做一次快速推理判断难度），也可以用规则（如问题长度、是否包含数学符号）。路由的准确率直接决定了成本效率——路由错误把困难问题分给了快速模型，会牺牲精度；把简单问题分给了推理模型，会浪费成本。

两类路由错误的代价并不对称

这是设计路由阈值时最重要的一个认知：把困难问题路由到快通道，和把简单问题路由到慢通道，代价完全不同。

错误类型直接后果用户感知可挽回性量级
难题走快通道
（漏判）		答案错误或明显敷衍强——用户会认为「这个产品不行」差，错误答案已经发出去了损失的是信任，难以用钱衡量
简单题走慢通道
（误判）		多花几秒、多花几分钱弱——用户大多不会察觉好，答案通常还是对的损失的是成本，可精确计算

结论很直接：路由阈值应当偏保守，也就是把边界情况推给慢通道。这与很多人的第一直觉相反——大家往往先想着省钱，把阈值卡得很紧，结果是省下了一点算力却掉了一批答对率，而答对率的损失是用户能感知的。正确的顺序是：先用保守阈值把质量守住，再基于线上数据逐步收紧。

另外还有一个常被忽略的成本项：路由本身也要花钱。如果你用一个 LLM 来判断难度，这次判断的延迟和成本要计入总账。当路由器本身接近被路由模型的成本时，整套方案就不划算了。所以生产里的路由器通常是极轻量的——小分类模型、甚至纯规则加关键词，追求的是「便宜且召回高」而不是「准确」。

模型路由和思考预算是互补的：路由决定"用什么模型"，思考预算决定"这个模型想多久"。生产系统通常两者结合——先路由到合适的模型类别，再在该模型内部调思考预算。这也是为什么 Qwen3 的"先合后拆"教训重要：它说明"用一个模型覆盖所有场景"的路线走不通，模型路由作为独立环节是必要的。

展开：怎么给自己的业务定预算档位（一个可操作的流程）

「MEDIUM 该给多少 token」不能拍脑袋，也不能照抄别人的数字——它取决于你的题型分布。下面是一个可以在一两天内跑完的流程：

  1. 抽样：从线上日志里抽 200～500 条真实请求，按业务类型分层抽样（别只抽最常见的那类，长尾题型往往才是预算敏感的）。
  2. 建立参考答案：能自动判对错的（数学、结构化抽取、代码单测）优先；不能自动判的，用人工标注一个小集合，或者用一个明显更强的模型加高预算跑出的结果作为参考。
  3. 扫描预算：对每条样本，分别用若干个预算档（例如关闭 / 1k / 4k / 16k）各跑 3 次，记录正确率、实际思考 token、端到端延迟。
  4. 画曲线：横轴是实际消耗的思考 token 中位数，纵轴是正确率。你几乎一定会看到一条先陡后平的曲线。
  5. 找拐点：曲线由陡变平的位置，就是这类题型的合理预算。拐点之后每多花一倍算力换来的正确率提升通常不到一个百分点，不值得。
  6. 分层落库：不同业务类型的拐点不同，把它们写进配置而不是硬编码，方便后续按线上数据调整。

这个流程有两个容易做错的地方。第一，每档必须重复多次——推理模型的思考过程是采样出来的，单次结果的方差很大，跑一次就下结论几乎必然误判。第二，横轴要用实际消耗而不是预算设置值，因为预算是上限不是消耗量，用设置值画出来的曲线会严重失真。

跑完之后你通常会得到一个让人意外的结论：大部分业务类型的拐点比直觉低得多。很多团队原本按「越多越好」给到几万 token 的预算，实测发现四千就已经到平台期了——直接省下大半成本，而质量指标一点没动。

展开：思维链可见性——一个安全与产品的交叉问题

「能不能看到模型在想什么」不只是一个 API 能力差异，它牵扯三方面的真实问题：

1. 产品体验。 把思考过程展示给用户是一把双刃剑。好处是等待期有东西可看、显得「在认真工作」、也便于用户自己判断答案可不可信；坏处是思维链里充满自我怀疑、走岔路、推翻重来，普通用户看到「等等，我刚才算错了」会降低对产品的信任。折中做法是只展示一个精简摘要或进度条，完整思维链放在「查看推理过程」的折叠区里。

2. 内容安全。 思维链没有经过和最终答案同等强度的安全对齐——模型在思考时可能把不该说的中间假设写出来。如果你要把思维链透传给终端用户，必须对它单独过一遍内容审核，不能只审最终答案。更保险的默认策略是：思维链只进日志、不进 UI。

3. 忠实度。 一个更根本的问题：写出来的思维链未必是模型内部真正的计算过程，它可能是事后编出来的合理化说辞。这意味着「思维链看起来很严谨」不能作为「答案可信」的证据，把它当成审计凭证是危险的。这一点在 推理模型 里有更完整的讨论。

综合这三点，一个稳妥的默认姿势是：后端完整记录、前端最多给摘要、审计不依赖它、安全审核单独做。

落地检查清单

把这一页的内容收成一张上线前逐项过的清单：

  • 是否把思考 token 和答案 token 拆成了两个观测指标？合在一起看等于放弃了成本归因。
  • 是否处理了答案为空的情况？预算耗尽在思考上是真实会发生的。
  • 重试是否有次数上限和总预算上限？没有的话它会变成成本放大器。
  • 是否有降级留痕？调用方要 OFF 但实际是 LOW，这件事必须能在日志里查到。
  • 思维链是否确定不会漏给终端用户？包括被截断导致标记不配对的情况。
  • 预算档位是否写在配置里而不是硬编码？厂商调整取值范围时你要能热改。
  • 是否为每家厂商留了金丝雀用例？API 语义变化要能第一时间发现。
  • 路由阈值是否偏保守？漏判难题的代价远高于误判简单题。
  • 是否跑过低预算 vs 高预算的翻转率实验？这是判断「多想有没有用」的唯一直接证据。

要点速查

  • Overthinking：推理模型对简单问题过度推理，不仅浪费算力还可能把对的改成错的。根源是 RLVR 只奖励答对不惩罚想太多。
  • 识别信号：思考/回答长度比、思考长度 P99/P50、低高预算翻转率、预算命中率。其中翻转率最直接。
  • 思考预算：控制思维链长度的旋钮，语义上是上限而非目标值。自主 vs 可控是根本权衡——四家厂商在这条线上选了不同位置。
  • 四套接口不兼容：OpenAI 用 reasoning_effort（三档离散）、Anthropic 用 budget_tokens（连续）、Gemini 用 thinkingBudget（连续+可关闭）、Qwen 用 enable_thinking（布尔）。具体取值以官方文档为准。
  • 预算耗尽的行为不统一：可能强制收敛、返回空答案、报错或截断在思考中。封装层必须全部当成可能发生的来防御。
  • 计费与上下文：思考 token 一般按输出计价，是否占用后续上下文、是否计入 max_tokens 各家不同，必须实测确认。
  • Qwen3 先合后拆：把思考/非思考合并到一个模型的尝试遇挫——两种模式在权重上竞争，训练信号冲突。教训：快思考和慢思考不是一组权重能兼顾的。
  • 统一封装：用离散档位做交集抽象，降级要留痕、空答案要兜底、思考 token 要单独上报。最大风险是持续维护而非初始实现。
  • 模型路由：比思考预算更根本——不同问题用不同模型。两类路由错误代价不对称，阈值应偏保守。路由器本身的成本也要计入总账。
  • 定档方法：抽样 → 建参考答案 → 扫预算 → 画「实际思考 token vs 正确率」曲线 → 取拐点。拐点通常比直觉低得多。

篇章视角

围绕“混合推理与思考预算”继续深入

发展脉络

推理由一次前向生成发展为带搜索、验证器和自适应预算的测试时计算，推理质量与计算量开始显式交换。

机制抓手

区分采样、束搜索、树搜索、验证器和思维长度；记录 token、并行分支、停止条件和最终选择规则。

工程权衡

更长的推理链不必然更准确，延迟、显存、重复率和错误传播都需要纳入预算。

前沿观察

混合推理、过程奖励、草稿-验证解码和自适应思考预算是当前主线，仍需任务级而非单一榜单评估。

实践检查能设计一个带预算上限和失败回退的推理服务，并解释 verifier 错误如何影响最终答案。

学习目标

最小实验

验收标准

输出按难度分层的质量-成本曲线，能找出至少一个增加预算却变差的样本；给出路由阈值，使预算相对全量最高档至少下降 30%。
