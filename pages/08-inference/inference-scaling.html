推理时扩展

训练 scaling law 的边际收益在递减，但推理时多花算力还能买到精度——这就是推理时扩展（inference-time scaling）。与其把算力全砸在训练一个更大的模型上，不如让一个中等模型在推理时多想几步。CoT、Self-Consistency、Best-of-N、树搜索是四条已验证的路线，每条都有自己的算力-精度曲线。测试时训练（TTT）是第五条路，理论上收益最大，但始终没有进入生产推理栈——原因值得深究。

推理时扩展的本质是：用更多的推理算力换取更高的回答准确率。五条路线的区别在于"怎么花这笔算力"——CoT 是让模型多写步骤，Self-Consistency 是多采样几次取多数票，Best-of-N 是多生成几个用打分器选最好的，树搜索是系统性地探索推理空间，TTT 是推理时直接更新权重。前三条已经在生产中广泛使用，树搜索成本高但有特定场景，TTT 理论上限最高但工程上至今没有落地。

先建立一个共同的坐标系：算力可以花在三个地方

讨论「推理时扩展值不值」之前，得先把算力的三个去处摆清楚。它们的成本结构完全不同，混在一起讨论必然得不出结论：

算力去处什么时候花成本特征收益特征调整成本
预训练模型诞生前，一次性极高的一次性投入，之后摊薄到每次调用提升的是「知识与基础能力」的天花板极高——要重新训练
后训练模型发布前，周期性中等一次性投入提升的是「能力被激发出来的程度」中——可以迭代但有周期
推理时每次请求，持续按请求量线性增长，永远付提升的是「这一次答对的概率」极低——改个参数就行

关键差异在最后一列。预训练和后训练的算力是沉没成本：花完了就固定在权重里，好也罢坏也罢，改不了。推理时的算力是可变成本：你可以按问题、按用户、按业务线分别决定花多少，也可以随时调整。

这个「可变」的性质，才是推理时扩展真正的价值所在——它把「模型有多强」这个原本静态的属性，变成了一个可以按需分配的运行时决策。同一套权重，给竞赛数学题分配 50 倍算力，给闲聊分配 1 倍算力，整体效果远好于对所有请求一视同仁。

为什么推理时扩展有效：算力的第二条 scaling 曲线

传统 scaling law 说：模型越大、数据越多，效果越好。但模型训练好之后，推理时每个问题只做一次前向传播——不管问题多难，花在它身上的算力是固定的。这显然不合理：简单问题花太多算力（浪费），困难问题花太少算力（不够）。

推理时扩展打破了这个限制：让推理算力变成一个可调的旋钮。简单问题快速回答，困难问题多花算力。研究表明，在数学推理任务上，一个 7B 模型配合 Self-Consistency 可以超过一个 70B 模型的单次推理——推理时多花 10 倍算力，比训练时多花 10 倍算力的边际收益更高。

这背后的直觉是：模型的知识在训练后就固定了，但"怎么用这些知识推理"有巨大的弹性空间。同一个人，给他 30 秒和 30 分钟做同一道数学题，正确率可以差几倍——模型也一样。

更深一层：为什么「多试几次」在数学题上格外管用

上面那个类比只讲了直觉，还有一个更精确的解释：生成和验证的难度不对称。

对很多问题来说，「想出一个解」很难，「检查一个解对不对」却容易得多。数独就是典型例子——解一个盘面要花很久，验证一个已填好的盘面只需要扫一遍行列宫。数学证明、代码实现、逻辑推理都有类似性质。

这个不对称性是推理时扩展的理论基础：只要生成 $N$ 个候选的成本，低于「把生成能力提升到一次就对」的成本，多生成再挑选就是划算的。而挑选这一步，要么免费（多数票，不需要额外模型），要么便宜（一个小得多的验证器）。

反过来也解释了推理时扩展的边界：在验证同样困难的任务上，它就不灵了。「这篇文章写得好不好」「这个战略建议是否明智」——这类问题你生成 100 个候选也挑不出最好的那个，因为你没有可靠的挑选依据。这就是为什么推理时扩展的成功案例几乎全部集中在数学、代码、逻辑这些「可验证」领域。

一句话直觉 训练 scaling 是"把学生教得更好"，推理时扩展是"考试时给更多时间"。两者互补，但推理时扩展的边际成本更低——不需要重新训练，只在推理时多花算力。更准确地说：推理时扩展是在用「验证比生成容易」这个性质套利。
新手最容易搞错 推理时扩展不是「免费的午餐」，也不是「所有任务都适用」的万能药。最容易犯的两个错误：一是把「采样次数 N」当成精度的保证——N 的收益是对数递减的，N 从 1 到 4 的提升远大于从 16 到 64 的提升，而且扩出来的候选里混着大量平庸甚至错误的答案，「挑出对的」才是瓶颈，这需要验证器（见 验证器与过程奖励模型）；二是在「无法验证」的任务上硬套——写一篇文案、做一个开放创意，你生成 100 份也挑不出「哪份更好」，此时扩展不仅无效，还白烧算力。判断标准只有一个：你的任务上，「检查一个答案对不对」是不是比「生成一个答案」便宜得多？是，才值得扩展。

路线 1：CoT——让模型把推理过程写出来

CoT（Chain-of-Thought）是最基础也最广泛使用的推理时扩展方式：让模型在给出答案前，先写出推理过程。这不是一个复杂的算法——本质上就是在 prompt 里加一句"Let's think step by step"——但效果惊人。

CoT 为什么有效？关键在于自回归生成的机制。模型每生成一个 token，都会把它加回输入再生成下一个。这意味着推理过程中的中间步骤会作为额外的上下文影响后续生成。一道多步数学题，如果要求模型直接给答案，它需要在一次前向传播中完成所有推理——这超出了模型的单步能力。但如果允许它写中间步骤，每一步都可以"看到"前面已经写的步骤，相当于把一个长推理分解成多个短推理，每步只需要做一小步推进。

换个角度说：不写 CoT 时，模型的「思考深度」被限制在网络层数上；写 CoT 时，思考深度变成了层数 × 生成的 token 数。生成的中间 token 相当于一块外部草稿纸，把原本必须在一次前向里完成的计算，摊到了几十上百次前向里。这也解释了为什么 CoT 在多步算术上收益最大，而在「判断这句话的情感」这类单步任务上几乎没有收益——后者本来就不需要草稿纸。

CoT 的算力-精度曲线有一个有趣的特征：它几乎是免费的。相对于直接给答案，CoT 只是多输出了一些 token，每个 token 的生成成本和答案 token 一样。在大多数 API 计价模型中，这意味着按输出 token 付费——多想几步就是多付几步的钱，线性且可预测。

CoT 的局限是：它依赖模型已经具备逐步推理的能力。一个未经推理训练的模型，即使加"Let's think step by step"，生成的推理步骤也可能是错的——garbage in, garbage out。CoT 激发的是模型已有的推理潜力，不能无中生有。推理模型（o1、R1 等）通过 RLVR 训练把这种潜力强化到了极致，详见 推理模型。

路线 2：Self-Consistency——多次采样取多数票

CoT 用贪心解码时，一条推理路径走错了就全错了。Self-Consistency 的思路是：不走一条路，走多条路，看哪条路到的终点最多。

具体做法：对同一个问题，用较高温度（如 0.7-1.0）采样 $N$ 条不同的 CoT 推理路径，每条路径各自得出一个答案。然后取多数票——出现次数最多的答案作为最终答案。这背后的假设是：正确的推理路径有多条，它们最终都收敛到同一个正确答案；而错误推理路径各自错到不同的答案，不会集中。所以多数票会自然筛出正确答案。

$$\hat{y} = \text{mode}\!\left(y_1, y_2, \ldots, y_N\right)$$

Self-Consistency 的算力是 CoT 的 $N$ 倍（$N$ 条独立采样），精度提升在数学和推理任务上非常显著。研究表明，$N$ 从 1 增加到 40，精度持续提升，但边际收益递减——$N=5$ 时已能获得大部分增益。

它的局限是只适用于有离散答案的问题。数学题的答案是一个数，可以做多数票；但开放性生成（写文章、翻译）没有"同一答案"的概念，多数票无意义。Self-Consistency 在数学、代码、多选问答上效果最好，在开放式生成上不适用。

实现细节：答案归一化才是最大的坑

Self-Consistency 的算法只有一行（数众数），真正的工程量全在怎么判断两个答案是不是「同一个答案」上。这一步做错了，多数票会退化成随机选。

同一个答案的不同写法朴素字符串比较的结果需要的归一化
0.5 / 1/2 / 50% / .5四个不同答案，各得 1 票统一转成有理数或标准小数
1,000 / 1000 / 1 000三个不同答案去掉千分位分隔符与空白
x = 3 / 3 / 答案是 3三个不同答案抽取答案本体，去掉前缀
2\sqrt{3} / 2√3 / 3.464三个不同答案符号表达式规范化；数值近似要设容差
True / true / 是三个不同答案大小写与语言的统一映射

这些看起来是琐碎的字符串处理，但它们直接决定了 Self-Consistency 有没有效。一个没有做归一化的实现，在 $N=20$ 时可能出现「20 条路径给出 15 种写法」的局面，众数只有 2 票，跟随机选没什么区别。而做好归一化后，同样的 20 条路径可能坍缩成 3 种答案，众数拿到 12 票，信号一下就清晰了。

另一个常被忽略的点：无法解析出答案的路径怎么处理。模型偶尔会生成一段推理但没给出可提取的最终答案。正确做法是把它们剔除出投票池并单独计数——如果剔除比例过高（比如超过两成），说明你的答案抽取正则或提示词格式有问题，应该先修这个，而不是加大 $N$。

import re
from collections import Counter
from fractions import Fraction

def normalize_answer(raw: str):
    """把各种写法归一到可比较的形式。返回 None 表示无法解析。"""
    if raw is None:
        return None
    s = raw.strip()
    # 去掉常见前缀与包裹
    s = re.sub(r"^(答案是|答案为|answer\s*[:=]|所以)\s*", "", s, flags=re.I)
    s = s.strip(" .。$\\boxed{}")
    s = s.replace(",", "").replace(" ", "").replace("，", "")

    # 布尔与是非
    low = s.lower()
    if low in {"true", "yes", "是", "对"}:
        return "TRUE"
    if low in {"false", "no", "否", "不对"}:
        return "FALSE"

    # 百分比
    if s.endswith("%"):
        try:
            return str(Fraction(s[:-1]) / 100)
        except Exception:
            return None
    # 分数与小数统一成 Fraction 的字符串形式
    try:
        return str(Fraction(s))
    except Exception:
        pass
    # 其余情况保留原串，交给上层判断
    return s or None


def extract_answer(text: str):
    """从一条 CoT 里抽出最终答案。优先取显式标记。"""
    m = re.search(r"\\boxed\{([^}]*)\}", text)
    if m:
        return m.group(1)
    m = re.search(r"(?:最终答案|Final Answer)\s*[:：]\s*(.+)", text)
    if m:
        return m.group(1).splitlines()[0]
    # 兜底：取最后一行里的最后一个数
    tail = text.strip().splitlines()[-1] if text.strip() else ""
    nums = re.findall(r"-?\d+(?:\.\d+)?", tail)
    return nums[-1] if nums else None


def self_consistency(generate, prompt, n=16, temperature=0.8):
    """generate(prompt, temperature) -> str，返回一条完整 CoT"""
    votes, unparsed = [], 0
    traces = {}
    for _ in range(n):
        text = generate(prompt, temperature)
        ans = normalize_answer(extract_answer(text))
        if ans is None:
            unparsed += 1
            continue
        votes.append(ans)
        traces.setdefault(ans, text)      # 保留一条代表性推理供展示

    if not votes:
        return {"answer": None, "confidence": 0.0, "unparsed": unparsed}

    counter = Counter(votes)
    best, cnt = counter.most_common(1)[0]
    return {
        "answer": best,
        "trace": traces[best],
        "confidence": cnt / len(votes),   # 得票占比可作为粗糙置信度
        "distinct": len(counter),         # 不同答案的种类数
        "unparsed": unparsed,             # 抽取失败数，过高说明格式有问题
    }
得票率是一个免费的置信度 confidence = 众数票数 / 有效票数 这个数字几乎不花额外成本，却非常有用：得票率接近 1 说明模型很确定，接近 1/N 说明模型在瞎猜。可以用它做自动兜底——得票率低于阈值时，转人工、走更强的模型、或者直接告诉用户「这题我不太确定」。这比什么都不做要好得多，也比 logprobs 那种 token 级置信度更贴近「答案层面的把握」。

路线 3：Best-of-N——用打分器选最优

Self-Consistency 用多数票选答案，但多数票只看答案不看过程。如果一个答案出现了 3 次但每次推理过程都不同，而另一个更严谨的推理得出的答案只出现 1 次，多数票会选前者。Best-of-N 改用一个打分器来选择——不只是看答案，而是评估整条推理过程的质量。

具体做法：采样 $N$ 个回答，用一个打分器（reward model 或 verifier）给每个回答打分，选分数最高的作为最终输出。打分器可以是：

  • 结果奖励模型（ORM）：只看最终答案给分。简单但无法区分"推理错但答案碰巧对"的情况。
  • 过程奖励模型（PRM）：对推理过程的每一步打分。更精确但训练成本高，详见 验证器与过程奖励模型。
  • LLM-as-Judge：用另一个大模型评估回答质量。灵活但成本高，且引入裁判模型自身的偏差。
  • 硬验证器：能自动判对错的场景直接用它——代码跑单测、数学题比对标准答案、SQL 在沙箱里执行。只要有硬验证器就优先用它，它不会像学习出来的打分器那样被钻空子。

Best-of-N 与 Self-Consistency 的关键区别：Self-Consistency 是"无监督"的（不需要打分器，只数票），Best-of-N 是"有监督"的（需要打分器来排序）。Best-of-N 更灵活——适用于开放式生成，不限于离散答案——但打分器的质量直接决定了选择质量。如果打分器不好，Best-of-N 可能比随机选还差。

在 RLHF 中，Best-of-N 常被用作RLHF 的下界基准——如果你的 RLHF 训练后的模型还不如用 SFT 模型做 Best-of-32，说明 RLHF 训练有问题。这也说明 Best-of-N 是一种简单但有效的推理时扩展方式。

加权多数票：把两条路线合起来

Self-Consistency 和 Best-of-N 并不互斥，最常见的生产做法其实是二者的混合——加权多数票：每个答案的得分不是简单计票，而是把投给它的所有路径的验证器分数加起来。

$$\hat{y} = \arg\max_{y} \sum_{i=1}^{N} \mathbb{1}[y_i = y] \cdot s_i$$

其中 $s_i$ 是第 $i$ 条路径的验证器分数。当所有 $s_i$ 相等时，它退化成普通多数票；当只取最大值时，它退化成 Best-of-N。这个形式的好处是同时利用了「多条路径都到这个答案」和「这些路径质量高」两个信号，在实践中通常比单用其中一个更稳。

路线 4：树搜索——系统性地探索推理空间

前三条路线都是"独立采样再选择"——每条推理路径独立生成，互不影响。树搜索更进一步：让推理路径分支和回溯，像下棋一样系统性地探索推理空间。

树搜索的优势是能在推理过程中主动回溯——发现某条路走不通时，退回去试另一条。CoT 和 Self-Consistency 是"一条路走到黑"，树搜索可以"走不通就换"。在复杂的数学证明或代码生成中，这种系统性探索比盲目采样高效得多。

用一句话概括三者的差别：Self-Consistency 是「独立跑 N 次，事后比较」，树搜索是「边跑边比较，把算力挪到有希望的分支上」。后者的算力利用率更高——它不会把预算浪费在明显走偏的路径上——代价是需要一个能在「半截推理」上打分的模型，也就是 PRM。

但树搜索的工程代价远高于前三条路线：

  • 需要过程奖励模型：每一步推理都需要一个价值估计来决定往哪个方向扩展。训练 PRM 的成本不低。
  • 推理延迟高：需要多次前向传播（选择、扩展、模拟），延迟是 CoT 的几十倍。不适合实时交互场景。
  • 实现复杂：需要维护搜索树、管理 KV Cache 的复用和回滚，工程复杂度高。
  • 「步骤」的边界难定义：树的每个节点应该是一句话？一个推导步骤？固定 token 数？粒度太细则树爆炸，太粗则失去回溯的意义。这个超参对效果影响很大，却没有通用答案。

树搜索在 2025-2026 的生产应用仍然有限，主要用在离线场景——比如生成高质量训练数据（用树搜索跑出高质量推理轨迹，再蒸馏给小模型），或者高价值低频率的推理任务（如竞赛级数学）。实时对话场景几乎不用树搜索，因为延迟无法接受。

KV Cache 是树搜索最容易被低估的工程难点 树搜索会频繁地「回到某个中间节点再往别的方向走」。如果每次都从头重算 prompt 和已有前缀，算力开销会比理论值高出好几倍。要做得高效，必须让搜索树的节点共享公共前缀的 KV Cache，并支持在分叉点做廉价的分支与回滚。这本质上是一个前缀树（radix tree）式的缓存管理问题，跟推理引擎的内部实现耦合很深，很难在应用层做好。相关机制见 KV Cache 与 推理引擎。

一个重要的实践认知：这些路线不是互斥的，而是可组合的。一个推理模型可以先做 CoT（训练时已内化），再做 Self-Consistency（多次采样取多数票），如果问题足够难再升级到树搜索。推理模型把 CoT 的能力内化进了权重，但 Self-Consistency 和树搜索仍然是推理时可以叠加的外部手段。

并行 vs 串行：延迟不等于算力

上表的「算力倍数」和「延迟」是两个独立维度，容易被混为一谈。区别在于扩展是并行的还是串行的：

这个区分在容量规划时非常重要。Self-Consistency 的 $N=16$ 在低负载时几乎不增加用户感知延迟（16 条并行跑），但它把你的服务并发容量直接砍到了十六分之一。等到流量上来，排队延迟会突然爆炸——你会看到一条「负载到某个点之后 P99 断崖式恶化」的曲线。反过来，长 CoT 对吞吐的冲击小得多，但每个用户都得实打实地等。

实践建议：把「算力预算」和「延迟预算」分开设，并且都要压测。只测单请求延迟而不测高并发下的表现，是推理时扩展上线后最常见的事故来源。

预算自适应：不要对所有问题花一样的钱

固定 $N$ 是最简单的做法，也是最浪费的做法。真实的题目难度分布是不均匀的：一大半题目 $N=1$ 就对了，剩下的才需要多采样。把省下来的预算挪给难题，同样的总算力能换到明显更高的整体正确率。

做法很直接：先跑少量采样，看它们是否一致；一致就直接返回，不一致再追加。这个「按难度分配算力」的思想在论文里有一个专门的名称——compute-optimal allocation（最优算力分配）——下面这张论文原图是它最直观的证据。

这张图一共有四条曲线，新手读它先把曲线分成两组：上方的「compute-optimal」组（按难度分配预算），和下方的「fixed」基线组（所有题一视同仁地采 N 次）。横轴是总的推理算力（用生成的样本数衡量），纵轴是最终准确率。两条 compute-optimal 曲线——一条用「上帝视角的难度标签」（oracle，论文里指用真实正确性信息分难度桶），一条只用 PRM 的预测来分桶（predicted）——几乎完全重叠。这意味着什么？你不需要提前知道每道题的正确答案，只要有一个大致靠谱的「难度估计器」，就能实现接近理论最优的算力分配。而两条 compute-optimal 曲线都比固定预算的基线明显偏左上：在同样的算力下准确率更高，或者说在同样准确率下消耗的算力少了约 4 倍（论文原文的例子是 16 次 vs 64 次采样）。这就是「预算自适应」这一节存在的全部理由——不是省一点是一点，而是同样的钱能买到近一个数量级更好的效果。

from collections import Counter

def adaptive_self_consistency(
    generate, prompt,
    n_init=4, n_step=4, n_max=32,
    high_conf=0.75, low_conf=0.4,
    verifier=None, temperature=0.8,
):
    """先少采样，分歧大才追加。返回答案与决策路径。

    generate(prompt, temperature) -> 一条完整 CoT 文本
    verifier(answer) -> bool，可选的硬验证器（跑单测 / 对标准答案）
    """
    votes = []
    log = []

    def stats():
        c = Counter(votes)
        if not c:
            return None, 0.0, c
        best, cnt = c.most_common(1)[0]
        return best, cnt / len(votes), c

    budget = n_init
    while True:
        need = budget - len(votes)
        for _ in range(max(0, need)):
            ans = normalize_answer(extract_answer(
                generate(prompt, temperature)))
            if ans is not None:
                votes.append(ans)

        best, conf, counter = stats()
        log.append({"sampled": len(votes), "conf": round(conf, 3),
                    "distinct": len(counter)})

        # ① 高共识：直接收工，这是绝大多数请求的出口
        if best is not None and conf >= high_conf:
            return {"answer": best, "confidence": conf,
                    "cost": len(votes), "path": "consensus", "log": log}

        # ② 预算用尽：能验证就验证，不能就上报低置信
        if budget >= n_max:
            if verifier is not None:
                passed = [a for a in counter if verifier(a)]
                if len(passed) == 1:
                    return {"answer": passed[0], "confidence": conf,
                            "cost": len(votes), "path": "verified",
                            "log": log}
            return {"answer": best, "confidence": conf,
                    "cost": len(votes), "path": "low_confidence",
                    "log": log}

        # ③ 中间区间：追加一批再看
        budget = min(budget + n_step, n_max)

这段逻辑里有三个值得注意的设计：

  • 阈值是两档而不是一档：高于 high_conf 直接返回，低于 low_conf 说明模型在瞎猜、再加采样也难收敛，此时更该走验证器或转人工，而不是继续烧钱。中间区间才是「追加采样最划算」的地方。
  • 返回值里带上 cost 和 path：没有这两个字段，你就无法在线上统计「自适应到底省了多少」，也无法发现某类问题总是走到 low_confidence 分支。
  • 验证器只在最后用：验证器通常比生成便宜但不免费，放在共识失败之后调用，能避免对绝大多数简单题做无谓的验证。
自适应会让延迟方差变大 固定 $N$ 的延迟是稳定的；自适应的延迟取决于问题难度——简单题快，难题要跑好几轮。这意味着 P99 延迟会明显高于 P50。如果你的 SLA 是按 P99 定的，自适应带来的成本节省可能被延迟违约抵消。折中做法是给自适应加一个墙钟超时：到点无论共识与否都返回当前最优答案并标注置信度。

路线 5：TTT——理论上限最高但未进生产

测试时训练（Test-Time Training，TTT）是最激进的推理时扩展：不只是多采样或多搜索，而是在推理时直接更新模型权重。具体做法是：遇到一个测试问题时，先在相关问题上做几步梯度下降（用模型自己生成的相关训练数据），微调一下权重，再用更新后的模型回答原始问题。

TTT 的理论吸引力在于：它直接缩小了"训练分布"和"测试分布"的差距。如果测试问题来自一个训练时没见过的领域，TTT 可以在推理时快速适配。研究表明，TTT 在分布外（OOD）泛化上的收益可以超过前四条路线的总和。

但 TTT 至今没有进入生产推理栈，原因有三：

  • 推理延迟不可接受：梯度下降需要多次前向+反向传播，每个请求要等几分钟到几十分钟。没有用户能接受一个对话 API 响应这么慢。
  • 权重更新的状态管理：推理时更新权重意味着每个请求的模型权重都不一样。在多用户服务中，你怎么管理"用户 A 的 TTT 更新"和"用户 B 的 TTT 更新"不互相干扰？为每个请求维护独立的权重副本在工程上几乎不可行。
  • 灾难性遗忘风险：在推理时做梯度下降，更新方向只来自一个问题的相关数据，极易破坏模型在其他能力上的表现。你可能为了答对这道数学题，忘了怎么做翻译。

值得补充的是第二点其实有一条可能的绕路：只更新一小组适配参数而不是全量权重（例如只训一组 LoRA 旁路）。这样每个请求的「个性化状态」只有几十 MB，理论上是可以按请求隔离管理的。但这条路径同样没有解决延迟问题——反向传播的成本摆在那里——所以目前仍停留在研究阶段。相关的参数高效微调机制见 参数高效微调。

当前状态 TTT 在学术界是一个活跃方向，但截至 2026 年仍未有生产系统采用。推理时扩展的生产实践以前四条路线为主。TTT 的思想——推理时适配——在更受控的形式下以 RAG（检索增强生成，不改权重只改输入）和 in-context learning（上下文学习）的形式落地，这些方式不需要更新权重，工程上可行。

失效模式：推理时扩展什么时候不管用

推理时扩展不是万能药。下面这些情况下，加算力不但没用，还可能反向掉点：

失效模式表现根本原因正确的做法
系统性偏差$N$ 条路径全都错到同一个答案，多数票信心十足地选中错误错误来自模型的共同先验，而非随机噪声——采样多少次都一样这是知识/能力问题，要靠 RAG、微调或换模型

其中「打分器被钻空子」值得特别警惕，因为它的表现极具欺骗性——所有内部指标都在变好（平均打分持续上升），只有真实质量在下降。这本质上就是 reward hacking 在推理时的版本：$N$ 越大，你就越是在对打分器的缺陷做搜索。防范办法是定期用人工评估或独立的硬验证器抽查 Best-of-N 的输出，而不是只看打分器自己给的分。

怎么测：把算力-精度曲线画出来

决定用哪条路线、$N$ 取多少，唯一可靠的依据是在你自己的数据上画出算力-精度曲线。别人论文里的曲线只能说明方向，不能替你做决策。

一个可执行的实验设计：

  1. 准备评测集：至少 200 条，覆盖你的真实难度分布。关键是要包含简单题——只用难题测，会严重高估推理时扩展的收益。
  2. 确定横轴：用实际消耗的 token 数（输入+输出+思考）而不是 $N$。不同路线的单条成本不同，用 $N$ 做横轴无法公平比较 CoT 和树搜索。
  3. 确定纵轴：能自动判分就自动判；不能就抽样人工评。纵轴一定要是端到端的业务指标，不能用打分器自己给的分（那是自证）。
  4. 每个点重复多次：采样有随机性，单次结果不可信。同一配置至少跑 3 遍取均值，并记录标准差。
  5. 加两条基线：一是「不做任何扩展的单次 CoT」，二是「用更强的模型做单次 CoT」。第二条基线经常被忽略，但它回答了一个关键问题：这笔算力花在扩展上，是不是不如直接换个更贵的模型？
  6. 找拐点，不找最高点：曲线右端总是最高的，但那里的性价比极差。真正要找的是斜率明显变缓的那个位置。

第 5 条特别值得强调。很多团队做完实验的结论是「$N=32$ 的 Self-Consistency 比 $N=1$ 提升了若干个点」，然后就上线了——却没算过同样的钱直接调用更强的模型能提升多少。这两个方案的成本可能相当，效果却未必是扩展占优。把「换模型」当成一条基线，是这个实验里最容易被跳过、也最容易改变结论的一步。

展开：为什么多数票有效——一个简化的概率模型

Self-Consistency 的有效性可以用一个古典结论来理解：孔多塞陪审团定理（Condorcet's Jury Theorem）。它说的是，如果每位陪审员独立地以概率 $p$ 做出正确判断，那么当 $p > 0.5$ 时，多数票的正确率随人数增加而单调上升并趋近于 1；当 $p < 0.5$ 时，多数票的正确率反而随人数增加而趋近于 0。

套到 Self-Consistency 上，这个模型给出三条有用的推论：

  1. 基础正确率必须过半（或至少高于「最常见的错误答案」的概率）。如果模型在某类题上单次正确率只有 20%，而某个特定错误答案的出现概率有 35%，那么加大 $N$ 只会让多数票越来越稳定地选中那个错误答案。这正是「系统性偏差」失效模式的数学解释。
  2. 独立性是关键假设。定理要求各次判断相互独立。实际采样中，同一个模型的多次采样远非独立——它们共享同一套权重和先验，错误是高度相关的。这就是为什么真实收益远小于定理预测的理想值，也是为什么提高采样温度、变换提示词措辞、甚至混用不同模型能进一步提升多数票效果：这些做法在人为地增加路径之间的独立性。
  3. 错误必须分散。定理隐含假设错误答案不集中。数学题恰好满足这一点——算错可以错到无数个不同的数上；而是非题就不满足——错误只有一个方向，全部集中，多数票基本无效。这解释了为什么 Self-Consistency 在开放数值答案上效果最好，在二选一判断上几乎没用。

从这三条可以得到一条实用的判断准则：在决定用不用 Self-Consistency 之前，先看两个数——单次正确率是否明显过半，以及错误答案是否分散。两个条件都满足才值得投入；只满足一个的话，收益会远低于预期。

展开：推理时扩展的算力经济学

推理时扩展的核心权衡是：多花的推理算力值不值得？这取决于场景：

  • 高价值低频率（如竞赛数学、代码安全审计）：树搜索的 100x 算力完全值得，一次正确的答案价值远超算力成本。
  • 中价值中频率（如客服、代码辅助）：Self-Consistency 或 Best-of-N 的 5-10x 算力是合理区间，精度提升带来的用户满意度值得这笔开销。
  • 低价值高频率（如内容推荐、简单问答）：连 CoT 都可能不值得，直接快速回答。多花 3 倍算力换 2% 的精度提升，在亿级请求量下不划算。

一个实际的经验法则：推理时扩展的算力预算应该与问题的单次价值成正比。单次价值 1 美分的请求，不值得花 10 美分的推理算力；单次价值 100 美元的任务（如代码安全审计），花 1 美元的推理算力完全合理。这也是为什么推理时扩展最先在数学竞赛和代码生成等高价值场景落地。

还有一个常被忽略的维度：错误的成本。同样是一次调用，「答错只是用户重问一遍」和「答错导致一笔错误的转账」完全不是一回事。真正的判断公式应该是：值得投入的额外算力 ≈ 错误率的下降幅度 × 单次错误的代价。在错误代价极高的场景（医疗辅助、金融风控、生产环境变更），即使正确率只能从 97% 提到 98%，花十倍算力也是合算的；反之在容错场景，这一个百分点根本不值得。

最后提醒一个反直觉的结论：推理时扩展的性价比会随着基座模型变强而下降。模型单次正确率从 60% 涨到 90% 之后，能靠多采样捞回来的空间就只剩那 10% 了，而算力成本没变。所以每次基座升级后，都应该重跑一遍算力-精度曲线——之前定的 $N$ 很可能已经不是最优了，甚至可能变成纯浪费。

推理时扩展与推理模型的关系

推理时扩展和推理模型（o1、o3、R1）是两条独立但互补的路线。推理模型通过 RLVR 训练，把"多想几步"的能力内化进了权重——它在训练时就被奖励了更长的有效推理。推理时扩展则是不改权重、在推理时用更多算力换精度。

两者的关系可以这样理解：

  • 推理模型降低了 CoT 的成本——模型自己就知道什么时候该多想，不需要用户手动加"Let's think step by step"。
  • 推理模型提高了 Self-Consistency 和 Best-of-N 的效果——因为每次采样本身就是高质量的推理，而不是随机猜测。
  • 推理模型让树搜索的每步扩展更有效——因为模型对中间状态的评估更准确。

换句话说，推理模型提升了推理时扩展每单位算力的"性价比"。不过要注意一个叠加时的坑：推理模型本身已经消耗了大量思考 token，再叠加 $N$ 倍采样，成本是乘法关系而不是加法关系。一个思考 5000 token 的模型做 $N=16$ 的 Self-Consistency，单次请求就是 8 万 token 的思考量。所以在推理模型上做并行扩展时，$N$ 要比在普通模型上取得小得多，通常 4～8 就够了。详见 推理模型。

展开：推理模型上做扩展，成本怎么「乘法叠加」——手算一笔账

很多团队在推理模型上线后才第一次意识到「成本乘法」有多吓人。设一个普通模型的单次回答约 200 token，一个推理模型的单次请求是「思考 5000 token + 回答 200 token」。

普通模型 + Self-Consistency N=16：16 × 200 = 3200 token。成本可控，这也是普通模型时代大家敢把 N 开到 40 的原因。

推理模型 + Self-Consistency N=16：16 × 5200 = 83200 token，约 8.3 万。相比前一条贵了 26 倍，而精度提升远没有 26 倍——因为推理模型每次采样本身就已经是高质量推理了，重复采样能捞回来的「余量」小得多。

再叠加验证器（Best-of-N + ORM）：除了生成 16 份（8.3 万 token），还要让 ORM 给每份打分。ORM 打分要对整段序列做一次完整前向，成本与生成相近长度的序列几乎相同，于是又要再加 8.3 万 token 当量的算力。单次请求总成本超过 16 万 token 当量。

这笔账给出三条实操结论：其一，推理模型上的 N 用 4～8 就够了，再加纯属烧钱；其二，验证器如果不是显著轻量（蒸馏版、只看尾部状态），就不要和推理模型叠加用；其三，这也是为什么「预算自适应」在推理模型场景的价值远大于普通模型——普通模型上省一半预算可能只是少花点钱，推理模型上省一半预算意味着省下几万 token 的成本。

重点深化：把 test-time compute 变成可控预算

前面的路线回答了「还能怎么多想」，但生产系统还要回答「这次请求最多允许花多少钱」。把问题形式化：给定请求 $x$、生成策略 $\pi$、候选数 $k$、每条轨迹的 token 成本 $c_i$ 与验证成本 $v_i$，在预算 $B$ 内选择动作序列 $a_{1:T}$，最大化最终质量：

$$\max_{a_{1:T}}\; \mathbb{E}[U(y)\mid x,a_{1:T}]\quad\text{s.t.}\quad C(a_{1:T})=\sum_i(c_i+v_i)+C_{\mathrm{tool}}\le B,\quad L(a_{1:T})\le D$$

其中 $U(y)$ 是业务效用（正确率、通过率或人工偏好），$C$ 是 token/GPU/工具成本，$L$ 是端到端延迟，$D$ 是 deadline。test-time compute budget 不是简单的 max_tokens：它应同时记录生成 token、候选条数、验证器调用、工具调用和墙钟时间，并允许在中途根据置信度、分支价值和剩余预算重新分配。

候选级答案得票率、ORM/PRM 分数、重复率给高潜力分支追加采样/搜索置信度越过阈值
工具级工具成功率、返回信息增益、调用耗时优先调用硬验证器或低延迟工具结果已可验证或工具预算耗尽
系统级队列深度、GPU 利用率、p95 延迟降级到小 $N$、短 CoT 或单次解码触发全局预算闸门

一个实用的 adaptive allocation 策略是先小后大、边生成边决策：先并行生成 $N_0=4$ 条；若得票率超过 0.75 或硬验证器已通过，立即结束；若分歧处于中间区间，追加 4 条；若 PRM 判断某分支明显更有希望，则把剩余预算转给该分支做树搜索；达到 $B$ 或 $D$ 时强制收口。论文 Scaling LLM Test-Time Compute Optimally 展示了按难度分配预算相对固定采样的优势，但线上必须用真实业务数据重新校准阈值。

def allocate_budget(state, budget, deadline_ms):
    # state: candidates, vote_share, verifier_scores, elapsed_ms
    if state.hard_verified_answer is not None:
        return "stop", 0
    if state.vote_share >= 0.75 and state.parsed_rate >= 0.8:
        return "stop", 0
    if state.elapsed_ms >= deadline_ms or state.cost >= budget:
        return "stop", 0
    if state.vote_share < 0.40 and state.has_hard_verifier:
        return "verify", min(2, budget - state.cost)
    # 将剩余预算给边际价值最高的分支，而非平均撒给所有分支
    branch = state.best_prm_branch if state.best_prm_branch else "parallel"
    return branch, min(4, budget - state.cost)
面试表达 固定 $N$ 优化的是平均效果；adaptive allocation 优化的是「单位成本下的效果」，同时必须把 deadline 作为硬约束。回答时先说目标函数，再说观测信号、追加规则和强制停止条件，避免只停留在「难题多想几步」的口号层面。

Verifier、ORM、PRM：先分清「判对」与「打分」

三者经常被混用，但可靠性边界不同。Verifier 是任务层面的判定器，可以是确定性的程序，也可以是学习模型；ORM（Outcome Reward Model） 只对最终结果给分；PRM（Process Reward Model） 对中间步骤或状态给分，用于提前剪枝和搜索。PRM 的代表性研究是 Let's Verify Step by Step。

组件输入输出强项典型风险
硬 Verifier答案、代码、SQL、约束通过/失败或可解释错误数学标准答案、单元测试、形式化约束，确定性强只覆盖定义好的验收条件
ORM完整回答/最终答案一个结果分数实现简单，适合 Best-of-N 排序看不到中间错误，容易被表面表达或漏洞利用
PRM部分推理步骤/状态逐步分数或价值估计可在树搜索中剪枝、把预算给高潜力分支步骤切分、标注成本和分布偏移很敏感

可验证任务边界可以按三档判断：A 档是可执行验证（代码测试、数学精确答案、SQL 结果集、格式/权限约束）；B 档是部分可验证（事实性、引用完整性、结构规则，可用检索与规则组合）；C 档是开放价值判断（战略、文案、审美、长期影响），只能得到 noisy preference，不能把 ORM 分数当作真值。C 档仍可做多候选，但要报告不确定性，不能声称「采样越多就必然更好」。

当我们把 $N$ 调大并选择最高分候选时，实际上是在优化评分器本身。如果评分器偏爱冗长、特定格式或迎合性措辞，Best-of-N 会主动搜索这些漏洞，这就是 reward hacking。相关讨论见 Understanding and Avoiding Reward Hacking in RL。缓解措施包括：优先硬验证；独立 ORM/PRM/规则交叉检查；限制候选数和分数外推；对高分样本做人工或隐藏集抽查；监控「评分上升但真实通过率下降」的 divergence。

不要把高分当真相 verifier 的 coverage 决定了它能保证什么。一个只检查最终数值的 ORM 无法证明推理正确；一个只跑单测的代码 verifier 也可能漏掉性能、权限和未覆盖分支。上线前要写清「验证器保证的性质」和「没有保证的性质」。

pass@k：成功率、成本与延迟的简单算例

对代码生成或其他「至少一个候选正确」的任务，Evaluating Large Language Models Trained on Code 给出常用的 pass@k 估计。若一次独立采样正确概率为 $p$，理想化近似为：

$$\mathrm{pass@}k = 1-(1-p)^k$$

例如单次通过率 $p=0.30$，每条候选成本 1 单位、串行延迟 1 秒：

系统组合：并行采样、树搜索、工具调用与 speculative decoding

生产系统通常不是四选一，而是分层组合。一个可落地的请求路径是：

  • 并行采样 + speculative decoding：每个候选都由 draft model 提案、target model 验证，可降低单候选的解码墙钟；但 draft/target KV cache、GPU 显存和并发槽位会放大，不能把单条加速直接乘到整体吞吐。
  • 并行采样 + 工具调用：候选先生成计划，工具调用应在沙箱中隔离并设置次数、时间和输出大小上限；工具结果要回注上下文后再让 verifier 判定，不能只看模型自报「执行成功」。
  • 树搜索 + PRM + 工具：PRM 对中间步骤排序，工具对可执行节点给硬反馈；失败节点立即剪枝，避免把剩余预算花在已知不可行分支。
  • 组合顺序：先做低成本路由和小批并行采样，再做硬验证；只有高价值且仍不确定的请求才进入树搜索。否则系统会把最昂贵的路径当默认路径，吞吐和 p95 都会失控。

线上推理系统：p50/p95、吞吐、取消、超时与预算闸门

平均延迟不能代表用户体验。应至少分解 TTFT（首 token）、decode time、tool time、queue time 和 end-to-end latency，并按路由、模型、预算档位分别统计 p50/p95。Google SRE 对 SLO、过载处理和 tail latency 的说明可参考 Service Level Objectives 与 Handling Overload。

async def guarded_infer(req, runtime):
    gate = await runtime.gate.reserve(req.tenant, req.budget, req.deadline_ms)
    try:
        route = runtime.router.choose(req, gate.snapshot())
        async with runtime.deadline(req.deadline_ms) as cancel:
            result = await runtime.run(route, cancel=cancel)
        return {**result, "budget_used": gate.used(), "route": route.name}
    except TimeoutError:
        return await runtime.best_effort_result(reason="deadline")
    except CancelledError:
        await runtime.abort_children()  # 生成、验证器、工具调用一起取消
        raise
    finally:
        await gate.release_unused()

问题建议回答骨架
为什么 test-time compute 有效？生成难、验证相对易；额外采样/搜索降低随机错误，但只在可验证或有可靠选择器的任务上成立，收益递减且成本上升。
Self-Consistency 与 Best-of-N 怎么选？有离散答案且可归一化时多数票便宜；有开放输出或可靠打分器时 Best-of-N；有硬验证器时优先硬验证并在通过集合内聚合。
ORM 和 PRM 的核心区别？ORM 只看终局，适合排序；PRM 看过程，适合剪枝和树搜索，但标注与校准更难。两者都不是自动真值。
pass@k 为什么不等于线上成功率？pass@k 假设候选中至少一个正确且选择器能选中；线上还受候选相关性、verifier 误判、工具失败、超时和预算闸门影响。
如何降低 p95 而不明显掉点？先做难度路由；设置 deadline 和预算上限；高置信提前停止；拥塞时降级 N/模型；把慢工具与树搜索移到异步或离线队列。

故障排查 checklist

  1. 效果不升反降：确认答案归一化、候选是否真的多样；检查单次正确率是否低于 0.5、错误是否系统性相关；与更强模型单次调用做成本对齐基线。
  2. 验证器分数升、真实通过率降：抽查高分样本；按 ORM/PRM 分数分桶看独立指标；加入硬验证、隐藏测试和人工盲评，排查 reward hacking。
  3. p50 正常但 p95 爆炸：拆解 queue/prefill/decode/tool/verifier 时间；查看自适应追加比例、树深、最长 CoT 和未取消的后台任务。
  4. 吞吐突然下降：检查并行候选是否占满 KV cache 和 batch；检查 speculative acceptance rate、GPU 显存碎片、队列等待和每请求实际 token。
  5. 取消后 GPU 仍高：确认 cancellation 是否传播到生成、验证器、工具和子任务；确认 KV cache、临时文件、沙箱进程最终释放。
  6. 预算超支：检查追加前是否原子扣减；是否把验证器/工具成本计入同一预算；是否存在重试风暴、超时后孤儿任务或租户配额绕过。
  7. 工具调用循环：设置最大轮数、单轮 deadline、重复调用去重和工具结果大小限制；连续无信息增益时强制停止并返回当前最佳答案。
  8. 升级模型后成本仍高：重新绘制 cost-quality 曲线；更强基座可能让 N=1 已足够，旧的 N、PRM 和树搜索配置应重新校准。

要点速查

  • 本质：训练算力的边际收益递减时，推理时多花算力仍能买精度——这是 scaling 的第二条曲线。它之所以成立，是因为「验证比生成容易」。
  • 三种算力的区别：预训练和后训练是沉没成本，推理时算力是可变成本，可以按问题动态分配——这才是它的核心价值。
  • CoT：最基础，让模型写推理步骤，相当于给模型一块外部草稿纸，把思考深度从「层数」扩展成「层数 × token 数」。
  • Self-Consistency：多次采样取多数票，$N$ 典型 5-40，只适用于离散答案。最大的实现坑是答案归一化，做不好会让多数票退化成随机。
  • 得票率是免费的置信度：众数票数除以有效票数，可直接用于低置信兜底。
  • Best-of-N：采样 $N$ 个用打分器选最优，适用于开放式生成。有硬验证器时优先用硬验证器。先归一化去重再验证能省大半开销。
  • 加权多数票：把票数和验证器分数结合，通常比单用其中一个更稳。
  • 树搜索：MCTS 系统探索+回溯，算力利用率最高但延迟和工程代价最大。KV Cache 的前缀共享与回滚是最容易低估的难点。
  • 并行 vs 串行：并行扩展不增加单请求延迟但砍并发容量，串行扩展延迟线性增长但对吞吐冲击小。两者必须分开压测。
  • 预算自适应：先少采样，共识高就直接返回，分歧大才追加。用两档阈值，低置信直接走验证器或转人工。代价是延迟方差变大。
  • TTT：推理时更新权重，理论收益最大但未进生产——延迟不可接受、权重状态管理不可行、灾难性遗忘风险。
  • 失效模式：系统性偏差、无法验证、打分器被钻空子、归一化缺失、题目歧义、过度推理。加算力解决不了其中任何一个。
  • 评测方法：横轴用实际 token 消耗而非 $N$，纵轴用端到端业务指标，评测集必须包含简单题，并且一定要加「换更强模型」这条基线。
  • 算力经济学：投入应与「单次价值 × 错误代价」成正比。基座越强，扩展的性价比越低——每次升级模型都要重跑曲线。

面试深化：推理时算力预算与系统落地

面试中不要把 test-time compute 说成“把 max_tokens 调大”。更准确的定义是：给一次请求一个可观测、可扣减、可提前停止的推理预算，把生成候选、验证/打分、工具调用和墙钟时间统一纳入约束，再按中途信号把剩余算力投向最有希望的分支。目标是最大化单位成本下的业务效用，而不是无条件追求最高离线准确率。

$$\max \; \mathbb{E}[U(y)]\quad\text{s.t.}\quad C_{\text{gen}}+C_{\text{verify}}+C_{\text{tool}}\le B,\quad L\le D$$

其中 $B$ 是每请求预算，$D$ 是 deadline。预算账本至少要记录 candidate_count、输入/输出/思考 token、验证器与工具成本、budget_used、route、confidence 和取消原因；每次追加候选前原子扣减预算，避免并发分支或重试把账单冲破上限。

1. Verifier、ORM、PRM：选择信号决定预算是否值得

Verifier 是任务层面的判定器，既可以是执行单测、比对数学答案的硬验证器，也可以是学习模型；ORM（Outcome Reward Model）只看最终结果；PRM（Process Reward Model）给中间推理步骤或状态打分，可用于提前剪枝和树搜索。PRM 的代表性工作是 Let's Verify Step by Step。三者都必须说明 coverage：高分不是事实真值，硬验证也只保证它覆盖的性质。

组件观察对象适合的动作主要边界
硬 Verifier答案、代码执行结果、约束通过即停；失败则剪枝只保证显式定义的验收条件
ORM完整回答/最终答案Best-of-N 排序看不到中间错误，可能被表面特征或 reward hacking 利用
PRM部分步骤/搜索状态树搜索扩展与提前剪枝步骤切分、标注和分布偏移敏感

因此，生产顺序通常是“先低成本路由和小批采样，再硬验证；仍不确定才用 ORM/PRM 扩展”。开放式任务没有可靠验证器时，必须把输出当作 noisy preference，而不是声称采样越多就必然更好。

2. pass@k 与成本：多试不等于线上成功

在代码生成等“候选中至少一个正确”的任务上，Evaluating Large Language Models Trained on Code 使用 pass@k。若每次独立采样正确概率为 $p$，且有完美选择器，理想上界为 $\mathrm{pass@}k=1-(1-p)^k$。设 $p=0.30$、每候选成本 1 单位、单候选延迟 1 秒：

4$1-0.7^4=75.99\%$4约 1 秒
8$1-0.7^8=94.24\%$8约 1 秒

这个公式是上界，不是线上 SLA：候选相关、verifier 会误判、工具会失败，且并行 $k=8$ 会占用约 8 倍并发槽位。实验报告应同时给出 pass@1/pass@k、平均 token/GPU 秒、验证成本以及 p50/p95，而不是只报成功率。Snell 等人对按难度分配 test-time compute 的分析见 Scaling LLM Test-Time Compute Optimally。

3. p95、超时与预算闸门：把算法变成服务

固定 $k$ 只优化平均效果；线上必须把 tail latency 当硬约束。分别记录 TTFT、decode、queue、verifier、tool 和端到端延迟，并按路由/预算档位统计 p50、p95、p99。Google SRE 的 SLO 与 过载处理原则可作为系统设计参考。

闸门触发信号动作
请求级硬上限token、候选数、工具次数或 $B$ 用尽停止新增工作，返回当前最佳并标记置信度
deadline墙钟达到 $D$，或 p95 接近 SLA取消生成/验证/工具子任务，释放 KV Cache
全局熔断队列深度、GPU 利用率或租户配额超阈值禁用树搜索，降低 $N$ 或切换小模型
软阈值已消耗约 70% 预算但置信度仍低只允许低成本硬验证，禁止昂贵分支扩展

面试问答（3 题）

  1. 问：为什么 test-time compute 有效？
    答：生成一个正确解通常比检查一个候选更难；在数学、代码等可验证任务上，多采样/搜索能降低随机错误，再由多数票或 verifier 选择。但收益递减，候选相关或评分器不可靠时，增加算力只是在放大共同偏差。
  2. 问：ORM 和 PRM 怎么选，如何控制成本？
    答：ORM 看终局，适合 Best-of-N 排序；PRM 看过程，适合树搜索和提前剪枝；有硬验证器时优先硬验证。采用“先 $N_0$ 小批采样、置信度不足再追加、每次追加先扣预算”的策略，并对 p95 与 verifier 成本单独压测。
  3. 问：pass@k 很高，为什么线上仍超时或失败？
    答：pass@k 假设独立候选和完美选择器，线上还受候选相关性、verifier 误判、工具失败、队列和 deadline 影响。应把 pass@1/pass@k 与 token/GPU 成本、p95、取消率一起看；拥塞或超时触发预算闸门，降级到 N=1/短回答并返回低置信标记。
面试收束句 我会把推理时扩展设计成一个受预算和 deadline 约束的控制回路：小批采样获取信号，verifier/ORM/PRM 决定是否追加，p95 与全局队列触发降级，所有结果回传成本、路由和置信度。这样讨论的不是“多想几步”，而是单位成本下的可观测、可回滚系统。
