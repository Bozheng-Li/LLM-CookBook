推理算法：解码、验证器与 test-time scaling

从一次 token 采样开始，逐步解释温度、Self-Consistency、Best-of-N、树搜索和推理模型成本。

1. 解码不是训练

模型给出 logits，解码策略把它变成 token。温度 T 越低越确定，越高越多样；top-k 只保留最高 k 个 token，top-p 保留累计概率达到 p 的最小集合。固定 prompt 生成 20 次，比较重复率和事实错误，才能选择参数。

2. Self-Consistency 为什么有效

对需要离散答案的题目，采样 N 条独立推理链，再对最终答案投票。链之间高度相关时，投票只是在重复同一个错误；因此要保存完整轨迹，检查“答案一致但全错”的案例。

3. Best-of-N 与验证器

先生成 N 个候选，再用 ORM 或 PRM 选一个。验证器必须在训练外题目上校准，否则模型会迎合验证器。代码任务优先运行隔离单元测试；数学任务应先归一化等价表达式。

candidates = [sample(model, prompt) for _ in range(N)]
scores = [verifier(prompt, y) for y in candidates]
best = candidates[max(range(N), key=lambda i: scores[i])]

4. 树搜索与预算分配

树搜索保留多个部分答案，用 verifier 估值并扩展高潜力分支。它把计算集中到困难题，但 token 和 verifier 调用会乘法增长。生产系统应限制总 token、最大分支和提前停止条件，并画准确率-延迟-成本曲线。

5. 推理模型的运行时控制

DeepSeek-R1 等模型通过 SFT、RLVR 和拒绝采样获得更长推理。思维越长不一定越好：简单问题会 overthinking，复杂问题又可能提前停止。混合推理路由器可先估计难度，再决定 thinking budget，并纳入回归测试。

6. 可复现实验

准备 100 道未污染数学题，比较 N=1/4/16 的通过率、平均 token、验证器调用次数和 p95 延迟。报告按难度分桶，并人工检查验证器误判。
