进阶

服务化与推理经济学

把模型从「能跑」变成「能服务」要跨越一道巨大的工程鸿沟。同一个 7B 模型，单卡裸跑和千卡集群服务的吞吐可以差三个数量级——差距不在模型，在部署形态、SLO 设计和调度策略。本节聚焦纯技术侧：怎么部署、怎么设 SLO、怎么在吞吐-延迟-成本三角中找到你的最优点。

一图看懂

服务化的核心矛盾是一个三角约束：吞吐（每秒处理多少 token）、延迟（用户等多久）、成本（每 token 花多少钱）三者互相牵制——提高吞吐就要增大 batch，但 batch 大了延迟就高；降延迟就要减小 batch，但小 batch 的单位成本更贵。没有银弹，只有在你业务约束下的最优权衡。

部署形态：从单卡到千卡集群

LLM 服务的部署形态直接决定了能承载多少并发、延迟水平和成本结构。选择哪种形态，取决于你的流量模式和 SLO 要求。

部署形态典型配置适用场景并发能力
单机单卡1×A100/H100开发调试、小规模内部服务10-50 并发
单机多卡（TP）4-8×A100，张量并行70B 级模型单实例部署50-200 并发
多机多卡（TP+PP）多节点，张量+流水线并行超大模型（400B+）单实例100-500 并发
多实例负载均衡N 个独立实例 + LB生产高可用、水平扩展N × 单实例并发
PD 分离Prefill 节点 + Decode 节点大规模高并发服务1000+ 并发

从单机到多实例的关键变化是从「一台机器跑模型」到「一个集群服务流量」。前者的核心问题是模型怎么跑得快（推理引擎的事），后者的核心问题是流量怎么调度得合理（服务架构的事）。

单实例阶段

一个 vLLM/SGLang 实例处理所有请求。瓶颈在单实例的 max_concurrency。适合日请求量万级以下、延迟要求不严苛的场景。

多实例阶段

前置负载均衡器（Nginx/Envoy/专用网关）把流量分发到多个实例。关键设计：会话亲和性（同一会话路由到同一实例以利用 KV Cache）、优雅缩放、健康检查。

SLO 设计：用什么指标衡量「够好」

SLO（Service Level Objective）是服务化的契约——你向用户承诺的服务质量水平。LLM 服务的 SLO 和传统 Web 服务有本质区别：传统服务的延迟主要来自计算和 IO，LLM 服务的延迟还取决于生成长度（生成 1000 token 天然比 100 token 慢）。

指标定义为什么重要
TTFT（首 Token 延迟）从请求到达到第一个 token 返回的时间用户感知的「响应速度」，决定体验
TPOT（每 Token 延迟）生成阶段平均每个 token 的间隔时间流式输出的流畅度，>100ms 用户会感觉卡
端到端延迟从请求到达到完整响应的时间非流式场景的核心指标
吞吐量单位时间处理的 token 或请求数系统容量上限，决定成本效率
错误率请求失败 / 超时 / 截断的比例可用性底线

设 SLO 的关键原则：区分 Prefill 延迟和 Decode 延迟。TTFT 主要受 Prefill 计算和队列等待影响，TPOT 主要受 batch size 和显存带宽影响。把两者混在一起设一个「p99 延迟 < X」是常见错误——一个生成 2000 token 的请求和一个生成 50 token 的请求放在一起统计 p99 没有意义。

「为什么不把 Prefill 和 Decode 分开设 SLO」这个问题，可以用一张论文原图来解释。它来自 PD 分离奠基论文 DistServe（OSDI 2024），用同一张卡上的实测延迟回答了「混合部署到底付出了什么代价」。

读这张图先看它的上下两个半图。上半图是 TTFT（首 token 延迟）的 p90 对比，下半图是 TPOT（每 token 延迟）的 p90 对比。每一半里都有一组「现有系统」的柱子和一根「仅 Prefill / 仅 Decode 系统」的基线。注意上下半图的结论是一致的：把 Prefill 和 Decode 混在同一批 GPU 上时，两个指标同时变差——用户既等得更久才看到第一个字（TTFT 高），又看到后续每个字都慢吞吞（TPOT 高）。

第二，理解为什么会这样：图里的负载是「输入 512、输出 64」的合成流量。当 Decode 请求占着显存带宽逐 token 生成时，一个长 prompt 的 Prefill 突然插进来，会把 GPU 算力瞬间吃满——正在 Decode 的请求每一步都要等这个「庞然大物」先算完，TPOT 飙升；反过来，Decode 请求长期占据带宽，新请求的 Prefill 又挤不进去，TTFT 被拉长。这两个方向上的「互踩」，就是图上两根柱子同时变高的原因。

第三，从SLO 工程的角度读这张图，结论是：如果你在混合部署下要同时满足「TTFT p99 < 1s 且 TPOT p99 < 100ms」，唯一办法是过度配置——买更多的卡、把 batch 压小，让两个阶段互相干扰的概率降到足够低。而 DistServe 的测法告诉你，分离部署可以用同样的 GPU 数量在两项指标上都达标。这就是「SLO 是有价格的」最直观的证据：同样一个 SLO，用不同的部署形态实现，成本可以差出数倍。这也是本页后面「吞吐-延迟-成本三角」以及 PD 分离 一节的出发点。

实践经验 典型的 LLM 服务 SLO：TTFT p99 < 1-2s（Prefill 阶段），TPOT p99 < 50-100ms（Decode 阶段），端到端 p99 则按生成长度分档设定。SLO 不是越高越好——p99 TTFT 从 1s 降到 500ms 可能需要 3 倍的 GPU，但用户感知的提升微乎其微。
新手最容易搞错 新手最容易把「SLO」和「SLI」混为一谈，也最容易把「延迟」和「响应时间」划等号。SLO 是你承诺的目标（如 TTFT p99 < 1s），SLI 是实际测出来的指标值（如今天 TTFT p99 = 830ms），两者是「目标 vs 事实」的关系，SLO 靠 SLI 来验证。更隐蔽的坑是：对 LLM 服务，「响应时间」不是单一数字——它是 TTFT 和 TPOT 的组合。一个端到端 30 秒的响应可能是「首字 200ms + 每秒 35 token 匀速流出」，体验并不差；而一个「首字 8 秒 + 之后瞬间吐完」的响应，虽然端到端可能更快，体验却糟透了。所以衡量 LLM 服务必须拆开看，任何只报「平均延迟」的数字都有误导性。

吞吐-延迟-成本三角

这三个指标的权衡是服务化设计的核心。理解它们的关系，关键是理解 batch size 的作用：

具体来说，吞吐和成本的关系是非线性的：batch 从 1 增到 10，吞吐可能提升 8 倍（接近线性），成本降 8 倍；但从 10 增到 100，吞吐可能只提升 2-3 倍（因为显存带宽瓶颈开始显现），而延迟却线性增长。最优 batch size 通常在 GPU 利用率达到 70-85% 的拐点附近。

策略特点适用场景

吞吐优先大 batch、少实例、高利用率批处理、后台任务、数据标注

自动扩缩容：什么时候加机器

生产服务的流量通常有明显的波峰波谷——白天高峰、深夜低谷。固定实例数要么白天不够用（SLO 违约），要么晚上浪费（GPU 闲置）。自动扩缩容（Autoscaling）是解决这个问题的关键。

传统 Web 服务的 autoscaling 通常基于 CPU 利用率或 QPS，但 LLM 服务的关键指标不同：

  • KV Cache 利用率：当 KV Cache 使用率持续 > 80% 时，新请求会被排队等待，此时应该扩容。
  • 队列深度：等待 Prefill 的请求数持续超过阈值时，说明 Prefill 算力不足。
  • TTFT p99：当 TTFT 持续高于 SLO 时扩容，低于阈值时缩容。
常见误区 LLM 模型加载慢——一个 70B 模型加载到 GPU 可能需要 30-60 秒，这意味着扩容不是「秒级生效」的。Autoscaling 的触发阈值要设得比传统 Web 服务更早（比如 KV Cache 利用率 70% 而非 90%），给模型加载留出时间。冷启动延迟是 LLM 服务化与传统微服务最大的运维差异。

把扩容决策写成一个最小逻辑（示意，生产要结合多指标和冷却时间）：

class LLMAutoscaler:
    """基于 KV Cache 利用率与队列深度的扩缩容决策（示意）"""

    def decide(self, kv_util, queue_depth, ttft_p99_ms,
               slo_ttft_ms=2000, target=0.70):
        # 1. 提前扩容：给模型加载留缓冲，不在 90% 才动
        if kv_util > target or queue_depth > 32:
            return "scale_out"
        # 2. 已违约：立刻扩容，不再等
        if ttft_p99_ms > slo_ttft_ms:
            return "scale_out_urgent"
        # 3. 长期空闲：缩容省钱
        if kv_util < 0.30 and queue_depth == 0:
            return "scale_in"
        return "hold"

    def cooldown(self, last_action_ts, now, min_gap_sec=120):
        # 避免抖动：两次扩缩容之间至少间隔 min_gap
        return (now - last_action_ts) >= min_gap_sec

流量调度：会话亲和与前缀路由

多实例部署时，请求路由策略直接影响 KV Cache 命中率和成本：

轮询路由（Round Robin）

请求均匀分配到各实例。简单公平，但每个实例的 KV Cache 都从零开始，前缀缓存命中率低。

会话亲和路由（Session Affinity）

同一会话的请求路由到同一实例，复用已有 KV Cache。多轮对话场景下 TPOT 可降 30-50%。

更进阶的做法是前缀感知路由：根据请求的前缀（系统提示、RAG 上下文）选择已有该前缀 KV Cache 的实例。SGLang 的 RadixAttention 天然支持这种模式，vLLM 也通过前缀缓存实现类似效果。在大规模 RAG 服务中，前缀感知路由可以显著降低 Prefill 计算量。

高可用与容灾

LLM 服务的单点故障比传统服务更棘手——一个 70B 模型实例崩溃后，重启需要重新加载模型，恢复时间可能长达分钟级。高可用设计需要考虑：

  • 多实例冗余：至少 N+1 实例，单实例故障不中断服务。
  • 优雅降级：高峰期流量超过容量时，按优先级拒绝低优先级请求（而非全部超时）。
  • 模型预加载：备用实例预先加载模型，故障切换时秒级生效而非分钟级。
  • 请求超时与重试：设合理的请求超时，超时后重试到其他实例。注意重试会放大流量——N 次重试 = N 倍负载，需配合断路器。
展开：推理成本的量级估算

虽然具体价格随时间波动，但推理成本的技术结构是稳定的。一个 7B 模型在单张 A100 上的粗略估算：

  • A100 80GB 的理论峰值吞吐约 2000-3000 token/s（batch 较大时）
  • 一天 = 86400 秒，理论最大约 1.7-2.6 亿 token/天
  • 实际利用率 50-70%（排队、长短请求混杂、波谷），有效约 1-1.8 亿 token/天
  • GPU 小时成本（云厂商按需价格量级）分摊到每百万 token，大致在亚美分级别

这个估算只覆盖了 GPU 算力成本，实际服务成本还包括网络、存储、运维、多地域部署等。完整的成本归因（按工作流/租户/版本四维拆分）属于成本工程范畴，见 推理成本工程。

先定 SLO，再谈优化 很多团队一上来就调批处理、上 PD 分离，却没先写清楚 SLO。正确的顺序是：先用真实的延迟/吞吐/成本目标倒推需要哪种部署形态，再决定要不要 PD 分离、要不要前缀路由。没有 SLO 的「优化」很容易陷入「为了快而快」，最后 GPU 成本翻倍但用户无感。SLO 的设定本身也是权衡——p99 TTFT 从 1s 降到 500ms 可能要多花 3 倍算力。

单卡并发度与 TCO 的换算算例

服务化成本的所有讨论，最后都要落到一个核心问题：一张 GPU 到底能服务多少用户，以及每多服务一个用户边际成本是多少。这里用一组可验证的量级估算，把「并发度 ↔ 成本」的换算关系走一遍。数字以量级示意为准，不同模型和硬件会偏移，但结构不变。

以 7B 模型、单张 A100 80GB 为例。权重 FP16 约 14 GB，剩下约 66 GB 给 KV Cache 和激活。假设量化到 INT8 权重约 7 GB，剩下 73 GB。KV 每 token 约 1.25 MB（7B 模型、INT8 KV），一条 4096 token 的请求约占 5 GB。算上激活和缓冲，单卡大概能同时驻留 10-15 条这样的请求——这就是单实例的「并发上限」。再乘上平均生成速度（batch=12 时单卡吞吐约 1500-2500 token/s），一个 7B 服务一天能产出的 token 量级在 1-2 亿之间。

现在做成本换算。假设一张 A100 按需价格约每小时 3-4 美元（云厂商量级），一天约 80 美元，分摊到 1.5 亿 token，每百万 token 的成本约 0.5 美元。这个数字就是推理经济的「锚」：如果你的业务每百万 token 只能赚 0.2 美元，那这张卡是亏的；如果能赚 1 美元，毛利 50%。而任何优化——连续批处理把并发从 10 提到 20、量化把权重砍半、投机解码把有效吞吐提高 2 倍——都直接改变「每百万 token 成本」这个数。理解了这个换算链，就能理解为什么「优化吞吐」本质就是「优化毛利」。

这个算例还揭示一个反直觉结论：并发度不是越高越好。把 batch 从 12 拉到 24，吞吐可能只涨 30%，但单请求 TPOT 翻倍、SLO 违约率上升。当系统逼近「带宽墙」时，加并发换来的吞吐增量越来越小，延迟代价却线性增长。所以「最经济并发度」不在最大吞吐点，而在「边际吞吐收益 ≈ 边际延迟代价」的平衡点——这个点通常比硬件极限低 30-50%，也就是前文说的 GPU 利用率 70-85% 拐点。

SLO 的代价曲线：过度配置的隐性成本

SLO 不是免费的，每收紧一个百分点的延迟承诺，背后都是实打实的算力。理解这条「代价曲线」，才能避免最常见的浪费——为了一个用户根本感知不到的延迟提升，多花一倍的 GPU。

延迟指标有一个重要特性：p99 的改善是「边际递减」的。把 TTFT p99 从 3 秒压到 1 秒，通常需要明显加大 batch 余量或增加实例，用户从「明显等待」到「顺畅」的体验提升非常大；但从 1 秒压到 0.5 秒，可能需要再加 50% 的算力去对付尾延迟（长 prompt 突发、GC 抖动、网络波动），而用户在 1 秒和 0.5 秒之间的感知差异微乎其微。这条曲线的形状是：前半段斜率陡（划算）、后半段斜率平（浪费）。

过度配置的隐性成本还不只 GPU 本身。更宽松的 SLO 意味着可以接受更小的 batch 余量、更少的预留实例、更晚的扩容触发——这些都是在「降低每 token 成本」和「降低延迟违约率」之间做位移。一个务实的做法是给 SLO 分级：核心功能（登录、支付相关）承诺 p99 < 1s，非核心功能（推荐语、润色）承诺 p95 < 3s，让有限的算力优先保障用户真正在等的路径。全站一视同仁地追求「p99 < 500ms」，往往是成本失控的开始。

另一个常被忽略的成本是「SLO 与流量峰值的关系」。如果 SLO 要求「任何时刻 p99 < 1s」，容量规划就必须按峰值流量来配 GPU——而峰值可能只是均值的好几倍，这意味着大部分时间 GPU 闲置。如果改成「p99 < 1s 允许在 95% 的时间窗口内满足」，就可以用均值 + 少量弹性补齐峰值，GPU 利用率显著提升。SLO 的措辞（是「绝对满足」还是「按时间窗口满足」）直接决定 TCO，值得在服务设计之初就想清楚。

展开：从 SLO 反推 GPU 数量的一整套手算

把「SLO → 并发 → GPU 数」这条链完整走一遍，看看每个数字是怎么来的。以 7B 模型、单卡 A100 80GB、FP16 权重（约 14GB）为例。

第 1 步，定单卡并发。前面算过，剩约 56 GB 给 KV。若平均请求 2048 token、每 token KV 约 0.5 MB，单条请求约 1 GB，单卡约 56 并发。但这是「显存上限」，不是「SLO 上限」——56 条并发时 TPOT 会因 batch 太大而飙升，必须打折。

第 2 步，从 SLO 反推 batch 上限。假设 TPOT SLO 是 p99 < 80ms。经验上 batch=16 时单卡 TPOT 大约 40-60ms，batch=32 时可能到 100-150ms。所以为了守住 80ms，实际可用的并发得压在 16-24，而不是 56。这就是「SLO 把显存并发打了对折」——显存让你能放得下，SLO 才决定你真正敢放多少。

第 3 步，乘上流量需求。假设目标高峰并发 200 条（在线用户 × 同时使用率估算），200 ÷ 20 ≈ 10 张卡。再按「按峰值 + 冗余 20%」预留，约 12 张卡。如果 SLO 放宽到 TPOT p99 < 150ms，batch 能提到 32，同样的流量只要 7 张卡——SLO 每放松一点，GPU 需求就掉一截，这就是前文「SLO 的代价曲线」的量化版本。

这套手算里的数字都是量级估计，真实值要以你的模型、硬件和流量回放实测为准。但推导顺序（显存上限 → SLO 上限 → 流量需求 → 冗余）是通用的，缺了任何一步，容量规划都会失真——尤其是第二步，几乎所有团队都会在这里少算。

负载混合与成本归因：把「贵」算清楚

多业务共用一个推理集群时，最大的管理问题是成本归因：同一批 GPU 上跑着搜索、对话、批处理三种负载，月底账单出来了，怎么分摊？分摊不公平，业务方就没有优化自己负载的动力。

成本归因的最小可行单位是「每 token 成本」：把 GPU 总成本除以总产出的 token 数，得到平均单价，再按每个业务的 token 消耗量分摊。但直接用「平均单价 × token 数」有偏差——长上下文请求的 KV 占用大、batch 里摊薄效果差，单位成本远高于短请求。更公平的做法是按「占用的 GPU 时间」而非「产出的 token 数」归因：一个请求的 GPU 时间 = prefill 计算时间 + decode 计算时间 + 它占用的 KV 显存时间。前者由算力决定，后者由显存占用 × 驻留时长决定。把这四个分量分别计量，长请求和短请求的成本差异就显现出来了——很多「看起来便宜」的请求实际是昂贵的长尾。

归因粒度再细一层，就是按租户/产品/模型版本拆：同一产品的新旧模型版本跑在同一集群，新版更快但 KV 更贵，成本怎么分？实践中通常用「每请求的 token 数 × 每 token 基准价 + 长度溢价」的计价模型，让每个业务方看到的成本与它消耗的真实资源挂钩。只有成本归因清晰，业务方才会主动优化 prompt 长度、缓存复用率、请求并发策略——而这些恰恰是推理成本里最可控的部分。

最后提醒：成本归因本身也有成本。计量日志要写、存储要占、报表要生成，如果业务量小到「省下的钱还不够做归因的服务器钱」，退回到简单的「按 token 均摊」更划算。归因的精细度应该和集群规模匹配——单机几块卡，按 token 均摊足够；千卡集群，才值得上完整的四维归因体系。

从延迟看成本：在线与离线负载的分池策略

一个集群里同时跑在线（对话、搜索）和离线（批处理、评测、数据标注）负载，是最常见的生产形态。两种负载对延迟的诉求几乎相反，强行混在一个池子里，要么在线请求被离线长任务拖垮，要么离线任务被在线请求「饿死」。

在线负载的特征是延迟敏感、到达随机、每请求短小。它的成本优化空间在于：不能无限堆 batch（SLO 约束），因此单卡吞吐有硬上限；真正省钱的手段是提高缓存命中率（前缀复用）、压缩 KV、以及尽量压低「空闲等待」——一个在线实例在低峰时段可能只有 30% 利用率，这部分就是纯浪费。

离线负载的特征是延迟无感、批量大、可排队。它的成本优化空间恰恰相反：可以把 batch 推到接近硬件极限（延迟无所谓）、可以接受很长的队列（任务本身就要跑几十分钟）、可以放在低峰时段执行以利用闲时算力。离线任务的「最经济 batch」通常比在线任务大得多，因为它不背着 SLO 的枷锁。

因此分池的核心不是「物理上分开」，而是让两类负载各自取到适合自己的运行形态：在线池追求「低延迟 × 高命中」，离线池追求「大 batch × 高利用率」。具体做法有三条。一是时间分池：在线负载在白天高峰独占，离线任务调度到夜间和周末低峰，利用闲时算力跑批处理——这比买两台机器便宜得多。二是空间分池：高峰时段在线与离线确实要抢 GPU 时，用配额和优先级保证在线请求优先，离线任务降级到剩余算力。三是弹性分池：离线任务可以「随时被抢占、断了重跑」（checkpoint 续跑），所以它在低峰时吃满、高峰时让路，成为在线集群的「弹性缓冲」。

这三条里最容易被忽略的是第三条。离线任务如果能容忍抢占和断点续跑，它本质上就是集群里的「可压缩负载」——在线流量高时被压缩掉，在线流量低时撑满算力。这比单纯的时间分池灵活得多，能让 GPU 的平均利用率从 40% 提到 70% 以上。代价是实现成本：任务要支持 checkpoint、断点续跑、以及「随时让路」的调度协议。要不要做，取决于你的离线任务占比——离线任务越多，这个投入越值。

最后用一句话总结分池策略：让延迟敏感的和延迟无关的负载不要互相污染，让可压缩的负载给不可压缩的负载让路。在线池为 SLO 服务，离线池为利用率服务，两者通过调度和配额松耦合，而不是挤在同一个 batch 里互相将就。

还有一个容易踩的坑是「分池不等于分硬件」：很多团队分完池就各自买机器，导致在线池低峰闲置、离线池高峰排队。更经济的方式是让两个池共享同一批物理 GPU，通过调度层按时间片或配额动态划分——在线时段在线优先，低峰时段离线吃满。只要离线任务支持抢占续跑，物理共享几乎总能比物理隔离更省。判断标准很简单：把两个池各自 GPU 的利用率曲线画出来，如果峰值和低谷正好错开，就该合并物理资源、只在调度层分池。这条经验在千卡集群和单卡创业公司同样适用，区别只在于实现的复杂程度。简单场景用「低峰时段手动切批处理」就够了，复杂场景才需要引入完整的优先级调度器，两者之间的投入回报需要结合团队实际情况衡量。

要点速查

  • 本质：服务化设计的核心是在吞吐-延迟-成本三角中找到业务约束下的最优权衡，batch size 是三角的枢纽。
  • SLO 指标：TTFT（首 token 延迟）和 TPOT（每 token 延迟）要分开设，不要混成一个 p99 延迟——Prefill 和 Decode 的瓶颈完全不同。
  • 部署形态：从单机单卡到多实例负载均衡再到 PD 分离，选择取决于流量规模和 SLO 要求。
  • 自动扩缩容：基于 KV Cache 利用率和队列深度而非 CPU；模型加载慢，扩容阈值要提前设。
  • 会话亲和：多轮对话场景下同一会话路由到同一实例，TPOT 可降 30-50%。
  • 高可用：N+1 冗余 + 模型预加载 + 优雅降级，LLM 实例恢复慢是最大的运维差异。
  • 与成本工程的边界：本页讲怎么部署和调度让系统又快又稳，每 token 花多少钱的归因和优化见 推理成本工程。
