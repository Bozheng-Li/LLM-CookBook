端侧部署与小模型 SLM

手机里的模型不是「缩小版的 GPT」，而是一套完全不同的工程权衡：它牺牲上限能力，换来隐私、延迟和零成本。理解 SLM 的能力边界、压缩手段、推理栈选型和端云协同的分工逻辑，才知道什么任务该交给本地，什么任务必须上云。本节从能力边界到工程落地，做完整拆解。

一图看懂

端侧部署的本质是一条「能力 ↔ 代价」的交换线：量化、剪枝、蒸馏把模型压到 1–8B 参数、几个 GB 以内，塞进手机和 PC；系统层面再用 llama.cpp / MLX 等推理栈把它跑起来；最后用一个路由策略决定「本地算还是云端算」。三个环节缺一不可。

一、SLM 能做什么，不能做什么

小语言模型（Small Language Model）通常指 1B–8B 参数、能在单设备上运行的模型。典型代表有 Qwen-2.5-7B、Llama-3.2-3B、Phi-3.5-mini（3.8B）、Gemma-2-2B 等。先说结论：SLM 擅长「模式匹配型」任务，不擅长「知识密集型」和「多步推理型」任务。

这个能力边界的根源在于参数量与能力的关系不是线性的。模型的参数同时承担两个角色：存储知识和执行计算。参数少了，知识储量直接下降（事实性问答会出错），推理深度也受限（没有足够的「计算电路」做多步推导）。但语言模式识别——比如意图分类、摘要、改写——对参数量的需求低得多。

任务类型端侧 SLM 表现推荐参数量原因
文本分类 / 意图识别优秀1-3B任务模式固定，参数量足够拟合
摘要、改写、补全良好3-7B不需要外部知识，靠语言模式即可
简单问答一般7B+ RAG常识可能够用，事实性知识易错
格式化输出（JSON）良好3-7B模式可学习，需少量 few-shot
多步推理 / 数学偏弱—推理深度受参数量限制
最新资讯 / 私域知识不可用—知识截止 + 没有检索入口
常见误区 不要用「小模型也及格」的心态做产品。端侧模型回答错误时用户不会怪网络，只会怪产品。正确的姿态是：先明确哪些任务能接受 SLM 的错误率，再决定放端侧。用置信度路由做兜底——低置信度的请求升级到云端。

二、把模型塞进设备：压缩四件套

设备可用内存通常只有 4–16 GB（且要和系统、其他 App 共享），而 7B 模型 FP16 权重就约 14 GB。要落地，必须叠加以下手段。这些手段不是「选一个」，而是「全都要」。

压缩顺序有讲究 四件套不是随意叠加的。通常先做蒸馏得到更小的基础模型（如 7B→3B），再对 3B 做量化（Q4）和剪枝，最后在运行时用 KV 压缩兜底。反过来先量化再蒸馏会很别扭——蒸馏需要教师模型的软标签，量化后的学生本身精度已受损。最稳妥的起点是：直接选一个官方出的「小模型 + 已量化」组合（如 Qwen2.5-3B-Instruct-Q4_K_M），而不是自己从头压。

2.1 量化：第一手段

4-bit 量化把 7B 压到约 3.5 GB，是目前端侧主力手段。GGUF 格式（llama.cpp 生态）支持多种量化精度：

量化格式每参数比特7B 模型大小精度损失推荐场景
Q8_08.5~7.2 GB~0%PC / 高内存设备
Q5_K_M5.5~4.8 GB＜0.5%高端手机
Q4_K_M4.8~4.1 GB＜1%主流手机（推荐）
Q3_K_M3.9~3.3 GB1-2%低内存设备
Q2_K2.6~2.7 GB3-5%极限压缩（不推荐）

选型建议：Q4_K_M 是性价比之王——大小和精度的平衡点最好，适合绝大多数端侧场景。详见 量化 Quantization。

2.2 知识蒸馏：用大模型教小模型

用大模型当老师，把小模型「教」到接近能力。蒸馏不是简单的微调，而是让小模型学习大模型的输出分布（软标签），而非硬标签。这样小模型能学到「虽然选 A，但 B 也有 30% 的概率」这种额外信息。

典型实践：Phi 系列用 GPT-4 生成高质量教科书数据训练 3.8B 模型，在部分基准上接近 Llama-2-70B 的表现。详见 知识蒸馏。

2.3 剪枝与稀疏

去掉低价值神经元/注意力头，配合蒸馏恢复效果。剪枝分两种：

  • 结构化剪枝：整行整列地删，删完模型架构变小，推理直接加速。代表方法如 SparseGPT、Wanda。
  • 非结构化剪枝：单个权重置零，需要稀疏矩阵支持才能加速，硬件友好性差。

2.4 KV 压缩与卸载

降低长上下文时的显存尖峰。端侧场景的上下文通常较短（几百到几千 token），但 Agent 场景需要多轮对话，KV 会累积。配合 KV 分级存储 的思路，把冷 KV 放到 CPU 内存。

三、端侧推理栈：主流方案对比

模型压缩完了，还需要一个高效的推理引擎把它在设备上跑起来。端侧推理栈的选型直接影响速度、兼容性和开发体验。

新手最容易搞错 新手评估端侧模型时，最常见的错误是只看「模型文件能不能装进内存」，然后得出结论「能跑」。「放得下」和「跑得动」是两回事。装进内存只解决了容量问题；跑得动还受两个隐性约束：一是内存带宽——端侧芯片的带宽远低于服务器 GPU，每生成一个 token 都要把全部量化权重读一遍，带宽决定稳态 tok/s 的上限，这跟服务器推理的 Decode 瓶颈一模一样；二是散热与降频——满速推理几十秒就触发系统降频，速度直接腰斩。同样的 Q4 模型，在 A 手机上可能 25 tok/s，在 B 手机上因为带宽低或散热差可能只有 8 tok/s。所以「能装下」只够你继续往下论证，真正的验收标准是「在目标真机上、持续推理 1 分钟后的稳态速度」——用压测代替猜想。

四、端云协同：路由与分工

端云协同不是「非此即彼」，而是让路由策略按任务特性分派。好的路由策略能在用户无感的情况下，既享受端侧的速度和隐私，又获得云端的能力。

实践中常见的路由规则：

  • 延迟敏感：输入法联想、实时语音转写 → 端侧（云端 RTT 100-300ms，端侧 10-50ms）。
  • 隐私敏感：医疗记录、聊天内容、文档草稿 → 端侧（数据不出设备）。
  • 离线可用：飞机、地铁、弱网 → 端侧（唯一选择）。
  • 知识密集：需要最新资讯或私域数据 → 云端（RAG 加持）。
  • 推理密集：数学、代码、长文规划 → 云端（参数量需求高）。

「端侧一个模型、云端一个模型、两者怎么配合」这个问题，苹果在 2024 年的 Apple Intelligence 技术报告里给出了一个非常清晰的参考架构，下面这张是报告里的原图。

逐块读这张图，注意它把「端云协同」画成了三个层次。第一，最上面是模型本体：图里同时画出「端侧语言模型」（约 3B 参数，跑在设备上）和「服务器语言模型」（大模型，跑在 Private Cloud Compute 上）——两者是同一个家族、同一套架构，而不是两个毫不相关的模型。这个「同源」设计是端云协同的关键：端侧负责的「简单任务」和云端负责的「复杂任务」共享同一套分词、同一套能力底座，路由切换时行为一致性更好。第二，中间是成排的适配器（LoRA Adapter）：同一个基座模型挂着一排轻量适配器，每个适配器对应一类任务（如摘要、改写、特定领域问答）。这对应本页「压缩四件套」之外的第五种思路——不换模型，只换适配器：任务 A 用适配器 1，任务 B 切换成适配器 2，基座权重完全共享。适配器只有几 MB 到几十 MB，分发成本远低于换整个模型。第三，端侧与服务器侧各有一套适配器：图里端侧和服务器模型各自挂着自己的适配器组——这暗示了端云协同的完整分工：同一任务，端侧有一个「轻量版」适配器，服务器有一个「完整版」适配器，路由时按设备能力与任务复杂度选择。

这张图对工程实践最大的启示是：端云协同不一定是「两个不同公司造的模型拼起来」，更成熟的做法是「一个模型家族 + 按层拆分的部署」。它把「端侧 SLM 和云端大模型」从「竞争关系」变成了「同一系统的两个档位」——端侧挡位保底（隐私、离线、低延迟），云端挡位兜上限（能力、知识、推理）。做端云路由设计时，先把这两个档位画清楚，再考虑本文开头的五条路由规则，顺序不能反。

4.1 置信度路由

进阶做法是置信度路由：先让端侧模型给出答案和置信分，置信度低于阈值再升级到云端——既保住大部分请求的隐私与速度，又用云端兜住难例。

class EdgeCloudRouter:
    """端云协同置信度路由"""

    def __init__(self, local_model, cloud_api,
                 confidence_threshold=0.7,
                 max_local_tokens=512):
        self.local = local_model
        self.cloud = cloud_api
        self.threshold = confidence_threshold
        self.max_tokens = max_local_tokens

    def route(self, query, context=""):
        """路由决策：先端侧，低置信度则升级云端

        Returns:
            {"source": "local"|"cloud",
             "answer": str,
             "confidence": float,
             "latency_ms": int}
        """
        import time
        t0 = time.time()

        # 1. 先尝试端侧模型
        local_result = self.local.generate(
            query,
            context=context,
            max_tokens=self.max_tokens,
            return_confidence=True
        )

        # 2. 检查置信度
        if local_result["confidence"] >= self.threshold:
            return {
                "source": "local",
                "answer": local_result["text"],
                "confidence": local_result["confidence"],
                "latency_ms": int((time.time() - t0) * 1000)
            }

        # 3. 低置信度：升级到云端
        cloud_result = self.cloud.chat(
            messages=[
                {"role": "user",
                 "content": f"上下文：{context}\n\n问题：{query}"}
            ]
        )

        return {
            "source": "cloud",
            "answer": cloud_result["content"],
            "confidence": None,  # 云端不返回置信度
            "latency_ms": int((time.time() - t0) * 1000),
            "local_confidence": local_result["confidence"]
        }

    def batch_route(self, queries):
        """批量路由：统计端侧命中率"""
        results = [self.route(q) for q in queries]
        local_count = sum(1 for r in results if r["source"] == "local")
        print(f"端侧命中: {local_count}/{len(results)} "
              f"({local_count/len(results)*100:.1f}%)")
        return results

代价是端侧模型需要校准自己的置信度——这是模型训练时就该设计的。校准不好的模型会「过度自信」（错误答案也给高分）或「不够自信」（正确答案也频繁升级云端），两者都会损害用户体验。

五、电池与散热：被忽视的约束

端侧推理的能耗和发热是产品层面的硬约束。一个 7B 模型满速推理时功耗可达 5-10W，持续 30 秒手机就会明显发热，系统会自动降频——速度从 20 tok/s 掉到 5 tok/s。

发热不是小事 手机芯片的降频是被动温控，应用层无法关闭。一旦触发，不是某个请求变慢，而是整机所有推理一起变慢——正在跑的其他用户请求也会受影响。更隐蔽的是「温热态」：手机从裤兜里拿出来时本来就 35°C，稍微一推理就到降频阈值。所以端侧服务不能按峰值算力设计 SLO，而应按「持续可维持算力」设计，通常只有峰值的一半甚至更低。
策略做法效果代价
推理节流限制生成速度到 5-10 tok/s发热可控用户等待时间增加
模型降级发热时自动切到更小模型功耗减半输出质量下降
批量处理积攒请求后一次性推理减少冷启动开销单请求延迟增加
温度感知监控芯片温度，过热时暂停保护硬件服务中断
展开：手算一次端侧生成的「时间 × 电量」账

「端侧推理多耗电」这件事，用数字说话才直观。以 7B-Q4 模型（约 4.1 GB）、实测 20 tok/s、满速推理功耗约 5W 为例。

第一笔账：生成 300 token（一段中等长度的回答）要多久。300 ÷ 20 = 15 秒。这 15 秒里芯片满速运行，如果手机同时在做别的事（后台刷新、播放音频），总功耗会更高。

第二笔账：这 15 秒耗了多少电。能量 = 功率 × 时间 = 5W × 15s = 75 焦耳。换算成常用单位，1 瓦时 = 3600 焦耳，所以约 0.02 瓦时。手机电池容量约 15-20 瓦时，这意味着一次 300 token 的生成只占电池容量的千分之一——单次看确实不多。

第三笔账：但发热是另一回事。耗电少不等于不发热。15 秒的持续 5W 高负载，芯片结温会迅速爬升，散热差的手机几十秒就顶到降频阈值——降频后速度掉到 5-8 tok/s，300 token 要 40-60 秒，用户直接感知到「越用越卡」。所以端侧真正的问题不是「总耗电」，而是「持续高功率的持续时间」：短促的 5W 没问题，连续 2 分钟的 5W 就会触发温控。

由此得到一个设计原则：把端侧任务设计成「短时、间断」，而不是「长时、连续」。需要长时间生成的（如整篇长文），要么拆成多段让芯片间歇休息，要么直接路由到云端；连续对话类产品（如语音陪伴）则要主动限速或降级到更小的模型，把持续功率压到 2-3W 以下，才能在「不降频」的前提下长期工作。

六、模型分发与更新

端侧模型的分发是一个容易被忽视的工程问题。一个 4GB 的量化模型通过 App Store 分发，意味着用户要下载 4GB 额外数据。更新模型意味着重新下载 4GB——这在移动网络环境下是很大的负担。

常见的分发策略：

  • App 内置：把模型打包进 App。优点是开箱即用，缺点是 App 体积大、更新慢。
  • 首次启动下载：App 体积小，首次使用时下载模型。优点是灵活，缺点是首次体验差。
  • OTA 增量更新：只下载模型 diff。优点是流量小，缺点是实现复杂，需要差分压缩技术。
  • 多模型按需下载：按任务类型提供多个小模型，用户用到哪个下哪个。

八、真实应用场景

端侧 SLM 已经在多个方向规模化落地，核心逻辑都是「用有限的参数换取隐私、延迟和离线的确定性」：

选型与落地路径总结：先确认任务类型是否匹配 SLM 能力边界 → 再按内存预算选模型尺寸与量化档位 → 选推理栈 → 设计路由策略 → 做好电池与分发管理。端侧不是大模型的替代，而是大模型的「最后一公里」——让最常用、最私密、最需要速度的能力出现在用户手里。

延迟预算算例：30 tok/s 到底够不够用

端侧模型的速度（token/s）经常被拿来和云端对比，但「够不够快」其实取决于用途，而不是绝对数字。把几类典型任务的延迟预算拆开算一遍，比空谈「快慢」有用得多。

先看交互式对话。人类阅读速度大约是每秒 4-8 个字，中文一个 token 通常对应 1-2 个字，所以 15-20 tok/s 已经超过了人类的阅读速度——模型生成的文字，人根本来不及读完。这也是为什么端侧 7B-Q4 的 15-20 tok/s 在聊天场景完全够用：用户读得比模型写得还慢，速度不再是人感知的瓶颈。真正影响体验的不是速度，而是首 token 延迟——如果按下发送后要等 2-3 秒才出第一个字，哪怕之后每秒钟 30 字，用户也会觉得「卡」。端侧的优势恰好在此：没有网络 RTT，首 token 通常几十毫秒，体验是「秒出」。所以端侧体验的核心指标其实是 TTFT，而不是稳态 tok/s。

再看输入法联想和语音转写这类「实时跟随」场景。输入法联想要求每击键一次就要给出候选词，可用预算约 10-30 ms；语音转写要求字幕基本跟得上说话速度，可用预算约 50-100 ms 每句。这些预算对 7B 模型来说太紧张，但对 0.5-1B 的超小模型（如 SmolLM2-135M、Gemma-2-2B）完全够用——它们跑在 30-60 tok/s 甚至更快，一次联想只需生成几个 token。这类场景选模型的标准是「够用里选最小」，而不是「最大里选够用」。

最后是长文档摘要、代码补全这类「一次性生成一大段」的任务。这里用户等的是总时长：如果一段 500 字的摘要用 20 tok/s 生成，约需 25-50 秒，这对移动场景来说偏长。此时才值得考虑三种手段：上云端、用更大模型（提高单次生成质量减少重试）、或者把任务拆小（分段摘要再合并）。反过来，如果只是抽取几个关键词或做意图分类，总产出只有几个 token，1-2 秒内就完成，端侧毫无压力。

把四类任务的预算汇总成一句话：短输出、频繁调用的任务，端侧延迟预算充裕；长输出、单次调用的任务，端侧容易触及等待时间上限。做产品设计时，先按任务的「输出长度 × 调用频率」画一张分布，再把端侧 tok/s 换算成每个任务的实际等待时间，就知道哪些任务天然适合端侧、哪些必须路由到云端。

五个反面信号：什么时候别上端侧

端侧部署的决策里，最容易被忽视的是「哪些场景不该用端侧」。以下五个信号只要中了两条以上，就该重新考虑是不是真的要上端侧。

信号一：任务需要最新知识或私域数据。端侧模型的知识截止于训练时刻，且没有内置检索能力。如果产品核心是回答「今天有什么新闻」「我司内部文档怎么说」，端侧模型要么答错、要么需要复杂的本地 RAG 兜底——而本地 RAG 的检索质量、索引更新成本，往往比直接上云端高一个数量级。这类任务放端侧，是在用更大的工程复杂度换更差的结果。

信号二：用户对错误率零容忍。医疗建议、法律意见、代码安全审查这类任务，端侧模型的幻觉是产品不可接受的。即使有置信度路由兜底，兜底本身也只是「把难例送去云端」——既然最终大部分还是要上云，不如直接上云，把端侧省下的那点成本让给更可靠的架构。

信号三：模型需要频繁更新。端侧模型的更新依赖 OTA 分发，而一个 3-4 GB 的模型每次更新都是实打实的流量和用户打扰。如果业务模型每周都在迭代（新话术、新风格、新规则），端侧永远滞后于云端，产品能力会被分发节奏拖死。端侧适合「能力稳定、低频迭代」的模型。

信号四：设备碎片化严重。iOS 和 Android 各有一堆芯片、内存档位、系统版本，同一个量化模型在不同设备上的表现（速度、内存、发热）可能差出一倍。如果要在几十种设备型号上逐一调优、测试、灰度，维护成本会迅速吞掉端侧省下的算力钱。团队没有足够的设备矩阵和测试资源时，端侧就是负担。

信号五：没有持续的功耗与发热预算。7B 满速推理功耗 5-10W，30 秒就触发降频。如果产品的使用场景是「长时间连续对话」（如车载助手、语音陪伴），芯片会持续高负载，降频后体验反而比云端还差。端侧适合「短时、间断」的使用模式，不适合「持续、高强度」的负载。

最后补充一个判断框架：把「隐私、延迟、离线」三条端侧的核心价值，和「能力、更新、稳定性」三条云端的核心价值，放到一张表里逐项打分——只有当隐私/延迟/离线对你业务的权重明显高于能力/更新/稳定性时，端侧才值得投入。否则，端云协同中的「端」做得再漂亮，也只是一块成本，而不是能力。反过来也一样：如果隐私不是卖点、延迟不是痛点、离线只是「偶尔需要」，那端侧模型带来的能力折损、分发成本和测试负担，就全部变成了纯开销。此时把模型放回云端、用端侧只做轻量的任务分类与路由，往往才是整体成本最低的架构。

要点速查

  • 本质：端侧 SLM 用参数量换隐私、延迟、成本与离线能力，适合模式匹配型任务，不适合知识密集与多步推理。
  • 能力边界：分类/摘要/改写 → 强（1-3B）；简单问答/格式化 → 可用（3-7B+微调）；事实问答/推理/最新知识 → 弱（需上云）。
  • 压缩四件套：量化（Q4_K_M 主力）、蒸馏（大模型教小模型）、剪枝（去低价值权重）、KV 压缩（省运行内存）。
  • 推理栈选型：llama.cpp（全平台生态最好）、MLX（Apple 最优）、WebGPU（零安装）、MNN/NCNN（移动原生集成）。
  • 内存预算：8GB 手机跑 7B-Q4 刚好，留给 KV 只有 0.5-1GB（~2-4K 上下文）；3B 模型更从容。
  • 端云协同：按延迟/隐私/离线/知识/推理五个维度路由；置信度路由做兜底，低置信度升级云端。
  • 电池与散热：7B 满速推理 5-10W，30 秒发热降频；策略包括节流、模型降级、批量处理、温度感知。
  • 模型分发：内置（开箱即用但体积大）、首次下载（灵活但首次体验差）、OTA 增量（省流量但实现复杂）。
  • 常见坑：高估小模型能力导致产品翻车；忽视电池与发热（长上下文在端侧非常耗电）；忽视「模型更新要重新分发」的运维成本；不做置信度校准就上路由。

学习目标

在目标设备用 llama.cpp 或平台原生运行同一模型的 FP16、8bit、4bit 版本，执行 20 条固定任务和 15 分钟持续负载；记录质量、RSS、TTFT、tokens/s、温度和功耗。

验收标准
