技术全景图

「大模型技术」这四个字底下装着十几个彼此独立又互相咬合的领域。这一页把它们拆成 16 篇，说清每一块解决什么问题、和相邻的块怎么衔接、以及你遇到具体问题时该翻到哪一页。这是你在这本手册里的导航地图，也是一张排障索引。

一图看懂

整本手册按七个阶段编排，从「语言怎么变成数字」一路走到「上线之后怎么不出事」。箭头是推荐顺序，不是硬性依赖——真实学习几乎总会分支和回环。

先分清两条流水线：训练态与服务态

刚入门时最容易混淆的一件事，是把「训练时发生的事」和「线上服务时发生的事」搅在一起。它们的目标、瓶颈、优化手段完全不同：训练态追求吞吐，服务态追求延迟；训练态可以慢慢来，服务态每一毫秒都要算钱。

论文原图：为什么系统篇必须接在模型篇之后

全景图里 05 篇 GPU 与算子系统看起来像「可选深入」，但它并不是和模型无关的旁支。模型层的注意力会生成大量中间矩阵，训练和推理都要把这些数据在高带宽显存、片上缓存与计算单元之间搬运。下面这张 FlashAttention 论文原图把这个关键事实画了出来：算法是否快，不只由乘法次数决定，还由数据搬运是否高效决定。

读图时先看两层内存：HBM 容量大但离计算单元更远，SRAM 小但访问快。朴素注意力往往先物化巨大的注意力矩阵，再反复读写它；FlashAttention 则把 Q、K、V 切成小块，在 SRAM 里完成局部计算并在线更新结果，尽量避免把中间矩阵写回 HBM。图中的方块不是装饰，而是在说明「同一个数学结果，可以有不同的内存访问路径」。

这张图对阅读顺序的启示是：先在 03 篇理解注意力的张量关系，再到 05 篇理解数据搬运，最后到 09 篇观察推理引擎如何把这些优化变成吞吐和延迟指标。遇到「模型结构没变，速度却差很多」时，优先检查算子融合、批处理、缓存命中和内存读写，而不是只比较 FLOPs。系统层正是把抽象公式变成真实账单的那一层。

怎么用这张图定位自己 如果你的工作是「让模型学会某件事」，你在左边；如果是「让模型稳定地服务用户」，你在右边。大多数应用团队一辈子只待在右边，这完全正常——右边同样有做不完的深水区。真正需要两边都懂的，是那些要判断「这个问题该用微调解决还是用提示解决」的人。

一次线上请求会穿过哪些模块

把服务态展开看，一个「用户提问、系统回答」的过程实际上要经过五到七个组件。理解这条链路的价值在于：线上出问题时，你能快速定位到是哪一层的锅。

这条链路里每一步都对应手册的某一篇：入口护栏见 护栏与输出校验，上下文组装见 上下文工程，检索层见 RAG 检索增强生成，推理见 推理引擎，可观测性见 可观测性与全链路追踪。

用代码看这几层怎么落地

上面那张图翻译成最小可用的代码骨架，大致是下面这样。真实系统会复杂很多，但层次划分是一样的——每一层都能独立替换、独立评估、独立监控，这是这套分层最大的工程价值。

def answer(user_input, session):
    # ① 入口护栏：不合规的输入根本不该进到模型  → 12 篇
    if not guard_input(user_input):
        return refuse("input_blocked")

    # ② 检索：把事实外置，减少幻觉             → 10 篇
    docs = retriever.search(user_input, top_k=20)
    docs = reranker.rerank(user_input, docs, top_n=5)

    # ③ 上下文组装：在有限预算内排布信息        → 10 篇
    prompt = render(
        system=SYSTEM_PROMPT,
        history=session.recent_turns(budget=2000),
        evidence=docs,
        question=user_input,
    )

    # ④ 推理：解码参数决定输出风格与稳定性      → 08 / 09 篇
    out = llm.generate(prompt, temperature=0.2, max_tokens=800)

    # ⑤ 出口校验：格式与内容双重把关，失败要 fail closed → 12 篇
    ok, cleaned = validate_output(out, schema=ANSWER_SCHEMA)
    if not ok:
        return refuse("output_invalid")

    # ⑥ 可观测性：没有这一步，线上等于盲飞      → 12 篇
    trace.log(prompt=prompt, output=cleaned, model=llm.version,
              tokens=out.usage, latency_ms=out.latency)
    return cleaned
新手最常缺的两层 大多数人写出来的第一版是「拼个提示词，调一次 API，返回结果」——缺的正是第 ⑤ 层出口校验和第 ⑥ 层可观测性。缺前者，脏数据会直接流进下游状态；缺后者，出了问题你连「昨天是不是也这样」都答不上来。这两层在 demo 阶段可以省，在生产阶段一定会补回来，区别只是主动补还是出事后补。

一个模型的完整生命周期

如果把视角再拉高一层，从「一个模型从无到有再到退役」来看，整本手册可以串成一条闭环。这条闭环解释了为什么评估与可观测性被排在很后面，却是整个环里最容易被跳过、也最不该跳过的一环。

换个视角：按概念而不是按流程

上面几张图都是按「流程」组织的。但当你在读论文或看别人的技术方案时，更常需要的是按概念族快速定位。下面这张概念地图把同一批内容重新按四个层次归了一次类。

层与层之间靠什么衔接：概念图里看不见的接口

概念地图把技术栈切成四层，但真正理解这套系统，还要看清层与层之间靠什么「咬合」在一起。这些接口在图上没有画出来，却是日常排障时最常出问题的地方——层内的问题通常好修，缝上的问题往往要动两头。

表示层与模型层之间的接口，是词表与嵌入矩阵。文本先被分词器切成 token，再查嵌入矩阵变成向量，模型层的注意力才能开始工作。接口是否匹配，直接表现为「扩词表之后要不要重新对齐嵌入」「遇到词表外的字怎么办」。很多看起来是模型层的问题，根子其实在表示层的这道接口上——比如中文模型对生僻字表现差，多半是分词和词表设计的问题，而不是注意力机制的问题。

模型层与训练层之间的接口，是权重本身加一套隐藏约定。权重怎么初始化、激活按什么数值范围归一化，训练配方必须和架构设计保持一致。同一份数据，换一个初始化方式或归一化位置，收敛行为可以差很远。这就是为什么架构论文和训练代码必须成对阅读、不能只抄一半——只看模型结构不看训练细节，复现出来的效果往往对不上。

训练层与运行层之间的接口，是模型文件加推理引擎的兼容性。训练时用 fp16 累加，推理时量化成 int8，精度一变输出分布就会漂移；KV Cache 的布局、批处理的方式，也由训练产出的权重格式决定。部署篇里大量「明明没改模型怎么效果就变了」的困惑，其实都发生在这道接口上。要追这种问题，先查精度、再查引擎配置，别急着怀疑模型本身。

运行层再往下，还有一道通向「人」的接口：提示词与工具的协议。模型层以上的所有设计，最终都要通过运行层暴露成 API 和消息格式；你写的 system prompt、函数调用 schema，是运行层与外部世界之间唯一的通道。这道接口设计得好，模型换谁都行；设计得差，换模型等于重写整个应用。这也是 model-agnostic 设计反复被强调的原因——它本质上是把「缝」标准化，让两头都可以独立更换。

把四层地图记成「四个盒子加三条缝」很有用：平时读技术方案，先判断讨论发生在哪个盒子；遇到问题，先怀疑是不是某条缝对不上。这样定位问题，比从头到尾通读一遍架构快得多，也是这套全景图在日常工作里最常见的用法。

展开：如何沿依赖闭环排查一个线上问题

假设用户反馈「文档问答最近变慢，而且答案偶尔引用旧版本」。不要从模型名字开始查，而要沿闭环逆向走：先看 12 篇的 trace，确认延迟增长发生在检索、上下文组装还是模型生成；再看 10 篇的检索索引是否更新；如果索引没问题，再检查 09 篇推理引擎的批处理和 KV Cache 是否改变。

如果答案质量下降但延迟正常，顺序应反过来：先看 13 篇评测门禁是否捕捉到回归，再检查 10 篇的切分、重排和上下文预算，最后才怀疑 07 篇后训练模型。这个顺序遵循「离现象最近的可观测层优先」，可以避免一上来重训模型这种代价很高、证据很弱的动作。

定位完成后必须把结论送回闭环：索引刷新问题进入 12 篇运维规则，检索失败样本进入 13 篇评测集，模型行为变化进入 07 篇后训练或 14 篇治理审查。全景图的价值不是让你记住 16 个标题，而是让每次修复都有回流位置，系统不会在同一个坑里反复摔倒。

展开：这张地图的三条编排原则

为什么是这个顺序、这个切分？背后有三条刻意的取舍，说清楚有助于你理解各篇之间那些看起来奇怪的分工。

原则一：同一篇内只允许一个分类维度。比如后训练篇统一在「训练算法」这一个维度上——SFT、DPO、RLHF、推理 RL 都是算法。而「合成数据」虽然主要服务于后训练，却被放进了预训练篇，因为它是一种数据方法论而不是训练算法，塞进来会破坏维度一致性。它在预训练篇里和「数据工程」构成「合成语料 + 真实语料」的并列对子，反而自洽。

原则二：按「改什么」而不是按「叫什么」归类。典型例子是压缩：知识蒸馏被放在后训练篇，量化被放在效率篇。听起来两者都是「把模型变小」，但蒸馏是换一个更小的模型去继承能力，属于训练问题；量化是不改能力只改数值表示，属于部署问题。同理，扩散语言模型被排在架构篇而不是推理篇，判据是它改变了权重层面的兼容性。

原则三：安全被拆成四方而不是合成一篇。因为安全在四个完全不同的位置发生，需要四套不同的手段：训练侧把安全烙进权重（安全对齐）、执行侧管住 Agent 能做什么（Agent 安全）、运行时侧那道可插拔的闸门（护栏）、攻方与测评侧主动找漏洞（安全与红队）。合成一篇会让读者误以为做了其中一件就安全了。

顺带解释一个常见疑问：为什么 GPU 与算子系统排在第 05 篇这么靠前，却标注为「可选深入」？因为它在依赖关系上确实位于训练之前——不了解显存层级就没法理解并行策略为什么那样设计。但对只想会用大模型的读者，它可以整篇跳过，需要时再回看。位置按依赖排，可选性按角色标，两者并不矛盾。

手册边界之外的相邻领域

要点速查

  • 7 阶段 16 篇：基础层 → 架构核心 → 训练全流程 → 推理部署 → 应用与 Agent → 工程化与治理 → 动手实践。
  • 先分清两条流水线：训练态追吞吐、服务态追延迟；两者通过「权重交付」和「数据回流」相连。
  • 一次请求穿过六层：入口护栏 → 检索 → 上下文组装 → 推理 → 出口校验 → 可观测性。新手最常缺后两层。
  • 生命周期有两条关键回边：评估不达标回炉后训练，线上数据回流补充语料。
  • 概念地图四层：表示层、模型层、训练层、运行层。改动层次越靠下，影响面越大。
  • 排障先查索引表：按现象定位比按目录翻找快得多。
  • 编排三原则：一篇一个维度、按「改什么」归类、安全拆成四方。
  • 05 GPU 篇是可选的：位置按依赖排，可选性按角色标，只想会用大模型可以整篇跳过。

发展脉络

大模型工程已从单一模型训练扩展为数据、训练、推理、应用、评测和治理的完整技术栈，每层都有独立版本与责任边界。

机制抓手

用数据契约连接训练，用 API/事件契约连接服务，用评测集连接质量，用 trace 连接线上反馈；任何层都应可替换且可回放。

工程权衡

自研越深控制力越强但验证和运维成本越高；托管能力降低启动成本，却带来供应商、隐私和可观测性边界。

前沿观察

模型网关、统一评测、Agent 协议和推理资源编排正在成为跨层基础设施，不能由单个 prompt 代替。
