模型家族与选型

在一个新项目上做的第一个技术决策几乎总是「用哪个模型」。这一页不讲哪个最新最强——版本号三个月就过期——而是给你一套不会过时的选型方法论:看懂每个家族的基因、问对四个问题、理解为什么最终答案通常是混合路由。

参数量级与显存占用：把「多大」算成「多贵」

看家族表时，一个绕不开的追问是：这些模型到底有多大？参数量不是虚荣指标，它直接决定两件最实际的事——能不能放进你的显卡，以及每跑一次要付多少算力钱。学会做量级换算，选型就从拍脑袋变成算账。

先记住一组常识量级。1B（十亿）参数是「小模型」的门槛，7B 到 14B 是「中等模型」，70B 以上是「大模型」，700B 以上属于「旗舰级」。同一个家族往往同时推出多个尺寸：同一份训练配方，用不同的参数量配出 1.5B、7B、14B、72B 几档，让不同预算的人各取所需。尺寸越小，单位成本越低，能力也相应打折——你选的是「能力与成本的切片」。

显存占用是第一个要算的账。加载模型权重时，最粗略的估算是：每 10 亿参数用 fp16 精度存约需 2 GB 显存。于是 7B 模型权重约 14 GB，70B 约 140 GB——一张 80 GB 的旗舰卡装不下 70B 的完整权重，必须先量化或切分。而训练比推理更吃显存：推理只需要权重，训练还要额外缓存梯度、优化器状态和中间激活，通常要按权重的数倍来预留。一个经验说法是训练显存约为推理的三四倍起步，具体账目见 推理服务成本 与 分布式训练 里的显存分析。

参数量还决定速度与成本。同一个模型，输出一个 token 的计算量大致与参数量成正比；在相同硬件上，7B 的生成速度通常明显快于 70B，单位 token 的电费也更低。这就是为什么「能用小模型绝不用大模型」不是偷懒，而是算过账后的理性选择——高频低难度流量用大模型，等于拿火箭运蚂蚁。

但也要记住参数量不是全部。MoE（混合专家）模型总参数很大，实际每个 token 只激活一部分专家，推理时的有效计算量远小于总参数所暗示的；而推理时扩展（思考模型）靠多花推理算力换准确率，与参数量是两条独立的曲线。所以「参数量越大越好」这句直觉，在 MoE 和推理模型面前都要打折扣。

选型的最后一步，是把你候选的几档模型连同显存需求和成本量级写进决策表，再套用前文四问的约束过滤。这样得出的结论才是能落地、能算账的结论，而不是又一场「参数军备竞赛」的旁观。

家族基因地图

当你面对十几个名字时，最有效的办法不是记型号，而是记基因。下面这张思维导图按三个正交维度把家族拆开:开放方式(开源权重 vs 闭源 API)、能力取向(通用 vs 代码专精)、地域(国际 vs 国内)。同一个家族可能同时落在多个分支里——例如 Qwen 既是开放权重，又有代码专精的 Coder 子线。

读图提示 闭源 API 家族(GPT/Claude/Gemini/Kimi)无论能力多强，都无法自托管、数据必须出站，这是基因决定的，不随版本变化。开放权重家族(Qwen/DeepSeek/Llama/Mistral)则天生可落地、可微调、可私有化——但要自己承担运维。

论文原图：家族差异最终会落到注意力数据流

模型家族选型不能只看宣传页上的「旗舰」或「开源」标签，因为家族的设计取舍最后都会落到一件具体的事：一次请求怎样在网络里搬运信息、消耗显存并产生 token。下面这张原图来自 Transformer 论文的注意力章节，它把缩放点积注意力和多头注意力画成了可追踪的计算管线。理解这条管线后，你会更容易理解为什么有的家族强调多头、分组或多查询注意力，有的家族强调长上下文、代码能力或推理预算。

读左图时，把 Q、K、V 想成三份清单：Query 是「我现在想找什么」，Key 是「每个位置提供什么索引」，Value 是「真正要取回的内容」。先用 Q 和 K 算相关性，再用相关性加权 V，模型才得到当前位置应该关注的上下文。右图的多头就是并行做几组不同的检索，让不同头学习不同关系；这也是为什么只比较参数量不够，还要问架构是否把计算预算花在你的任务上。

选型案例可以这样落地：如果任务是高频摘要，先用小尺寸开放权重模型跑自己的评测集；如果任务是少量但极难的代码修复，再把复杂请求路由到推理能力更强的后端；如果上下文很长，则额外测首 token 延迟、KV Cache 占用和中段信息召回。论文图提供的是机制底座，最终决策仍必须由你的数据、延迟、合规和成本共同决定。

四问决策框架

不要从「哪个模型最强」开始，从你的约束条件开始。顺着下面四个问题过一遍，候选集会自己收窄。这套框架的精髓是:把「选模型」翻译成「算约束」。

第一问:数据能出站吗?

如果你的输入数据含 PII、受 HIPAA/GDPR/等保约束、或合同要求数据不出本地，那么所有纯 API 模型(GPT、Claude、Gemini、Kimi)直接排除。可选范围只剩开放权重模型。这是硬约束，不是优化项。

第二问:真需要前沿推理吗?

「前沿推理能力」指的是只有少数模型能做好的事:复杂多步推理、长篇代码生成、深度分析。统计你的流量里这类请求占比——通常不超过 10%。绝大多数请求用中等模型就够了，把最贵的算力留给最难的那一小撮。

第三问:月 token 量在哪一档?

月消耗低于 5000 万 token:托管 API 几乎必然更便宜——省掉了 GPU 闲置、运维人力、故障恢复。超过 2 亿 token:自托管几乎必然赢。中间档没有捷径，必须建含 GPU 租赁、工程人力、运维工具的全成本模型。别只拿单价去乘，那样算出来的永远是自托管便宜。

第四问:运维能力到位吗?

自托管不只是装个 vLLM 跑起来。你需要能处理:节点故障自动切换、模型版本滚动更新、延迟 SLO 监控、显存 OOM 的根因定位。没有这些能力，自托管的单位成本优势会被故障时间吃掉。关于自托管真实成本，详见 推理服务成本。

四问的默认解 数据不能出站 → 只能自托管开源。数据能出站 + 不用前沿推理 + 量低于 5000 万 → 直接上托管 API。数据能出站 + 需要前沿推理 → 闭源吃那 10% 的硬骨头。四问的本质是把「选模型」变成「算约束」，答案通常不在单个模型身上。

把四问串起来，会得到一条清晰的决策状态机:从收集硬约束出发，沿「数据 → 推理需求 → 量级 → 运维」一路收窄，所有分支最终都汇入「锁定 model-agnostic 架构」这一个终态。

混合路由:不是二选一

认真跑完四问之后，一个结论会反复出现:单一模型不是最优解。项目里通常同时存在这几类请求:

  • 不到 10%的请求真的需要前沿推理(复杂多步题、长篇代码、深度分析)——这些值得花大价钱走闭源;直接用最贵的那个就对了。
  • 剩下 90%是高频低难度——摘要、翻译、格式转换、简单问答——用成本低得多的自托管模型或廉价 API 完全够用。
  • 还有一类纯判定性的请求(意图识别、安全分类)——小模型就能做，专门跑一个路由分支。

这就是混合路由(hybrid routing)的核心逻辑:闭源前沿吃最难的那 10%，开源吃高频的那 90%。中间的路由器按问题类型、复杂度预估、预算上限决定走哪路。三类请求的差异可以摊成一张表:

请求类型典型占比推荐后端成本特征
前沿推理(硬骨头) 约 10% 闭源前沿(GPT / Claude) 单位成本高，但绝对量小，整体可控
高频低难度 约 80% 开源自托管(Qwen / DeepSeek / Llama) 量大但单位成本极低，决定总体账单
纯判定路由 约 10% 小模型 最快最便宜，只做意图识别/分类

混合路由在工程上意味着路由逻辑、成本归因、fallback 三件套。落地的关键是把复杂度分类器本身也做成可观测、可回退——分类错了要有兜底(例如前沿模型超时被降级到开源模型)。相关技术见 混合推理与思考预算 和 推理成本工程。

架构第一原则 从第一天起就把接口做成 model-agnostic。统一的消息格式、统一的函数调用协议、统一的后端适配层。今天你的流量分布决定了某种路由比例，三个月后某个新模型发布就可能改变答案——但如果每一处调用都写死了模型名，重路由的成本会高到让你放弃。

代码大模型:2026 年商业落地体量最大的场景

代码生成不是大模型的一个小分支——它是 2026 年 AI 商业落地面向最广、营收最高的单一场景。代码大模型共享通用 LLM 的架构骨架，但在三个维度上有针对性的专项设计。

FIM:不是从开头写，是从中间补

标准自回归训练永远是「给定前缀 $P$，预测下一个 token」。但编程的真实场景经常是:前面有一段代码，后面也有一段，你要补中间的缺口。这就是 FIM(Fill-in-the-Middle，填充式训练)要解决的问题。

FIM 把每一段训练语料随机切为三截:前缀(Prefix)、中间(Middle)、后缀(Suffix)。训练时不按顺序生成，而是同时看到前缀和后缀，只预测中间缺失的部分。输入格式类似于:

《PRE》def foo(x):\n    # 前缀:已经写好的上下文\n《SUF》\n    return result\n《MID》result = x * 2 + 1

模型学会在给定两端约束的情况下生成中间——这正是 IDE 里代码补全、行内编辑的实际使用模式。由于模型必须「看懂两边」才能补对中间，FIM 训练的模型在理解代码结构上也更稳健。主流代码大模型全部采用 FIM 作为训练目标之一。

仓库级上下文:不让模型只看一个文件

你在 IDE 里补全代码时，上下文远远不止当前文件这一个。同一个仓库里的类型定义、函数签名、配置常量——这些信息散落在几十个文件里，但对生成正确的代码缺一不可。

仓库级上下文组织通常包含三层:

  • 当前文件:光标所在文件的全部内容。
  • 跨文件依赖图:当前文件 import 了什么、调用了哪些仓库内的函数，按引用关系链入上下文。常用方法包括基于静态分析的符号索引和基于相似度的最近文件检索。
  • 仓库元信息:目录结构、项目类型、构建配置，告诉模型「这是一个什么项目」。

把这三层组织好的关键限制词永远是上下文预算——一个中型仓库可能有几十万行代码，塞不进任何模型的窗口。所以跨文件上下文的选择(哪个文件、哪一段)本身就是一道信息检索题。相关技术见 上下文工程。

执行反馈训练:让代码跑起来才算数

传统语言模型的训练信号只来自「下一个 token 猜对没有」——但对于代码来说，一段从未被实际执行过的代码，你无法知道它对不对。

执行反馈训练(execution feedback)给这条链路加上了真正的验证:模型生成代码后，用对应的单元测试跑一遍，把通过与否作为奖励信号回传训练。这个信号完全不需要人工标注——单元测试本身就是天然的、可自动化的 verifier。

典型的工作流:

这和 推理强化学习 RLVR 的思路一脉相承:用可验证的客观结果代替人类偏好。区别在于代码场景里验证器(tests)是免费搭好的，不需要额外构造——这是代码 RL 相比通用 RLHF 最大的工程优势。

一个最小可运行的路由示例

理论说完，给一段可直接落地的路由骨架。它把「复杂度分类」做成独立函数，后端通过统一接口调用——这样换模型只改 backends 配置，不动业务代码。注意这里用字符串标签表示复杂度，真实系统应换成带置信度的分类器输出。

# 最小混合路由骨架:关注结构,不是具体模型名
def route(prompt, est_complexity, budget):
    if est_complexity == "hard" and budget >= "high":
        return backends["frontier"]  # 闭源前沿,吃 10% 硬骨头
    if est_complexity == "trivial":
        return backends["small"]     # 小模型,纯判定/分类
    return backends["open"]         # 开源自托管,吃 90% 高频

def answer(prompt):
    complexity = classify(prompt)        # 独立可替换的分类器
    backend = route(prompt, complexity, current_budget())
    try:
        return backend.generate(prompt)  # 统一接口,后端可热切换
    except TimeoutError:
        return backends["open"].generate(prompt)  # fallback 兜底
深入:一次真实选型如何从约束走到候选集

假设你要做一个企业内部知识问答：输入包含内部文档，不能直接离开内网；每月请求量还没有稳定下来；用户既有简单查条款，也有少量跨文档综合问题。第一步不是打开榜单，而是把「不能出站」记为硬约束，先排除纯 API 后端。第二步把请求按难度分层，而不是给所有请求配同一个大模型。

接着准备三组候选：一个小尺寸开放权重模型负责分类与简单问答，一个中等模型负责大多数检索生成，一个更强模型只处理复杂综合问题。用同一份脱敏评测集记录答案正确性、引用命中率、首 token 延迟、峰值显存和每千次请求成本。只有当候选在你的约束下比较，家族标签才真正转化成工程决策。

最后做一个为期一周的影子流量实验：新模型只接收请求并记录结果，不直接影响用户；把失败样本按「知识缺失、检索错误、推理不足、格式错误、延迟超标」分类。这样你能判断问题究竟该换模型、改检索、改提示还是加后处理，而不是把所有失败都归因于「模型不够大」。

深入:选型常见的三个认知陷阱

陷阱一:把「榜单第一」当成「我的任务第一」。公开基准衡量的是通用能力分布，而你真实的请求分布和它的重叠度可能很低。一个在 MMLU 上略输 2 分的模型，可能在你最高频的那类任务上反而更强——因为它更便宜，你能把它调得更好。选模型要拿你自己的评测集说话。

陷阱二:低估自托管的隐性成本。很多人用「单价 × 预计 token」算出「自托管更省」，却没算 GPU 闲置(晚高峰打满、凌晨空转)、工程师排障时间、版本升级回归测试。这些隐性成本经常让「更便宜」的结论反转为「更贵」。推理服务成本 里有一套更完整的全成本建模方法。

陷阱三:把路由写死。在代码里到处写 model="gpt-4" 看似省事，但当三个月后某开源模型追平能力、价格腰斩时，你要把每一处调用都改一遍。从第一天就用 model-agnostic 接口和配置驱动的路由，切换成本趋近于零。架构弹性比单点性能更保值。

要点速查

  • 选型方法论:从约束出发，不是从「谁最强」出发。四问逐一答完，候选集会自己收敛。
  • 四问:数据能否出站?真需要前沿推理吗?月 token 量哪一档?有自托管运维能力吗?
  • 基因优先于型号:闭源 API 永远无法自托管、数据必出站;开放权重天生可私有化但要自己运维。
  • 授权是硬约束:Apache 2.0 最省心;Llama 社区许可对大体量有额外要求;DeepSeek 自定义许可需法务确认。
  • 混合路由是主流答案:闭源前沿吃 10% 硬骨头，开源吃 90% 高频——不是二选一。
  • model-agnostic 接口:从第一天就做成可替换，否则重路由成本会锁死你的架构。
  • 代码大模型三条专有设计:FIM 填充式训练(补中间而非续写)、仓库级上下文(跨文件依赖)、执行反馈训练(用单测通过做奖励信号)。
  • 型号快照不可靠:任何固定型号列表三个月内必过期，应以第三方持续评测为准。本页给的是不会过期的选型框架。
