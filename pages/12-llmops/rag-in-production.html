RAG 生产运维

RAG demo 跑通后，真正的考验是三个月后它还好不好用。源文档改了但向量库没刷新、检索策略调整后静默掉点、上下文悄悄超出窗口——这些不是算法问题，是运维问题。让它更准归 advanced-rag，让它跑三个月不烂掉归本条。本节讲 RAG 上线后三类最常见的静默失效，以及各自的监控信号和治理手段。

一图看懂

RAG 在生产中的失效不是报错——它照常返回答案，只是答案基于过时的信息、被噪声淹没的上下文、或被截断的检索结果。三类失效各有不同的根因，需要不同的监控信号来发现。

为什么 RAG 的运维和其他系统不一样

想象你把一个大型图书馆改造成了"AI 图书管理员"。图书管理员本身很聪明（模型），但它的工作质量取决于三件事：书架上是不是最新版的书（索引）、找书的时候有没有被无关书页干扰（检索质量）、以及它手头那本"参考手册"有没有超出它能一次性看完的页数（上下文窗口）。传统系统运维只关心"图书馆门有没有开"（可用性），而 RAG 运维还要关心"书架上的书是不是最新的、找的书对不对、参考手册塞没塞爆"——这三件事每一件都在静默变化，而且几乎都不产生报错。

传统检索系统（如 Elasticsearch）的运维关注的是索引健康、查询延迟、可用性。RAG 多了一层：检索结果要喂给 LLM 生成答案，所以检索质量本身就成了运维指标。更麻烦的是，RAG 的质量问题几乎都是静默的——系统不报错，只是答案开始变差。

RAG 运维的核心难点 传统系统的故障是"不工作"——503、超时、崩溃。RAG 的故障是"工作得不好"——返回了答案，但基于过时信息、被噪声干扰、或丢了关键上下文。用户不会报错，只会觉得"这个 AI 越来越笨了"，然后默默流失。你需要主动监控，不能等反馈。

本节不讨论怎么让 RAG 更准——那是 Advanced RAG 的范畴。本节讨论的是：一个已经调好的 RAG 系统，怎么保证它在生产环境中持续保持质量，不随时间衰减。

权威图：RAG 的骨架长什么样

聊运维之前，先确认我们运维的对象。RAG 的骨架来自 2020 年那篇奠基论文《Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks》，图里画的就是"检索器 + 生成器"这个组合：左边检索器从文档库里取出与输入最相关的片段，右边生成器拿到这些片段后生成答案。今天所有 RAG 系统——不管前端接了多少层查询改写、重排、混合检索——底层都还是这张图的形状。

新手读这张图，把它拆成三个"可以被运维"的部分看。第一，"Non-Parametric Memory"（非参数记忆）就是你的文档库 + 索引——这是运维最需要盯的部分：文档在更新，索引却没有跟着更新，就是本页后面要讲的"陈旧 Embedding"。第二，检索器（Retriever）负责从记忆里取片段——它取回来的片段质量如何，对应"检索噪声"。第三，生成器（Generator）把片段和输入一起生成答案——它一次能吞下的上下文是有限的，对应"上下文溢出"。整张图其实就告诉我们一句话：RAG 系统是"数据 + 检索 + 生成"三段式的组合体，而生产里出问题的地方，几乎都在前两段（数据和检索），而不是模型本身。把这句话记牢，后面的三类失效就都有了解释框架。

失效一：陈旧 Embedding——最隐蔽的杀手

怎么发生

你的知识库不是静态的——产品文档在更新、政策在调整、价格在变化。当源文档更新后，你需要重新生成对应的 embedding 并更新向量库。如果这个同步出了问题（定时任务挂了、增量更新漏了某批文档、文档被修改但 hash 没变导致跳过），向量库里存的还是旧版本的 embedding。

结果就是：用户问"最新的退款政策是什么"，RAG 检索到了旧的退款政策文档，模型基于旧政策生成答案——自信地答了过时的信息。没有报错，没有告警，只有用户被误导。

为什么这个问题特别难发现 陈旧 embedding 不会影响任何技术指标——检索延迟正常、检索结果数量正常、模型生成正常。唯一的问题是"内容过时了"，而这只有人看了答案才能发现。等你从用户投诉中发现时，可能已经错误回答了几千个请求。关于幻觉的成因和检测方法，详见 幻觉。

监控信号：文档版本 vs 向量版本

发现陈旧 embedding 的关键是对账（reconciliation）。为每个文档维护两个版本号：

  • 源文档版本：文档最后修改时间或内容 hash。文档管理系统里就有。
  • 向量版本：该文档对应的 embedding 生成时间或 embedding 模型版本。向量库的元数据里应该记录。

定期跑一个对账任务：扫描所有文档，比对源文档版本和向量版本。源文档版本比向量版本新 = 该文档的 embedding 是陈旧的。把"陈旧文档数"作为一个监控指标，超过阈值就告警。

展开：一个可以直接抄的对账任务（Python 骨架）

对账任务的主干逻辑很朴素，难点全在边界情况上：文档删除、chunk 级别的残留、以及"内容没变但切分策略变了"。下面这段骨架把三种情况都覆盖了。

import hashlib

CHUNKER_VERSION = "v3"        # 切分策略版本，变了要全量重建
EMBEDDER_VERSION = "bge-m3"   # embedding 模型版本

def content_hash(text: str) -> str:
    return hashlib.sha256(text.encode("utf-8")).hexdigest()

def reconcile(doc_store, vector_store, report):
    doc_ids = set(doc_store.list_ids())
    indexed_ids = set(vector_store.list_doc_ids())

    # 情况一：源文档已删除，向量还在 —— 孤儿向量
    for doc_id in indexed_ids - doc_ids:
        vector_store.delete_by_doc(doc_id)
        report.count("orphan_deleted")

    # 情况二：新文档从未被索引
    for doc_id in doc_ids - indexed_ids:
        reindex(doc_id, doc_store, vector_store)
        report.count("new_indexed")

    # 情况三：已索引，但内容或版本号对不上
    for doc_id in doc_ids & indexed_ids:
        doc = doc_store.get(doc_id)
        meta = vector_store.get_doc_meta(doc_id)
        stale = (
            meta["content_hash"] != content_hash(doc.text)
            or meta["chunker_version"] != CHUNKER_VERSION
            or meta["embedder_version"] != EMBEDDER_VERSION
        )
        if stale:
            # 关键：先按 doc_id 删干净所有旧 chunk，再整体重建
            vector_store.delete_by_doc(doc_id)
            reindex(doc_id, doc_store, vector_store)
            report.count("stale_rebuilt")

    report.gauge("stale_ratio",
                 report.get("stale_rebuilt") / max(len(doc_ids), 1))

三个必须强调的细节：

  • 重建必须"先按 doc_id 全删、再整体插入"，不能逐 chunk 更新。文档改动会让 chunk 边界整体位移——原来的第 3 个 chunk 在新文档里可能对应第 4 个，逐 chunk 覆盖会留下一批错位的残留，而且这些残留在检索时看起来完全正常。
  • 陈旧判定要同时看三个版本号：内容 hash、切分策略版本、embedding 模型版本。只比内容 hash 的话，你换了切分策略或换了 embedding 模型时，对账任务会一致认为"一切正常"。
  • 把 stale_ratio 做成告警指标，而不只是打一行日志。正常情况下每次对账后它应该回到接近 0；如果它长期停在某个水位，说明有一批文档的同步链路一直是坏的，只是没人发现。

增量更新策略

全量重建向量库太慢，通常用增量更新。但增量更新有几个坑：

  • 删除问题：文档被删了，但向量库里的对应向量没删（因为删除操作和更新操作走不同路径）。定期清理"孤儿向量"——源文档已不存在但向量还在的条目。
  • chunk 粒度问题：一个文档切成 10 个 chunk，文档改了其中一段。如果增量更新是文档级的（整个文档重新切分重新入库），旧的 10 个 chunk 需要先删除再插入新的。如果只做"新增"不做"删除"，会残留旧 chunk。
  • 更新延迟：文档更新到向量库更新之间的时间窗口，用户可能拿到旧信息。对时效性要求高的场景（如价格、库存），需要做准实时更新或加一层缓存校验。

同步链路要能"补跑" 实践中最常见的失效不是逻辑写错了，而是某次定时任务挂了，然后没有人补。因此同步链路要设计成幂等且可回放：任务失败时下一次运行能自动把上次漏掉的补上（这正是全量对账存在的意义——它天然就是一次补偿）。只做基于事件的增量更新而没有定期全量对账，等于把系统的正确性押在"每一个事件都不丢"上。

失效二：检索噪声——相关性在悄悄下降

怎么发生

随着知识库增长，向量库里的内容越来越多，检索的噪声也会增加。一个用户问题检索回来的 Top-5 chunk 里，可能只有 1 个真正相关，另外 4 个是语义相近但内容无关的"噪声 chunk"。这些噪声被塞进 prompt 后，稀释了模型的注意力，让模型更容易跑偏或幻觉。

检索噪声的恶化通常是渐进的——知识库从 1 万条增长到 10 万条，噪声比例慢慢升高。你不会在某一天突然发现问题，但三个月后回头看，答案质量已经明显下降了。

监控信号：检索质量指标

检索质量需要持续监控，不能只在线下评测时看。几个关键指标：

指标怎么算异常意味着
Top-K 平均相似度每条请求的 Top-5 chunk 与查询的余弦相似度均值持续下降 = 知识库增长后检索精度在恶化
Top-1 与 Top-5 相似度差Top-1 相似度减去 Top-5 相似度差值缩小 = 检索结果区分度在降低，噪声增多
无命中请求率Top-1 相似度低于阈值（如 0.7）的请求占比上升 = 越来越多的问题在知识库里找不到答案
用户反馈率点踩 / 重新生成的请求占比直接信号——但覆盖率低，需要和其他指标交叉看

这些指标在可观测性体系里应该作为 RAG 子链路 Span 的聚合指标，持续跟踪趋势。不是看绝对值，而是看趋势变化——如果 Top-K 平均相似度在过去一个月持续下降，就该调查原因了。

手算一组检索指标：0.66 的相似度说明什么

指标不是看过就算，要能读出结论。假设今天三条请求的 Top-5 平均相似度分别是 0.72、0.68、0.66，而一个月前的基线是 0.75。怎么解读？先看绝对值：0.66 是否低于"无命中阈值"（比如 0.7）——如果低于，说明这请求在向量库里几乎找不到相关段落。再看趋势：三天从 0.72 掉到 0.66，幅度虽然不大，但如果伴随"Top-1 与 Top-5 相似度差"从 0.10 缩到 0.05，那说明不光是整体分数在降，而是第一名和后面的差距在缩小——检索结果的"分辨力"变弱了，典型原因是知识库涨了但检索参数没跟着调，或新入库的文档语义互相接近。这组数字组合起来指向的运维动作是：看最近入库了什么、重排阈值要不要重调，而不是去改 prompt。检索指标的读法永远是多指标交叉，单一相似度数字几乎不说明问题。

缓解策略

  • 定期重排阈值调优：知识库增长后，原来设定的 Top-K 数量和重排阈值可能不再最优。定期用评测集重新调参。
  • 引入元数据过滤：在检索前先按元数据（时间、类别、权限）过滤，减少候选集。这不只是精度问题，也是安全问题——不同用户能看到的文档不同。
  • 监控无命中请求：如果大量请求的 Top-1 相似度都很低，说明知识库覆盖不足。分析这些"无命中"的问题，把它们作为补充知识库的输入——用户的提问就是知识库的缺口。
新手最容易搞错 很多团队用"检索到了多少条"（命中数量）当检索质量的监控指标，这是错的。命中数量回答的是"索引有没有正常工作"，回答不了"召回的质量好不好"。一条请求召回了 top-5，可能 5 条全是噪声——数量正常，质量很差。反过来，一条请求只召回了 2 条，可能 2 条都是高相关。正确的做法是监控"相似度分布"（Top-1 的分数、Top-1 与 Top-5 的差值、无命中占比）而不是"条数"。同理，"有检索结果"不等于"检索结果有用"，这两者的监控信号完全不同。

失效三：上下文溢出——静默截断

怎么发生

RAG 系统的 prompt 由系统提示 + 检索到的 chunk + 用户问题 + 对话历史组成。随着对话轮次增加、检索的 chunk 越来越长、系统提示不断加规则，总长度可能悄悄超出模型的上下文窗口。

超出窗口的后果取决于模型 API 的行为：有的直接报错（好，至少你知道了），有的静默截断（坏，你不知道丢了什么）。如果是静默截断，可能把系统提示的尾部截掉了（约束规则丢失），也可能把对话历史的开头截掉了（上下文丢失），还可能把 RAG 检索结果截掉了（知识丢失）。每种截断的症状不同，但都表现为"答案质量下降"。

最容易忽略的场景 你的系统提示从 500 token 涨到了 1500 token（产品加了一堆规则），RAG 上下文从 2000 token 涨到了 4000 token（检索策略改了 top-K），对话历史 10 轮 3000 token——加起来 8500 token，模型窗口是 8192。差一点点，不报错但截断了。上下文溢出经常不是因为某一个部分暴涨，而是所有部分都在慢慢涨。

监控信号：Token 预算追踪

在 trace 里记录每个请求的 prompt 组成和 token 数，然后监控：

  • 输入 token 分解：系统提示 token / RAG 上下文 token / 对话历史 token / 用户问题 token 各占多少。看趋势，不看绝对值。
  • 窗口利用率：输入 token / 模型上下文窗口大小。超过 80% 就该告警——你离溢出只差一次系统提示加几行规则。
  • 截断事件计数：如果模型 API 返回了截断标志（如 finish_reason = "length"），记录并告警。

Token 预算管理是一个工程问题，不只是"少塞点上下文"这么简单。详细的上下文分配与压缩策略见 上下文工程。

Chunk 策略版本化

切分策略（chunk size、overlap、切分方法）不是一次定终身的事。随着文档类型变化、业务需求调整，你可能需要修改切分策略。但修改切分策略等于整个向量库需要重建——所有 chunk 的边界都变了，旧的 embedding 全部失效。

这带来两个运维需求：

  1. 记录切分策略版本：向量库里每个 chunk 要记录它是用哪个切分策略生成的（版本号 + 参数）。这样你可以知道当前线上用的是哪个版本，以及是否所有 chunk 都已迁移到新策略。
  2. 双索引并行过渡：切换切分策略时，不要直接替换。建一个新的向量索引（新策略），让新旧索引并行运行一段时间。在canary验证新索引的检索质量后再切流量。如果新策略有问题，切回旧索引即可——零风险。
切分策略变更 = 一次"模型迁移" 把切分策略变更当成和换 embedding 模型一样的大事来对待：跑评测集、canary 流量、对比检索指标。很多团队在这上面栽过跟头——"只是把 chunk_size 从 512 改成 256"，结果召回率掉了 15%，因为小 chunk 丢失了更多上下文语义。

Embedding 模型迁移：静默掉点的重灾区

embedding 模型的迁移是 RAG 运维中最危险的操作之一。危险不在于操作复杂，而在于迁移不完整时系统不报错，只是静默掉点。

为什么会静默掉点

不同 embedding 模型的向量空间完全不可比。模型 A 的向量 [0.1, 0.3, ...] 和模型 B 的向量 [0.8, 0.2, ...] 在同一个向量库里混在一起，相似度计算的结果是毫无意义的。如果迁移时只更新了一部分文档的 embedding，剩下的还是旧模型的，检索结果会变成新旧向量混合的"随机噪声"。

更隐蔽的情况：你用新模型重新生成了所有 embedding，但查询侧还用旧模型编码用户问题。查询向量和文档向量来自不同模型，检索结果完全不可靠——但系统照常运行，只是准确率暴跌。

安全迁移流程

迁移方案有三种，成本和风险差别很大。除非是内部低风险系统，否则不建议选第一种：

方案服务影响成本回滚难度适用场景
原地全量覆盖重建期间检索质量不可用或新旧混合最低，只存一份极难——旧向量已被覆盖，回滚等于再重建一次只适合内部低风险、可停机的系统
双索引并行零影响，旧索引照常服务较高，两份存储 + 一次全量编码容易，路由切回旧索引即可生产系统的默认选择
影子对比后切换零影响最高，还要额外跑一遍查询编码容易高风险或大体量场景，需要真实流量证据再决策

选双索引方案时，要提前算好全量编码的时间和成本。一个百万级 chunk 的知识库重新编码一遍，可能需要几个小时到一整天，而且这段时间里源文档还在继续更新——所以重建过程本身也要能处理增量：先做一次全量快照重建，再把重建期间的变更补跑一遍，然后才进入对比阶段。

铁律：查询侧和文档侧必须同时切换 迁移时最常见的错误是分步切换——先切文档索引，再切查询编码器。在切换的中间窗口里，查询用旧模型编码、文档用新模型编码，检索结果完全不可靠。正确做法是：新索引建好后，查询侧和文档侧同时切到新模型，中间不做灰度——因为混合向量没有灰度可言。双索引并行期的"灰度"是在两个完整索引之间切换，不是在一个索引里混用两个模型。

向量库治理

向量库不是"建好了就不用管"的基础设施。随着数据增长，几个治理问题会浮现：

治理问题表现对策
孤儿向量源文档已删除，但向量库中对应的向量还在定期对账，清理无对应文档的向量
重复向量同一文档被多次入库，检索时返回重复 chunk入库前按文档 ID + chunk 位置去重
索引膨胀历史版本切分策略的残留向量未清理迁移完成后清理旧索引
权限泄漏用户 A 检索到了只有用户 B 才能看的文档检索时带权限过滤，不要依赖事后过滤

权限泄漏是安全问题中最严重的。正确做法是在检索阶段就做权限过滤（作为元数据过滤条件），而不是检索完再过滤——后者可能在截断或排序时已经把不该看的内容混进来了。安全和隐私的系统性讨论见 隐私与安全。

展开：为什么权限过滤必须做在检索里，而不是检索之后

"检索完再把没权限的结果过滤掉"听起来完全等价，而且实现简单得多。但它在四个地方会出问题，而且每一个都是真实事故的来源。

第一，结果数量会静默塌陷。你请求 top-5，检索器返回 5 条，后置过滤掉了其中 4 条没权限的，最后只剩 1 条进 prompt。系统不报错，用户拿到一个"信息不全"的答案。更糟的是这种情况对不同用户表现不同——权限少的用户体验持续更差，而你在聚合指标上看不出来，因为平均值被权限充足的用户拉平了。

第二，相似度分数的语义被破坏。你用来做监控的"Top-1 相似度""Top-1 与 Top-5 差值"这些指标，如果是在过滤前算的，反映的就不是用户真正看到的检索质量。过滤后再算，又会因为样本数不固定而失去可比性。前置过滤则不存在这个问题——检索出来的 5 条就是用户能看的 5 条。

第三，重排和截断会提前泄漏。如果链路是"检索 → 重排 → 截断 top-3 → 权限过滤"，那么无权限的文档已经参与了重排的打分，甚至可能把有权限的文档挤出了 top-3。用户虽然最终没看到那条内容，但他看到的结果集已经被不该影响他的数据影响了。在某些合规场景下，这本身就构成问题。

第四，最直接的——总有一条路径会忘记过滤。后置过滤意味着每一个调用检索的地方都要记得加过滤，包括你三个月后新加的那个"相关问题推荐"功能、那个导出摘要的定时任务、那个给运营看的调试接口。安全控制放在共享路径上才可靠，放在调用方手里迟早会漏。

正确的做法是把权限当成检索的元数据过滤条件：入库时给每个 chunk 打上可见性标签（部门、角色、密级、租户），检索时把当前用户的权限集合作为硬过滤条件传给向量库，让向量库在候选集层面就排除掉无权限的内容。主流向量库都支持带元数据过滤的向量检索。代价是过滤条件会影响索引的检索效率，需要为高频过滤字段建立合适的索引结构——但这是一个性能问题，比安全问题好解决得多。

最后补一句：权限变更也要能实时生效。如果 chunk 的可见性标签是入库时写死的，那么某人调岗、某文档升密之后，向量库里的标签还是旧的。要么把权限做成"查询时从权限系统实时解析成过滤条件"，要么给权限变更也建一条同步链路——和文档内容的同步链路是同一个问题。

运维日历：把这些检查变成例行工作

本节讲的所有机制，只要依赖"想起来的时候看一眼"，最后都会退化成不存在。把它们排进一张固定的日历，才是真正落地的样子。下面用一张甘特图把各周期的例行工作画在同一时间轴上，再配一张明细表说明每项动作的判据——「每天该做什么、每周该做什么」这种问题，应该能在一张图上回答，而不是翻文档。

下面这张表可以直接作为你团队的起点，按业务的变更频率调整周期：

周期动作产出与判据
持续（分钟级）检索质量指标聚合、窗口利用率、截断事件计数接入 可观测性看板；利用率超 80% 或出现截断即告警
每日增量对账 + 孤儿向量清理stale_ratio 回到接近 0；清理数量异常时人工确认
每周跑一遍检索评测集；复核"无命中"请求 top 列表召回指标不低于上周；无命中问题整理成知识库补充清单
每月全量对账；重排阈值与 top-k 复调；权限标签抽查全量与增量的差异应为零，有差异说明增量链路有漏洞

和其他章节的分工 这张日历里"怎么让它更准"的部分（重排策略、查询改写、混合检索）属于 Advanced RAG；"怎么衡量准不准"的方法论属于 评估方法；本节负责的是把这些检查变成有周期、有判据、有告警的例行工作，让系统三个月后还是三个月前那个样子。

要点速查

  • 本质：RAG 上线后的失效几乎都是静默的——不报错，只是答案变差。让它更准归 advanced-rag，让它跑三个月不烂掉归本条。
  • 骨架：RAG = 检索器 + 生成器（见 RAG 论文原图）。生产问题几乎都出在数据和检索段，而不是模型。
  • 三类失效：陈旧 embedding（源文档更新但向量库没刷）、检索噪声（知识库增长后相关性下降）、上下文溢出（prompt 悄悄超出窗口）。各有不同监控信号。
  • 陈旧 embedding：监控文档版本 vs 向量版本的对账。定期跑对账任务，发现不一致就重新生成。
  • 检索噪声：监控 Top-K 相似度趋势、Top-1 与 Top-5 差值、无命中请求率。关注趋势变化而非绝对值，且要看"质量分布"而非"命中条数"。
  • 上下文溢出：监控输入 token 分解和窗口利用率。超 80% 就告警。
  • Chunk 策略版本化：切分策略变更要像换模型一样对待——双索引并行 + canary 验证。
  • Embedding 迁移：查询侧和文档侧必须同时切换，不能混用不同模型的向量。双索引并行期是在两个完整索引间切换，不是混合使用。
  • 对账三要素：同时比对内容 hash、切分策略版本、embedding 模型版本；重建时先按 doc_id 全删再整体写入；把 stale_ratio 做成告警指标。
  • 同步链路要幂等可回放：只做事件驱动的增量更新而没有定期全量对账，等于把正确性押在"每个事件都不丢"上。
  • 权限必须前置过滤：后置过滤会导致结果数塌陷、监控指标失真、重排被无权限文档影响，而且总有调用路径会忘记加过滤。
  • 把检查排进日历：日对账、周评测、月全量、季度评估模型、变更走双索引。依赖"想起来看一眼"的机制等于不存在。
  • 常见坑：增量更新只新增不删除导致旧 chunk 残留；权限过滤做在检索后而非检索中导致泄漏；系统提示缓慢膨胀导致上下文溢出；换了 embedding 模型但对账只比内容 hash，于是全库陈旧却毫无察觉；用"命中条数"当检索质量指标。
