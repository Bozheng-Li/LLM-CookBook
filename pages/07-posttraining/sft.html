入门

SFT 监督微调

刚出炉的基座模型只会做一件事：接着往下写。你问它「帮我写封请假邮件」，它可能给你续上「帮我写封辞职邮件、帮我写封感谢邮件……」。SFT 要做的，就是把这个「文本续写器」调教成一个「听得懂人话、愿意回答问题」的助手。这是后训练的第一步，也是门槛最低、性价比最高的一步。

一图看懂

SFT 的全部动作可以概括成一句话：把大量「人问 → 好答案」的示范对话喂给基座模型，但只在「好答案」那部分算损失。模型照抄的不是知识（知识在预训练时已经学完了），而是行为格式——遇到问题该开口回答，而不是继续列举更多问题。

先摆正 SFT 在整条流水线上的位置

很多初学者会把「训练一个大模型」想象成一件事，实际上它至少是三件事，各自解决完全不同的问题。用一个类比：预训练是让一个人读完整个图书馆，他因此拥有了海量知识，但他不知道自己该扮演什么角色；SFT 是教他当一名客服/助教，告诉他「有人问你就答、答完就停、按这种格式答」；偏好对齐则是告诉他哪种答法客户更满意。

关于 SFT 在整条流水线里的位置，与其听我讲，不如直接看当年 OpenAI 那篇把「基座模型变成听话助手」的完整流程画成图的开创性论文——InstructGPT。下面这张原图是后训练领域被引用最多的一张流程图，它把「从基座到助手」拆成了三步：先做 SFT，再训奖励模型，最后用强化学习对齐。看懂它，你就知道 SFT 为什么只配当「第一步」，也明白它的能力边界从哪来。

新手读这张图，分三块看。第一块是左上角的 Step 1（第 1 步）：一个「示范数据集」（demonstrations）喂给预训练好的 GPT-3，做我们这一页讲的监督微调 SFT，产出「SFT 模型」。注意这里用的词是 demonstration（示范）而不是 answer（答案）——数据里的每一行都是「有人问、有人好好答」的完整对话，SFT 学的就是这种「应答示范」。

第二块是右上角的 Step 2（第 2 步）：让 SFT 模型对同一个问题生成多个回答，人工把这些回答按「哪个更好」排序，用排序数据训练一个奖励模型（Reward Model，RM）来给「回答质量」打分。这一块就是「从示范升级到偏好」——它不再告诉你标准答案是什么，而是告诉你「哪种答法更讨人喜欢」。第三块是下方的 Step 3（第 3 步）：用强化学习（PPO）让 SFT 模型尽量拿到奖励模型的高分，同时用 KL 惩罚约束它别跑太远。这三步串起来，才是你在 ChatGPT 里见到的那个助手。

这张图对理解 SFT 最重要的启示是：SFT 只是第一步，它产出的模型质量直接决定了后面两步的天花板。奖励模型给 SFT 模型的回答排序、强化学习在 SFT 模型附近搜索更高分的答案——如果第一步的示范数据本身质量不行，后面两步再努力也只能在「烂答案」里挑相对不那么烂的。这也是本页反复强调「数据质量优先于数量」的原因。反过来，如果只看这张图不往下看，又会误以为 SFT 就是全部——别忘了后面还有偏好对齐在等着接力，详见 RLHF 与 DPO。

这个位置决定了 SFT 的两条铁律。第一，SFT 不适合灌输新知识。如果你希望模型掌握公司内部的产品手册，用 SFT 把手册改写成问答对去训，效果通常远不如把手册放进 RAG 的检索库；真要走训练路线，也应该走 持续预训练 而不是 SFT。第二，SFT 对行为的影响立竿见影。几千条样本就能显著改变模型的回答长度、Markdown 使用习惯、开场白模式——这既是它的威力，也是它的危险：你在无意中喂进去的风格，模型会一字不差地学走。

一句话直觉 预训练决定模型知道什么，SFT 决定模型怎么表现，偏好对齐决定模型倾向于怎么表现更好。三者的杠杆完全不同：加知识请找预训练或检索，改行为才找 SFT。

SFT 和预训练用的是同一个损失函数

很多人第一次接触 SFT 会以为它是某种全新的训练方式。其实不是——SFT 的损失函数和 预训练目标 里的 CLM 一模一样，都是 next-token prediction：

$$\mathcal{L} = -\sum_{t} m_t \cdot \log P_\theta\!\left(x_t \mid x_{<t}\right)$$

唯一多出来的就是那个 $m_t \in \{0, 1\}$，也就是 loss mask。真正的差别只有两处：

数据形态变了

从「网页上抓来的连续文本」换成「结构化的对话样本」，每条样本有明确的角色划分和边界。

损失范围变了

预训练对每个位置都算损失；SFT 只对 assistant 回复部分算，用户提问部分 $m_t = 0$。

这个「同一个损失函数」的事实有个很实用的推论：凡是预训练那一套工程设施，SFT 全部可以复用——同样的分布式并行策略、同样的混合精度、同样的梯度检查点、同样的 checkpoint 格式。你不需要为 SFT 单独搭一套训练栈，只需要换一个 dataset 和一个 collator。这也是为什么 SFT 是后训练里工程复杂度最低的一环，跟 RLHF 要同时驻留四个模型完全不是一个量级。

Loss mask：新手第一个坑

为什么提问部分不算损失？因为你想让模型学会的是「给定问题，如何生成好回答」这个条件分布，而不是「如何生成一个问题」。如果对 prompt 部分也算损失，模型会把一部分容量花在拟合用户的提问风格上——而这些提问是数据集作者写的，不是真实用户会问的，学它纯属浪费，还会让模型在推理时倾向于自问自答。

实现上就是把 prompt 部分的 label 置为 -100（PyTorch 交叉熵的默认忽略值）：

prompt_ids = tok.apply_chat_template(msgs[:-1], add_generation_prompt=True)
full_ids   = tok.apply_chat_template(msgs, add_generation_prompt=False)

input_ids = full_ids
labels    = list(full_ids)
# 把 prompt 覆盖的位置全部屏蔽掉,只留回答部分参与损失
for i in range(len(prompt_ids)):
    labels[i] = -100

这段代码看起来平淡无奇，但它隐含了一个必须成立的前提：prompt_ids 必须是 full_ids 的严格前缀。绝大多数 tokenizer 满足这一点，但少数场景会翻车——比如某些 tokenizer 在词尾会做合并，把「回答的第一个字」和「模板的最后一个符号」合成同一个 token；再比如 add_generation_prompt=True 会追加一段引导文本，而在完整序列里这段文本可能被写成另一种形式。一旦前缀关系不成立，你的 mask 就会整体错位一到两个 token，训练照样能跑，loss 也会下降，但模型学到的东西是歪的。

务必做这个自检 写完 collator 后，取一条样本，把 labels != -100 的位置 decode 出来打印。你应该只看到 assistant 的回复内容加上结束符，一个字都不多、一个字都不少。这三行调试代码能省掉你后面几天的困惑——绝大多数「SFT 训了但没效果」的案例，根源都在这里。
常见误区 「多轮对话只需要对最后一轮的回答算损失。」——不一定。多轮样本里每一轮 assistant 的回复都可以算损失，这样一条样本能产出更多训练信号，也不用把同一段历史重复喂好几遍。要不要这么做取决于中间轮回复的质量是否同样可靠。
展开：多轮对话的两种展开方式与 packing 的坑

一条 5 轮的对话样本，有两种做法：

做法一：切成 5 条独立样本。第 k 条包含前 k-1 轮历史 + 第 k 轮问答，只对第 k 轮回答算损失。优点是每轮独立可控（可以按质量单独筛掉某一轮）；缺点是同一段历史被重复编码 5 次，算力浪费严重，长对话尤其夸张——一条 20 轮对话会膨胀成 20 条样本，总 token 数是原来的十倍量级。

做法二：保留成 1 条样本，5 段 mask。整条序列只前向一次，把 5 段 assistant 回复的位置全部置为可算损失。算力效率高得多，是目前主流框架的默认做法。代价是你没法对单轮做细粒度筛选，只能整条要或整条不要。

再说 packing 的坑。为了不浪费算力，训练时常把多条短样本首尾相接填满上下文窗口（sequence packing）。这里必须做一件事：屏蔽跨样本的注意力。如果不屏蔽，第二条样本的 token 就能「看到」第一条样本的内容，等于给模型喂了一堆莫名其妙的上下文；更糟的是推理时没有这种拼接，训练和推理的分布对不上。现代框架一般提供 position_ids 重置 + 块对角注意力掩码来解决，但如果你自己手写 collator，这是必须自己处理的一环。另一个小坑是 packing 之后每个 batch 里的有效 token 数变了，如果损失是按 batch 内 token 求平均，样本之间的实际权重会被隐式改变。

对话模板：效果断崖的头号来源

基座模型眼里只有 token 序列，它不知道什么叫「用户」和「助手」。这些角色信息是靠对话模板硬编码进文本里的——一组特殊标记，把多轮对话拍平成一条线性序列。一个 ChatML 风格的模板长这样：

<|im_start|>system
你是一个乐于助人的助手。<|im_end|>
<|im_start|>user
帮我写封请假邮件<|im_end|>
<|im_start|>assistant
好的,请告诉我请假的时间和事由……<|im_end|>

模板要负责三件事：标记角色边界（谁在说话）、标记回合结束（生成到哪里该停）、约定生成起点（推理时喂到 assistant 这一行为止，让模型接着往下写）。其中「回合结束标记」尤其关键：它同时被设置为 EOS，模型学会在合适的地方输出它，推理引擎看到它就停止解码。如果训练数据里漏掉了这个结束标记，模型就会停不下来，一直续写到 max_tokens——这是最典型的模板故障现象。

模板要素它解决什么缺失时的症状
角色起始标记
如 <|im_start|>user		让模型分清这段话是谁说的模型分不清指令和内容，容易被用户输入里的伪指令带偏
回合结束标记 / EOS
如 <|im_end|>		告诉模型「这轮说完了」停不下来，一路续写到 max_tokens，或者自己伪造下一轮用户提问
生成起点约定
推理时以 assistant 头结尾		让模型明确「现在轮到我说」模型继续补全用户的话，而不是回答
system 位承载全局人设与规则无法通过系统提示统一控制风格与安全策略
特殊 token 是否入词表决定标记被切成 1 个还是多个 token被切碎成普通字符，模型学不稳边界，还可能被用户在输入里注入伪造
真实的坑 训练时用的模板和推理时用的模板必须逐字节一致，包括换行符和空格。差一个换行，模型看到的就是分布外输入，表现会断崖式下跌——不是「略微变差」，而是可能开始胡言乱语或忽略指令。合并多个开源数据集时尤其容易踩：不同数据集自带不同模板，混在一起训，模型会学得精神分裂。

实践建议：不要自己手写拼接字符串。用 tokenizer 自带的 chat_template（定义在 tokenizer_config.json 里）统一生成，训练脚本和推理服务共用同一份，这样至少保证两端不会漂移。做持续微调时，也应沿用基座模型原有的模板，除非你有充分理由重新定义并准备好足量数据把它训透。

还有一个容易忽略的细节：特殊标记必须真的在词表里。如果 <|im_end|> 没有被注册为一个独立 token，它会被 BPE 切成 <、|、im、_end…… 一串碎片。模型当然也能学会输出这串碎片，但边界学得远不如单 token 稳，而且用户可以在自己的输入里原样打出这串字符来伪造角色切换——这是提示注入的一条经典路径（进一步的防护见 护栏与输出校验）。检查方法很简单：把模板 encode 一遍，看这些标记是不是各占一个 id。

数据质量优先于数量

这是 SFT 领域被反复验证的一条经验规律：几千条精心打磨的示范，效果常常胜过几十万条爬来的噪声数据。LIMA 那篇论文把这个观察推到了一个极端——用一千条人工精选样本做 SFT，就能得到相当可用的对话模型，并由此提出「表层对齐假说」：对齐主要是在激活预训练已有的能力，而不是注入新能力。原因并不神秘——预训练阶段模型已经把知识和语言能力装进权重了，SFT 只是在激活并规范化已有能力，需要的是清晰、一致、高质量的行为示范，而不是海量重复的模式。

更麻烦的是，低质量数据不是「没帮助」，而是有害：一条事实错误的回答会直接教模型编造；一条格式混乱的回答会污染输出风格；一条「我不知道」用在模型其实知道的问题上，会让它变得畏首畏尾。

质量维度看什么不合格的典型表现
正确性回答本身对不对事实错误、代码跑不通、数学算错
格式一致同类问题的回答结构是否统一有的用 Markdown 有的纯文本，标题层级混乱
指令贴合有没有真正回应用户要求答非所问、忽略「限 100 字」这类约束
多样性任务类型、领域、长度是否分散八成样本都是同一类改写任务
无泄漏是否混入评测集内容刷分虚高，线上表现对不上

数据配比：决定哪些能力被保住

还有一个容易被忽视的维度：数据配比。SFT 会按数据分布重塑模型的行为倾向——如果你的数据里 90% 是闲聊、10% 是代码，模型的代码能力大概率会退化。这不是因为它「忘了」怎么写代码，而是因为在给定问题时，它输出闲聊风格回答的概率被系统性抬高了。想保住哪项能力，就得在配比里给它留位置。

下面这张表给的不是标准答案（不同产品定位差别很大），而是一个思考配比时该盯的维度清单。真正的配比要靠评测集反推：先定义你在乎的几项能力，各准备一个小评测集，然后调配比、跑评测、看哪项掉了就补哪项。

数据类别它保住什么能力配比过低的症状配比过高的症状
通用问答 / 闲聊自然对话感、语气回答生硬、像在填表什么问题都答得又长又空
代码代码生成与解释代码能力明显退化，格式混乱非代码问题也倾向输出代码块
数学 / 推理分步推理习惯不会分步，直接给答案且常错简单问题也强行写一长串推理
长文写作长输出的组织能力写长文时结构散、写着写着跑题短问题也被答成小作文

最后一行值得单独说一句：安全数据配比过高导致的过度拒答，是 SFT 阶段最容易被忽视、上线后又最伤体验的问题。它的完整机理和校准方法见 对齐税与安全对齐。

边界说明 这些指令数据具体怎么造出来——self-instruct 自举、evol-instruct 演化、拒绝采样筛优、教师模型蒸馏——是另一个完整的话题，见 合成数据与数据飞轮。本页只讲拿到数据之后怎么用。

清洗流水线：拿到一批数据先做这五件事

不管数据是自己标的、开源下的还是模型生成的，进训练之前都建议过一遍下面这条流水线。顺序很重要——先做便宜的过滤，再做贵的。

第 ④ 步值得多说两句。去污染不是可选项。开源指令数据集里混进评测题目是极常见的事——有些是数据作者直接拿基准题做种子，有些是教师模型在生成时「回忆」出了训练时见过的题面。一旦污染，你会看到评测分数漂亮地上涨，而真实用户体验纹丝不动，团队还会基于这个虚高的数字做出错误的决策。最低成本的做法是：对每个评测集，把题面切成 n-gram，跟训练样本做重叠检测，命中就丢。更系统的讨论见 数据污染与评估可信度。

新手最容易搞错 很多人以为「SFT 就是把模型在问答数据上再训练一遍，等于复习知识」。实际上 SFT 更新的是输出的行为风格，不是知识本身。同一个模型，用「详细版示范」训完回答变长，用「简短版示范」训完回答变短，知识几乎不变——这就是为什么换个数据配方，模型「气质」立刻不同。想验证这个直觉，最直接的办法是拿同一个 SFT checkpoint 分别喂两种风格的数据各训一遍，观察同一批问题在两种模板下的回答长度差异。它清楚地展示了：你喂进去的不是「答案」，而是「怎么答」的示范。

一次 SFT 到底发生了什么：把训练循环拆开看

前面讲的都是「准备什么」，这一节讲「跑起来之后每一步在干嘛」。SFT 的训练循环极其标准，理解它有助于你在出问题时知道该往哪看。

展开：一个最小可读的 SFT 训练骨架（PyTorch 风格）

下面这段代码不追求可以直接复制上生产，而是把「一次 SFT 需要哪些部件」摊开给你看。真实项目建议直接用成熟框架的 SFT 训练器，参数名以官方文档为准。

import torch
from torch.utils.data import DataLoader

IGNORE = -100

def build_example(tok, messages, max_len=2048):
    """把一条多轮对话编码成 input_ids / labels,并对每一轮回答开放损失。"""
    input_ids, labels = [], []
    for i, msg in enumerate(messages):
        # 逐轮增量编码:先编到本轮为止的前缀,再编到含本轮内容
        prefix = tok.apply_chat_template(
            messages[:i], add_generation_prompt=(msg["role"] == "assistant")
        )
        whole = tok.apply_chat_template(messages[:i + 1])
        seg = whole[len(prefix):]              # 本轮新增的 token
        input_ids = whole
        # 前缀部分沿用已有 labels,新增段落按角色决定是否算损失
        if msg["role"] == "assistant":
            labels = labels + [IGNORE] * (len(prefix) - len(labels)) + list(seg)
        else:
            labels = labels + [IGNORE] * (len(whole) - len(labels))
    return input_ids[:max_len], labels[:max_len]


def collate(batch, pad_id):
    n = max(len(x["input_ids"]) for x in batch)
    ids  = torch.full((len(batch), n), pad_id, dtype=torch.long)
    lab  = torch.full((len(batch), n), IGNORE, dtype=torch.long)
    attn = torch.zeros((len(batch), n), dtype=torch.long)
    for i, x in enumerate(batch):
        L = len(x["input_ids"])
        ids[i, :L]  = torch.tensor(x["input_ids"])
        lab[i, :L]  = torch.tensor(x["labels"])
        attn[i, :L] = 1
    return {"input_ids": ids, "labels": lab, "attention_mask": attn}


def train(model, dataset, tok, epochs=2, lr=2e-5, accum=8, clip=1.0):
    dl = DataLoader(dataset, batch_size=4, shuffle=True,
                    collate_fn=lambda b: collate(b, tok.pad_token_id))
    opt = torch.optim.AdamW(model.parameters(), lr=lr, weight_decay=0.0)
    total = len(dl) * epochs // accum
    sched = torch.optim.lr_scheduler.OneCycleLR(
        opt, max_lr=lr, total_steps=total, pct_start=0.03, anneal_strategy="cos"
    )
    model.train()
    step = 0
    for _ in range(epochs):
        for i, batch in enumerate(dl):
            batch = {k: v.cuda() for k, v in batch.items()}
            # HF 风格模型内部已按 labels 做位移并忽略 -100
            loss = model(**batch).loss / accum
            loss.backward()
            if (i + 1) % accum == 0:
                torch.nn.utils.clip_grad_norm_(model.parameters(), clip)
                opt.step(); sched.step(); opt.zero_grad(set_to_none=True)
                step += 1
                if step % 50 == 0:
                    print(f"step {step} loss {loss.item() * accum:.4f}")

三个值得注意的地方：

  • 梯度累积（accum）是显存不够时凑大 batch 的标准手段。SFT 的有效 batch 一般不宜太小，否则梯度噪声大、训练不稳。
  • weight_decay 常设为 0 或很小。SFT 步数少，权重衰减带来的正则收益有限，反而可能把预训练学到的表示拉偏。
  • padding token 必须被 mask 掉，既在 attention_mask 里，也在 labels 里。这段代码用 IGNORE 初始化 lab 天然满足后者。

如果显存不够跑全参，把 model 换成挂了 LoRA 适配器的版本，其余代码一行不用改——这正是 参数高效微调 的优雅之处。

训练配方与过拟合判断

SFT 的超参空间不大，几个量级记住就够用了：

项目经验取值为什么
学习率（全参微调）比预训练低 1-2 个数量级，$10^{-5}$ 量级起步只是微调行为，不是重学知识；太大会把预训练能力冲掉
学习率（LoRA）可比全参高约一个数量级，$10^{-4}$ 量级可训练参数少得多，需要更大步长才动得起来
Epoch 数通常 2-3 轮，很少超过SFT 数据量小，多跑几轮极易背下答案
调度器warmup + cosine 衰减开头稳住，结尾收敛得干净
序列打包短样本拼接填满上下文提升算力利用率；注意跨样本要屏蔽注意力
梯度裁剪全局范数裁到 1.0 附近SFT 数据里偶有超长或异常样本，裁剪防止单个 batch 打飞权重
weight decay0 或很小步数少，正则收益有限，还可能拉偏预训练表示

怎么判断过拟合？验证集 loss 上翘是最直接的信号，但 SFT 有个特殊现象：验证 loss 还在降，模型却已经变差了。因为 loss 衡量的是「多像训练数据」，而你真正想要的是泛化的应答能力。所以务必配合人工抽检，重点看这几个征兆：

  • 回答变得模板化：不管问什么都是「首先……其次……最后……」三段式。
  • 开头千篇一律：每条回复都以同样的客套话起头。
  • 多样性塌陷：把 temperature 调高，输出几乎不变。
  • 原有能力退化：数学、代码这类没在 SFT 数据里出现的能力明显变弱。
省事的做法 数据量不大（比如几千到几万条）或显存吃紧时，先用 LoRA 跑通全流程再说。它训得快、改动可回滚、多个版本能热切换，非常适合快速迭代数据配方；确定配方之后再考虑要不要上全参微调。

全参、LoRA、还是只训部分层

方案显存量级（7B）迭代速度能力上限什么时候选它
全参微调百 GB 量级慢最高数据量大（十万条以上）、要改变模型的底层行为倾向、有多卡资源
LoRA / QLoRA十几到二十几 GB快多数任务够用默认起点。快速验证数据配方、单卡环境、需要多版本热切换
只训最后若干层介于两者之间中受限只想改输出风格、不想动深层表示；实践中已较少单独使用
只训嵌入 / 输出头小快很低扩词表后让新 token 学到合理表示，一般作为其他方案的前置步骤

一条务实的路线：先 LoRA 把数据配方调对，再决定要不要用同一批数据跑一次全参。因为 SFT 阶段的大部分收益来自数据而不是可训练参数量，先用便宜的方式把数据问题解决掉，性价比最高。

SFT 的能力上限在哪里

SFT 本质上是行为克隆：给一堆示范，让模型模仿。这决定了它有三层天花板。

无法超越示范者

模型学到的上限就是标注者的水平。示范里没有的解题思路，SFT 教不会。

不知道「更好」是什么

数据只给了一个正确答案，没告诉模型另外三个回答哪个更好、差在哪里。偏好排序这种信息，SFT 的损失函数根本表达不了。

只有正例，没有负例

SFT 只会说「照这样答」，从不说「别那样答」。想压制某类不良输出，得靠别的机制。

还有一个更微妙的问题：如果示范数据里包含模型其实并不知道的知识，SFT 等于在教它「用自信的语气说出自己不确定的内容」——这会加剧幻觉。反过来，如果大量示范都在说「我不确定」，模型又会变得过度保守。这两种失衡都不是靠加数据能解决的，因为问题出在「模仿」这个范式本身。

要突破这些上限，需要换一种监督信号：不再给「标准答案」，而是给比较——告诉模型 A 比 B 好。这正是 RLHF 登场的地方。

要点速查

  • 本质：损失函数与预训练的 CLM 完全相同，差别只在数据形态 + loss mask。全部工程设施可复用预训练那一套。
  • 定位：知识来自预训练，SFT 只塑造行为。想灌知识请找检索或持续预训练，别指望 SFT。
  • Loss mask：prompt 部分 label 置 -100，只对 assistant 回复算损失。写完必须 decode 验证一次。
  • 对话模板：训练与推理必须逐字节一致；统一走 tokenizer 的 chat_template，不要手拼字符串；特殊标记要真的在词表里。
  • 结束标记：漏掉回合结束符 → 模型停不下来，一直续写或自问自答。
  • 数据：质量优先于数量，噪声数据是负收益；配比决定哪些能力被保住；去重和去污染是性价比最高的两步。
  • 配方：学习率 $10^{-5}$ 量级（LoRA 可高一个数量级），2-3 个 epoch，梯度裁剪 1.0，weight decay 接近 0。
  • 过拟合判断：验证 loss 会骗人——从「甜点区」滑向复读时 loss 往往还在降。必须靠固定 prompt 的生成抽检 + 定期 checkpoint。
  • 方案选择：默认从 LoRA 起步调数据配方，配方定了再考虑全参。SFT 的收益主要来自数据而非可训练参数量。
  • 上限：行为克隆无法超越示范者，也学不到「哪个回答更好」；示范里有模型不知道的知识会加剧幻觉。
