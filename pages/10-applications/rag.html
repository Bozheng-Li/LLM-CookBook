进阶

RAG 检索增强生成

模型不知道你公司的内部文档，也记不住昨天发生的事。RAG 的思路很朴素：回答之前先去知识库里查资料，把查到的内容塞进上下文再作答。它是大模型落地企业场景最主流的方案。这一节从「为什么需要」讲到五步链路的每一个细节，再到嵌入模型选型、向量索引结构、评测集搭建和一次完整的故障排查演练。

一图看懂

RAG 把「闭卷考试」变成「开卷考试」。离线阶段把文档切块、向量化、存进向量库；在线阶段用用户问题去检索最相关的片段，连同问题一起交给模型生成答案。模型的能力没变，变的是它手上有什么材料。

为什么需要 RAG

先看一个具体场景。你给公司做一个 IT 支持机器人，员工问：「我的 VPN 报错 ERR_4013 怎么办？」通用大模型的回答一定是编的——因为 ERR_4013 是你们内部自定义的错误码，训练语料里根本没有。但如果你把公司的《VPN 故障处理手册》灌进知识库，模型检索到「ERR_4013：证书过期，请到 it.internal/renew 重新签发」这一段，答案立刻从瞎编变成可用。

这个例子里体现的，正是大模型几个绕不开的局限，而 RAG 恰好对症下药：

模型的问题具体表现RAG 的解法
知识截止训练后的新信息一概不知，问「上周发布的新版本有什么变化」只能编检索实时数据源，随时更新知识库即可
私域缺失不了解企业内部资料，内部错误码、流程规范、组织架构全是盲区把内部文档灌入向量库，无需训练模型
幻觉不知道就瞎编，且编得非常自信，格式和真答案一模一样基于检索到的真实片段作答，并可给出出处供人核验
更新成本高微调一次要准备数据、跑训练、做评测，周级起步改知识库即可，重新入库后分钟级生效
无法溯源模型说什么就是什么，用户无从验证每条结论挂上文档链接，把「相信我」变成「你自己看」
选型直觉 需要模型掌握新知识 → 用 RAG；需要模型改变行为风格或输出格式 → 用 微调。一句更好记的话：RAG 教的是「知道什么」，微调教的是「怎么说话」。两者常常配合使用，不是二选一。

RAG、微调、长上下文：三条路的分工

随着模型上下文窗口越做越长，经常有人问：「既然能塞 100 万 token，我直接把所有文档都塞进去不就行了，还要什么 RAG？」这个问题值得认真回答，因为它涉及三条技术路线的真实边界：

维度RAG微调全量塞长上下文
知识更新改库即生效，分钟级要重训，周级换输入即生效，秒级
知识规模上限无上限，取决于向量库容量受模型容量限制受上下文窗口硬限制
单次推理成本低，只塞 Top-K 片段低，不塞额外内容高，每次都为全量文档付费
能否溯源天然可以，检索结果就是出处不能理论可以，但模型容易引错
改变输出风格只能靠 Prompt，效果有限最擅长只能靠 Prompt
典型适用知识库问答、客服、文档助手特定格式输出、领域语气、工具调用习惯单份长文档分析、一次性任务

结论很清楚：长上下文和 RAG 不是替代关系。长上下文解决的是「一份材料太长」，RAG 解决的是「材料太多不知道该看哪份」。当你的知识库有十万份文档时，无论窗口多大都塞不下；而且即便塞得下，注意力在超长上下文里也会被稀释，中间部分的信息经常被忽略——这个现象通常被称为「中间迷失」（lost in the middle）。所以现实中的做法往往是两者结合：用 RAG 把候选缩小到几十份，再用长上下文把它们完整塞进去，而不是切成碎片。

① 切分 Chunking

文档太长塞不进上下文，必须切块。切分质量直接决定检索上限——切碎了丢失语义，切大了引入噪声。这一步看起来最不起眼，却是最常被低估的环节：很多团队花几周调重排器，回头发现真正的瓶颈在于切分把表格拦腰截断了。

为什么切分决定上限？因为检索的粒度就是 chunk 的粒度。如果一个问题的答案分散在两个 chunk 里，而你每次只取 Top-5，那么这两个 chunk 必须都进 Top-5 才可能答对——概率骤降。反过来，如果一个 chunk 里塞了五个不相关的话题，它的向量就是这五个话题的「平均语义」，对任何一个具体问题都不够像，反而检索不到。这就是所谓的语义稀释。

策略做法优点坑适合的文档
固定长度按字符或 token 数硬切实现最简单，长度可控会把句子、表格、代码块拦腰截断纯散文、日志
递归字符优先按段落，超长再按句子，再按词逐级回退通用性最好，绝大多数场景的默认选择对结构化内容仍然不友好通用文本
结构化按 Markdown 标题、HTML 标签、代码函数切切出的块天然是完整语义单元依赖文档本身规范；标题层级混乱时会失效技术文档、API 手册、代码库
语义切分逐句编码，在相似度骤降处断开断点最贴合语义转折需要把全文过一遍嵌入模型，建索引成本高话题跳跃频繁的长文
父子切分小块建索引，命中后返回其所属大块检索精准 + 上下文完整，兼得要额外维护父子映射关系需要完整上下文的问答

实践上通常设置 chunk 之间保留 10–20% 的重叠（overlap），避免关键信息正好被切在边界上。举个具体例子：chunk 大小 512 token、重叠 64 token，意味着每个新块会带上前一块结尾的 64 个 token。代价是索引体积增大约 12%，换来的是边界信息不丢。

切分最容易踩的三个坑 一是表格被拆散：表头在上一块、数据在下一块，两边都没法单独回答问题。二是列表编号断裂：「第 3 步」单独成块时失去了「安装流程」这个上下文。三是把 PDF 页眉页脚也切进去：每个 chunk 都带着「XX 公司机密 第 N 页」，这些高频重复文本会污染向量、拉高所有 chunk 之间的相似度。建议在切分前先做一遍清洗，剔除重复的页眉页脚和导航文本。
展开：一个带结构感知的切分实现

下面这段代码演示「结构化优先、递归兜底、父子映射」的组合策略。它先按 Markdown 标题切成语义节，节内超长再递归切小，同时记录每个小块归属的父块 id。

import re
from dataclasses import dataclass, field

@dataclass
class Chunk:
    text: str
    parent_id: str = ""          # 所属大块 id, 用于命中后回溯
    heading_path: str = ""       # 如 "安装指南 > 常见问题 > VPN"
    meta: dict = field(default_factory=dict)

def split_by_heading(md_text):
    """按 Markdown 标题切成语义节, 同时维护标题路径"""
    lines = md_text.split("\n")
    sections, cur, path = [], [], []
    for ln in lines:
        m = re.match(r"^(#{1,4})\s+(.*)$", ln)
        if m:
            if cur:
                sections.append((" > ".join(path), "\n".join(cur)))
                cur = []
            level = len(m.group(1))
            path = path[:level - 1] + [m.group(2).strip()]
        else:
            cur.append(ln)
    if cur:
        sections.append((" > ".join(path), "\n".join(cur)))
    return sections

def recursive_split(text, max_chars=512, overlap=64):
    """递归回退: 段落 -> 句子 -> 硬切"""
    if len(text) <= max_chars:
        return [text] if text.strip() else []
    for sep in ["\n\n", "\n", "。", ". ", " "]:
        parts = text.split(sep)
        if len(parts) == 1:
            continue
        out, buf = [], ""
        for p in parts:
            cand = (buf + sep + p) if buf else p
            if len(cand) <= max_chars:
                buf = cand
            else:
                if buf:
                    out.append(buf)
                buf = p if len(p) <= max_chars else ""
                if len(p) > max_chars:
                    out.extend(recursive_split(p, max_chars, overlap))
        if buf:
            out.append(buf)
        return _apply_overlap(out, overlap)
    # 所有分隔符都失效, 硬切兜底
    step = max_chars - overlap
    return [text[i:i + max_chars] for i in range(0, len(text), step)]

def _apply_overlap(parts, overlap):
    if overlap <= 0 or len(parts) <= 1:
        return parts
    out = [parts[0]]
    for prev, cur in zip(parts, parts[1:]):
        out.append(prev[-overlap:] + cur)
    return out

def build_chunks(md_text, doc_id):
    chunks = []
    for i, (path, body) in enumerate(split_by_heading(md_text)):
        parent_id = f"{doc_id}#sec{i}"
        for piece in recursive_split(body):
            chunks.append(Chunk(
                # 把标题路径拼进正文, 让 chunk 自带上下文
                text=f"[{path}]\n{piece}",
                parent_id=parent_id,
                heading_path=path,
                meta={"doc_id": doc_id},
            ))
    return chunks

关键细节是倒数第三行：把标题路径拼进 chunk 正文再去做向量化。这样即使切出来的小块只写了「重新签发证书即可」，它的向量里也带着「VPN 故障处理」的语义，检索命中率会明显提升。这个技巧成本几乎为零，收益却很稳定。

② 向量化 Embedding

把文本片段映射成高维向量，语义相近的文本在向量空间中距离也相近。这一步的数学基础在 词嵌入与向量空间 一节已经讲过，这里只关心工程侧的用法。检索时用余弦相似度衡量：

$$\text{sim}(q, d) = \cos(\theta) = \frac{\mathbf{q} \cdot \mathbf{d}}{\|\mathbf{q}\| \, \|\mathbf{d}\|}$$

为什么用余弦而不是欧氏距离？因为文本向量的模长往往和文本长度相关，而我们关心的是「方向是否一致」即语义是否接近，不希望长文档因为模长大就天然占优。实践中很多向量库会在入库时先做 L2 归一化，此时余弦相似度就退化为简单的点积，计算更快。

一个容易被忽略的成本项：向量化不是免费的。假设你有 100 万个 chunk，每个平均 400 token，那么建一次索引就要编码 4 亿 token。用本地开源嵌入模型跑，这是几小时的 GPU 时间；用 API，就是一笔实打实的账单。所以「换个嵌入模型试试」这句话在百万级数据量上不是一句轻松的话，它意味着一次完整的重建。

③ 检索 Retrieval

只用向量检索往往不够。混合检索（Hybrid Search）是当前的最佳实践：

稠密检索 Dense

基于 Embedding 的语义匹配。擅长理解同义改写，「怎么退货」能匹配到「退换货流程」；但对专有名词、编号、罕见词不敏感，「ERR_4013」在向量空间里和「ERR_4031」几乎一样近。

稀疏检索 Sparse

BM25 等关键词匹配。精确命中术语和标识符，「ERR_4013」一击即中；但不懂语义改写，用户问「怎么退货」而文档写「退换货流程」时可能完全召不回。

两者的失效场景恰好互补，所以标准做法是两路都跑，再把结果合并。合并最常用的是 RRF（Reciprocal Rank Fusion，倒数排名融合），它不看两边的原始分数（因为余弦相似度和 BM25 分数根本不在一个量纲上，没法直接相加），只看排名：

$$\text{RRF}(d) = \sum_{r \in R} \frac{1}{k + \text{rank}_r(d)}$$

其中 $R$ 是各路召回结果，$\text{rank}_r(d)$ 是文档 $d$ 在第 $r$ 路里的名次，$k$ 是一个平滑常数（原论文取 60，工程上常沿用这个默认值）。这个公式的妙处在于：它对分数量纲完全不敏感，只要求各路能给出排序。一个在两路里都排前十的文档，得分会显著高于只在一路里排第一、另一路里根本没出现的文档——这正是我们想要的「双重确认」效果。

还有一路容易被忘记：元数据过滤 很多问题其实带着硬性约束——「2026 年的报销标准」不应该召回 2024 年的文档，「华东区的政策」不应该召回华北区的。这类约束用向量相似度是表达不出来的，必须靠结构化字段过滤。所以入库时把日期、部门、文档类型、权限等级都写进 metadata，检索时先过滤再算相似度。这一步能挡掉大量「看起来很像但根本不该出现」的结果，性价比极高。顺带一提，权限过滤必须在检索层做，不能寄望于让模型「不要引用无权限文档」——那不是安全边界。

④ 重排 Rerank

检索阶段为了速度用的是「双塔」模型（问题和文档分别编码），精度有限。重排阶段用 Cross-Encoder 把问题和候选文档拼在一起精细打分，从 Top-50 里精选出真正相关的 Top-5。这一步性价比极高，通常能显著提升最终效果。

为什么拼在一起就更准？因为双塔模型编码文档时还不知道用户会问什么，它只能编码出一个「通用语义」；而 Cross-Encoder 是带着问题去读文档的，能捕捉「这句话正好回答了问题里的哪个部分」这种细粒度对应关系。代价是它无法预计算——每来一个新问题，所有候选都要重算一遍，所以只能处理几十条。

一个实践问题：粗召回的 Top-K 该取多少？取太小，正确答案根本没进候选池，重排再强也救不回来；取太大，重排耗时线性上涨。常见的起点是粗召回 50、精排后取 5，然后用你自己的评测集去调——如果发现「召回率@50」已经接近饱和而「召回率@100」几乎不涨，那 50 就够了。

⑤ 生成 Generation

把检索到的片段和问题组装成 Prompt。关键要求模型只依据给定资料作答，并标注引用来源，资料不足时明确说「不知道」。

这里有个反直觉的细节：片段在 Prompt 里的排列顺序会影响效果。由于长上下文中间部分容易被忽略，把最相关的片段放在最前面和最后面、把次相关的放在中间，通常比单纯按相关度降序排列更稳。另一个细节是要给每个片段编号并附上来源标题，这样模型既能引用，也能在片段冲突时说明「资料 [1] 和 [3] 说法不一致」。

展开：一个可用的 RAG Prompt 模板 
你是一个严谨的知识问答助手。请严格依据下面提供的【参考资料】回答用户问题。

规则:
1. 只使用参考资料中的信息作答,不要引入任何外部知识。
2. 每个关键结论后标注来源编号,如 [1][2]。
3. 如果参考资料不足以回答,直接说明"根据现有资料无法回答",不要猜测。
4. 若资料之间存在冲突,请指出冲突并列出各方说法,不要自行裁决。
5. 用户问题若与参考资料完全无关,礼貌说明本知识库不涵盖该主题。

【参考资料】
[1] (来源: {title_1}) {chunk_1}
[2] (来源: {title_2}) {chunk_2}
[3] (来源: {title_3}) {chunk_3}

【用户问题】
{question}

【回答】

要点：明确的约束规则 + 编号引用 + 允许「不知道」。这三条能显著降低幻觉率。第 4 条尤其重要——真实知识库里新旧文档冲突是常态，让模型自行裁决反而更危险，把冲突暴露给用户才是负责任的做法。

还有一个工程上的取舍：规则写得越严，模型越容易在资料稍有欠缺时就拒答，用户体验会变差；写得越松，幻觉率上升。这个阈值没有标准答案，要靠你自己的评测集在「拒答率」和「幻觉率」之间找平衡点。

from typing import List

def build_index(docs: List[str], embed_model, vector_db):
    """离线:切分 -> 向量化 -> 入库"""
    for doc in docs:
        chunks = split_text(doc, chunk_size=512, overlap=64)
        vectors = embed_model.encode(chunks)
        vector_db.add(vectors, metadata=chunks)

def reciprocal_rank_fusion(*rank_lists, k: int = 60):
    """只看排名不看分数, 天然跨量纲"""
    scores = {}
    for lst in rank_lists:
        for rank, doc_id in enumerate(lst, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)

def rag_answer(question: str, embed_model, vector_db,
               reranker, llm, filters: dict = None) -> str:
    """在线:过滤 -> 检索 -> 重排 -> 生成"""
    # 1. 混合检索, 两路各粗召回 50 条
    q_vec = embed_model.encode(["query: " + question])[0]
    dense_hits  = vector_db.search(q_vec, top_k=50, filters=filters)
    sparse_hits = bm25_search(question, top_k=50, filters=filters)
    candidates  = reciprocal_rank_fusion(dense_hits, sparse_hits)[:60]

    # 2. 精排, 选出最相关的 5 条
    top_chunks = reranker.rank(question, candidates, top_k=5)
    if not top_chunks:
        return "根据现有资料无法回答。"

    # 3. 最相关的放两端, 次相关的放中间, 缓解中间迷失
    ordered = _place_best_at_edges(top_chunks)

    # 4. 拼装 Prompt 并生成
    context = "\n".join(
        f"[{i+1}] (来源: {c.title}) {c.text}" for i, c in enumerate(ordered)
    )
    prompt = RAG_TEMPLATE.format(context=context, question=question)
    return llm.generate(prompt)

def _place_best_at_edges(chunks):
    """[1,2,3,4,5] -> [1,3,5,4,2] 把高分片段推到首尾"""
    head, tail = [], []
    for i, c in enumerate(chunks):
        (head if i % 2 == 0 else tail).append(c)
    return head + tail[::-1]

注意第 20 行的 "query: " + question：不少嵌入模型要求查询侧加特定前缀，漏加会明显掉点且不报错。具体前缀以你所用模型的官方文档为准。

嵌入模型与重排器选型

五步流程里，向量化和重排这两步各自依赖一个独立的小模型。它们的选型直接决定检索质量的上限——生成模型再强，也救不回没检索到的内容。

两类模型的分工

很多人把它们混为一谈，其实结构和用法完全不同：

嵌入模型 Bi-Encoder重排器 Cross-Encoder
怎么算查询和文档各自独立编码成向量，再比余弦相似度查询和文档拼在一起送进模型，直接输出相关度分数
能否预计算可以。文档向量离线算好存库，在线只算查询不能。每个「查询-文档」对都要现算
速度快，百万级文档毫秒响应慢，只能处理几十条候选
精度较低，查询和文档没有交互高，能捕捉细粒度语义匹配
在流程里的位置粗召回：从百万里捞出 Top-50精排序：从 Top-50 里选出 Top-5
换模型的代价极大，要重建整个向量库小，随时可换，不影响索引
为什么要两段式 Cross-Encoder 精度高但算不动全库，Bi-Encoder 算得动全库但精度不够。先用快的粗筛、再用准的精排，是检索系统的通用架构，和搜索引擎的召回-排序两阶段是同一个思路。表格最后一行还揭示了一个工程含义：重排器可以持续迭代，嵌入模型要一次选对。

选型该看什么

公开榜单（如 MTEB）是有用的起点，但不能直接当选型依据——榜单任务和你的业务分布往往差得很远。实际要看这几个维度：

  • 语言与领域匹配：中文场景优先选中文或多语训练充分的模型；法律、医疗、代码这类专业领域，通用模型的表现常常掉一大截。判断方法很简单：从你的业务里挑 20 个真实问题，人工看看 Top-5 里有几个是对的。
  • 向量维度：维度越高表达力越强，但存储和检索成本线性上升。百万级文档时，768 维和 1536 维的存储差一倍。部分模型支持维度截断（套娃式表示），可以按需取前 N 维——这个特性在成本敏感场景很有价值，但要确认你选的模型确实支持，普通模型截断维度会严重掉点。
  • 最大输入长度：决定了单个 chunk 能多大。超长的部分会被静默截断，这是很隐蔽的坑：你以为入库的是 1000 token 的完整段落，实际只有前 512 token 参与了编码，后面的内容在向量空间里根本不存在。
  • 对称还是非对称：「找相似句子」是对称任务，「用短问题找长文档」是非对称任务，两者最优模型不同。RAG 属于后者。
  • 是否需要指令前缀：不少嵌入模型要求查询侧加特定前缀（如 query: ），漏加会明显掉点，且不报错。同样的，文档侧可能要求另一个前缀，两边搞混了效果会更差。
  • 部署形态：API 调用省心但有延迟和单价，本地部署要占一张卡但可控。百万级以上的批量建索引，本地部署通常更划算。
换嵌入模型 = 重建整个向量库 不同模型的向量空间彼此完全不可比。换模型后，旧向量必须全部重新计算，否则检索结果会变成随机噪声。更危险的是这个过程不会报错——系统照常运行，只是答得驴唇不对马嘴。所以嵌入模型的选型要尽早定下来，迁移成本随数据量增长。真要迁移，正确做法是双写双索引、灰度切流、对比评测通过后再下线旧索引，而不是原地覆盖。这类线上治理问题的完整讨论见 RAG 生产运维。

向量库与索引结构：为什么它能在百万条里毫秒返回

如果老老实实拿查询向量和库里每一条算余弦相似度，百万条就是百万次点积，延迟根本不可接受。向量库之所以快，靠的是近似最近邻搜索（ANN）——用一点点召回精度换取几个数量级的速度提升。理解这个取舍很重要，因为它解释了一类诡异现象：「这条文档明明在库里，为什么就是检索不到？」

索引类型原理查询速度召回精度内存占用适用规模
Flat（暴力）和每一条都算一遍，无索引慢，线性增长100% 精确只存向量本身几万条以内，或作为精度基线
IVF（倒排文件）先聚类分桶，查询时只搜最近的几个桶快取决于搜几个桶，答案在没搜的桶里就漏了中等百万级
HNSW（分层小世界图）建多层跳表式图，从稀疏层逐层下沉逼近很快高，可调高，图结构本身很占内存百万到千万级，当前主流
PQ / 量化组合把向量压缩成短码，牺牲精度换内存快较低，需配合重排补偿低内存吃紧的超大规模
ANN 的精度不是 100% HNSW 有一个搜索宽度参数（常见命名为 ef_search 一类，具体参数名以你所用向量库的官方文档为准），它控制搜索时探索的邻居数量：调大则召回率上升、延迟上升，调小则相反。默认值往往偏保守。当你怀疑「明明有这条文档却检索不到」时，先用 Flat 暴力检索跑一遍同样的查询做对照：如果 Flat 能找到而 HNSW 找不到，那就是索引参数问题，不是嵌入模型问题。这个对照实验能省下大量走错方向的时间。

建立你自己的评测集

这是投入产出比最高、却最常被跳过的一步。没有评测集，所有调优都是盲调——你改了 chunk 大小，感觉「好像好一点」，但这个「好像」可能只是你恰好试的那三个问题变好了。

  1. 攒问题：从真实用户日志里捞 50–200 条代表性问题，覆盖高频、长尾、精确匹配、多跳几类。数量不必多，代表性比规模重要。如果还没上线没有日志，就让业务方每人写 10 个他们真会问的问题——注意是「真会问的」，不是「觉得应该测的」。
  2. 标注答案出处：人工标出每个问题应该命中哪些 chunk。这是唯一需要人力的环节，也是评测集的价值所在。标注时允许一个问题对应多个正确 chunk，也允许标注「本库无法回答」这种负样本——后者用来测拒答能力，同样重要。
  3. 算检索指标：见下表。注意召回率是上限——粗召回没捞到的，重排再强也救不回来。
  4. 纳入回归：切分策略、嵌入模型、Top-K、重排器，任何一处改动都跑一遍。没有回归集，你永远不知道这次调优是真提升还是随机波动。
指标衡量什么什么时候看它典型陷阱
召回率@K（Recall@K）该找到的 chunk 有没有进 Top-K调切分、调嵌入模型、调粗召回 K 值时K 取得太大时永远好看，要固定 K 横向比
MRR（平均倒数排名）第一个正确结果排在第几位只关心「有没有一条对的排前面」的场景多个正确答案时只看第一个，信息丢失
NDCG@K正确答案整体排得够不够靠前，考虑相关度分级调重排器时的主力指标需要分级标注，纯二值标注下退化
拒答准确率库里没有答案时，模型有没有老实说不知道上线前的安全检查容易被忽略，但这是幻觉的主要来源
引用正确率模型标的 [1][2] 是否真支撑它的结论溯源功能上线后需要人工或 LLM-as-Judge 抽检

把检索指标和最终答案质量分开看很重要：检索指标掉了，一定有问题；检索指标没掉但答案变差，问题在生成侧或 Prompt。这样能快速定位故障域，而不是每次都从头怀疑一遍。评测方法本身的偏差来源（比如 LLM-as-Judge 的位置偏好）见 评估方法论；线上持续监控的做法见 RAG 生产运维。

一次完整的排查演练

光有指标还不够，你得知道指标掉了之后往哪儿看。下面这个决策树是实战中最常用的排查顺序，核心原则是从数据源头往生成末端查，而不是反过来——因为末端的问题往往是源头问题的表现。

举一个真实感很强的例子走一遍这个流程。用户反馈：「问『差旅住宿标准是多少』，系统答的是 2023 年的旧标准。」

  1. 正确文档在库里吗？——查一下，2026 版《差旅管理办法》确实入库了。继续。
  2. Flat 暴力检索能找到吗？——能，2026 版排第 3。说明嵌入没问题。继续。
  3. 线上 ANN 能进 Top-50 吗？——能，排第 8。继续。
  4. 重排后能进 Top-5 吗？——不能，2023 版排第 2，2026 版被挤到第 7。找到了。

原因是两版文档措辞几乎一致，重排器无法从文本内容上分辨新旧。这类问题不该靠重排器解决，而该靠元数据过滤解决：给文档打上 effective_date 和 status 字段，检索时直接过滤掉已废止版本。这也印证了前面那个提示框的观点——能用结构化字段表达的约束，就不要指望向量相似度去理解。

常见坑位

检索不到 ≠ 模型不行 RAG 效果差，八成问题出在检索环节而非生成环节。排查顺序应该是：切分质量 → 检索召回率 → 重排精度 → Prompt 约束，最后才是换模型。换更贵的生成模型是最容易做、也最容易白花钱的动作。
  • chunk 过大：引入大量无关内容，稀释注意力，还烧 token。一个 4000 token 的 chunk 里可能只有 50 token 与问题相关，剩下的都是干扰。
  • 只用向量检索：遇到产品型号、人名、错误码这类精确匹配需求会大量漏召回。这是上线后最常见的第一波投诉来源。
  • 跳过重排：直接把 Top-K 粗召回结果喂给模型，噪声大、准确率低。重排器通常是整条链路里性价比最高的一次投入。
  • 不做溯源：用户无法验证答案真伪，信任度低。而且一旦出错，你连「模型是被哪段资料带偏的」都查不出来。
  • 忽略多跳问题：「A 的负责人所在部门的预算是多少」这类问题单次检索答不了，需要 Agentic RAG。
  • 把权限交给模型：在 Prompt 里写「不要引用用户无权查看的文档」是无效的。权限必须在检索层用元数据过滤实现，让无权文档从一开始就不进候选池。
  • 索引和源数据脱节：源文档改了但没触发重新入库，系统会自信地返回旧信息且不报错。这是运维期的头号杀手，必须有增量同步和新鲜度监控。
  • 用 LLM 生成评测集然后自己评自己：用同一个模型造问题、造标准答案、再当裁判，分数会虚高。评测集的标注环节必须有人参与，哪怕只是抽检。

要点速查

  • 本质：检索外部知识注入上下文，把闭卷变开卷。模型能力没变，变的是它手上有什么材料。
  • 五步：切分 → 向量化 → 检索 → 重排 → 生成。前四步决定上限，第五步决定下限。
  • 三条路的分工：RAG 教「知道什么」，微调教「怎么说话」，长上下文解决「一份材料太长」。不是替代关系。
  • 切分：结构化优先 + 递归兜底 + 10–20% 重叠 + 把标题路径拼进正文。父子切分兼顾精准与完整。
  • 检索：稠密 + 稀疏两路并行召回，用 RRF 按排名融合（跨量纲不敏感），再叠加元数据过滤。
  • 重排：Cross-Encoder 精度高但只能处理几十条，用漏斗架构「快的粗筛 + 准的精排」。
  • 嵌入模型要一次选对：换模型等于重建整个向量库，且失效时不报错。重排器则可以随时迭代。
  • ANN 不是精确检索：怀疑漏召回时，先用 Flat 暴力检索做对照实验定位问题环节。
  • 评测集是一切调优的前提：50–200 条真实问题 + 人工标注出处 + 召回率/NDCG/拒答准确率三类指标。
  • 排查顺序：文档在不在库 → Flat 能不能找到 → ANN 能不能召回 → 重排能不能选中 → 片段含不含答案 → 最后才是生成侧。
  • 权限必须在检索层做：Prompt 里的「不要引用」不是安全边界。
  • 不适用：需要改变模型行为风格或输出格式——那是微调的活。

关键问题与边界

Q1：RAG 和微调分别解决什么问题？

标准回答：RAG 主要解决“回答时能查到什么”，适合动态、私域、需要引用来源的知识；微调主要解决“模型怎么做、怎么说”，适合稳定的格式、风格和行为。动态知识通常优先 RAG，而不是不断重新微调模型。

Q2：为什么只看向量相似度不够，常要加 BM25 和 Reranker？

标准回答：Dense Retrieval 擅长语义相似，BM25 擅长精确词、编号和专有名词匹配；混合检索用两类召回互补覆盖，Reranker 再用更强的交互模型对候选文档重新排序。召回决定上限，重排改善候选顺序。

candidates = dense_topk + bm25_topk
reranked = cross_encoder(query, candidates)

Q3：RAG 效果差时，应该先查召回还是先改 Prompt？

标准回答：先拆开评估检索和生成。查看 Recall@K、MRR、NDCG，确认正确证据是否进入候选集；如果证据没召回，改 Prompt 没用，应排查切分、Embedding、查询改写和过滤条件。证据已召回但回答仍错，才进一步检查重排、上下文组织、引用约束和生成模型。

追问：为什么 Recall@K 是生成质量的上限？

如果正确文档没有进入 Top-K，生成器没有可靠证据可用，只能依赖参数记忆或猜测。生成模型再强也不能稳定恢复缺失信息，所以 RAG 评测必须把“召回对不对”和“引用用没用”分开看。

Q4：RAG 的权限控制应该放在哪里？

标准回答：必须在检索层做租户、用户和文档权限过滤，只让有权访问的候选进入上下文。不能只在 Prompt 里写“不要引用无权限内容”，因为模型看到了内容就可能泄露，Prompt 不是安全边界。

常见误区：向量库的召回分数高，不代表用户有权读取；权限过滤应成为检索查询的硬约束，并纳入回归测试。

参考文献与延伸阅读

  • Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks（Lewis et al., 2020, arXiv:2005.11401）— RAG 这个名字的出处。原始设定是检索器与生成器联合训练，与今天工程界主流的「冻结模型 + 外挂检索」有差别，但问题定义和评估框架至今适用。
  • Dense Passage Retrieval for Open-Domain Question Answering（Karpukhin et al., 2020, arXiv:2004.04906）— 双塔稠密检索的代表工作，解释了为什么 Bi-Encoder 能做到「文档向量离线预计算」，以及它相对 BM25 的强项与短板。
  • Efficient and Robust Approximate Nearest Neighbor Search Using Hierarchical Navigable Small World Graphs（Malkov & Yashunin, arXiv:1603.09320）— HNSW 原始论文。想搞清楚向量库为什么快、参数怎么调、召回率为什么不是 100%，读这篇。
  • Reciprocal Rank Fusion Outperforms Condorcet and Individual Rank Learning Methods（Cormack, Clarke & Buettcher, SIGIR 2009, ACM DL）— RRF 的出处，也是常数 $k=60$ 这个默认值的来源。
  • MTEB: Massive Text Embedding Benchmark（Muennighoff et al., arXiv:2210.07316）— 嵌入模型的综合评测基准。用它做初筛可以，但务必配合你自己的业务评测集做最终决策。
  • Retrieval-Augmented Generation for Large Language Models: A Survey（Gao et al., arXiv:2312.10997）— RAG 方法的系统综述，把 Naive / Advanced / Modular 三代范式梳理得比较清楚，适合建立全景认知后再深入某一支。
