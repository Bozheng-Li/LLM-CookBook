实战：手写 FlashAttention Kernel

理论讲得再清楚，不如亲手写一个 kernel。这一页用 Triton 实现分块注意力（FlashAttention 的核心思想），与标准实现对齐精度，再对比速度——你会发现「IO 感知」四个字从纸上落到了 GPU 上。

一图看懂

FlashAttention 的思想只有一句：别把完整的注意力矩阵写进 HBM，分块算、分块用。标准注意力要先算 $QK^\top$（N×N 矩阵）存显存再读回来；FlashAttention 把 Q、K 切成小块，在片上把「算分 + softmax + 加权求和」一气呵成，靠 online softmax 的增量技巧保证结果精确等价。

配套可运行代码 本页后半部分用 Triton 写 kernel，需要 GPU。examples/build-flashattention/ 提供一份纯 PyTorch 版本，CPU 也能跑通全部测试——算法（在线 softmax）与 kernel 版完全一致，只是没有 SRAM 常驻带来的加速。

一、为什么访存是瓶颈：先算一笔账

在写代码之前，先理解「为什么 FlashAttention 能快这么多」。GPU 上注意力不是「算不动」，而是「等内存」：

「等内存」不是一个模糊的说法，它有一个精确的工程定义：当一个 kernel 的耗时主要取决于数据进出内存的时间，而不是在计算单元上做运算的时间时，就称它是 memory-bound（访存受限）。标准注意力实现就是典型的访存受限——矩阵乘法本身算得极快，瓶颈几乎全在 HBM 读写。理解「访存受限 vs 计算受限」这对概念，是读所有 GPU 优化文章的前提：如果是访存受限，优化方向是「少搬数据」（分块、融合、缓存复用）；如果是计算受限，优化方向才是「少算」（稀疏、量化、低精度）。FlashAttention 的目标非常明确：把注意力从访存受限拉回计算受限，然后再考虑如何降低计算量。

标准注意力对一个长度为 N 的序列：计算 $QK^\top$ 得到 N×N 矩阵 → 写入 HBM → 读回做 softmax → 写回 → 读回乘 V。每次写读都是 N² 量级的数据搬运。FlashAttention 把 N×N 的中间矩阵「困在片上 SRAM」里，只对输入 Q、K、V 和输出 O 做 N 量级的 HBM 访问——这就是「IO 感知」（IO-aware）的含义。

用一组具体数字把「一笔账」算清楚。假设序列长度 N=2048、头维度 d=64、fp16（每元素 2 字节）。标准注意力中间的分数矩阵 S 是 N×N=4M 个元素，占 8MB 显存；它要被写入 HBM 一次、读回做 softmax 一次、把归一化后的概率矩阵 P 再写入一次、读回乘 V 一次——光是这个中间矩阵，就有约 32MB 的额外读写流量。而 FlashAttention 不写中间矩阵，只把输出 O（N×d×2 字节，约 256KB）写回，输入 Q、K、V 各读一次。两者在「中间矩阵」上的访存差距超过一百倍。以约 2TB/s 的 HBM 带宽估算，32MB 的搬运耗时约 16 微秒，而对应规模的分块矩阵乘法只需微秒量级——内存搬运明显是大头。

为什么自己写：一次「IO 感知」的完整体验

调用 torch.nn.functional.scaled_dot_product_attention 一行代码就能用上 FlashAttention，那为什么还要手写一遍？因为这页的目标不是「产出一个可用的 kernel」，而是「把 IO 感知这四个字变成肌肉记忆」。很多人在优化大模型时遇到瓶颈——训练慢、显存爆、长上下文 OOM——第一反应是换更大的机器，而不是先数一数数据被搬了多少次。手写一遍 kernel，你会建立三个反射：看到 N×N 中间矩阵先想「能不能不进 HBM」；看到长序列先想「访存与计算谁是大头」；看到重复读写先想「能不能合并成一趟」。这些反射在排查生产系统的性能问题时，比背十条优化口诀都管用。

另一个现实动机是：PyTorch 的内建实现虽然快，但它是个「黑盒」，你无法控制块大小、无法加自定义 mask、无法针对特定硬件调优。当你需要稀疏注意力、需要把注意力分数导出做可视化、需要在自定义硬件上部署时，理解 kernel 的每一行就是解锁这些能力的钥匙。所以这页的代码故意保持「教学清晰」优先于「极致性能」——先看懂，再谈优化。

二、Online Softmax：等价性的关键

分块处理的最大障碍是 softmax 的分母依赖「全部行」，而分块只能看到一部分。Online softmax 的解法是增量维护：

也许你会问：既然分块后需要「重加权」这么麻烦，为什么不能先算完所有分数再统一 softmax？因为那就回到了「先把 N×N 分数矩阵写进 HBM」的老路，违背了分块的初衷。online softmax 的全部意义在于：它让「算分 → softmax → 加权求和」三个步骤可以逐块融合，每处理一块就推进一点，不需要任何中间结果落盘。代价是多了重加权这步逐元素运算，但它发生在片上、速度极快，相比省下的 HBM 读写完全可以忽略。

  • 每处理一个 K 块，先算「上一轮最大值 $m_{prev}$ 与当前块最大值 $m_{cur}$」，再更新全局最大值 $m$；
  • 用 $e^{m_{prev} - m}$ 给旧累加结果重新加权，把新块并入；
  • 整个过程数值上等价于「先看全行再算 softmax」——输出与标准实现逐位一致（浮点舍入级别）。

把这三条翻译成公式。标准 softmax 是 $p_i = \exp(s_i - m) / \sum_j \exp(s_j - m)$，其中 $m = \max_j s_j$。分块时，假设已处理完一部分块，维护着 $m_{prev}$ 和 $l_{prev} = \sum \exp(s_j - m_{prev})$；现在来了一个新块，局部最大值为 $m_{cur}$，新的全局最大值 $m_{new} = \max(m_{prev}, m_{cur})$。由于减数变了，旧块的每一项都要乘一个「重加权系数」$\alpha = e^{m_{prev} - m_{new}}$ 才能和新块对齐到同一个参考系，于是 $l_{new} = l_{prev} \cdot \alpha + \sum_{j \in \text{new}} \exp(s_j - m_{new})$；输出同理 $O_{new} = O_{prev} \cdot \alpha + P_{new} V_{new}$。

用一个三元素的小例子验证这个递推是对的。设某行在第一个块里的分数是 $[1, 2, 3]$，标准做法：$m=3$，$l=\exp(1-3)+\exp(2-3)+\exp(3-3)=0.135+0.368+1=1.503$。现在来了第二个块，分数是 $[4, 1]$：$m_{new}=\max(3,4)=4$，$\alpha=e^{3-4}=0.368$，$l_{new}=1.503 \times 0.368 + (\exp(4-4)+\exp(1-4)) = 0.553 + 1.050 = 1.603$。再一次性对全部五个分数 $[1,2,3,4,1]$ 直接算：$m=4$，$l=\exp(1-4)+\exp(2-4)+\exp(3-4)+\exp(4-4)+\exp(1-4)=0.050+0.135+0.368+1+0.050=1.603$。两者完全一致——这就是「分块处理」与「全行处理」数值等价性的来源。O 的更新也是同一套重加权逻辑，只是把 $\exp$ 替换成概率对 V 的加权求和。

这个例子还解释了为什么 online softmax 不会引入额外误差：重加权系数 α 是精确的指数运算，唯一的区别只是运算顺序不同导致的浮点舍入差异，而 fp32 的舍入误差在 1e-7 量级，相对 fp16 量化本身的误差（约 1e-3）可以忽略。所以「FlashAttention 是精确算法」这句话的准确含义是：它和标准实现共享同一套数学公式，只在浮点运算顺序上有细微差别——这比任何「近似注意力」（线性注意力、稀疏注意力）都更让人放心，也是它能无痛替换标准实现的原因。

三、Triton 实现：分块 FlashAttention

现在动手。用 Triton 写一个分块注意力 kernel：外层循环遍历 K、V 块，内层做「算分数 → online softmax → 更新输出」。先看 kernel 的数据流：

选择 Triton 而不是 CUDA 的原因很实际：Triton 用 Python 编写、自动处理线程分配和数据搬运，写一个分块 kernel 只需几十分钟；手写 CUDA 则需要管理共享内存、同步屏障、线程块布局，复杂度高一个数量级。本页的目标是理解 FlashAttention 的算法骨架，Triton 恰好把这个骨架暴露得足够清晰，又不让底层细节淹没主线。等你在 Triton 里调通之后，如果还想追求极致性能，再考虑用 CUDA 重写同款逻辑。

写代码前先想清楚「为什么一定要按块切分」。GPU 的片上 SRAM（也叫共享内存）很小，通常只有几十到一百多 KB：A100 每个 SM 约 192KB，H100 约 228KB。要算一行 softmax，理想情况是整行分数都在 SRAM 里——但 N=8192 时一行分数就有 8192 个元素、fp16 下 16KB，而一个 kernel 往往同时要算 BLOCK_N 行，直接爆掉 SRAM。所以只能折中：每次从 HBM 加载一小块 K/V 到 SRAM，算完这一块对输出的贡献，更新状态量，再加载下一块。块的大小 BLOCK_N 和 BLOCK_K 就是「SRAM 容量、并行度、重加权频率」三者之间的权衡旋钮。

参数典型值作用调大的影响
BLOCK_N64–128Q 块的行数，决定每个程序处理多少行并行度更高，但占更多 SRAM
BLOCK_K32–64K/V 块的长度，决定重加权的频率块越大重加权次数越少，SRAM 占用越大
head_dim64–128单头维度，通常由模型结构决定不可自由调，与模型绑定

关于块大小的取舍，有一个实用的经验：先让 BLOCK_N × BLOCK_K 的分数块加两个 K/V 块的总字节数，明显小于 SRAM 容量，再在这个约束下尽量取大。块太小（如 16×16）时，重加权的开销和循环开销占比过高，访存省了但计算效率差；块太大（如 256×256）则会爆 SRAM 或者让单个程序占用过多片上资源、降低 SM 上的并发度。64×64 是大多数 GPU 上都安全且体面的起点。

import torch
import triton
import triton.language as tl

@triton.jit
def flashattention_kernel(
    Q, K, V, O,
    stride_qn, stride_qd,
    stride_kn, stride_kd,
    stride_vn, stride_vd,
    stride_on, stride_od,
    N, D,          # 序列长度, 头维度
    scale,         # 1/sqrt(D)
    BLOCK_N: tl.constexpr,   # Q 块大小
    BLOCK_K: tl.constexpr,   # K/V 块大小
):
    """FlashAttention 前向（分块版）

    思路：
      1. 外层循环遍历 K/V 块
      2. 每块内：算 QK^T 分数 → online softmax → 更新 O
      3. 全程不写完整 N×N 矩阵
    """
    pid_m = tl.program_id(0)   # Q 块的索引
    pid_h = tl.program_id(1)   # head 索引

    # Q 块的行范围
    offs_m = pid_m * BLOCK_N + tl.arange(0, BLOCK_N)
    offs_d = tl.arange(0, D)

    # 加载当前 Q 块
    q_ptrs = Q + pid_h * 0 + offs_m[:, None] * stride_qn + offs_d[None, :]
    q = tl.load(q_ptrs)  # [BLOCK_N, D]

    # 初始化 online softmax 状态
    m_i = tl.full([BLOCK_N], float("-inf"), dtype=tl.float32)
    l_i = tl.zeros([BLOCK_N], dtype=tl.float32)
    acc = tl.zeros([BLOCK_N, D], dtype=tl.float32)

    # 外层循环：遍历 K/V 块
    for k in range(0, tl.cdiv(N, BLOCK_K)):
        offs_k = k * BLOCK_K + tl.arange(0, BLOCK_K)

        # 加载 K、V 块
        k_ptrs = K + offs_k[:, None] * stride_kn + offs_d[None, :]
        v_ptrs = V + offs_k[:, None] * stride_vn + offs_d[None, :]
        k_block = tl.load(k_ptrs)  # [BLOCK_K, D]
        v_block = tl.load(v_ptrs)  # [BLOCK_K, D]

        # 计算分数：Q @ K^T * scale
        s = tl.dot(q, tl.trans(k_block)) * scale  # [BLOCK_N, BLOCK_K]

        # Online softmax 增量更新
        m_cur = tl.max(s, axis=1)                # 本块每行最大值
        m_new = tl.maximum(m_i, m_cur)           # 全局最大值
        p = tl.exp(s - m_new[:, None])           # 重缩放的概率
        alpha = tl.exp(m_i - m_new)              # 旧结果的重加权系数
        l_i = l_i * alpha + tl.sum(p, axis=1)    # 更新归一化因子
        acc = acc * alpha[:, None] + tl.dot(p, v_block)  # 更新输出
        m_i = m_new

    # 最终归一化
    acc = acc / l_i[:, None]

    # 写回输出
    o_ptrs = O + offs_m[:, None] * stride_on + offs_d[None, :]
    tl.store(o_ptrs, acc.to(O.dtype.element_ty))

这个 kernel 已经实现了 FlashAttention 的核心：外层循环 + online softmax + 增量加权。完整版本还需要处理：mask（padding）、多 head 的 stride、更优的块大小选择（如 BLOCK_N=128、BLOCK_K=64）。

把 kernel 逐段拆开读一遍。第一段，pid_m = tl.program_id(0) 和 pid_h = tl.program_id(1)：kernel 被启动成二维网格，第一维是 Q 块的行索引，第二维是 head 索引，每个程序负责「若干 Q 行 × 一个 head」的输出，天然并行。第二段，offs_m 和 offs_d 用 tl.arange 生成索引范围，再通过指针算术把 Q 块加载进来——这是 Triton 与 PyTorch 最大的不同：你得手动管理「数据在哪、怎么取」，而不是把张量丢给框架。第三段初始化三个状态量：m_i = -∞、l_i = 0、acc = 0，分别对应公式里的最大值、归一化因子和累加输出。第四段，外层 for k in range(...) 遍历 K/V 块，内层四行就是前面推导的 online softmax 更新：先算当前块每行最大值 m_cur，再取全局最大值 m_new = maximum(m_i, m_cur)，用 alpha = exp(m_i - m_new) 给旧结果重加权，然后同步更新 l_i 和 acc。循环结束后 acc / l_i 就是最终输出，写回 HBM。

理解这段代码的关键在于：tl.dot 的两处调用（分数和加权求和）是整段 kernel 里唯一的矩阵乘法，其余全是逐元素操作。这正是 FlashAttention 的另一个设计取向——把计算集中在 tensor core 擅长的矩阵乘上，让 softmax 等「非矩阵乘」操作占比降到最低。FlashAttention-2 的一个重要改进就是进一步压缩非矩阵乘操作的时间占比，让 SM 尽可能处在「在算矩阵乘」的状态而不是「在等数据」的状态。

3.1 causal mask 与 padding 怎么处理

真实场景里的注意力几乎都带 causal mask（解码器只允许看到当前位置及之前），batch 里还可能存在 padding。这两个都会让上面的「裸分块」版本输出错误结果，是完整版 kernel 必须处理的。causal mask 的常见做法是给 mask 区域的分数赋一个绝对值很大的负数（如 −1e9），这样 softmax 之后它们趋近于 0；由于块遍历是递增的，一个位置 j>i 的分数永远不在合法的「前缀」里，可以直接在算分阶段按 (i, j) 坐标过滤，甚至利用对角线优化——每个 Q 块只需要遍历到与自己行号对齐的 K 块为止，能省掉近一半的块遍历。padding mask 的做法类似：给 padding 位置对应的行/列分数打上负无穷。这些处理只影响分数矩阵的元素值，不影响 online softmax 的更新逻辑本身——m、l、O 的递推照常进行，被 mask 掉的分数自然会被排除在归一化之外。

四、封装与精度验证

kernel 写完后，需要封装成 Python 可调用的函数，并与 PyTorch 标准注意力做精度对齐——这是「手写 kernel 能不能用」的验证门槛。

def flash_attention(Q, K, V):
    """封装 Triton kernel：单头注意力

    Args:
        Q, K, V: [N, D] 张量（单 head）
    """
    N, D = Q.shape
    O = torch.empty_like(Q)

    BLOCK_N = 64
    BLOCK_K = 64

    grid = (triton.cdiv(N, BLOCK_N), 1)
    flashattention_kernel[grid](
        Q, K, V, O,
        Q.stride(0), Q.stride(1),
        K.stride(0), K.stride(1),
        V.stride(0), V.stride(1),
        O.stride(0), O.stride(1),
        N, D, 1.0 / (D ** 0.5),
        BLOCK_N=BLOCK_N, BLOCK_K=BLOCK_K,
    )
    return O


def reference_attention(Q, K, V):
    """标准注意力（PyTorch 参考实现）"""
    scores = Q @ K.transpose(-2, -1) / (Q.shape[-1] ** 0.5)
    probs = torch.softmax(scores, dim=-1)
    return probs @ V


# 精度验证：随机数据对比
torch.manual_seed(0)
N, D = 1024, 64
Q = torch.randn(N, D, device="cuda", dtype=torch.float32)
K = torch.randn(N, D, device="cuda", dtype=torch.float32)
V = torch.randn(N, D, device="cuda", dtype=torch.float32)

out_fa = flash_attention(Q, K, V)
out_ref = reference_attention(Q, K, V)
err = (out_fa - out_ref).abs().max().item()
print(f"最大绝对误差: {err:.6f}")
# 期望输出 ~1e-5 量级（浮点舍入差异）

# 速度对比
import time
def bench(fn, n_iter=20):
    for _ in range(3): fn()  # warmup
    t0 = time.time()
    for _ in range(n_iter): fn()
    return (time.time() - t0) / n_iter * 1000

fa_ms = bench(lambda: flash_attention(Q, K, V))
ref_ms = bench(lambda: reference_attention(Q, K, V))
print(f"FlashAttention: {fa_ms:.2f} ms")
print(f"标准注意力:    {ref_ms:.2f} ms")
print(f"加速比:        {ref_ms / fa_ms:.2f}x")

这段封装代码里有三个工程细节值得说。第一，grid 只设了两维——(triton.cdiv(N, BLOCK_N), 1)，第二维填 1 是因为这里是单 head 版本；多 head 时第二维填 head 数量，kernel 里通过 pid_h 去索引不同 head 的 Q/K/V，注意所有 stride 的计算都要把 head 维加进去。第二，BLOCK_N=64、BLOCK_K=64 是最保守的选择——64×64 的分数块在 fp16 下只有 8KB，任何 GPU 的 SRAM 都放得下；想要性能上限可以试 128×64 或 128×128，但必须先验证精度仍对齐。第三，scale = 1.0 / (D ** 0.5) 在 host 侧就算好传进去，而不是在 kernel 里算——把能预计算的都预计算，是 kernel 编程的基本素养。

精度验证用 torch.manual_seed(0) 固定随机种子，保证每次跑的输入一致、结果可复现；(out_fa - out_ref).abs().max() 取最大绝对误差，是核验精度的标准口径——误差在 1e-5 量级，说明 online softmax 的重加权逻辑正确；如果误差到 1e-3 以上，几乎可以断定是 alpha 那个系数写错了（把 m_new 和 m_i 的先后搞反是最常见的 bug）。速度对比要在 warmup 之后计时，因为第一次调用要触发 Triton 编译 kernel，花几秒到几十秒，不能计入基准。

顺带一提，上面的 reference_attention 用 scores = Q @ K.transpose(-2, -1) 会显式构造 N×N 矩阵——N=1024 时只有约 4MB，没有问题；但如果直接拿它去跑 N=32768 的基准，参考实现会先 OOM。这个细节正好再次印证了第一节的账：标准实现的 N×N 中间矩阵在长序列下是显存和访存的双重杀手，而 kernel 版因为不构造中间矩阵，天然没有这个问题。

五、为什么长序列加速更明显

FlashAttention 的加速比随序列长度增大而增大——这正是「IO 感知」的体现：序列越长，标准实现的 N×N 中间矩阵越大，HBM 读写开销越惊人。

为什么加速比不是「线性增长」而是「越来越陡」？因为标准实现的开销中，中间矩阵是 N² 项，FlashAttention 省掉的就是它；而 FlashAttention 的开销主要是加载 K/V 块（N×d 项）。两者的比值随 N 增长近似正比于 N/d——N 越大，省得越多。这也是为什么同样的优化在短序列上「没什么感觉」，一旦进入 4K、8K 甚至 32K 上下文，就是数量级的差距。下图把两种实现按「哪些数据进出 HBM」摆在一起对比，能更清楚地看到差异点在哪。

环节标准注意力FlashAttention
分数矩阵 S完整 N×N 写入 HBM分块，始终在 SRAM 内
访存复杂度O(N²)（中间矩阵多次读写）O(N)（只读写输入输出）
softmax 计算全行一次性（需整行在内存）online 增量（逐块合并）
峰值显存需容纳 N×N 矩阵只需输出 O 与当前块
数值结果—与标准实现一致（舍入级别）
适用场景短序列、原型验证长序列、训练与推理

工程直觉：短序列（N < 512）用标准实现就够，FlashAttention 的收益不明显甚至可能更慢（kernel 启动开销）；长序列（N > 2048）才是 FlashAttention 的主场。生产系统（vLLM、SGLang）在长上下文场景全面使用它。

块大小的最终答案不能靠推理，要靠实测。一个可复现的调参流程是：固定 N=4096、d=64，把 (BLOCK_N, BLOCK_K) 依次扫过 (32,32)、(64,32)、(64,64)、(128,64)、(128,128)、(256,128)，记录每个组合的耗时，找出当前硬件上的最优配置；再在 N=1024 和 N=8192 上复核一次，确认最优块大小对序列长度不敏感。这个过程通常只要几分钟，却能换来 20% 到 40% 的性能差。注意对比基线要固定在同一套精度（fp16 或 bf16）和同一块 GPU 上，跨卡对比没有意义。

六、进阶：向后传播与其他变体

变体改进适用
FlashAttention-2减少非矩阵乘运算、更好的并行训练 + 推理通用

分块反向反向时重算而非存储训练省显存
稀疏 FlashAttention只算非零块稀疏注意力

这些变体的演进方向是一致的：要么让「非矩阵乘」时间更短（FA-2 的并行策略），要么利用新硬件的特性（FA-3 的 Hopper 异步执行），要么减少要算的内容（稀疏化、GQA 的共享 KV）。如果你在读它们的源码或论文时能认出「分块 + online softmax + 重计算」这三件套，就抓住了大半的架构脉络。对绝大多数应用而言，你不需要自己实现这些变体——PyTorch 的 SDPA 和各类推理引擎会替你选择，但理解它们共同的内核，能帮你在「换引擎、调显存、加自定义 mask」时做出正确的判断。

反向传播实现的核心：把前向的块遍历「重放」一遍，每块重新计算分数（而非存储 N×N 矩阵），从而反向也保持 O(N) 访存。这正是 FlashAttention 在训练中省显存的来源。把「重放」的过程画成时序图更直观：前向只保存每块的统计量，反向按相同的块遍历顺序重新加载 K/V、重新计算分数，再结合已保存的梯度更新权重。

这里有一个 trade-off 值得说透：重放能省显存，代价是反向多算一遍矩阵乘法（约 1.33 倍的前向计算量，业界称「重计算」）。对显存极度紧张的训练场景，这个代价通常值得——毕竟省下来的可能是整张卡。实际工程里，torch.nn.functional.scaled_dot_product_attention 已经内建了 FlashAttention 的前向和反向，多数时候不需要手写反向，但理解「为什么它能省显存」依然是排查显存问题时的重要基本功。

深入：重加权系数 α 的数学直觉

online softmax 里最反直觉的一步是 $O_{new} = O_{prev} \cdot \alpha + P_{new} V_{new}$：为什么旧输出要乘一个系数 α？因为 softmax 的归一化分母是「以当前最大值为基准」的，当全局最大值从 $m_{prev}$ 涨到 $m_{new}$ 时，旧块每一项 $\exp(s - m_{prev})$ 都需要换算成 $\exp(s - m_{new}) = \exp(s - m_{prev}) \cdot e^{m_{prev} - m_{new}}$，多出来的那个 $e^{m_{prev} - m_{new}}$ 就是 α。所以旧输出按 α 缩一缩，就能和新块「对齐到同一个参考系」再相加。

一个容易忽视的点：α 一定小于等于 1（因为 $m_{new} \ge m_{prev}$），所以旧数据的贡献只会被「压缩」而不会被「放大」。这意味着如果某一轮算出的最大值偏大（比如块里混进一个异常大的分数），后面所有旧数据都会被压得很小——数值上没有问题，但这属于数据层面的异常而不是算法 bug。这是在线算法与离线算法的一个微妙行为差异：离线算法对「先看到哪块」不敏感，在线算法则隐式地受块顺序影响。

另外值得注意，整个递推过程在 kernel 里用 fp32 累加而不是 fp16：因为 $l$ 和 $O$ 是逐步累加的量，fp16 只有约 3 位十进制有效数字，在长序列的多次累加中会放大舍入误差。这也是前面 kernel 代码里把状态量声明成 tl.float32、只在最后写回时转回输出精度（fp16/bf16）的原因。

读图先找两层存储：外层的大矩形代表 GPU 的 HBM，里面较小的区域代表片上 SRAM。Q、K、V 被切成块后，不是把完整的 N×N 分数矩阵写回 HBM，而是在 SRAM 中完成当前块的矩阵乘、online softmax 和 V 的加权累积；因此图中反复移动的是输入块，最终写回的是 O，而不是 S/P。

再沿着 Q 块和 K/V 块的交叉方向看：每一个块对都贡献一部分输出，行方向维护最大值与归一化因子，列方向逐块扫描键和值。这个布局解释了为什么算法仍然精确——它改变的是数据搬运顺序，不是注意力公式；同时也解释了为什么块大小、dtype、mask 和硬件后端会直接影响是否能落在快速路径上。

新手最容易搞错 FlashAttention 不是把注意力近似成线性注意力，也不是“只计算一小部分 token”。它仍然计算完整的精确注意力，只是不把完整的中间矩阵落到 HBM；若看到显存或速度异常，先检查是否静默回退，而不是先改数学公式。
展开：最小可运行版本、验证步骤与排查清单

最小实验可以先用 PyTorch 的 SDPA：创建同形状的 CUDA Q/K/V，使用 sdpa_kernel(SDPBackend.FLASH_ATTENTION) 强制后端，随后与 math 后端输出比较最大绝对误差。输入从 N=128、head_dim=64、float16 开始，确认结果有限且误差在可接受范围后，再逐步增加到 1024、4096，并记录峰值显存和 kernel 名。

排查顺序是：设备是否为 CUDA，dtype 是否为 fp16/bf16，head_dim 是否被后端支持，Q/K/V 是否 contiguous，mask 是否使用标准 causal 形式，最后用 profiler 确认实际 kernel。若强制后端直接报错，这是好事，说明你没有把回退误当成成功；替代方案是先用 math 后端保证正确性，或直接使用 PyTorch SDPA 让框架自动选择。

要点速查

  • 本质：FlashAttention = IO 感知的分块注意力，把 N×N 中间矩阵困在片上 SRAM，访存从 O(N²) 降到 O(N)。
  • 关键技巧：online softmax 增量维护最大值 m、归一化因子 l、输出 O，数值等价标准实现。
  • kernel 骨架：外层循环遍历 K/V 块 → 算分数 → online softmax 更新 → 最后除 l 归一化。
  • 验证门槛：与 PyTorch 参考对比，最大绝对误差应 < 1e-5。
  • 加速规律：序列越长加速越明显（N=512 约 2x，N=32768 可达 8-15x）；短序列收益小。
  • 生产使用：vLLM、SGLang 等推理引擎在长上下文全面使用；短序列可退回标准实现。
  • 常见坑：online softmax 的重加权系数写错导致精度不符；忽略 padding mask；短序列硬上 kernel 反而更慢。
