自注意力与多头注意力

一个注意力头只能给出一张权重表，可词与词之间的关系远不止一种：指代、语法、搭配、位置远近……多头注意力的办法很朴素——既然一张表不够，那就同时开好几张。而因果掩码则解决了另一个问题：让「预测下一个词」这件本质上串行的事，在训练时能一次算完。这一节会把张量形状一步一步走完，把参数量算到个位，把掩码的坑挨个踩一遍。

一图看懂

多头注意力不是把注意力算 8 遍，而是把每个词向量的 512 维切成 8 份 64 维，每份独立做一次注意力，最后拼回 512 维再过一个输出投影。就像看一份合同，法务、财务、技术三个人各看各关心的条款，最后把三份批注汇总成一份意见——总工作量没变，但视角从一个变成了三个。

先厘清：自注意力的「自」是什么意思

上一节讲的注意力是一个通用算子：给一组 Query、一组 Key/Value，算出加权结果。它并没有规定这三组东西从哪来。「自注意力」的意思就是：Q、K、V 全部由同一个序列投影而来。

这个约束听起来平淡，但它带来的能力是质变的。序列自己看自己，等于让句子内部每个词都能主动去问「跟我有关的词在哪」。翻译时源语言看源语言、代码补全时上文看上文、图像 patch 之间互相看——同一个算子换个输入来源就能覆盖。

形态Q 来自K / V 来自信息流方向典型出现位置
自注意力（双向）序列 A序列 A每个位置 ↔ 所有位置BERT 的每一层、Encoder 层
因果自注意力（单向）序列 A序列 A 中位置 ≤ 当前每个位置 ← 左侧位置GPT / Llama 的每一层
交叉注意力序列 B（解码端）序列 A（编码端）B 的每个位置 ← A 的所有位置T5 / BART 解码器第二个子层

三种形态用的是同一段代码，区别只在喂进去的张量和掩码。这也是为什么现代框架里只有一个 scaled_dot_product_attention 函数，靠参数区分场景——理解了这一点，读任何模型源码时就不会被「这里怎么又出现一个 attention」搞晕。

一句话直觉 自注意力 = 一个班级里所有同学互相提问；交叉注意力 = 这个班的同学去问隔壁班的同学。提问的动作完全一样，只是问的对象换了。

一个头为什么不够

回顾上一节的结论：注意力对每个位置产出一行 Softmax 权重，这一行的和恒等于 1。「和为 1」是个很强的约束——它意味着注意力必须做取舍。

看这句话：

The lawyer who reviewed the contract yesterday said it was fine.

当模型处理 it 时，至少有三件事同时需要关注：

  • 指代关系：it 到底指 contract 还是 lawyer？这需要把权重压给 contract。
  • 句法角色：it 是 said 引导的宾语从句的主语，需要关注 said。
  • 局部搭配：it was 是个紧邻的固定结构，需要关注右边一个词。

单头注意力只有一行权重，这三种需求要在同一个概率分布里抢份额。给 contract 分 0.6，给 said 就只剩 0.4 可分——不同性质的关系被迫在一个预算里竞争，结果是每种都被稀释成平均值。更糟的是，加权求和会把这几个词的 Value 混成一锅粥，下游没法再区分「这部分信息是从指代来的，那部分是从句法来的」。

换成 4 个头之后，每个头有自己独立的一行权重、自己独立的 64 维输出子空间。第 1 个头可以把 0.85 给 contract，第 2 个头把 0.7 给 said，互不影响；而且它们写入的是输出向量里不重叠的维度段，下游的 $W^O$ 有机会把它们区分开再重新组合。

处理 it 时的需求单头（1 张权重表）4 头（4 张权重表）
找到指代对象 contract只能分到部分权重头 1 独占，权重可给到很高
关联主句谓语 said与指代抢预算头 2 独立处理，不挤占头 1
捕捉相邻搭配 it was基本被挤掉头 3 专职做局部窗口
输出可分离性混成一个向量，无法区分来源写入不同维度段，$W^O$ 可再组合
一句话直觉 单头是「只允许投一票的选举」，多头是「开 h 个独立投票箱」。每个箱子可以有完全不同的赢家，互不挤占。

怎么切：参数量为什么几乎没涨

这是多头注意力最容易被误解的地方。很多人第一反应是「8 个头 = 8 套 QKV 投影 = 参数量 ×8」，这是错的。

真实做法是切分而非复制。设模型维度 $d_{model}$、头数 $h$，则每个头的维度是

$$d_k = d_v = \frac{d_{model}}{h}$$

投影矩阵 $W^Q$、$W^K$、$W^V$ 的形状仍然是 $d_{model} \times d_{model}$，只是投影出来的结果被在最后一维上切成 h 段，每段送给一个头。换句话说，那 8 个头的投影矩阵本来就是同一个大矩阵的 8 个列块，拼起来正好是原来的大小。

$$\text{head}_i = \text{Attention}(QW_i^Q,\; KW_i^K,\; VW_i^V)$$ $$\text{MHA}(Q,K,V) = \text{Concat}(\text{head}_1, \dots, \text{head}_h)\,W^O$$

用原始 Transformer base 的配置（$d_{model}=512$，$h=8$）算一遍形状：

张量形状说明
输入 $X$$n \times 512$n 个 token，每个 512 维
$W^Q / W^K / W^V$$512 \times 512$与头数无关，不随 h 变化
投影后 reshape$8 \times n \times 64$切成 8 个头，每头 64 维
单头分数矩阵$n \times n$共 8 份，并行计算
Concat 后$n \times 512$$8 \times 64 = 512$，维度回到原样
$W^O$$512 \times 512$把拼接结果混合成最终输出

参数量合计 $4 \times 512^2 \approx 105$ 万（不含偏置），无论 h 取 1、8 还是 16，这个数字都不变。计算量也基本一致：分数矩阵那一步，单头是 $n^2 \times 512$，八头是 $8 \times n^2 \times 64$，同样是 $n^2 \times 512$。多头真正多出来的开销只有 reshape / transpose 带来的访存，以及 h 次较小矩阵乘法对 GPU 利用率的轻微影响。

把数字落到一次真实前向上

抽象的形状不容易有体感，换成一组常见的推理配置算算看：batch $B=2$、序列长度 $n=1024$、$d_{model}=4096$、$h=32$、$d_k=128$。

  • 分数矩阵元素数：$2 \times 32 \times 1024 \times 1024 = 67{,}108{,}864$ 个数。FP16 下就是 128 MiB——这还只是一层的中间结果。32 层全部保留会直接吃掉 4 GiB。
  • 这一步的乘加量：$2 \times B \times h \times n^2 \times d_k \approx 1.72 \times 10^{10}$，约 17.2 GFLOP。
  • 序列翻倍到 2048：元素数与算力都乘以 4，分数矩阵变成 512 MiB。

这组数字解释了两件事：为什么 FlashAttention 死磕「不把 $n \times n$ 写回显存」这一件事，以及为什么长上下文的成本增长让人吃不消。

常见误区 「头越多越好」是不成立的。$d_{model}$ 固定时，头数翻倍意味着每头维度减半。$d_k$ 太小（比如降到 16 以下）时，单个头的 Query-Key 匹配退化为低秩运算，表达力明显不足，反而掉点。现代模型的 $d_k$ 普遍稳定在 64 或 128，头数是由 $d_{model}$ 除出来的结果，而不是先定的超参。

$d_k$ 一路稳定在 64 或 128，从 2017 年到今天几乎没变。真正在变的是最后一列：Query 头数和 KV 头数开始解绑。这就是下面要讲的现代演进。

展开：多头注意力最小实现（PyTorch 风格） 
import torch
import torch.nn as nn
import torch.nn.functional as F

class MultiHeadAttention(nn.Module):
    def __init__(self, d_model, n_heads):
        super().__init__()
        assert d_model % n_heads == 0
        self.h = n_heads
        self.d_k = d_model // n_heads
        # 注意:这里就是三个 d_model x d_model 的大矩阵,不是 h 套小矩阵
        self.W_q = nn.Linear(d_model, d_model, bias=False)
        self.W_k = nn.Linear(d_model, d_model, bias=False)
        self.W_v = nn.Linear(d_model, d_model, bias=False)
        self.W_o = nn.Linear(d_model, d_model, bias=False)

    def forward(self, x, causal=True):          # x: (B, n, d_model)
        B, n, _ = x.shape

        # 投影后切头: (B, n, d_model) -> (B, h, n, d_k)
        def split(t):
            return t.view(B, n, self.h, self.d_k).transpose(1, 2)

        q, k, v = split(self.W_q(x)), split(self.W_k(x)), split(self.W_v(x))

        scores = q @ k.transpose(-2, -1) / (self.d_k ** 0.5)   # (B, h, n, n)

        if causal:
            # 上三角(不含对角线)置为 dtype 最小值,而不是 -inf
            mask = torch.triu(torch.ones(n, n, dtype=torch.bool, device=x.device), diagonal=1)
            scores = scores.masked_fill(mask, torch.finfo(scores.dtype).min)

        attn = F.softmax(scores, dim=-1)
        out = attn @ v                                          # (B, h, n, d_k)

        # 拼回来: (B, h, n, d_k) -> (B, n, d_model)
        out = out.transpose(1, 2).contiguous().view(B, n, -1)
        return self.W_o(out)

注意 transpose(1, 2) 出现了两次：第一次把头维提到前面好做批量矩阵乘，第二次换回来准备拼接。这两行是多头实现里最容易写反的地方，维度对不上时先查它们。

还有一个静默的坑：transpose 之后张量不再连续，必须先 .contiguous() 才能 .view()，否则会报错或者（在某些写法下）拼出错位的结果。用 .reshape() 可以绕过报错，但也会掩盖真正的形状错误。

动手验证：形状对不对，跑一遍就知道

理解多头最快的办法是打印形状。下面这段可以直接贴进解释器，把每一步的张量尺寸打出来，顺便和框架内置实现对一下答案：

import torch
import torch.nn.functional as F

B, n, d_model, h = 2, 6, 8, 2
d_k = d_model // h
x = torch.randn(B, n, d_model)

# 手动切头
q = x.view(B, n, h, d_k).transpose(1, 2)      # (2, 2, 6, 4)
print("切头后:", q.shape)

scores = q @ q.transpose(-2, -1) / d_k ** 0.5  # (2, 2, 6, 6)
print("分数矩阵:", scores.shape)

# 因果掩码:上三角屏蔽
mask = torch.triu(torch.ones(n, n, dtype=torch.bool), diagonal=1)
scores = scores.masked_fill(mask, torch.finfo(scores.dtype).min)
w = F.softmax(scores, dim=-1)

# 校验 1: 每一行权重之和必须是 1
print("行和:", w.sum(-1))

# 校验 2: 第 0 个位置只应该看见自己
print("首行权重:", w[0, 0, 0])

# 校验 3: 与框架内置实现对齐(数值应非常接近)
ref = F.scaled_dot_product_attention(q, q, q, is_causal=True)
mine = w @ q
print("最大误差:", (ref - mine).abs().max().item())

三条校验分别对应三个最常见的 bug：行和不为 1 说明 Softmax 的维度写错了（写成 dim=-2 是经典错误）；首行权重不是 one-hot 说明掩码方向反了（diagonal 参数取错）；与内置实现误差过大 说明缩放因子或转置顺序有问题。

不同的头在看什么

训练完成后把注意力权重画出来，确实能看到一些头呈现出稳定的模式。常见的几类：

位置头

权重几乎全压在「前一个词」或「后一个词」上，相当于学出了一个局部卷积窗口。这类头在浅层尤其多。

句法头

动词关注它的宾语、介词关注它的宾语、限定词关注中心名词——权重分布与依存句法树高度吻合。

指代头

代词稳定地指向它的先行词，如 it → contract。多出现在中间层。

注意力汇聚头

大量权重堆在序列首个 token（BOS 或第一个词）上，这个现象被称为 attention sink，可以理解为「这一步没什么要看的」的默认去处。

attention sink 不只是个可视化趣闻，它有实际工程后果：做流式推理、滑动窗口裁剪 KV Cache 时，如果把最前面几个 token 一起丢掉，模型输出质量会明显崩坏。所以「无论窗口怎么滑，永远保留最初几个 token」成了长对话场景的一条常见工程做法。

别把可解释性当真理 上面这套「某某头」的说法广为流传，但它的干净程度被严重高估了。几点必须说清楚：
  • 大量头没有可命名的模式。能被人类归类的只是少数，更多头的权重图看上去就是一片弥散的噪声。
  • 头之间高度冗余。多项研究发现，推理时剪掉相当比例的注意力头，任务性能只有很小的下降——说明「每个头各司其职」的图景并不准确。
  • 功能不稳定。同一个头在不同输入、不同领域上的行为可能完全不同，「指代头」往往是在特定探测集上做的事后归因，换个分布就不成立了。
  • 头不是独立的。$W^O$ 会把所有头的输出混合，真正被下游使用的是混合后的结果，单独解读一个头本身就有偏差。

因果掩码：让串行任务并行训练

自注意力默认是「全体大会」，每个位置都能看到所有位置。这在 BERT 那种理解任务里没问题，但对 GPT 这类自回归语言模型是致命的。

语言模型的训练目标是：给定前 $t-1$ 个 token，预测第 $t$ 个。如果位置 $t-1$ 的注意力能看到位置 $t$，那它就直接看到了答案。模型会飞快地学会一个恒等映射——训练损失降到接近 0，而推理时未来 token 根本不存在，输出立刻崩掉。这就是典型的标签泄漏。

解决办法是在 Softmax 之前，把「看向未来」的那些分数全部屏蔽掉。掩码矩阵是一个下三角结构：

Query \ Keyt1t2t3t4t5
t1✓−∞−∞−∞−∞
t2✓✓−∞−∞−∞
t3✓✓✓−∞−∞
t4✓✓✓✓−∞
t5✓✓✓✓✓

第 $i$ 行表示第 $i$ 个 token 的可见范围：只能看自己和自己之前。对角线保留，因为一个词看自己是允许的。

为什么是 −∞ 而不是 0

这是个高频疑问，答案在于掩码作用的位置是 Softmax 的输入，不是输出。

如果把被屏蔽位置的分数设成 0，经过 Softmax 后得到的是 $e^0 = 1$，归一化之后它反而拿到了一个不小的权重——0 在 logits 空间里是个「中等偏上」的分数，完全没有屏蔽效果。要让 Softmax 之后的权重真正为 0，需要

$$\lim_{s \to -\infty} \frac{e^{s}}{\sum_j e^{s_j}} = 0$$

举个具体的数：假设一行未屏蔽位置的分数是 $[2.0,\ 1.0]$，被屏蔽位置本来是 $3.0$。把它设成 0，Softmax 后三者权重约为 $[0.63,\ 0.23,\ 0.09]$——那个「屏蔽掉」的位置还占了 9%。设成 $-10^4$ 时，$e^{-10^4}$ 在浮点下直接下溢为 0，权重才真正归零。

所以必须把分数推到负无穷。工程实现上有两个细节：

  • 用 dtype 的最小值而非字面 -inf。torch.finfo(dtype).min 更安全：真正的 -inf 在后续算子里参与乘法或加法容易产出 NaN，FP16 下尤其脆弱。
  • 当心整行被屏蔽。如果某一行所有位置都是 −∞（padding 与因果掩码叠加时可能出现），Softmax 分母为 0，直接得到 NaN 并污染整个批次。这是训练突然出现 NaN 损失的经典原因之一。
顺序不能错 掩码必须加在缩放之后、Softmax 之前。写成 softmax(mask(scores) / sqrt(d_k)) 会把 −∞ 也除一遍（数值上通常仍是极小值，但配合有限的 finfo.min 时可能被稀释到不够小）；写成掩码加在 Softmax 之后再重新归一化，则是另一套实现，容易和缩放逻辑打架。跟着标准顺序走最省事。

掩码不止一种

实际训练里，注意力掩码往往是好几层语义叠加出来的。搞清楚它们各自解决什么问题，能省掉大量调试时间：

掩码类型屏蔽的是什么形状什么时候需要忘了会怎样
因果掩码当前位置右侧的所有 token下三角，$n \times n$所有自回归语言模型标签泄漏，损失异常低、推理崩溃
Padding 掩码为对齐长度而补的 PAD token每个样本一行，$B \times n$batch 内序列长度不等时模型把 PAD 当真实内容读，短句表现变差
文档分隔掩码同一条序列里跨文档的注意力块对角 × 下三角把多篇短文档打包进一条序列时上一篇文章的内容污染下一篇的预测
前缀掩码（Prefix-LM）只对生成段做因果限制，前缀段双向可见左侧矩形 + 右下三角UL2 / GLM 这类前缀语言模型失去前缀双向理解的优势
滑动窗口掩码距离超过窗口 W 的历史带状下三角局部注意力、长上下文降本复杂度回到 $O(n^2)$

合并多个掩码时最稳妥的做法是先在布尔域里做逻辑与，最后一次性转成加性分数。如果对两个已经变成 −∞ 的加性掩码直接相加，很容易叠出 $-2 \times 10^{38}$ 这种溢出值，FP16 下直接变成 -inf，再往下走就是 NaN。

训练的并行性正是靠它换来的

这才是因果掩码最值得体会的一点。没有掩码时，要训练一个自回归模型，朴素做法是把一条长度 $n$ 的样本拆成 $n$ 条：用前 1 个词预测第 2 个、用前 2 个词预测第 3 个……跑 $n$ 次前向。

有了下三角掩码，情况完全不同：一次前向，序列里每个位置的输出天然就只依赖它左边的内容。于是位置 1 的输出可以拿来预测 token 2，位置 2 的输出预测 token 3……$n$ 个训练信号在同一次前向里全部产生，损失一次性求和。

训练阶段推理阶段
未来 token已知（整条序列都在手上）未知（还没生成出来）
是否需要掩码需要，否则泄漏答案不需要，未来本就不存在
前向次数1 次算出 n 个位置的损失n 次，每次只出 1 个 token
GPU 利用率高，是大矩阵乘低，受访存带宽限制
瓶颈资源算力（compute-bound）显存带宽（memory-bound）

「训练并行、推理串行」这个不对称，是理解后续一系列推理优化的起点：既然推理时每步都要重算前面所有 token 的 K 和 V，而它们其实一模一样，那就把它们缓存下来——这就是 KV Cache 的由来。

从 MHA 到今天

标准 MHA 提出至今没有被推翻，但在两个方向上被大幅改造：

  • 算得更快：朴素实现要把 $h$ 个 $n \times n$ 的分数矩阵完整写进显存，长序列下访存量惊人。FlashAttention 通过分块和在线 Softmax 让分数矩阵永远不落显存，数学结果完全等价。今天几乎所有框架的默认路径都是它。
  • 存得更省：MHA 的每个头都有自己独立的 K 和 V，推理时缓存开销与头数成正比。MQA / GQA / MLA 让多个 Query 头共享同一组 K、V，以很小的质量代价把 KV Cache 压缩数倍，已经是现代模型的标配。

手把手读 GQA 论文原图

「共享 KV」到底长什么样，看一张论文原图最直观。2023 年 Google 的 Ainslie 等人在 GQA 论文里画了一张经典的对比图，把 MHA、MQA、GQA 三种注意力头结构并排摆在一起，一眼就能看出「Query 头」和「KV 头」的绑定关系是怎么一步步松开的。

逐块读这张图。整张图分成三列，每一列都是「上方一行 Query 头、下方一行 Key 与 Value 头」，连线表示「这个 Query 头用哪组 K、V」。第一列是 MHA（多头注意力）：每个 Query 头都连着自己独立的一组 Key 和 Value，KV 头数和 Query 头数完全相等——这就是本页前面一直在讲的标准结构，KV 缓存也因此和头数成正比。第三列是 MQA（多查询注意力）：所有 Query 头全部连向唯一的一组 Key 和 Value，KV 头数压缩到 1，缓存最小，但所有头被迫共享同一套「被检索的索引」，表达能力受限。中间一列是 GQA（分组查询注意力）：Query 头被分成若干组，组内共享一组 K、V，组与组之间各自独立——它是前两者的折中：比 MHA 省缓存，比 MQA 保表达。

对照本页前面的 KV 缓存公式读这张图，结论就出来了：KV 缓存的体积只由「KV 头数」决定，与 Query 头数无关。所以把 KV 头数从 32 降到 8，缓存直接砍到四分之一，而 Query 头还是 32 个、问法还是 32 种——这正是 Llama-2-70B 一类大模型的选择，也是 GQA 在 2023 年后成为事实标准的原因。

新手最容易搞错 两个高频误解必须纠正。第一个：「多头注意力 = 把注意力重复算 8 遍」——错。多头是「切分」而非「复制」：$W^Q$、$W^K$、$W^V$ 仍然各是一个 $d_{model}\times d_{model}$ 的大矩阵，只是投影结果被在最后一维切成 $h$ 段，每段送一个头。参数量与头数无关。第二个：「GQA 是连 Query 头也一起减少了」——也不对。GQA 只共享 KV，Query 头保持原样；Query 头一旦减少就等于直接砍掉输出向量里的独立维度段，质量损失是立竿见影的。
踩坑实录：把多头实现成 h 套独立小矩阵，参数暴涨 8 倍

一个非常经典的手写实现错误：新手照着论文公式 $\text{head}_i = \text{Attention}(QW_i^Q, KW_i^K, VW_i^V)$ 逐字实现，用 h 个独立的 nn.Linear(d_model, d_k) 分别做投影——代码能跑、结果也「看起来对」，但一算参数量，比预期大了 8 倍，显存直接爆掉。

问题出在「切分」与「复制」的理解上。标准实现是一个大的 nn.Linear(d_model, d_model) 投影完，再把结果 view(B, n, h, d_k) 切成 h 段；而错误实现是 h 个独立的小 Linear，每个都是 d_model × d_k，总参数正好多出 $h$ 倍。两者数学上并不等价——独立小矩阵让每个头拥有完全独立的投影空间，等于把模型宽度扩大成了 $h \times d_k$，而大矩阵切块让所有头共享同一个 $d_{model}$ 维空间的不同子空间。

排查方法很简单：把模型的参数量打印出来，和 $4 \times d_{model}^2$（每层注意力，含 $W^O$）对一遍，对不上就先怀疑这里。顺带一提，正规框架里 nn.MultiheadAttention 也是用大矩阵加 reshape 实现的——对照官方实现最省心。

$$\text{bytes/token} = 2 \times L_{layers} \times h_{kv} \times d_k \times \text{bytes per element}$$

前面的 2 是因为 K 和 V 各存一份。代入 Llama-2-7B 的配置（32 层、32 个 KV 头、$d_k=128$、FP16）：

配置KV 头数每 token 占用4K 上下文32K 上下文
MHA，32 层，$d_k=128$32512 KiB2 GiB16 GiB
GQA，32 层，$d_k=128$8128 KiB0.5 GiB4 GiB

按 FP16 每元素 2 字节、单条序列计算；上表的 GQA / MQA 行是在同一骨架上只改 KV 头数的对照，不代表某个具体模型的官方配置。

一个 7B 模型 FP16 权重约 14 GB。上表第一行告诉你：只要上下文拉到 32K，KV 缓存就能再吃掉一个模型那么多的显存。这就是 GQA 几乎变成默认选项的原因——把 KV 头从 32 降到 8，缓存直接砍到四分之一，而质量损失小到多数场景可以忽略。

换句话说，「多头」这个结构保留了下来，被改造的是「每个头都要有一套完整 KV」这个假设。

展开：为什么 Query 头不能也一起共享

既然共享 K / V 影响不大，为什么不干脆把 Query 头也砍掉几个？因为两者在计算图里的地位完全不对称。

Query 头数决定「有多少种不同的问法」。每个 Query 头对应输出向量里一段独立的维度，砍掉一个 Query 头就是直接砍掉一段输出容量，等于减小了模型宽度，质量下降是线性且明显的。

K / V 头数决定「被检索的索引有多少套」。多个 Query 头去查同一套索引，只是让它们的检索目标空间被迫共享，但每个头依然可以用自己的 Query 投影问出不同的问题、得到不同的权重分布。信息瓶颈存在，但远没有砍 Query 头那么直接。

另一个现实约束是：KV 需要在推理全过程被缓存，Query 不需要。Query 每步用完即弃，缓存开销为零。所以省显存的动机天然只指向 K 和 V 这一侧。

这也解释了 GQA 的分组设计为什么合理：把 32 个 Query 头分成 8 组、每组共享一套 KV，既保住了 32 种问法，又只付 8 套索引的缓存代价。详见 注意力变体。

要点速查

  • 自注意力：Q / K / V 全部来自同一序列。加不加因果掩码决定它是双向还是单向；换成另一序列做 K / V 就变成交叉注意力。三者共用同一段代码。
  • 动机：单头只有一行和为 1 的权重，多种关系被迫争抢同一份预算；多头给每种关系独立的投票箱，且写入互不重叠的维度段。
  • 做法：切分而非复制。$d_k = d_{model}/h$，投影矩阵仍是 $d_{model} \times d_{model}$。
  • 参数量：$4 d_{model}^2$（$W^Q, W^K, W^V, W^O$），与头数无关；计算量同理基本持平。
  • 头数选择：实际固定的是 $d_k$（常见 64 / 128），头数由 $d_{model}$ 除出来。$d_k$ 过小会掉点。
  • 显存直觉：$B=2$、$n=1024$、$h=32$ 时，单层分数矩阵 FP16 就占 128 MiB，长度翻倍变四倍——这是 FlashAttention 存在的理由。
  • 可解释性：确有位置头 / 句法头 / 指代头 / attention sink，但冗余度高、不稳定，别当成严格的功能划分。
  • 因果掩码：下三角，屏蔽未来防止标签泄漏；用 −∞（实现上取 finfo.min）而非 0，因为它作用在 Softmax 输入端。
  • 掩码家族：因果 / padding / 文档分隔 / 前缀 / 滑动窗口，合并时先在布尔域做与运算，最后一次性转加性掩码。
  • 最大价值：掩码让 n 个位置的训练信号在一次前向里全部产生，这是 Transformer 训练效率的根基。
  • 常见坑：整行被掩 → Softmax 出 NaN；Softmax 维度写成 dim=-2；transpose 后忘了 contiguous；掩码方向写反。

发展脉络

多头注意力从等量 Q/K/V 头发展到 MQA、GQA 和 MLA，演进重点从表达子空间转向减少 decode 阶段 KV 读取。

机制抓手

Q 头按 head_dim 切分；GQA 让多个 Q 头共享一组 K/V 头，输出拼接后再经 Wo 投影回 D，广播关系必须显式验证。

工程权衡

更多 Q 头增加可分工子空间，但 KV 头越多缓存和带宽越高；过度共享又可能损害质量与长上下文召回。

head pruning、latent KV 与跨层缓存共享仍在探索，必须联合报告质量、KV 字节/token 和 TPOT。
