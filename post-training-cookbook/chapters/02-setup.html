1. 硬件梯度：从 RTX 4090 到 H100

后训练对硬件的需求可以用一句话概括：显存决定"能不能跑"，算力决定"跑多快"，互联决定"多卡扩不扩得动"。显存是最刚性的约束——模型权重、梯度、优化器状态加激活值必须同时放得下；算力（以厂商标称的 bf16 张量峰值计：RTX 4090 约 165 TFLOPS，A100 80G 约 312 TFLOPS，H100 SXM 约 989 TFLOPS，均不含稀疏加速）决定迭代速度，只影响你的时间成本；而卡间互联（NVLink vs PCIe）影响张量并行与多卡 RL 的通信效率，在消费级多卡机器上经常成为隐性瓶颈。

先建立显存的量级直觉（详细推导见 第 42 章）。混合精度 + AdamW 下，全量微调的常数为每个参数约 16 字节：bf16 权重 2 字节、bf16 梯度 2 字节、fp32 主权重 4 字节、一阶与二阶动量各 4 字节——即 7B 模型全量微调在跑第一条数据之前，就需要约 112 GB 显存容纳权重、梯度与优化器状态，再加激活值，2×A100-80G 起步并不夸张。而参数高效微调（Parameter-Efficient Fine-Tuning, PEFT）改写了游戏规则：LoRA（Low-Rank Adaptation）冻结原权重、只训练低秩适配器（第 14 章），显存主体是 bf16 基座（7B 约 14 GB）；QLoRA 把基座量化到 NF4（7B 约 3.5 GB），把 65B 模型的微调压进单张 48 GB 显卡（QLoRA 论文的原始实绩）。这张梯度差，就是你选卡的依据。

再补两个容易被忽略的变量。激活值随 batch 与上下文长度线性增长：同样是 7B LoRA，4K 上下文的显存需求可能是 1K 上下文的三倍以上，因此选卡之前先明确你的典型序列长度；梯度检查点（gradient checkpointing）用约三成的额外计算时间换取大幅的激活显存节省，是单卡长序列任务的标配开关。互联对 RL 后训练的影响远大于对 SFT 的影响：RLHF 与 GRPO 的采样与训练在多个进程间来回搬运权重，PCIe 多卡机器上的权重同步可能占掉训练循环的相当一部分时间——这正是 verl、OpenRLHF 这类框架强调把 rollout 引擎与训练引擎混合编排、共址部署的原因（第 45 章）。实践建议：SFT 类任务可以放心选 PCIe 消费级多卡，RL 类任务则优先考虑带 NVLink 的云实例。

💡 实践建议：先用小模型把流程跑通，再为效果换大模型

绝大多数流程性 bug（模板错位、数据格式错误、超参数量级错误）与大模型无关。正确姿势是：用 Qwen2.5-0.5B/1.5B 把数据 → 训练 → 评测闭环调通，再切到目标规模模型调效果。本章 10 分钟冒烟测试用的就是 0.5B——它能在任何 8 GB 以上显存的卡上运行。

小结：显存是刚性约束、算力是时间约束、互联是扩展约束；LoRA/QLoRA 把 70B 级微调压进单卡，而 RL 后训练始终比 SFT 贵一个档位。

2. 软件栈：CUDA、PyTorch 与版本兼容

新手最容易在这里耗掉一个晚上，所以先把逻辑讲透。NVIDIA 软件栈分两层：驱动（driver）是操作系统内核态的底层组件，必须与显卡匹配、由你安装或云镜像预装；CUDA 运行时（runtime）是用户态计算库。关键事实：通过 pip 安装的官方 PyTorch wheel 自带完整的 CUDA 运行时，你不需要单独安装 CUDA Toolkit——唯一的要求是驱动版本足够新。CUDA 12 系列具备次版本兼容机制：任何 cu121/cu124/cu126 的 wheel，原则上只要驱动不低于 CUDA 12.0 基线（Linux ≥ 525.60.13，Windows ≥ 528.33）即可运行；例外是硬件代际——RTX 50 系（Blackwell）必须使用 cu128 及以上构建（PyTorch 2.7+），对应驱动 ≥ 570.26。只有当你需要从源码编译扩展（如 flash-attn）时，才需要安装与 PyTorch 构建版本一致的 CUDA Toolkit（含 nvcc）。

安装命令如下。第 1 步配置国内 PyPI 镜像加速所有依赖；第 2 步从 PyTorch 官方源安装带 CUDA 运行时的 wheel（官方源在国内直连可能较慢，可改用上海交大等 PyTorch wheel 镜像）；第 3 步设置 Hugging Face 国内镜像，模型与数据集下载提速的关键；第 4 步安装训练栈。

install.sh（bash） 
# ① 全局使用国内 PyPI 镜像（也可用清华 TUNA：https://pypi.tuna.tsinghua.edu.cn/simple）
pip config set global.index-url https://mirrors.aliyun.com/pypi/simple/

# ② 安装带 CUDA 运行时的 PyTorch（wheel 自带 runtime，无需另装 CUDA Toolkit）
pip install torch==2.6.0 --index-url https://download.pytorch.org/whl/cu124

# ③ Hugging Face 国内镜像：下载模型/数据集前设置环境变量（建议写进 ~/.bashrc）
export HF_ENDPOINT=https://hf-mirror.com

# ④ 训练栈（走第 ① 步配置的国内镜像；版本组合见 6.2 节 requirements.txt）
pip install transformers==4.51.3 datasets==3.5.0 accelerate==1.6.0 trl==0.17.0 peft==0.15.2

两个补充。其一，驱动安装是整条链路中唯一无法用 pip 解决的部分：Linux 服务器建议安装生产分支驱动（如 550 系），Ubuntu 用户可直接安装系统仓库中的对应版本，装完 nvidia-smi 能正常出表即视为就绪；云实例一般已预装，选镜像时确认驱动版本即可。其二，如果不想自己拼环境，NVIDIA NGC 的 PyTorch 容器与 PyTorch 官方 Docker 镜像是两个"开箱即用"的选项——前者针对专业卡做过内核级调优，后者版本跟进快，第 6 节的 Dockerfile 即基于后者构建。

⚠️ 常见误区：在系统 Python 里"哪坏修哪"

直接往系统环境塞一堆包，冲突后反复卸载重装，是环境问题变成"玄学"的根源。正确做法是下一节的环境隔离：每个项目一个独立环境，版本锁定，坏了就删掉重建——重建成本只有 5 分钟。另外，Windows 用户建议使用 WSL2（Ubuntu 子系统）作为训练环境：绝大多数训练框架对 Linux 的支持与文档远好于原生 Windows，驱动装在 Windows 侧即可被 WSL2 透明使用。

小结：pip 装的 PyTorch 自带 CUDA 运行时，只看驱动版本；RTX 50 系必须 cu128；一切训练依赖都应装在隔离环境里。

3. 核心工具栈全景

后训练的工具生态可以用五层架构描述：最上层是方法与算法层（SFT、DPO、PPO、GRPO、RLVR 等本书第 3–6 部分的内容）；其下是训练与对齐框架层，把算法实现为可配置的训练器；再下是分布式与效率层，解决"放不下、跑不快"；然后是推理与 rollout 层，负责高速生成（评测与 RL 采样都依赖它）；底层是硬件与运行时层。理解分层的好处是：出问题时能快速定位到层，换工具时知道替换的是哪一层。

4. 环境管理最佳实践：隔离与版本锁定

环境管理的两条铁律：隔离（每个项目一个独立环境，绝不污染 base）与锁定（环境跑通立即固化版本清单，与代码一起提交）。后训练栈的依赖树又深又动态——transformers、trl、peft、vllm 各自都有快速的版本迭代，某些接口甚至每隔几个版本就改名（如 TRL 0.20 把 max_seq_length 改名为 max_length）——不锁版本意味着你的实验在半年后无法复现，也意味着别人无法帮你 debug。conda 与 venv/uv 都能满足要求：conda 在需要安装非 Python 依赖（如 ffmpeg、特定 CUDA 工具链）时更省心，uv 以极快的解析速度和更严格的锁文件（uv.lock）正在成为新项目的流行选择；本书统一用 Miniconda 演示，读者迁移到 uv 没有任何障碍。

env_setup.sh（bash） 
# ① 建议用 Miniconda/Miniforge 管理多套互不污染的环境
conda create -n posttrain python=3.11 -y
conda activate posttrain

# ② 训练栈一律装进独立环境，绝不污染 base
pip install -r requirements.txt

# ③ 复现锁定：环境跑通后立即固化，与代码一起提交到仓库
pip freeze > requirements.lock
conda env export > environment.yml

# ④ 新机器一键还原（先装好驱动，再执行）
conda env create -f environment.yml && conda activate posttrain
requirements.txt

三点解释。其一，这份组合围绕 torch 2.6.0 + cu124 构建，vllm 0.8.5 与之匹配（vLLM 对 torch 版本极其敏感，混装是常见翻车点）；flash-attn 提供 wheel 安装，避免本地编译对 nvcc 的依赖。其二，pip freeze 的输出包含所有间接依赖，比手写 requirements.txt 更"硬"，两者建议都入库：手写文件表达意图（直接依赖），lock 文件表达事实（完整解析结果）。其三，Jupyter 用户注意：内核必须指向 posttrain 环境的 Python（python -m ipykernel install --user --name posttrain），否则笔记本会静默使用错误环境——这是"我明明装了为什么 import 不到"的头号原因。

几个值得养成的日常习惯：动手前用 conda env list 确认当前环境；用 pip list --outdated 周期性审视依赖，但升级永远在独立分支上先跑通冒烟测试再合入；把模型缓存指到大容量数据盘（如 export HF_HOME=/data/hf_cache），避免缓存悄悄写满系统盘——这两类"磁盘意外"在 0.5B 小模型阶段无害，到 32B 模型阶段就意味着数小时的重新下载。

💡 实践建议：把"环境健康检查"写进仓库

在仓库放一个 10 行的 check_env.py（打印 torch/CUDA/各包版本与 GPU 名称），README 要求"任何 issue 必须附上它的输出"。这一个习惯能过滤掉 80% 的环境类求助，也是团队协作的好传统。

小结：隔离与锁定是可复现性的地基——每个项目一套环境，跑通即 freeze，升级先过冒烟测试。

5. 10 分钟冒烟测试：第一个 SFT

现在把整条链路走通。冒烟测试的目标不是训练效果，而是验证"环境 → 数据 → 训练 → 保存 → 推理"五个环节全部健康——任何一个环节出错，都应该在本阶段暴露，而不是等到你用 70B 模型训练三天后才发现。选型刻意取最小：Qwen2.5-0.5B-Instruct（0.5B 参数，下载约 1 GB，任何 8 GB 以上显存的卡可跑）加 2000 条多轮对话样本，1 个 epoch 大约需要几分钟。

MODEL_ID = "Qwen/Qwen2.5-0.5B-Instruct"   # 0.5B，含现成对话模板

def main():
    tok = AutoTokenizer.from_pretrained(MODEL_ID)
    model = AutoModelForCausalLM.from_pretrained(
        MODEL_ID,
        torch_dtype=torch.bfloat16,   # 消费级卡建议 bf16（40 系后硬件原生支持）
        device_map="auto",
    )

    # trl-lib/Capybara：多轮对话数据集（messages 字段），取前 2000 条做冒烟
    ds = load_dataset("trl-lib/Capybara", split="train[:2000]")

    cfg = SFTConfig(
        output_dir="smoke_sft_out",
        num_train_epochs=1,           # 冒烟只为跑通，不求效果
        per_device_train_batch_size=4,
        gradient_accumulation_steps=4,  # 等效 batch = 16
        learning_rate=2e-5,           # SFT 全量微调的常见量级
        logging_steps=10,
        bf16=True,
        report_to="none",             # 不接 wandb/tensorboard
        seed=42,
        # 序列截断：TRL 0.20+ 参数名为 max_length=1024；0.17 版本为 max_seq_length
    )

    trainer = SFTTrainer(
        model=model,
        args=cfg,
        train_dataset=ds,             # 含 messages 列时，TRL 自动套用模型对话模板
        processing_class=tok,         # 旧版 TRL 此参数名为 tokenizer
    )
    trainer.train()
    trainer.save_model("smoke_sft_out/final")
    print("冒烟测试通过：loss 应从约 2.x 降到 1.x。")

if __name__ == "__main__":
    main()

运行 python smoke_sft.py，健康的表现是：日志每 10 步打印一次 loss，数值从 2.0~2.5 附近逐步下降到 1.5 上下（数据集不同会有浮动，关键是单调下降趋势）；训练结束后 smoke_sft_out/final 目录里有完整的模型与分词器文件。第一次运行最常见的三种失败都值得预演：Connection error 或下载卡住——Hugging Face 直连问题，回到第 2 节设置 HF_ENDPOINT 后重跑；CUDA out of memory——按第 7 节的顺序减 batch、加梯度累积；数据或模板相关报错——先确认数据集含 messages 字段、tokenizer 带聊天模板。至于日志怎么读，冒烟场景下只需关注三件事：loss 是否开始下降、是否出现 NaN、显存峰值离上限还有多少余量；loss 曲线的深入解读（欠拟合、过拟合、灾难性遗忘的信号）在第 16 章展开。最后一步验证：用训练目录加载模型，确认生成管道端到端可用。

📘 关于冒烟测试的三点说明

其一，首次运行会下载约 1 GB 模型与几十 MB 数据，国内读者务必先设置 HF_ENDPOINT=https://hf-mirror.com，或改用 ModelScope 下载 Qwen 模型。其二，TRL 对话数据的约定是数据集含 messages 列（role/content 结构），SFTTrainer 会自动套用 tokenizer 内置的聊天模板——模板机制本身的细节是 第 15 章的主题。其三，如果你的卡只有 8 GB 显存且 OOM，把 batch size 降到 1、加 gradient_accumulation_steps=16，0.5B 模型在任何卡上都能跑动。

小结：冒烟测试的意义在于把"环境是否健康"变成 10 分钟内的确定答案——闭环通了，后面所有章节的实验才有了可信的出发点。

6. Docker 与云 GPU：没有本地卡怎么办

没有合适的本地显卡不是问题，租用云端 GPU 已是常态，Docker 则是让"我这里是好的"到"云上也是好的"的关键。Docker 镜像把 CUDA 运行时、PyTorch 与全部依赖固化成一个不可变的单元，配合 NVIDIA Container Toolkit（宿主机只需装驱动，--gpus all 即可把 GPU 透传给容器），能彻底消灭"云上环境与本地不一致"这类问题。下面是一个最小可用的训练镜像。

镜像选型有两派。极简派从 pytorch/pytorch 官方镜像出发自行安装依赖（如上），体积可控、版本自由，适合个人与本书的实验；全家桶派直接使用 NVIDIA NGC 的 PyTorch 容器或各训练框架发布的官方镜像，内置调优好的 CUDA/cuDNN/NCCL 组合，适合专业卡与生产环境。无论哪一派，都建议把模型缓存（/root/.cache/huggingface）与数据目录挂载为宿主机卷：容器可以随时销毁，数据与缓存必须留下来——这也是云环境与本地环境在工程习惯上的最大差异。

云 GPU 平台的选择主要看三件事：价格、镜像生态与数据安全。下表给出类型化对比（价格为写作时点的量级参考，波动较大，以各官网实时报价为准）。共同注意事项：按量计费的实例释放即数据消失——把数据集与 checkpoint 定期同步回对象存储（OSS/S3）或本地；AutoDL 这类平台提供按 GB 计费的持久网盘，长项目建议启用。

🚨 重要警告：云上环境的安全纪律

第一，绝不把 Hugging Face token、API key、SSH 私钥写进 Dockerfile 或 ENV 指令——镜像层是永久记录，用运行时挂载或密钥管理服务注入。第二，公开分享镜像前用 docker history 检查各层是否夹带敏感文件。第三，云实例上的数据默认随实例释放而消失，也默认不受你公司安全策略保护：商业数据上云前确认合规边界。

7. OOM 与驱动问题：快速排查清单

环境问题的表现千变万化，但 90% 落在三类：显卡不可见、显存不够（OOM）、多卡通信卡死。遇到问题按下面的顺序执行，大多数能在几分钟内定位。

  1. 显卡与驱动可见性：nvidia-smi 无输出说明驱动层就没通（新装机先装驱动；WSL2 用户确认 Windows 侧已装驱动）；右上角的 "CUDA Version" 是该驱动支持的上限，不是已安装的版本。
  2. PyTorch 侧自检：确认 torch.cuda.is_available() 为 True、torch.version.cuda 与驱动匹配；若报 no kernel image，说明 wheel 的 CUDA 构建不含你的显卡架构（典型：RTX 50 系用了 cu124 wheel），换 cu128。
  3. 显存占用排查：nvidia-smi --query-compute-apps=pid,used_memory --format=csv 查看是谁占着显存——云机上残留的僵尸进程（Jupyter 内核、上一个未退出的训练）是头号惯犯。
  4. OOM 处置顺序：减 batch size 并加梯度累积 → 开启 gradient_checkpointing → 缩短 max_length → 换 LoRA/QLoRA → ZeRO-3 / CPU offload（第 43 章）。按此顺序逐级升级，不要一上来就上分布式。
  5. 多卡通信卡死：优先检查共享内存（容器内 --shm-size=64g）；设 NCCL_DEBUG=INFO 看卡在哪一步；PCIe 多卡机器可试 export NCCL_P2P_DISABLE=1 排除 P2P 问题。
  6. 硬件级故障：sudo dmesg -T | grep -i -E "xid|nvrm" 查看 Xid 错误码（如 Xid 79 常提示显存故障）——云机上遇到应立即换实例而不是反复重试。
  7. loss 异常：NaN 通常是学习率过大或 fp16 数值溢出——降到 2e-5 以下、统一用 bf16；loss 纹丝不动则先查学习率是否真的生效、数据是否为空。

8. 本章小结

  • 硬件选型的三要素：显存决定能不能跑（全量微调约 16 字节/参数，7B 即约 112 GB）、算力决定多快、互联决定多卡扩展效率。
  • LoRA/QLoRA 是消费级显卡的入场券：QLoRA 已实现在单张 48 GB 卡上微调 65B 模型（arXiv:2305.14314）；RL 后训练显存需求显著高于 SFT，需为参考模型与采样引擎留余量。
  • pip 安装的 PyTorch 自带 CUDA 运行时，只看驱动版本（CUDA 12 系基线 Linux ≥ 525.60.13）；RTX 50 系必须 cu128 构建；只有源码编译扩展才需要 CUDA Toolkit。
  • 工具栈五层架构：方法算法层、训练框架层（TRL/LLaMA-Factory）、分布式层（DeepSpeed/FSDP）、推理 rollout 层（vLLM/SGLang）、硬件运行时层；选型口诀"学习用 TRL、交付用配置化框架、研究级 RL 用 verl/OpenRLHF"。
  • 环境管理两条铁律：每项目独立环境 + 跑通即锁定版本；requirements.txt 表达意图、pip freeze 表达事实，双双入库。
  • 冒烟测试（Qwen2.5-0.5B + TRL SFTTrainer + 2000 条样本）验证"环境→数据→训练→保存→推理"闭环，是后续所有实验的地基；云上训练遵守数据持久化与密钥安全两条纪律。
  • 排查口诀：由外向内分层定位——驱动可见性、运行时匹配、显存占用、通信、数值稳定性。
🧠 自测题（点击展开答案）
问题 1：为什么通过 pip 安装的 PyTorch 通常不需要单独安装 CUDA Toolkit？什么情况下才需要？

因为官方 PyPI wheel 把完整 CUDA 运行时库打包在轮子里，运行期只依赖 NVIDIA 驱动（CUDA 12 系列靠次版本兼容机制，驱动达到 12.0 基线即可）。需要单独安装 CUDA Toolkit（含 nvcc 编译器）的情况只有一类：从源码编译 CUDA 扩展（如自行编译 flash-attn），此时 toolkit 版本必须与 PyTorch wheel 的 CUDA 构建一致；用预编译 wheel 或官方 Docker 镜像即可绕开。

问题 2：7B 模型分别用全量 SFT（AdamW 混合精度）、LoRA、QLoRA 微调，显存的大头各是什么？

全量 SFT 的大头是优化器相关状态：按每参数约 16 字节计（bf16 权重 2 + bf16 梯度 2 + fp32 主权重 4 + 一阶/二阶动量各 4），7B 即约 112 GB，再加激活值，需 2×A100-80G 起步。LoRA 冻结原权重，大头变成 bf16 基座（约 14 GB）加很小的适配器与优化器状态，24 GB 单卡可跑。QLoRA 把基座量化为 NF4（约 3.5 GB），大头缩到量化权重加少量适配器开销，16 GB 级单卡即可，QLoRA 论文因此能在单张 48 GB 卡上微调 65B 模型。

问题 3：冒烟测试为什么选 0.5B 模型、2000 条样本、只跑 1 个 epoch？它验证什么、不验证什么？

目标是把"环境—数据—训练—保存—推理"闭环的验证时间压到 10 分钟以内：小模型把失败归因聚焦到环境与流程（依赖冲突、模板错位、数据格式），而非超参与规模。它验证的是链路健康——CUDA 可用、数据管道正确、模板套用正常、优化在推进、权重能落盘、生成端到端可用；它不验证训练效果（2000 条样本不会带来能力提升），因此 loss 下降趋势正常即通过，不应期待模型"变聪明"。

问题 4：云上租 GPU 训练，最重要的两条安全纪律是什么？分别对应什么操作？

第一条是数据持久化：按量实例释放即数据消失，必须把数据集与 checkpoint 定期同步回对象存储或本地网盘，长任务还需支持断点续训（竞价实例可能被回收）。第二条是密钥安全：绝不把 token、API key 写进 Dockerfile 或 ENV——镜像层是永久记录，应通过运行时挂载或密钥服务注入，公开镜像前用 docker history 检查各层。此外商业数据上云前要确认合规边界。
