第 13 章 · SFT 损失实现细节

SFT 的算法只有一行负对数似然，工程实现却埋着上百行决定成败的细节：shift 对齐、ignore_index、loss mask 策略、packing 与块对角注意力、长序列的 logits 显存。本章把"从一段多轮对话到 loss 标量"的完整链路逐站拆开，给出手写 collator、TRL 与 LLaMA-Factory 的对应配置，以及一份"训练正常却越训越笨"的静默 bug 清单。

1. 从一行公式到一次"正确"的训练

第 12 章给出了监督微调（Supervised Fine-Tuning, SFT）的目标函数：给定指令 \(x\) 与目标回答 \(y\)，最小化回答部分的负对数似然

\[ \mathcal{L}_{\mathrm{SFT}}(\theta) = -\frac{1}{\sum_i |r_i|}\sum_{i}\sum_{t \in r_i} \log \pi_\theta\!\left(y_t \mid x_i, y_{t < t}\right) \]

其中 \(r_i\) 表示第 \(i\) 条样本中参与训练的 token 集合。这行公式在纸面上毫无争议，但在代码里，它的每一次落地都要回答四个实现问题：预测目标与 logits 如何对齐（shift）；哪些 token 算 \(r_i\) 的成员（loss mask）；多条样本如何拼成一个 batch（padding 与 packing）；分母是按 token 平均还是按样本平均（loss 归一化）。这四个问题每一个都有 2~4 种选项，组合起来就是几十种实现——其中大多数在数值上"看起来都在正常下降"，只有少数是真正对的。

更麻烦的是，损失实现的错误几乎全是静默错误：它不会抛异常，loss 曲线平滑下降，评测分数却明显低于预期。最典型的三类是：prompt 意外参与训练（模型学会复述问题）、EOS 没进训练目标（生成停不下来）、特殊 token 被 BPE 拆碎（模板边界失真）。第 15 章会专门处理模板一侧，本章聚焦损失一侧，按数据流动顺序讲完整条链路：

2. 逐 token 交叉熵：shift、reshape 与 ignore_index

因果语言模型在位置 \(i\) 的输出，是对第 \(i+1\) 个 token 的预测分布。这意味着 logits 与"预测目标"天然错开一位：要把 \(T\) 个位置的 logits 变成 \(T\) 个监督信号，必须把标签序列向左移一位——位置 \(i\) 的 logits 对齐到 labels 的第 \(i+1\) 位。这一步 shift 是所有 CE 实现的起点，也是 off-by-one bug 的高发区。先看对齐关系：

有了对齐关系，逐 token 交叉熵就可以完全向量化：把 \(B \times (T-1)\) 个位置的 logits 摊平成 \((B(T-1)) \times V\) 的矩阵，直接调用一次 交叉熵（Cross Entropy）。下面这段代码就是 SFT 损失的全部数学内容，任何框架里的实现都是它的变体：

sft_loss.py — 向量化 SFT 损失 
import torch
import torch.nn.functional as F

def sft_loss(logits: torch.Tensor, labels: torch.Tensor) -> torch.Tensor:
    """逐 token 交叉熵的向量化实现。
    logits: [B, T, V]  模型输出（未 softmax）
    labels: [B, T]     与 input_ids 同长同位；不训练的位置已填 -100
    """
    B, T, V = logits.shape
    # 关键一步：logits 取前 T-1 个位置，labels 取后 T-1 个位置，完成错位对齐
    shift_logits = logits[:, :-1, :].contiguous()        # [B, T-1, V] 预测方
    shift_labels = labels[:, 1:].contiguous()             # [B, T-1]    监督方
    # 摊平后一次算完所有位置的 CE；ignore_index=-100 的位置不参与求和与平均
    loss = F.cross_entropy(
        shift_logits.view(-1, V),                         # [B*(T-1), V]
        shift_labels.view(-1),                            # [B*(T-1)]
        ignore_index=-100,
        reduction="mean",                                 # 对"有效 token"求平均
    )
    return loss

# 等价的手写版本（帮助理解 reduction 语义）：
# valid = shift_labels.view(-1) != -100
# per_tok = F.cross_entropy(shift_logits.view(-1, V), shift_labels.view(-1),
#                           reduction="none")
# loss = per_tok[valid].mean()      # 分母 = 有效 token 数，而不是 B*(T-1)

三个细节值得说透。第一，为什么偏偏是 -100：PyTorch 的 F.cross_entropy 默认 ignore_index=-100，词表 ID 永远非负，所以 -100 天然不会与任何合法 token 冲突；你也可以换成别的负数，但必须同步传 ignore_index 参数，且张量运算库、拼接函数都要一致——没有理由偏离默认值。第二，reduction="mean" 的分母是"有效 token 数"，不是 \(B \times T\)：被 mask 的位置既不贡献分子也不贡献分母，这正是第 4 节"packing 污染 loss 统计"的根源——不同样本的有效 token 数不同，token 级平均等于变相按长度加权。第三，labels 里保留的是"当前位"的 token，不是"下一位"：mask 应该按 input_ids 的位置构造（哪个 token 是回答，哪个位置才训练），shift 交给 CE；先手动 shift 再 mask 是最常见的 double-shift 错误来源。

📘 概念辨析：HuggingFace 模型的 labels 约定

HF 的 AutoModelForCausalLM.forward(labels=…) 内部已经做了 shift：传入的 labels 应与 input_ids 同长同位（模型内部取 labels[..., 1:] 与 logits[..., :-1] 对齐）。因此自写 collator 时直接在"当前位"填 -100 即可；如果你照抄了训练循环里 labels[:, 1:] 的写法再传给模型，就发生了双重 shift，监督目标整体右移一格——症状是 loss 略低、模型学到的条件分布整体错位一个 token。自己手写 loss（如上面的 sft_loss）时才需要显式 shift。

本节小结：逐 token CE = 错位对齐 + 摊平 + ignore_index=-100 的向量求平均；"labels 同位存放、shift 交给框架"是避免 off-by-one 的最稳约定。

3. Loss Masking 四种策略：到底训哪些 token

"训哪些 token"是 SFT 里影响最大的实现决策，没有之一。同一条多轮对话数据（system + 两轮 user/assistant），按训练范围可以划出四种策略，它们改变的是有效监督信号的数量、来源与目标分布：

  • 策略 A：只训 response——只有 assistant 轮的内容（含收尾的 im_end/EOS）参与训练，system 与 user 全部 mask。这是 InstructGPT 以来最主流的做法，目标分布与推理时"给定上下文生成回答"完全一致。
  • 策略 B：全序列训练——包括 system 和 user 在内全部算 loss。等价于把对话当成普通语料做语言建模，监督信号最多，但模型会用容量去学"如何写用户的问题"。
  • 策略 C：多轮 per-turn 控制——逐轮决定训不训：典型变体是只训最后一轮 assistant（LLaMA-Factory 的 mask_history），或对后面的轮次加权。适合"历史轮质量参差、但最后一轮是精修答案"的数据。
  • 策略 D：system 不训、其余全训——system 是行为说明书而非要复述的内容，mask 掉；user 与 assistant 都训练。介于 A、B 之间，常见于数据量小、想榨干监督信号的场合。

四种策略的取舍核心是"监督信号的纯度换数量"。把范围铺得越宽（B、D），单条样本提供的梯度信号越多、loss 下降越快，但优化方向里混入了"生成用户输入"的任务；收敛到"只训 response"（A），目标分布最纯，代价是有效 token 数变少、对数据量更敏感。实证结果也支持"因数据而异"：Flan Collection 的消融发现，在大规模多任务混合上 packing 后不加 mask 对多数任务无害，但对话类数据不 mask 会明显变差（Longpre et al., 2023）；LIMA 只用 1000 条精选数据训练 response，说明高质量、目标对齐的信号比信号数量更重要（Zhou et al., 2023）。此外无论选哪种，assistant 轮的收尾 token 必须在训练范围内——它承担"学会停止"的职责，mask 掉它是"生成停不下来"的头号原因。

策略训练范围有效信号量主要风险 / 副作用典型适用场景
A 只训 responseassistant 轮内容 + 收尾 token低数据需求量大；user 写得好坏不学指令跟随、对话助手（默认首选）
B 全序列全部 token高容量分给"生成提问"；对话数据上易学坏领域继续预训练、语料稀少的风格迁移

💡 实践建议：用"loss 差值"快速审计 mask

审计一个陌生脚本的 mask 是否生效，最便宜的测试是构造一条已知样本：把 assistant 回答整段替换成一个从未见过的随机 token 串。如果第 1 步 loss 远高于该模型词表的 \(\ln |V|\)（如 15 万词表约 11.9），说明随机 token 确实被算进 loss（mask 生效）；再检查把回答整段 mask 掉后 loss 是否变成"nan 或报错"——如果 mask 后仍能算出很低的 loss，说明 prompt 也在参与训练。

本节小结：mask 策略决定模型学"生成回答"还是"复述全篇"；默认只训 response 并保留收尾 token，切换策略前先想清楚目标分布是否还与推理一致。

4. Packing：序列拼接、块对角注意力与 loss 统计污染

一个 batch 里的样本长度参差（几百到几千 token），朴素的右 padding 会把大量算力浪费在 pad 位上——经验上浪费 20%~40% 的计算很常见。序列拼接训练（Packing）的解法是：把多条样本首尾相接拼成长度恰好为 max_length 的"块"，一个 batch 的每一行都是"满"的，彻底消灭 padding。这个思想来自预训练语料的组织方式（T5、GPT 系预训练都对语料做拼接，Raffel et al., 2020），SFT 把它搬过来时却多了一个预训练没有的问题：SFT 样本之间互相独立，拼在一起后如果注意力畅通无阻，样本 B 的回答会"看见"样本 A 的内容——既污染训练信号，也让推理与训练的条件分布不一致。

因此 SFT 的 packing 必须配合块对角注意力（Block-Diagonal Attention）：注意力矩阵只在每个样本内部允许交互，样本之间的块全部置为 \(-\infty\)。直观结构如下：

为什么必须块对角：如果不挡，样本间的注意力等价于"每条样本的数据分布被同一个 batch 里的其他样本污染"，模型会学到虚假的跨样本依赖；此外 padding-free 拼接后 position_ids、RoPE 的相对位置也要在样本内归零，否则位置编码同样串味。工程上没人显式构造 \(N \times N\) 的大掩码（32k 上下文的掩码矩阵本身就要 GB 级内存），标准做法是 FlashAttention 的 变长接口（varlen API）：传一个 cu_seqlens（累积长度）数组，kernel 按段计算注意力，显存与算力都只花在真实 token 上（Dao et al., 2023）。HuggingFace 的 DataCollatorWithFlattening 与 TRL 的 packing_strategy="bfd"（best-fit-decreasing 装箱）走的就是这条路。

collator = DataCollatorWithFlattening(tokenizer=tok, return_position_ids=True)

feats = [{"input_ids": e["input_ids"], "labels": e["labels"]} for e in batch_rows]

packing 的第二重坑：loss 统计被污染。拼接本身不改变数学目标，但它改变了"哪些梯度共享一个分母"。token 级平均（reduction="mean"）下，一个优化步的 loss 是整个 batch 所有有效 token 的平均——长样本贡献的梯度假日权重与它的长度成正比；packing 把样本边界抹掉后，这种按长度加权被进一步放大且更隐蔽（例如 1 条 8k 的样本与 8 条 1k 的样本在 token 平均下权重相差 8 倍）。样本级平均（每条样本先对自身 token 求平均，再对样本求平均）则让每条数据"一人一票"，对小数据、精修数据更公平，代价是实现复杂（要在 loss 里保留样本维度）。两种口径没有绝对对错，但必须知道自己在用哪种：当你从"逐样本循环训练"切到"packing 大 batch 训练"后发现最优学习率变了，多半就是这个口径切换在起作用。

归一化口径公式隐含的加权方式适用场景与风险
token 级平均（框架默认）\(\mathcal{L} = -\frac{1}{N_{\mathrm{tok}}}\sum \log p\)长样本权重大（按 token 数）大数据、长度分布均匀时最稳；长度方差大时被长样本主导，packing 下更明显
样本级平均\(\mathcal{L} = -\frac{1}{N_{\mathrm{seq}}}\sum_i \frac{1}{|r_i|}\sum_{t \in r_i}\log p\)每条样本等权精修小数据、混长度数据；需自写 loss，注意梯度尺度变化
轮次级平均（多轮扩展）每个 assistant 轮内平均后再平均每轮等权多轮对话防"长回答轮垄断"；实现成本最高
表 13-2：loss 归一化口径对比。切换口径后学习率通常需要重新搜索，两者不可混用比较
⚠️ 常见误区：开了 packing 就默认安全

不是所有框架的 packing 都带块对角注意力。历史上不少实现（包括一些知名项目的早期版本）用"朴素拼接 + 普通因果注意力"，即预训练式 packing：训练照常收敛、loss 正常下降，但样本间互相泄漏，模型在多轮对话与长上下文任务上的表现悄悄劣化。核对方法：看框架文档是否明确写着 block-diagonal / varlen / FlashAttention-2（如 TRL 的 packing_strategy="bfd"、LLaMA-Factory 的 neat_packing: true）；只写 "packing" 而无注意力说明的要存疑。

本节小结：packing 消灭 padding 但引入两个新问题——注意力必须块对角（varlen 实现）、loss 归一化口径决定样本权重；两者都是静默影响效果的旋钮。

5. assistant_masks 与多轮对话的 loss 设计

第 3 节的 mask 策略落到实现层，核心是"assistant 轮在 token 序列里占据哪些区间"。手写区间容易错位，HF tokenizer 从 4.44 起提供了官方机制：apply_chat_template(..., return_assistant_tokens_mask=True) 返回一个 0/1 的 assistant_masks，前提是对话模板用 {% generation %}...{% endgeneration %} 块标出了"assistant 生成的内容"。模板作者用 generation 标记声明边界，tokenzier 负责把边界翻译成 token 级掩码——这正是模板与 loss mask 的联动点（第 15 章会回到这个话题）。

assistant_mask_demo.py 
from transformers import AutoTokenizer

tok = AutoTokenizer.from_pretrained("meta-llama/Llama-3.1-8B-Instruct")
messages = [
    {"role": "system", "content": "You are a helpful assistant."},
    {"role": "user", "content": "写一首关于秋天的短诗。"},
    {"role": "assistant", "content": "落叶铺满小径，风把夏天折叠收好。"},
]
enc = tok.apply_chat_template(
    messages,
    add_generation_prompt=False,
    return_dict=True,                     # 返回 dict 而不是裸张量
    return_assistant_tokens_mask=True,    # 关键：返回 assistant_masks
)
input_ids = enc["input_ids"]              # List[int]
mask      = enc["assistant_masks"]        # List[bool]，1=assistant 生成内容
# 训练标签：同位存放，mask 为 0 的位置填 -100（shift 交给模型内部）
labels = [tok_id if m else -100 for tok_id, m in zip(input_ids, mask)]
# 注意：若模板没有 {% generation %} 块，这里会直接抛 ValueError，
# 不少模板（如早期 Qwen）需要自己补写 generation 标记

多轮对话还有一层设计自由度：每个 assistant 轮都训，还是只训最后一轮，或者加权。三者对应第 3 节的策略 A 与 C 的不同变体。决策依据是数据的"历史可信度"：如果历史轮是精标数据（模型的历史行为就是目标行为），逐轮训练最大化信号；如果历史轮来自弱模型回放（self-instruct 类管线），历史行为本身是要被淘汰的旧策略，只训最后一轮（或对后面轮次更高权重）能让目标分布更接近"以当前模型的历史为上下文生成新回答"，同时缓解多轮数据里"长回答轮垄断梯度"的问题。工程上不需要发明新机制：把 0/1 的 assistant_masks 换成每轮的权重数组即可，CE 侧用逐 token 加权实现（等价于对 reduction="none" 的结果乘权重再归一）。

📘 与 TRL 的对应关系

TRL 对"只训 response"提供了两条路线：assistant_only_loss=True（对话数据 + 带 generation 标记的模板，token 级精确 mask）与 completion_only_loss（prompt-completion 格式数据，按"提示/补全"两段 mask，配合 DataCollatorForCompletionOnlyLM 可用 response 前缀定位边界）。前者的边界由模板作者声明，后者由 response 模板串匹配定位——第 9 节会讲到，后者有"前导空格导致的 tokenize 不一致"经典坑。第 7 节给出两者的完整配置示例。

本节小结：优先用 tokenizer 的 assistant_masks 拿 token 级边界，把"训哪些轮"做成权重而非硬编码；模板缺少 generation 标记时要么补模板、要么退回 response 前缀匹配方案。

6. 长序列 SFT 的显存细节：logits 才是大头

很多团队把长序列 SFT 的显存瓶颈想成注意力，实际上现代实现里（FlashAttention 让注意力激活随序列长度线性增长），最大的单项激活是输出投影后的 logits：形状 \([B, T, V]\)，其中 \(V\) 是词表大小。做一个估算：Qwen2.5 词表 \(V \approx 15.2\) 万，单条 32k 序列的 bf16 logits 就要 \(32768 \times 152064 \times 2 \approx 9.9\) GB；交叉熵反向还要一份 fp32 梯度与 softmax 中间量，峰值接近 30 GB——这还只是 batch=1 的单条序列。下表给出不同序列长度的量级（按 \(V=152064\)、bf16 前向 / fp32 反向拷贝估算，随实现略有出入）：

序列长度 Tbf16 logits（前向）CE 反向峰值（含 fp32 拷贝，估算）常见后果
4k约 1.2 GB约 3.7 GB通常无感
16k约 4.9 GB约 15 GBbatch=1 已吃掉一张卡的大半
32k约 9.9 GB约 30 GB不做优化基本训不动
64k约 19.9 GB约 60 GB必须用融合/分块交叉熵
表 13-3：单条序列 logits 与交叉熵的显存占用估算（V=152064，bf16 权重；fp32 中间量按 2 倍 bf16 计）。整体显存账的系统性梳理见第 42 章

对策按性价比排序。第一，融合交叉熵（fused / chunked CE）：不一次性物化完整 logits，而是把序列切成块，逐块算"lm_head 投影 + 交叉熵 + 梯度"，显存从 \(O(T \cdot V)\) 降到 \(O(\mathrm{chunk} \cdot V)\)——Liger Kernel 的 fused_linear_cross_entropy 已被 TRL/LLaMA-Factory 以 use_liger_kernel=True（TRL）或 enable_liger_kernel: true（LLaMA-Factory）集成，长序列 SFT 基本必开。第二，梯度检查点（gradient checkpointing）：用重算换激活显存，对 logits 无效但能砍掉其余激活。第三，控制有效词表：如果任务只涉及中英混合语料，可用 logit 裁剪类技巧（只对出现过的 token 子集算 CE）——收益大但实现侵入性强，一般团队到不了这一步。第四，序列并行/上下文并行把单条序列切到多卡（见第 43 章），是 64k 以上场景的最终解法。

💡 实践建议：长序列 SFT 显存优化检查单

按顺序开：FlashAttention-2（注意力激活线性化）→ 梯度检查点 → 融合交叉熵（Liger）→ 8-bit 优化器或分页优化器（优化器状态，第 14 章 QLoRA 同款技巧）→ 序列并行。每开一项记录一次峰值显存与吞吐，别一次全开——融合 CE 与某些自定义注意力实现存在兼容性问题，出问题时无法定位是哪一项引入的。

本节小结：长序列 SFT 的显存大头是 \([B,T,V]\) 的 logits 与 CE 中间量；分块融合 CE 是标配解法，注意力反而早已不是瓶颈。

8. 手写一个正确的 SFT Collator

框架参数覆盖不了的定制需求（逐轮加权、混合数据源、特殊掩码规则）最终都要回到自己写 collator。下面是一个完整可用的多轮 SFT collator，涵盖本章所有要点：逐轮渲染求区间、assistant 区间进 labels、收尾 token 包含在训练范围内、padding 部分全部 -100、以及一个防 BPE 边界漂移的自检方法：

sft_collator.py — 完整手写 SFT Collator 
import torch
from typing import Any

class MultiTurnSFTCollator:
    """把 HF 对话格式的 messages 列表转成 input_ids / labels / attention_mask。

    核心约定（与第 2 节一致）：
    - labels 与 input_ids 同长同位，非训练位置填 -100；
    - shift 交给模型的内部 loss，这里不做任何手动移位；
    - assistant 轮的收尾 token（im_end/EOS 等）包含在训练区间内。
    """

    def __init__(self, tokenizer, max_length: int = 4096,
                 last_turn_only: bool = False, turn_weights: list | None = None):
        self.tok = tokenizer
        self.max_length = max_length
        self.last_turn_only = last_turn_only        # 策略 C：只训最后一轮
        self.turn_weights = turn_weights            # 策略 C'：逐轮加权（可选）

    def encode_example(self, messages: list[dict]) -> dict:
        # ---- 第一步：逐轮渲染，用"前缀 token 长度差"定位每轮的 token 区间 ----
        ids: list[int] = []
        spans: list[tuple[int, int]] = []           # 每轮的 (start, end)
        prev_len = 0
        for i in range(len(messages)):
            partial_ids = self.tok.apply_chat_template(
                messages[: i + 1],                  # 截止到本轮（含本轮全部内容）
                tokenize=True,
                add_special_tokens=False,           # 模板自带 BOS，防止双 BOS（第 15 章）
            )
            new_seg = partial_ids[prev_len:]        # 本轮新增 token（含模板标签）
            start = len(ids)
            ids.extend(new_seg)
            if messages[i]["role"] == "assistant":
                spans.append((start, len(ids)))     # assistant 轮整段（含收尾 token）
            prev_len = len(partial_ids)
        # 截断保护：从尾部截，保证最后的回答轮完整
        if len(ids) > self.max_length:
            overflow = len(ids) - self.max_length
            ids = ids[overflow:]
            spans = [(
                max(0, s - overflow), max(0, e - overflow)
            ) for s, e in spans]
            spans = [sp for sp in spans if sp[1] > sp[0]]
        if not spans:
            raise ValueError("截断后没有任何 assistant 区间，检查 max_length 或数据")
        return {"input_ids": ids, "spans": spans}

    def verify(self, messages: list[dict]) -> None:
        """自检：整段重 tokenize 应与逐轮拼接一致（防 BPE 边界漂移）。
        不一致说明模板边界处存在跨 token 合并，需要改用整段渲染+字符偏移定位。"""
        whole = self.tok.apply_chat_template(messages, tokenize=True,
                                             add_special_tokens=False)
        piece = self.encode_example(messages)["input_ids"]
        assert whole == piece, "逐轮 tokenize 与整段 tokenize 不一致，边界有合并漂移"

    def __call__(self, batch: list[list[dict]]) -> dict[str, torch.Tensor]:
        feats = [self.encode_example(m) for m in batch]
        maxlen = max(len(f["input_ids"]) for f in feats)
        pad_id = self.tok.pad_token_id or self.tok.eos_token_id
        b = len(feats)
        input_ids  = torch.full((b, maxlen), pad_id, dtype=torch.long)
        labels     = torch.full((b, maxlen), -100, dtype=torch.long)
        attn_mask  = torch.zeros((b, maxlen), dtype=torch.long)
        for i, f in enumerate(feats):
            n = len(f["input_ids"])
            ids_t = torch.tensor(f["input_ids"], dtype=torch.long)
            input_ids[i, :n] = ids_t
            attn_mask[i, :n] = 1
            spans = f["spans"][-1:] if self.last_turn_only else f["spans"]
            for j, (s, e) in enumerate(spans):
                w = 1.0
                if self.turn_weights is not None:      # 逐轮加权：labels 存
                    w = self.turn_weights[j]           # 真值，权重交给 loss 侧
                labels[i, s:e] = ids_t[s:e]            # 同位存放，含 im_end
        # 注意：逐轮加权需要自定义 loss（reduction="none" 后乘权重再平均），
        # 上面的 labels 构造只覆盖 0/1 mask；加权版请返回 spans 交给训练循环。
        return {"input_ids": input_ids, "labels": labels, "attention_mask": attn_mask}

这段代码有三个值得咀嚼的设计。第一，"逐轮渲染求差"定位区间：让模板引擎自己决定每轮边界在哪，collator 不 hardcode 任何模板字符串，换模型只换 tokenizer；代价是逐轮调用模板有开销，且依赖"整段 tokenize == 逐段拼接"，所以配了一个 verify 自检——一旦断言失败（BPE 在边界处发生跨轮合并），就要退回"整段渲染 + 用 decode 长度反查区间"的更稳实现。第二，labels 与 input_ids 同位：呼应第 2 节，这里绝不 shift。第三，padding 全 -100 且 pad_token 有兜底：很多基座模型没有 pad_token，用 eos 顶替时务必确认 labels 的 padding 位已被 -100 覆盖，否则模型会学"EOS 之后继续输出 EOS"。

💡 实践建议：把 collator 当作可测试的纯函数

collator 是整个 SFT 管线里最适合单元测试的部件：给它 3~5 条构造样本（含超长截断、单轮、多轮、空 system），断言 labels 的非 -100 区间 decode 回来恰好等于 assistant 内容 + 收尾 token。把这组测试放进 CI，框架升级、模板更换时跑一遍，能拦住本章第 9 节里一半的 bug。

本节小结：手写 collator 的正确性 = 逐轮渲染定位区间 + 同位 labels + padding 全 mask + 边界自检；写完先测，再进训练。

9. 常见 Bug 清单：那些"loss 正常下降但模型变笨"的原因

最后把本章散落的坑收拢成一张排查表。这些 bug 的共同点是静默：不报错、loss 可以下降、粗看评测也能过，但对比消融时分数差一截。排查的通用方法论是"把 batch 解码出来看"：取一个 batch，tokenizer.decode(labels[labels != -100]) 打印，肉眼确认"训练的内容"到底是不是你以为的内容；再打印 decode(input_ids) 与渲染文本逐字符 diff，确认特殊 token 没有被拆碎、BOS 没有重复。除此之外，从 loss 初值也能读出信息：第 1 步 loss 应接近 \(\ln |V|\)（15 万词表约 11.9），明显偏低说明 mask 失效或数据泄漏，明显偏高说明标签错位。

#Bug典型症状根因与修复
1mask 错位：prompt 参与训练模型爱复述问题；loss 偏低区间定位差一位（换行/空格归属）；打印 decode(labels != -100) 对齐到字符级检查

🚨 重要警告：loss 初值是免费的体检报告

训练启动后的第 1 个 loss 值蕴含大量信息：\(\ln |V|\) 附近（15 万词表约 11.9）说明 mask 与对齐基本正常；显著偏低（比如 3~5）几乎必然意味着 prompt 参与训练、数据泄漏进训练集、或者 base 模型本身已在同类数据上训过；出现 nan/inf 先查学习率与 fp16 溢出再查数据。把"第 1 步 loss 落在合理区间"写成训练脚本的启动断言，是成本最低的护栏。

本节小结：SFT 的实现 bug 都是静默的；排查三板斧——解码 labels 肉眼检查、loss 初值 sanity check、collator 单元测试——能覆盖绝大多数事故。

10. 本章小结

  • 向量化 CE：错位对齐（logits[:-1] 对 labels[1:]）+ 摊平 + ignore_index=-100；HF 约定 labels 与 input_ids 同位存放、shift 在模型内部完成，手动 shift 是双重移位 bug 的根源。
  • mask 策略：只训 response（默认）、全序列、只训最后一轮、system 不训各有场景；无论哪种，assistant 收尾 token 必须进训练目标，否则生成停不下来。
  • packing：消灭 padding 的代价是两件配套工程——块对角注意力（FlashAttention varlen / cu_seqlens / position_ids 重置）与 loss 归一化口径的显式选择（token 平均 vs 样本平均）。
  • assistant_masks：优先用 tokenizer 的 generation 标记机制拿 token 级边界，多轮控制做成逐轮权重；模板缺标记时补模板或退回前缀匹配。
  • 长序列显存：瓶颈是 \([B,T,V]\) 的 logits 与 CE 中间量（32k 单条峰值约 30 GB，估算），分块融合 CE（Liger）+ 梯度检查点是标配，64k 以上考虑序列并行。
  • 框架参数：TRL 与 LLaMA-Factory 的 packing/loss 参数一一对应（表 13-4）；用机制理解参数，警惕 assistant_only_loss 的模板前提与朴素 packing 的静默泄漏。
  • 排查三板斧：解码 labels 逐字符检查、第 1 步 loss ≈ \(\ln|V|\) 的 sanity check、collator 单元测试。

本章解决"损失怎么算对"；下一章转向"算多少参数"——LoRA 家族用低秩增量把 70B 模型的全参微调装进单机八卡。之后第 15 章补齐本章反复引用的另一半：对话模板与特殊 token 如何决定 token 边界。

🧠 自测题（点击展开答案）
问题 1：为什么 -100 能安全地充当"不参与训练"的标记？如果改用 0 会发生什么？

词表 ID 永远是非负整数，-100 不可能是任何合法 token，因此 PyTorch 把它设为 cross_entropy 的默认 ignore_index：这些位置既不进入 loss 分子，也不进入平均的分母。若改用 0，它会被当作 ID 为 0 的真实 token（通常是 BOS/unk）参与训练，模型会被迫学习"在这些位置预测 0"，产生大量错误监督信号；除非显式传 ignore_index 并保证该值不与任何合法 ID 冲突，否则没有理由偏离 -100。

问题 2：packing 打开、保持 token 级平均不变，为什么长样本的话语权会变大？给出两种修正思路。

token 级平均的分母是"batch 内有效 token 总数"，梯度按 token 数分配：一条 8k token 的样本对这步梯度的贡献是 1k 样本的 8 倍。packing 让一行装下更多不同长度的样本，长度差异被混合在同一个分母里，加权效应更隐蔽。修正思路一：改用样本级平均——每条样本先对自身有效 token 求平均，再对样本求平均，实现上要保留样本维度做两次归约；思路二：保持 token 平均但对样本按长度重加权（如每 token 权重 1/|r_i|，等效样本平均），或在数据侧做长度分桶均衡。注意切换口径后学习率要重新搜索，且两种口径的 loss 值不可直接比较。

问题 3：一个 15 万词表模型的 SFT，第 1 步 loss 只有 2.1。列出三个最可能的原因与验证方法。

原因一：mask 失效、模型基本没有收到监督或 supervision 泄漏——验证：解码 labels[labels != -100]，确认非 -100 区域是否为空或与输入重复；原因二：训练数据与 base 模型的预训练/既有 SFT 数据高度重叠（模型已经会答）——验证：拿一批未训练过的留出样本看 loss 是否同样偏低，或对数据做去重检查；原因三：实现把 loss 算在了错误的范围上（例如把 ignore_index 错传、或对 logits 做了 softmax 后又过一次 CE）——验证：用第 2 节的独立实现 sft_loss 对同一 batch 复算 loss 比对数值。附带检查：确认不是优化器状态残留（断点续训读错了 checkpoint）。

问题 4：写出一行"把 prompt 带进训练"的典型错误代码，并解释错在哪。

典型错误（针对 HF 模型）：labels = torch.roll(input_ids, shifts=-1, dims=-1); labels[:, -1] = -100 之后再按"labels 与 prompt 对齐"的方式 mask——这里手动做了 shift，而 HF 模型内部还会再做一次 shift，等于双重移位：模型在位置 i 的预测被监督成 token i（而不是 i+1），整个条件分布错位一格。正确做法是 labels 与 input_ids 同位存放，仅在 assistant 区间写真值、其余写 -100，shift 完全交给模型内部的 loss。同理，自己在训练循环里手写 CE 时才需要 logits[:, :-1] 与 labels[:, 1:] 的显式对齐（第 2 节）。
