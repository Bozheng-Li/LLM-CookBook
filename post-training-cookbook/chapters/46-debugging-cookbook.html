大模型后训练是高度复杂的重度工程系统，数以百计的 GPU 节点在高速互联网络上并发协同，任何一个微小的数值波动、代码错位或网络抖动都会引发灾难性的训练事故。从半夜突然喷涌的 NaN / Inf 损失，到突如其来的 CUDA Out of Memory 显存击穿；从训练曲线看似平滑下降但下游评测全面崩溃的离奇现象，再到分布式集群毫无报错的静默死锁。本章以实战一线“死亡现场”为切入点，系统梳理 NaN 诱因与梯度排查路径，深入剖析 Loss Spike（损失突刺）的物理机制与检查点回滚策略；深入 CUDA 显存分配器底层机制、内存快照分析与重计算优化；拆解标签移位、掩码泄露与数据打包边界等隐蔽逻辑 Bug；详解 NCCL 超时、拓扑不匹配与网络死锁诊断，并提供自绘故障决策树与自动化异常监控 Hook 工具代码。

1. 训练故障全景与“死亡现场”分类

在大语言模型后训练工程中，一个训练任务往往需要连续调度数十至上千张 GPU 运转数天乃至数周。与传统单机深度学习任务不同，大模型后训练处于数值稳定性极限与硬件物理边界的剃刀边缘。一旦发生故障，不仅会造成数以万计的算力成本损失，还会直接打乱产品发布节奏。

工程实践中的训练事故通常可以归纳为以下四大类核心“死亡现场”：

  1. 数值崩溃（Numerical Explosion）：训练进行到某一 Step，Loss 瞬间从正常的 1.2 突变为 NaN（Not a Number）或 Inf（Infinity）。由于反向传播链条的级联污染，随后所有权重的梯度被彻底清零或腐蚀，Checkpoint 彻底报废。即使未彻底变成 NaN，偶发出现的 Loss Spike（损失突刺） 也会使模型权重偏离原有收敛轨迹，导致灾难性遗忘。
  2. 显存击穿（Memory Collapse）：任务在稳定运行数千步后，突然在某个包含特定长样本的 Batch 上抛出 CUDA out of memory（OOM），整个分布式进程组瞬间崩溃。由于显存碎片化与动态激活值分配的不确定性，这种崩溃往往具备极强的隐蔽性。
  3. 逻辑污染（Silent Logic Failure）：训练过程极度“平稳”，Loss 稳健收敛，但最终生成的模型在下游基准评测中胡言乱语、重复吐字、甚至连基本的对话格式都无法遵循。排查发现通常是数据预处理阶段的标签对齐偏差（Off-by-one）或掩码覆盖错误。
  4. 通信死锁（Distributed Deadlock）：集群所有 GPU 突然利用率归零，无任何报错抛出，系统陷入无限期的静默停摆，直至 NCCL Watchdog 超时熔断。这通常由于集合通信屏障的跨卡步调失调或底层物理网络丢包导致。

2. Loss 崩塌实录：NaN / Inf 诱因、Loss Spike 与排查路径

在所有训练故障中，Loss 变为 NaN 是最具毁灭性的事故。因为一旦 NaN 渗透进优化器状态（一阶动量和二阶动量），整个模型的权重将彻底不可挽回地被腐蚀。

2.1 NaN 的四大底层根本诱因

  1. 梯度爆炸（Gradient Explosion）：由于学习率（Learning Rate）设置过高、或者在特定 Batch 中存在分布异常的脏数据（例如无意义的超长重复字符序列、乱码数据），反向传播产生的局部梯度极具破坏性。梯度数值瞬间突破上限，加到参数上导致输出无穷大。
  2. 低精度浮点下溢与上溢（FP16 Overflow）：正如第 44 章所述，标准 FP16 的上限仅为 65504。在自注意力算子中，若未缩放的点积 \( Q K^T \) 稍有偏差（例如某个元素的绝对值达到 80 以上），其指数 \( e^{80} pprox 5.5 imes 10^{34} \) 会直接在 FP16 下击穿产生 Inf；而在 Softmax 归一化时，Inf / Inf 便直接产出 NaN。
  3. 交叉熵损失或 KL 散度中的数学非法定义（\(\log(0)\)）：在强化学习偏好对齐（PPO、DPO、GRPO）中，损失函数高度依赖于生成概率的对数比值： \[ \log rac{\pi_ heta(y \mid x)}{\pi_{ ext{ref}}(y \mid x)} = \log \pi_ heta(y \mid x) - \log \pi_{ ext{ref}}(y \mid x) \] 若某个 Token 的预测概率被数值截断为绝对的 0.0，其对数 \( \log(0) = -\infty \)；随后进行算术运算时立即触发 NaN。
  4. 除以零（Division by Zero）：在 LayerNorm 或 RMSNorm 中，分母需要除以特征方差的平方根 \( \sqrt{\sigma^2 + \epsilon} \)。若数值极端导致方差为 0 且 \( \epsilon \) 过小（如设置成 \( 10^{-12} \) 而数据类型为 FP16），会触发除零崩溃。

2.2 Loss Spike（损失突刺）的发生机理与平复策略

很多时候，Loss 并未立即变成 NaN，而是在平稳下降的曲线上突然出现一个高耸的尖峰（Loss Spike，例如从 1.1 暴涨到 8.5），随后虽然慢慢恢复，但模型的下游评测指标却永久性地受损。Meta 在 Llama 2 与 Llama 3 的训练技术报告中均明确指出：Loss Spike 的本质原因是某些极端批次的数据在特定深层 Transformer 层诱发了激活值异常值（Outliers），进而导致反向传播梯度瞬间剧烈震荡。

应对 Loss Spike 的工程化 SOP 包含以下三个黄金原则：

  • 自动回滚与数据剔除（Rollback & Skip）：高频保存 Checkpoint（如每 200 步保存一次轻量权重）。一旦监控系统检测到单步 Loss 突刺超过移动平均值的 3 倍，立即终止当前步，自动回滚至前一个健康 Checkpoint，并精确打印出当前触发异常的 Batch 样本 ID，将其从数据管道中永久剔除后重新加载训练。
  • 自适应学习率缓降（Learning Rate Warmdown）：若在特定步长频繁突刺，说明模型进入了高度非凸的峡谷地带。此时可临时介入将学习率调低 30%~50%，平稳穿过震荡期后再恢复。
  • AdamW 的 \(\epsilon\) 保护：在混合精度下，将优化器的数值稳定项从默认的 eps=1e-8 适度调大至 eps=1e-6 或 1e-5，可以显著降低二阶矩开方除法时的微小抖动。

2.3 自适应全局梯度范数裁剪数学推导

为了在工程层面上彻底封杀 NaN 与梯度突刺，必须配置强制的全局梯度范数裁剪（Global Gradient Norm Clipping）。设模型所有可训练参数的集合为 \( \Theta = \{ heta_1, heta_2, \dots, heta_P\} \)，其对应的梯度张量集合为 \( G = \{g_1, g_2, \dots, g_P\} \)。

全局梯度的 \( L_2 \) 范数计算为：

\[ \|G\|_2 = \sqrt{\sum_{p=1}^P \sum_{i} (g_p^{(i)})^2} \]

若 \( \|G\|_2 > ext{max\_norm} \)，则对每一个参数的梯度张量执行严格等比例收缩：

\[ g_p \leftarrow g_p imes rac{ ext{max\_norm}}{\|G\|_2 + 10^{-6}} \]

在分布式环境（ZeRO-3 / FSDP）下，各个 GPU 仅持有局部参数分片，因此必须在所有 Rank 之间执行一次 All-Reduce(Sum) 聚合局部梯度的平方和，随后各卡开方得到完全相同的全局范数，保证所有切片梯度的缩放因子严格一致。工业界推荐在全参数 SFT 中将 max_grad_norm 设定为 1.0，而在强化学习 PPO/GRPO 中严格收紧至 0.5。

3. OOM 显存溢出终极急救与快照分析

CUDA out of memory 是大模型后训练最令人头痛的随机故障。许多任务在跑了 500 个 Step 后突然毫无征兆地挂掉。其背后的机理不仅是张量尺寸过大，更是 CUDA 显存分配器的底层碎片化问题。

3.1 CUDA 显存分配器（Caching Allocator）与碎片化

PyTorch 并不在每次创建张量时都直接调用底层的 cudaMalloc（该系统调用极其昂贵，涉及主机与 GPU 的上下文切换与同步），而是由内部的 CachingAllocator 预先向显卡申请大段连续显存池。当程序需要释放张量时，显存并不会归还给操作系统，而是留在缓存池中等待下一个张量复用。

然而，大模型输入样本的长度通常是高度动态波动的（例如一条 512，下一条突然达到 4096）。动态申请和释放不同形状的激活张量，会导致显存池中产生大量细碎的显存空洞。当系统需要申请一个 2 GB 的连续激活值张量时，即使当前显存池总计还有 4 GB 的空闲容量，但没有任何一段物理连续空间能够塞进 2 GB，PyTorch 便会抛出令人费解的 OOM 错误：

RuntimeError: CUDA out of memory. Tried to allocate 2.00 GiB (GPU 0; 79.15 GiB total capacity; 72.30 GiB already allocated; 1.45 GiB free; 4.20 GiB reserved in total by PyTorch)
💡 治愈显存碎片的急救环境变量

在启动训练脚本前，显式注入以下环境变量，强制 PyTorch 显存分配器使用更细粒度的分块扩展机制：

bash 
export PYTORCH_CUDA_ALLOC_CONF="expandable_segments:True,max_split_size_mb:128"

其中 expandable_segments:True 是 PyTorch 2.1+ 引入的神级配置，它利用虚拟内存映射，允许将非连续的物理页面拼合成虚拟连续地址，直接消除绝大部分因外部碎片引发的假性 OOM！

3.2 使用 PyTorch Memory Snapshot 定位内存泄漏

当显存持续缓慢增长直至溢出（内存泄漏 Memory Leak）时，肉眼检查代码极其困难。PyTorch 提供了底层的显存追踪快照工具。通过在可疑步长前后开启快照记录，可以将显存分配记录导出为交互式可视化网页文件进行逐行代码定位：

memory_trace.py 
import torch

# 启动显存历史记录（记录最多 100,000 次分配事件）
torch.cuda.memory._record_memory_history(max_entries=100000)

# 执行训练循环...
for step, batch in enumerate(dataloader):
    train_step(batch)
    if step == 10:
        # 导出快照文件，可在 https://pytorch.org/memory_viz 网页中直接拖入查看
        torch.cuda.memory._dump_snapshot("cuda_memory_snapshot.pickle")
        torch.cuda.memory._record_memory_history(enabled=None)
        break

3.3 激活检查点（Activation Checkpointing / 梯度重计算）

解决真性 OOM（即总物理空间确实不足）的最有效武器是激活检查点（Gradient Checkpointing）。在标准的反向传播中，前向计算产生的所有中间隐藏状态（Hidden States）都必须暂存在显存中；而开启梯度重计算后，前向传播仅保存每个 Transformer Block 的输入 Tensor，丢弃所有 Block 内部细节。反向传播回传到该 Block 时，重新执行一次局部的微前向计算。

正如第 42 章推导，这仅仅增加了 33% 的计算量（多做一次前向），却能将激活值显存暴降 70%~85%！在千亿模型或 8k 以上长上下文微调中，激活检查点是必须开启的强制选项。

4. 隐蔽逻辑 Bug：Loss 下降但评测崩塌

相较于直接崩溃的硬性报错，更可怕的是无报错的静默逻辑 Bug：训练 Loss 按照教科书般的轨迹平滑下降，但训练完成后评估模型，发现其输出逻辑全无，甚至只会无限重复单个词。

4.1 离谱的“标签移位（Off-by-One）”错误

在因果自回归语言模型（Causal LM）中，目标是根据第 \( t \) 个 Token 预测第 \( t+1 \) 个 Token。因此，模型输出的未归一化对数概率（Logits）必须与标签（Labels）向后错开一位对齐：

\[ ext{Inputs} = [x_1, x_2, \dots, x_{T-1}], \quad ext{Targets} = [x_2, x_3, \dots, x_T] \]

在原生代码中，标准的计算方式必须是：

shift_labels.py 
# 正确的因果移位：去除 logits 最后一个位置，去除 labels 第一个位置
shift_logits = logits[..., :-1, :].contiguous()
shift_labels = labels[..., 1:].contiguous()
loss = loss_fct(shift_logits.view(-1, shift_logits.size(-1)), shift_labels.view(-1))

很多初学者错误地写成了对齐匹配：loss = loss_fct(logits, labels)。此时模型学的不是“预测下一个词”，而是“机械记忆当前输入的词”！由于残差连接的存在，模型会迅速找到作弊捷径：将输入词直接复制到输出，Loss 迅速下降到极低的 0.1 甚至更小。但一旦进入实际推理生成，模型丧失了任何生成下文的能力，只会变成一个原样复读机。

4.2 掩码泄露：Prompt 未被屏蔽为 -100

在监督微调（SFT）中，经典的标准是仅对 Assistant 的回答（Response）部分计算 Loss，而必须将 User 的提示词（Prompt）部分使用 -100 进行掩码忽略：

Token 序列 <|user|> 你好 <|assistant|> 很高兴 为您 服务 <|eos|>
正确 Labels -100 -100 -100 很高兴 为您 服务 <|eos|>
错误 Labels（泄露） <|user|> 你好 <|assistant|> 很高兴 为您 服务 <|eos|>
表 46-1：SFT 训练中 Prompt 掩码正确与错误设置对比

若 Prompt 未被掩码，由于 Prompt 往往占据了文本长度的 70% 以上，模型会耗费绝大部分更新梯度去拟合静态的用户提问甚至系统提示词（System Prompt），导致对核心推理逻辑的拟合能力严重退化。

4.3 多样本打包（Packing）边界跨样本注意力污染

为了提升吞吐，现代后训练广泛采用 样本打包（Sequence Packing / Sample Multiplexing）：将多个短对话用特定的结束符（如 <|eot_id|>）拼接成一条固定长度为 4096 或 8192 的长序列。若直接对该序列运行标准因果注意力，排在后面的样本会通过自注意力矩阵“看到”排在前面的完全无关的样本内容，产生严重的跨样本语义交叉污染！

急救规范：在使用 Packing 时，必须传入切分边界索引（如 cu_seqlens 累积序列长度），并强制调用支持分块因果掩码的 FlashAttention VarLen 接口（flash_attn_varlen_func），确保样本间注意力严格物理隔离。

5. 多卡与跨机通信故障排查：NCCL 死锁与网络诊断

在大规模分布式训练（ZeRO-3 / FSDP / TP / PP）中，网络通信故障排查难度最大。最常见的报错是：

torch.distributed.DistBackendError: NCCL error in: /pytorch/torch/csrc/distributed/c10d/ProcessGroupNCCL.cpp, 
Watchdog caught collective operation timeout: WorkNCCL(OpId=42, Timeout(ms)=1800000) timed out after 1800 seconds

5.1 导致 NCCL 超时的三大元凶

  1. Rank 负载极度不均衡（木桶短板效应）：在分布式训练中，所有的集合通信（如 Reduce-Scatter 或 All-Gather）都是强同步阻塞屏障（Barrier）。若某张卡分配到的样本序列极长，计算前向传播花费了 10 秒，而其他卡仅花费 1 秒，那么其余所有卡必须在通信原语处挂起等待 9 秒。如果数据集中偶然混入了一个超长或死循环的离群样本，某张卡计算超时，其余卡在等待超过 NCCL_TIMEOUT 阈值后便会集体超时崩溃。
  2. Rank 0 独占阻塞操作：在很多代码中，开发者习惯在 Rank 0 上执行 Checkpoint 保存或评估：
    python 
    if rank == 0:
    # 漫长的云盘同步或大模型序列化，耗时超过 30 分钟
    save_checkpoint_to_s3(model)
dist.barrier() # 其余 Rank 等待 Rank 0，直接超时暴毙！
  3. 跨节点 InfiniBand / RoCE 网卡静默丢包与 PFC 死锁：在采用以太网 RoCE v2 的集群中，若网络交换机未正确配置 ECN（显式拥塞通知）与 PFC（基于优先级的流量控制），瞬时大突发流量会导致 PFC 拥塞风暴（PFC Storm）与死锁，跨节点 RDMA 吞吐瞬间暴跌至零，引发整个分布式任务死锁挂起。

5.2 生产级 NCCL 排查黄金配置与网络诊断

排查通信死锁必须开启详细日志追踪。在多机启动前务必声明：

bash 
# 开启最高级别 NCCL 跟踪日志
export NCCL_DEBUG=INFO
export NCCL_DEBUG_SUBSYS=COLL,ENV,NET
# 捕获通信死锁时的 C++ 详细调用栈
export TORCH_DISTRIBUTED_DEBUG=DETAIL
# 将超时时间临时延长至 2 小时便于排查定位慢节点
export NCCL_TIMEOUT_MS=7200000
# 禁用 CUDA 图可能引发的通信挂起
export NCCL_ASYNC_ERROR_HANDLING=1

6. 生产级生产代码：自动化异常监控 Hook 工具

为了在第一时间捕获 NaN、Inf 和梯度异常，而不是等到数小时后模型彻底腐蚀才发现，以下 Python 代码提供了一个即插即用的全自动训练异常监控 Hook 系统。它可以精确记录每一层的激活值范数、反向传播梯度范数，并在检测到首个 NaN 的纳秒级时间内精准打印出是哪一个具体的层出了问题：

anomaly_monitor_hook.py 
import math
import torch
import torch.nn as nn
from typing import Dict, Optional

class AnomalyMonitorHook:
    """生产级大模型训练数值异常与梯度范数自动化监控器"""
    def __init__(self, model: nn.Module, max_norm_threshold: float = 100.0):
        self.model = model
        self.max_norm_threshold = max_norm_threshold
        self.hooks = []
        self.layer_stats: Dict[str, Dict] = {}
        self._register_hooks()

    def _register_hooks(self):
        """为模型的每个注意力层与 MLP 层挂载前向与反向观察钩子"""
        for name, module in self.model.named_modules():
            # 针对 Transformer 的核心层级进行挂载
            if any(key in name for key in ["self_attn", "mlp", "input_layernorm", "post_attention_layernorm"]):
                # 1. 前向传播钩子：监控激活值是否产生 NaN/Inf
                h_fwd = module.register_forward_hook(self._make_fwd_hook(name))
                # 2. 反向传播钩子：监控梯度是否产生爆炸或溢出
                h_bwd = module.register_full_backward_hook(self._make_bwd_hook(name))
                self.hooks.extend([h_fwd, h_bwd])

    def _make_fwd_hook(self, layer_name: str):
        def hook(module, input_t, output_t):
            # 处理多输出情况（如 Attention 可能返回 tuple）
            t = output_t[0] if isinstance(output_t, (tuple, list)) else output_t
            if isinstance(t, torch.Tensor):
                has_nan = torch.isnan(t).any().item()
                has_inf = torch.isinf(t).any().item()
                if has_nan or has_inf:
                    raise RuntimeError(
                        f"🚨 [前向崩溃] 层 '{layer_name}' 输出激活值出现异常数值！"
                        f"NaN: {has_nan}, Inf: {has_inf}, 形状: {list(t.shape)}"
                    )
        return hook

    def _make_bwd_hook(self, layer_name: str):
        def hook(module, grad_input, grad_output):
            g = grad_output[0] if isinstance(grad_output, (tuple, list)) else grad_output
            if isinstance(g, torch.Tensor):
                has_nan = torch.isnan(g).any().item()
                has_inf = torch.isinf(g).any().item()
                if has_nan or has_inf:
                    raise RuntimeError(
                        f"🚨 [反向崩溃] 层 '{layer_name}' 梯度回传发生数值污染！"
                        f"NaN: {has_nan}, Inf: {has_inf}, 形状: {list(g.shape)}"
                    )
                # 计算局域梯度范数
                norm = g.norm(2).item()
                if norm > self.max_norm_threshold:
                    print(f"⚠️ [梯度警报] 层 '{layer_name}' 局部梯度范数达到异常高值: {norm:.2f}")
        return hook

    def inspect_parameters(self) -> float:
        """在优化器 step 之前统计全局参数梯度范数"""
        total_norm_sq = 0.0
        for p in self.model.parameters():
            if p.grad is not None:
                param_norm = p.grad.detach().norm(2).item()
                if math.isnan(param_norm) or math.isinf(param_norm):
                    return float("nan")
                total_norm_sq += param_norm ** 2
        return math.sqrt(total_norm_sq)

    def remove_hooks(self):
        """移除全部钩子，释放系统资源"""
        for h in self.hooks:
            h.remove()
        self.hooks.clear()

# 使用示例
if __name__ == "__main__":
    print("[INFO] 初始化测试模型与监控 Hook...")
    test_model = nn.Sequential(
        nn.Linear(128, 128),
        nn.LayerNorm(128),
        nn.Linear(128, 10)
    ).cuda()
    
    monitor = AnomalyMonitorHook(test_model, max_norm_threshold=50.0)
    
    # 模拟正常步
    x = torch.randn(8, 128, device="cuda")
    out = test_model(x)
    loss = out.sum()
    loss.backward()
    grad_norm = monitor.inspect_parameters()
    print(f"正常步全局梯度范数: {grad_norm:.4f}")

8. 本章小结

  • 四大死亡现场：大模型后训练常见事故高度集中在 NaN/Inf 数值崩溃、CUDA OOM 显存击穿、评测崩塌隐蔽逻辑 Bug 以及 NCCL 分布式死锁。
  • NaN 防御体系：淘汰 FP16 全面采用 BF16 规避指数溢出；严格配置阈值为 1.0 的自适应全局梯度范数裁剪；对对数比值和概率实施 clamp 下限保护；对 Loss Spike 建立自动回滚剔除 SOP。
  • OOM 急救之道：深入理解 CachingAllocator 的碎片化机制，借助 expandable_segments:True 消除虚拟地址空洞；全线开启激活检查点（Gradient Checkpointing）以 33% 算力开销换取 80% 显存节省。
  • 杜绝隐蔽逻辑错位：因果语言模型必须执行严密的标签移位（Off-by-One）；SFT 训练必须严格将 Prompt 提示词标记为 -100 阻止模型记忆作弊；多样本 Packing 必须物理隔离因果注意力和边界。
  • 分布式通信健壮性：消除跨 Rank 数据长度不均衡造成的“木桶阻塞”；严禁 Rank 0 独占执行过长的阻塞写盘；开启 NCCL_DEBUG=INFO 与超时监控实现网络故障精准溯源。
🧠 自测题（点击展开答案）
问题 1：在 SFT 监督微调中，如果错误地将 Prompt 部分也计算了 Loss（未设为 -100 掩码），为什么训练 Loss 下降平稳但生成评测性能极差？

答案：因为在典型的对话微调数据集中，输入提示词（User Prompt）通常占据了整个序列 Token 总量的 60%~80% 甚至更多。如果 Prompt 未被掩码，模型在前向计算和反向传播中，绝大部分梯度更新都被用来“死记硬背”用户输入的语法特征和提示词模式。由于提示词是给定的已知输入，模型拟合已知文本非常容易，因此整体 Loss 会显得收敛得非常漂亮；但模型在关键的 Assistant 回答生成部分分配到的梯度权重被严重稀释，导致真正决定模型生成能力的因果推理逻辑没有得到充分微调，从而在下游生成评测中表现低劣。

问题 2：为什么显存明明剩余数吉字节（GB），PyTorch 申请一个仅几百兆（MB）的 Tensor 依然会触发 CUDA out of memory？如何彻底解决？

答案：这是由于 CUDA 显存分配器内部产生了严重的“外部显存碎片”。在长短不一的动态序列训练中，不同大小的张量被频繁申请与释放，导致未被释放的空闲显存被割裂成大量微小的非连续碎片。虽然这些碎片加总起来的剩余容量看似充足，但当系统试图申请一个必须在“物理上连续”的大张量时，无法找到任何一个单块连续空洞容纳该张量，从而引发假性 OOM。彻底的急救方案是注入环境变量 export PYTORCH_CUDA_ALLOC_CONF="expandable_segments:True"，利用底层虚拟内存分页机制允许非连续物理碎片映射为连续虚拟空间，从而彻底消除此类崩溃。

问题 3：在分布式训练中，为什么仅仅某一张 GPU 遇到脏数据计算时间变慢，会导致全局数百张卡集体报告 NCCL Watchdog Timeout 超时崩溃？

答案：因为分布式数据并行（DDP、ZeRO、FSDP）在反向传播和优化器同步阶段，必须调用集合通信原语（如 All-Reduce、Reduce-Scatter）。所有的集合通信原语在底层都是强同步屏障（Barrier），要求参与通信的所有 GPU 节点必须全部就绪后才能开始数据交换。如果有某一张卡由于分配到异常超长的离群样本导致计算迟滞，其余所有先算完的卡都必须在网络通信接口处处于阻塞自旋等待状态。一旦这张慢卡的延迟超过了 NCCL 设定的超时阈值（通常默认为 30 分钟），其余所有正常卡上的 Watchdog 监控线程便会判定发生死锁并强行中断进程，导致整个集群训练任务集体崩溃。
