1. RLHF 的真正痛点：80% 耗时的 Rollout 泥潭

很多初涉大模型强化学习（RLHF）的工程师，往往将主要精力集中在算法损失函数的优化上——例如探索 PPO 的裁剪因子、KL 散度的惩罚系数、或是 GRPO 的群组相对优势估计。然而，一旦将代码推向生产级集群并启动端到端训练监控面板（如 TensorBoard 或 Weights & Biases），一个令人崩溃的硬件瓶颈便会无情暴露：整个训练循环中，超过 70% 甚至 85% 的物理时间被消耗在了自回归生成（Rollout / Sampling）阶段，而真正执行梯度计算的反向传播阶段耗时不足 20%。

这种反直觉现象的本质在于大模型训练（Training）与推理采样（Rollout Generation）在底层计算模式上的截然不同：

  • 训练阶段（Forward + Backward）：是典型的计算密集型（Compute-Bound）任务。输入序列的所有 Token 是已知的（Prompt + Ground Truth Response），整个序列可以作为统一的大矩阵一次性灌入 GPU 执行高度并行的 GEMM 计算。Tensor Core 的利用率极高，算力利用率（MFU）通常可维持在 45%~55% 之间。
  • Rollout 生成阶段（Autoregressive Decode）：是典型的访存密集型（Memory-Bound）任务。在自回归生成过程中，每前向计算一步，仅能产出单一一个 Token。为了预测下一个 Token，GPU 必须将数百亿参数的模型权重以及整个历史序列的键值对缓存（KV Cache）从全局显存（HBM）中完整读取一遍，而这一次漫长的访存仅换来了单 Token 极微小的浮点计算。此时 Tensor Core 大面积处于饥饿状态，显卡带宽打满但算力利用率（MFU）往往跌破 5%！
🚨 推理强化（Reasoning RL）带来的 Rollout 灾难

在以 DeepSeek-R1 或 OpenAI o1 为代表的推理增强模型中，长思维链（Chain-of-Thought, CoT）的自回归生成长度动辄达到 8k、16k 甚至 32k Tokens。在 GRPO 算法中，为了准确评估数学或代码题目的奖励分布，一个 Prompt 甚至需要并行采样 8 到 16 条候选回复（\( G=16 \)）。

假设单个微批次包含 16 个 Prompt，每个 Prompt 采样 16 条链，总并发序列数为 \( 16 imes 16 = 256 \)。若平均生成长度为 8192 Tokens，整个采样阶段需要生成的全局 Token 总量高达：

\[ N_{ ext{tokens}} = 256 imes 8192 pprox 2.1 imes 10^6 ext{ Tokens} \]

若使用未经优化的原生 PyTorch 自回归采样，单次 Rollout 耗时将长达数小时，而随后的 PPO 更新仅需几十秒。优化 Rollout 基础设施，不再是一项可选的锦上添花，而是决定强化学习后训练能否跑通的绝对生命线！

本节小结：自回归生成的访存受限属性与思维链长度的急剧膨胀，使 Rollout 成为现代 RLHF 训练中绝对的耗时死结，必须引入专用高性能推理引擎进行架构级救赎。

2. PagedAttention 原理与显存碎片终结

在 vLLM（Woosuk Kwon 等人，UC Berkeley）诞生之前，制约高并发自回归采样的最大工程死穴是显存碎片化（Memory Fragmentation）。在标准 PyTorch 推理中，为了给每个并发请求存储 KV Cache，系统必须预先为每个序列分配一块连续的物理显存空间。

2.1 传统连续 KV Cache 的三大顽疾

传统连续分配机制导致了极其严重的显存浪费：

  1. 过度预分配（Over-Allocation）：由于用户请求的最大输出长度是不可预测的（设最大长度为 max_model_len = 4096），系统必须假设每个请求都会生成 4096 个 Token，并预先为每个序列开辟对应 4096 长度的显存。然而现实中绝大多数请求在生成几百个 Token 后便提前终止（输出了 <|endoftext|>），预分配的数 GB 显存被完全浪费。
  2. 内部碎片（Internal Fragmentation）：在请求未达到预分配长度前，分配的内存槽位一直处于未被写入的空置状态，无法被其他请求复用。
  3. 外部碎片（External Fragmentation）：不同请求的到达与结束时间高度动态。当一个长请求结束后释放了一块不规则的连续显存时，由于新来的请求尺寸不匹配，这部分零散空间很难再被重新利用，形成大量显存孤岛。

真实生产环境测试表明，传统推理框架中仅有 20%~40% 的显存真正存储了有效的 KV 数据，其余 60%~80% 均沦为碎片和预占泡影，直接导致单卡允许的最大并发批次（Concurrency Batch Size）被大幅压制。

2.2 PagedAttention：操作系统虚拟内存思想的映射

vLLM 借鉴了现代操作系统内核中的虚拟内存（Virtual Memory）与分页（Paging）机制，提出了 PagedAttention：

  • 逻辑 KV 块（Logical KV Blocks）：在逻辑概念上，每个序列的 KV Cache 依然是一个一维连续增长的向量序列。PagedAttention 将其按固定大小切片（例如每个 Block 包含 16 个 Token 的 KV 向量）。
  • 物理显存页面（Physical Block Pages）：在 GPU 全局显存（HBM）中，开辟一个扁平的、固定大小的物理页面池（Memory Pool）。所有物理块在空间上可以完全不连续、随机离散分布在显存的任何角落。
  • 块表映射（Block Table）：系统为每个请求维护一张轻量的块表（类似于 OS 的页表 Page Table）。块表记录了该请求的“逻辑块序号”到“物理块地址”的映射关系。

2.3 动态显存收益与写时复制（Copy-on-Write）

PagedAttention 彻底改变了显存利用的游戏规则：

  • 按需分配，显存利用率逼近 96%：系统只在生成序列真正跨越 Block 边界时（如生成第 17 个 Token 时），才向物理池申请分配一个新的空闲 Page。无论序列长短，显存浪费永远被严格约束在最后一个未填满的 Block 内部（以 Block Size=16 为例，平均每个序列仅浪费 8 个 Token 的显存空间）。
  • 天然契合强化学习多采样分支（GRPO / Rejection Sampling）：在 GRPO 或束搜索（Beam Search）中，多个响应共享同一个输入 Prompt。在传统框架中，同一个 Prompt 的 KV Cache 会被机械地复制 \( G \) 次（如 16 次），造成海量冗余。在 PagedAttention 下，所有采样分支的块表直接指向相同的物理 Prompt 页面，引用计数累加；当某个分支在生成各自的第 1 个不同 Token 时，触发 写时复制（Copy-on-Write, CoW），仅为该分支开辟新的私有 Page。这使得输入 Prompt 的显存开销直接降低了 \( (G - 1)/G \)，在长 Prompt 强化学习中显存节约达数倍！

3. 连续批处理与计算流调度优化

除了显存管理，传统推理框架在批处理（Batching）调度层面同样存在严重缺陷：静态批处理（Static Batching）要求所有请求必须对齐。若同一个 Batch 中请求 A 生成 20 个 Token 就结束，而请求 B 需要生成 1000 个 Token，请求 A 必须持续进行无意义的 Padding 计算，直至请求 B 完成。此时 GPU 算力严重浪费在无用的 Padding 占位符上。

3.1 连续批处理（Continuous / In-Flight Batching）

现代高性能引擎（如 Orca、vLLM、SGLang、TensorRT-LLM）引入了连续批处理（Continuous Batching）。其调度粒度不再是整个序列请求，而是每次单 Token 的迭代（Iteration-Level Scheduling）：

  • 在每一步迭代执行完毕后，调度器会扫描当前 Batch。若某个请求输出了 EOS 结束符，它被立即移出 Batch 并返回客户端；
  • 同时，调度器立即从等待队列中拉取新的等待请求加入正在执行的 Batch 中；
  • 这种动态的“随退随进”机制让 GPU 的 Tensor Core 始终维持在近乎饱和的状态，批处理利用率接近 100%。

3.2 块状预填充（Chunked Prefill）与算力均衡

在连续批处理中，系统同时面临两种截然不同的计算负载：Prefill 阶段（处理用户 Prompt 输入，计算密集型）与 Decode 阶段（逐个自回归吐字，访存密集型）。

若一个包含 16k 长度超长 Prompt 的请求突然进入系统，如果一次性对整个 16k 序列执行 Prefill，它会强行霸占整个 GPU 算力长达数百毫秒，导致同卡上正在执行 Decode 的其他几十个并发请求遭遇严重的调度饥饿（Inter-token Latency 飙升）。

为了解决这一冲突，Chunked Prefill（分块预填充）技术被引入：将超长 Prompt 强制切分成多个小块（例如每块 512 个 Token）。在每次迭代中，调度器将一个 Prefill 切块（512 Tokens）与当前正在进行的 Decode 请求（例如 64 个 Token）打包在同一个 Forward 运算中：

  • Prefill 切块的高密度浮点计算，正好填补了 Decode 阶段 Tensor Core 的计算算力空闲；
  • Decode 请求的高频访存与 Prefill 结合，大幅提升了全局硬件算力与显存带宽的综合利用率；
  • 消除了长 Prompt 带来的长时间卡顿，保证了整体采样的平滑与低延迟。

4. 投机解码（Speculative Decoding）加速 Rollout

尽管 PagedAttention 与连续批处理将并发吞吐推向了极限，但自回归生成“单步串行”的本质物理法则依然没有被打破。为了在不牺牲任何输出质量的前提下成倍缩短单个序列的生成延迟，投机解码（Speculative Decoding）成为了生产级 Rollout 的前沿利器。

4.1 投机采样的两阶段机制

投机解码的核心思想是让小模型（草稿模型 Draft Model）快速试错猜测，让大模型（目标模型 Target Model）并行验证纠偏：

  1. 草稿推测（Draft Phase）：使用一个参数量小、生成速度极快的小模型（例如用 0.5B 或 1.5B 的小模型作为 70B 目标模型的草稿机），在本地以极低延迟快速向前自回归猜出 \( K \) 个 Token（例如 \( K=5 \)）： \[ ( ilde{x}_1, ilde{x}_2, \dots, ilde{x}_K) \]
  2. 并行验证（Verification Phase）：目标大模型（Target Model）并不需要一步一步串行生成，而是将这 \( K \) 个预测 Token 作为输入，执行一次性并行前向传播（Parallel Forward）！一次 Forward 即可同时产出所有 \( K \) 个位置上的条件概率分布 \( p(x_{i} \mid x_{
  3. 保真拒绝采样（Rejection Sampling）：系统根据目标模型与草稿模型的概率比值，使用精巧的随机采样法则逐一检验各个 Token 是否被接受。若前 \( j \) 个 Token 被接受，第 \( j+1 \) 个被拒绝，系统保留前 \( j \) 个合法 Token，并由大模型基于其前向分布直接产出一个纠正 Token，随后丢弃剩余的猜测。
📘 严密的数学无损性：分布严格恒等

投机解码最迷人的理论特性在于：它在数学上严格保证了最终输出的 Token 采样分布与纯粹使用大模型自回归生成的分布完全一致！对于草稿模型提议的 Token \( x \)，其接受概率为：

\[ P_{ ext{accept}} = \min\left(1, rac{p(x)}{q(x)} ight) \]

其中 \( p(x) \) 是目标大模型给出的概率，\( q(x) \) 是草稿小模型给出的概率。若被拒绝，算法从残差分布 \( \max(0, p(x) - q(x)) \) 中重新采样。经数学证明，无论草稿模型有多弱，最终采样序列的全局分布与目标大模型严格等价，绝无任何精度或偏好损失！

4.2 在强化学习环境中的收益评估

在代码与数学推理 RLHF 中，长思维链包含大量结构化、低熵的模板代码（如 for i in range(...) 或 def solution(...)）与逻辑推理连接词。草稿模型对这些 Token 的命中率极高（接受率常常超过 80%~90%）。在生产环境中，单步投机解码通常能带来 2.0x ~ 2.8x 的真实端到端 Rollout 延迟缩减，极大加速了强化学习的迭代闭环。

5. Trainer 与 Engine 解耦架构：Ray 分布式实践

在早期的强化学习框架（如原版 TRL 或 Deepspeed-Chat）中，训练（Actor 策略更新）与推理（Rollout 生成）被强行硬编码在同一个执行流中：GPU 先以评估模式加载模型生成回复，随后原地切换为训练模式执行反向传播。这种紧耦合模式在生产环境中存在致命缺陷：

  • 显存分配死锁：训练框架（如 DeepSpeed ZeRO-3）为了通信效率会常驻全部显存池，导致无法再为推理引擎（如 vLLM）开辟庞大的物理 PagedAttention 显存池；
  • 并行策略冲突：Rollout 阶段推理引擎通常需要纯张量并行（如 TP=4 或 TP=8），而训练阶段全参微调更适合 ZeRO-3 或 FSDP；
  • 资源利用率极低：当模型在低速单卡生成时，整个分布式训练集群的跨机网络和优化器完全停摆等待。

5.1 现代解耦方案：OpenRLHF 与 verl 架构设计

现代业界标杆框架（如 OpenRLHF、ByteDance verl）普遍采用了基于 Ray 的分布式解耦拓扑体系：

集群组件 角色与运行环境 采用的技术栈 核心硬件指标
Inference Engine 进程池 专门负责接收 Prompt 并以极致并发吞吐执行 Rollout 生成与 Logits 缓存 vLLM / SGLang + PagedAttention + TP 追求超大 Batch 并发、低延迟，显存主要划归为 KV Cache 池
Trainer 进程池 专门负责从推理引擎拉取生成结果，计算 PPO/GRPO Loss 并反向更新模型权重 PyTorch FSDP / DeepSpeed ZeRO-3 + FlashAttention-2/3 追求高算力 MFU、显存主要划归为梯度与优化器状态
Ray 分布式流式总线 负责在 Engine 与 Trainer 之间高效流式传输生成的 Token 张量与更新后的最新参数 Ray Plasma 共享内存 + 异步点对点 RPC + NCCL 参数广播 通过跨节点高速通信将采样与训练流水线化重叠

在每个强化学习迭代中：

  1. Trainer 完成上一步的优化器更新后，触发参数同步钩子，通过 NCCL 直接将最新的模型权重就地广播并覆写到 Engine 的显存中；
  2. Engine 立即全速启动高并发采样，利用连续批处理与 PagedAttention 快速吐出本轮全部轨迹；
  3. 生成的轨迹通过 Ray Plasma 零拷贝共享内存直接管道式喂入 Trainer，无缝开启下一轮反向传播。

6. 生产级生产代码：基于 vLLM 异步流水线的并行采样

以下代码提供了一个高度贴近生产级 RLHF Rollout 采样的实现，展示了如何使用 vllm.AsyncLLMEngine、SamplingParams 以及异步并发队列构建超高吞吐的批处理采样工作流：

vllm_rollout_worker.py 
import asyncio
from typing import List, Dict
from vllm import AsyncLLMEngine, AsyncEngineArgs, SamplingParams

class HighThroughputRolloutEngine:
    """工业级强化学习 Rollout 异步采样引擎封装"""
    def __init__(self, model_path: str, tensor_parallel_size: int = 4, gpu_memory_utilization: float = 0.85):
        # 配置高性能推理引擎参数
        engine_args = AsyncEngineArgs(
            model=model_path,
            tensor_parallel_size=tensor_parallel_size,
            gpu_memory_utilization=gpu_memory_utilization,  # 将 85% 显存划拨给 PagedAttention
            max_model_len=8192,
            enable_chunked_prefill=True,                   # 开启分块预填充防止计算饥饿
            swap_space=4,                                  # CPU 交换内存大小 (GB)
            trust_remote_code=True,
            dtype="bfloat16",
        )
        self.engine = AsyncLLMEngine.from_engine_args(engine_args)
        print(f"[INFO] vLLM 推理引擎初始化完毕 (TP={tensor_parallel_size})")

    async def generate_single(self, prompt: str, sampling_params: SamplingParams, request_id: str) -> Dict:
        """单请求异步前向管道"""
        results_generator = self.engine.generate(prompt, sampling_params, request_id)
        final_output = None
        async for request_output in results_generator:
            final_output = request_output
            
        # 提取生成的回复与每个 Token 的 Logits 统计
        text_outputs = [output.text for output in final_output.outputs]
        token_ids = [list(output.token_ids) for output in final_output.outputs]
        return {
            "request_id": request_id,
            "prompt": prompt,
            "responses": text_outputs,
            "token_ids": token_ids,
        }

    async def batch_rollout(self, prompts: List[str], group_size: int = 8, temperature: float = 0.8) -> List[Dict]:
        """并行批量采样（支持强化学习 GRPO 多路径分支采样）"""
        # 为强化学习配置采样超参数
        sampling_params = SamplingParams(
            n=group_size,               # 单 Prompt 采样 G 个回复
            temperature=temperature,
            top_p=0.95,
            max_tokens=2048,
            stop_token_ids=[128001, 128009], # Llama 3 专用 EOS
        )

        tasks = []
        for i, p in enumerate(prompts):
            req_id = f"rlhf_rollout_{i}"
            tasks.append(self.generate_single(p, sampling_params, req_id))

        print(f"[INFO] 正在并发执行 {len(prompts)} 个 Prompt 的采样本周 (群组大小 G={group_size})...")
        trajectories = await asyncio.gather(*tasks)
        print("[INFO] 批量采样全量就绪，准备向 Trainer 管道传输张量。")
        return trajectories

# 独立运行入口
if __name__ == "__main__":
    async def main():
        engine = HighThroughputRolloutEngine(
            model_path="/models/Meta-Llama-3-8B-Instruct",
            tensor_parallel_size=1
        )
        sample_prompts = [
            "请给出利用快速排序解决数组乱序的 Python 实现，并证明时间复杂度。",
            "解答方程: 3x^2 - 12x + 9 = 0，写出详细推导过程。"
        ]
        results = await engine.batch_rollout(sample_prompts, group_size=4)
        for r in results:
            print(f"Prompt: {r['prompt'][:30]}... -> 生成了 {len(r['responses'])} 条候选响应")

    asyncio.run(main())

6.2 引擎间权重热更新（Weight Reloading）核心伪代码

为了让推理引擎能够即时感知 Trainer 的最新梯度步长，以下展示了基于内存张量直接更新 vLLM 权重的关键机制：

weight_sync_protocol.py 
import torch

def update_vllm_weights_in_place(vllm_model_runner, new_param_dict: dict):
    """在不重启 vLLM 实例的情况下，原地将训练器产生的新权重载入推理显存池"""
    # 获取 vLLM 内部绑定的 PyTorch Module
    engine_model = vllm_model_runner.model
    
    with torch.no_grad():
        for name, param in engine_model.named_parameters():
            if name in new_param_dict:
                # 使用直接内存拷贝，避免重建张量引发的显存碎片
                param.data.copy_(new_param_dict[name].data)
            else:
                pass
    torch.cuda.synchronize()
    print("[SUCCESS] 推理引擎底层模型参数原地更新完毕，无显存重新初始化开销。")

7. 常见坑点与排查实录

  • 坑点一：Trainer 与 vLLM 部署在同张卡时触发 CUDA OOM。
    现象分析：在小规模调试或单机多卡运行时，尝试在单卡上同时拉起 FSDP 训练器与 vLLM 实例，引擎初始化时直接抛出 CUDA out of memory。
    根本原因：vLLM 在启动时默认会预先探测并占用 90%（gpu_memory_utilization=0.90）的全部可用物理显存作为其 PagedAttention 显存池，导致后启动的训练器连一个浮点数都无法分配。
    急救方案：在资源受限混部环境下，必须显式限制 gpu_memory_utilization=0.4；生产级方案则必须执行物理卡隔离——例如 8 卡机中卡 0~3 专供 Trainer（ZeRO-3），卡 4~7 专供 Engine（vLLM TP=4）。
  • 坑点二：长文本生成时出现静默截断导致奖励模型偏好崩塌。
    现象分析：在运行强化学习时，模型的胜率不仅不上升，反而逐渐胡言乱语；检查日志发现输出文本在末尾被强行切断，无 <|eot_id|>。
    根本原因：max_tokens 参数设置过于严苛，或者 PagedAttention 的全局预置块被耗尽（Block Pool Exhausted），引擎在显存见顶时被迫提前强制结束序列。
    急救方案：调大推理引擎的 max_model_len，合理设置每批并发请求数；在强化学习数据流中增加校验钩子，对于由于超长被截断的序列赋予较低惩罚值，杜绝模型学习到被截断的破损句式。
  • 坑点三：异步采样生成的 Logits 与训练器前向重新计算的 Logits 存在数值漂移。
    现象分析：在 PPO 训练中，计算重要性采样权重比率 \( r_t( heta) = rac{\pi_ heta(a_t|s_t)}{\pi_{ ext{old}}(a_t|s_t)} \) 时，第一步的 \( r_t \) 居然偏离 1.0 较远（例如变成了 1.15 或 0.85）。
    根本原因：vLLM 推理时为了速度开启了某些特定算子优化（如不同版本的 FlashAttention、或 FP8/INT8 量化 KV Cache），而训练器使用的是原生 FP32/BF16 无损计算，两者底层的浮点舍入路径不一致导致概率差分。
    急救方案：确保 Engine 与 Trainer 在注意力实现上采用相同版本的 FlashAttention 内核，关闭低精度有损 KV 压缩，保证老策略概率的数学一致性。

8. 本章小结

  • Rollout 瓶颈根源：自回归解码逐 Token 生成的特性导致计算强度极低，受制于 HBM 显存带宽墙，在 RLHF/GRPO 训练中占据 70%~85% 的全局物理耗时。
  • PagedAttention 架构：通过将逻辑 KV 序列切分为固定大小的 Block 并映射至离散物理页面池，彻底消除了显存外部碎片与过度预分配，显存利用率跃升至 96% 以上，并依托写时复制原生加速多分支采样。
  • 批处理流调度：连续批处理（Continuous Batching）在迭代级别动态进退请求，避免静态填充气泡；Chunked Prefill 将长输入切块并与 Decode 混合执行，化解了调度饥饿并实现算力均衡。
  • 投机解码赋能：采用轻量草稿模型推测与目标大模型并行校验两阶段，在保证采样分布严格无损的前提下实现 2 倍以上单流延迟加速。
  • 解耦分布式拓扑：以 Ray 为中枢将 Trainer（专精反向计算与参数更新）与 Engine（专精高并发采样）物理隔离解耦，通过零拷贝内存与快速通信协议，是打通现代大规模强化学习生产闭环的终极架构。
🧠 自测题（点击展开答案）
问题 1：在传统大模型推理中，为什么说预分配连续显存会导致高达 60%~80% 的显存碎片浪费？

答案：因为在自回归生成开始前，系统无法事先预知每个请求究竟会输出多少个 Token，为了防止在生成过程中因空间不足而中断，系统只能按照模型支持的最大序列长度（如 4096）为每一个请求预先分配一整段连续的物理显存空间。然而在实际交互中，绝大多数响应在输出几十到数百个 Token 后就会遇到 EOS 结束，剩余预分配的大段连续显存一直处于闲置未用状态，却无法被其他请求占用（内部碎片）；同时，不同长短请求动态到达与离开后，在显存中留下了大量大小不一、不连续的显存空洞，难以被新请求完全填充复用（外部碎片）。这两者共同造成了巨额的显存浪费。

问题 2：为什么投机解码（Speculative Decoding）能够保证生成的最终文本在统计分布上与直接使用大模型采样严格一致，绝无任何精度损失？

答案：投机解码并非盲目相信小模型的输出，而是引入了严密的保真拒绝采样（Rejection Sampling）准则。对于草稿小模型提议的每一个 Token，大模型都在单次并行前向传播中计算出其真实条件概率，并根据概率比值 \( \min(1, p(x)/q(x)) \) 决定是否接受；如果草稿 Token 被拒绝，算法并不简单回退，而是严格从残差分布 \( \max(0, p(x) - q(x)) \) 中重新采样一个替补 Token。经过概率统计严谨推导，这一机制在数学上严格满足目标大模型原生的概率分布，因此整体输出序列的分布与纯粹由大模型逐字生成的分布在数学上是完全恒等的。

问题 3：在 RLHF 生产训练中，为什么必须将训练器（Trainer）与推理引擎（Engine）解耦，而不是直接用 Hugging Face Trainer 原生跑生成？

答案：因为训练与推理对硬件显存和并行拓扑的诉求是根本矛盾的。训练阶段需要庞大的静态显存来承载模型梯度和优化器状态，通常依赖 DeepSpeed ZeRO-3 或 FSDP 进行跨节点分片；而推理 Rollout 阶段不需要任何梯度和优化器，但需要将绝大部分显存划归给 PagedAttention 的动态 KV Cache 池，且通信对低延迟要求极高，更适合单节点内的张量并行（TP）。如果强行紧耦合在同一进程中，训练器的显存预占会导致推理引擎无法分配 KV Cache，造成最大并发数极低、显存碎片化严重；解耦后，两者各自独占优化的显卡资源和并行策略，仅通过轻量的高速通信同步模型权重与生成数据，能够将全局集群吞吐提升数倍。
