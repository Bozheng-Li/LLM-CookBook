第 38 章 · 基准测试大全

基准测试（Benchmarks）是大模型研发迭代中的通用度量衡。从海量学科常识到高难度奥赛数学，从原子级函数生成到仓库级代码修补，从受控指令遵循到开放域人类偏好，各类评测集构成了后训练模型能力的多维雷达。本章深入拆解当代大模型研发中不可或缺的核心评测基准，剖析其设计哲学、题目构造、评分判据与工程陷阱，并给出工业级统一基准自动化流水线的实现。

1. 大模型基准测试的演进脉络与能力分层

自大语言模型进入以指令微调和偏好对齐为主导的后训练时代以来，基准测试的形态经历了翻天覆地的跃迁。早期的自然语言处理评测集（如 GLUE、SuperGLUE、SQuAD）主要面向分类、抽取与语义匹配任务。模型只需输出固定的类别标签或在原文中定位起始与终止跨度。随着参数量突破百亿规模并涌现出强大的上下文学习（In-Context Learning）能力，评测范式迅速转向无约束长程文本生成与复杂跨领域推理。

然而，静态测试集的“天花板效应”正在加速显现。2020 年发布的 MMLU（Massive Multitask Language Understanding）曾被视为通用学术知识的严苛考场，当时最先进的模型仅能取得 40% 左右的准确率；而如今头部开源模型与专有模型在 MMLU 上的表现普遍跃升至 85%~90% 以上，近乎饱和。这种能力膨胀迫使评测界不断推出难度更高、对抗性更强、评估机制更严密的第二代基准——例如引入更多干扰项并剔除噪声样本的 MMLU-Pro、面向专业级竞赛的 AIME、真实工程级代码仓库修复评测 SWE-bench，以及可对指令硬约束进行客观规则判决的 IFEval。

📘 概念辨析：能力评测的四个层次

1. 原子记忆与知识泛化层（Knowledge Retrieval）：检验模型底层参数化知识库的广度与精度。以 MMLU、CMMLU、C-Eval 为典型代表，采用多项选择题（MCQ）形态，核心测试“知道什么”。

2. 符号操作与多步逻辑演绎层（Symbolic & Mathematical Reasoning）：检验模型分步规划、数学归纳与严格符号推演能力。以 GSM8K、MATH、AIME 2024 为代表，核心测试“如何思考”。

3. 形式化受限生成层（Constrained & Programmatic Generation）：检验模型在形式逻辑与确定性环境下的可执行产出。以 HumanEval、MBPP、SWE-bench、IFEval 为代表，通过沙箱执行与严苛断言检验“能否落地”。

4. 开放语义交互与人类对齐层（Open-ended Pragmatic Alignment）：检验多轮对话中的连贯性、语调得体性、安全性及复杂人类偏好满足度。以 MT-Bench、Arena-Hard 为代表，核心测试“是否好用”。

2. 通用学科与知识理解：MMLU、MMLU-Pro 与 CMMLU

2.1 MMLU：经典学科知识评测的标杆与局限

MMLU（Massive Multitask Language Understanding）由加利福尼亚大学伯克利分校 Hendrycks 等人于 2020 年发布，是衡量模型通识教育水平的里程碑式基准。全集包含 57 个学科任务，横跨人文学科（历史、哲学、法律）、社会科学（经济学、心理学、社会学）、硬科学（物理、化学、生物、高等数学）以及职业专业领域（临床医学、注册会计师、计算机安全），总计 15908 道 4 选 1 单选题。

MMLU 的标准评测设置通常采用 5-shot 提示词。评测协议分为两种模式：

  • 对数似然打分（Perplexity / Log-likelihood Scoring）：计算模型在四个候选字母（'A'、'B'、'C'、'D'）上的下一个 Token 条件概率 \( P(\text{token} \mid \text{Prompt}) \)，选取极大值 \( \arg\max_{c \in \{A,B,C,D\}} P(c \mid \text{Prompt}) \)。该方式计算完全确定、零方差、开销小，常用于 Base 模型评测。
  • 生成式抽取（Generative CoT Extraction）：强制模型输出思维链，最后通过正则表达式提取形如 The correct answer is (C) 的结论。该模式专为 Chat/Instruct 模型设计，能更充分激发模型的推理潜能。

随着模型能力的暴涨，MMLU 暴露出一系列致命缺陷：4 选 1 使得纯随机猜测也有 25% 的期望命中率；部分题目存在事实性错误、题干表述歧义或数据标注噪音；且海量互联网语料导致 MMLU 测试集被预训练阶段无意或故意污染的风险极高。

2.2 MMLU-Pro：针对前沿大模型的抗饱和增强版

为解决 MMLU 的区分度退化问题，Wang 等人于 2024 年推出了 MMLU-Pro。MMLU-Pro 在设计上进行了三次激进手术：

  1. 候选项扩展至 10 选 1：将选项从 4 个扩展为最多 10 个（A 到 J），将随机猜测期望值从 25% 直降至 10%，大幅压低了模型“撞大运”的得分底线。
  2. 引入高质量推理密集型学科：大幅削减纯粹依靠死记硬背的事实性题目，将重心向大学物理、生物化学、离散数学、工程计算等强推理学科倾斜。
  3. 全面转向思维链（Chain-of-Thought, CoT）评估：不再采用单 Token 条件概率打分，强制要求模型展开逐步推演，更加贴近真实工业问答环境。

实验表明，在 MMLU 上得分达到 88% 的旗舰模型，在切换至 MMLU-Pro 后得分普遍回落至 60%~70% 区间，重新拉开了前沿模型之间的梯队差距。

2.3 CMMLU：中文综合学科基准的本土化重构

为了精准评估大模型在中文语境下的学术与常识理解深度，Li 等人构建了 CMMLU（Comprehensive Chinese Multitask Language Understanding）。CMMLU 覆盖了基础教育、大学学科、中国公务员考录、法律司法考试、执业医师考核等 67 个专业科目，共计 11528 道题目。

与单纯机器翻译 MMLU 的早期中文基准不同，CMMLU 具有强烈的中国本土文化与制度特色。例如其中包含了中国传统历史事件、古代汉语诗词鉴赏、中国近现代法学及本土民俗医学等。评测中文模型在 CMMLU 上的表现，能够直接揭示模型在跨语言对齐过程中的文化底蕴、制度常识及本土法律合规能力。

3. 复杂数学逻辑推理：GSM8K、MATH 到 AIME 2024

数学推理是大语言模型符号建模与逻辑推演能力的“试金石”。数学问题的输出通常是精确数值或封闭表达式，具备不容置疑的客观正确性标准，因而成为后训练（尤其是强化学习与过程监督）最核心的攻坚阵地。

💡 实践建议：数学基准评测的 Prompt 与格式规范

评测不同难度的数学基准时，提示词的设计直接决定指标的浮动。对于 GSM8K，标准 Few-shot CoT 提示格式通常约定以 #### <数字> 结尾；而在零样本（0-shot CoT）下，通常在 Prompt 末尾强制追加 Please reason step by step, and put your final answer within \boxed{}.，统一输出锚点以便正则解析。

3.1 GSM8K：初等应用题的推理起跑线

GSM8K（Grade School Math 8K）由 OpenAI 于 2021 年推出，包含 8500 道美国小学水平的多步应用题（7473 题训练集，1319 题测试集）。解决题目通常需要 2 到 8 个算术步骤，涵盖四则运算、分数比例和简单代数方程。其答案必须为严格整数。

在当前的后训练评测体系中，GSM8K 准确率早已成为基准门槛。开源 7B~8B 规模的优秀模型（如 Llama-3-8B-Instruct、Qwen2.5-7B-Instruct）在 8-shot 或 0-shot CoT 下的得分均已超过 80%~85%。GSM8K 主要用于监控模型是否具备基础多步推理骨架，一旦在后训练迭代中发现 GSM8K 指标发生超过 2% 的下滑，往往意味着 SFT 或对齐策略引发了严重的数学概念遗忘或过度简短化。

3.2 MATH：高中奥林匹克级挑战

MATH 数据集由 Hendrycks 等人从 AMC 10、AMC 12、AIME 以及高中数学联赛中筛选提炼而成，包含 12500 道极富挑战性的数学难题（测试集 5000 题）。题目划分为 7 个分支学科（代数、计数与概率、几何、数论、预备微积分等），难度严格划分为 Level 1 到 Level 5。

与 GSM8K 不同，MATH 题目的最终答案不仅包含整数，还涵盖多项式、无理根式、分数、区间乃至 LaTeX 排版公式（如 \frac{3\sqrt{5}}{2}）。这给自动提取与等价性判决带来了极高的工程挑战。传统的字符串精准匹配（Exact Match）在此彻底失效，必须引入符号代数引擎（如 SymPy）对模型输出与真实答案进行解析化约与数值差值判定。

3.3 AIME 2024：前沿长思维链与测试时计算的决战场

随着以 OpenAI o1、DeepSeek-R1 为代表的长思维链（Reasoning LLM）模型的问世，传统基准在区分顶尖推理智能体时再次失效。AIME（American Invitational Mathematics Examination）成为衡量最顶层数学逻辑推演的黄金标尺。AIME 试卷每套包含 15 道极具深度的奥林匹克进阶题目，答案为 000 到 999 之间的三位整数。

在 AIME 评测中，模型必须展开上万甚至数万 Token 的深度推导、自省反思、死胡同回溯与多路验算。评估 AIME 2024 时，除了常规的单次贪婪解码通过率 pass@1 外，通常采用 pass@k 与 Majority Voting (Consensus@k) 机制来衡量模型测试时计算（Test-Time Compute）扩展带来的收益：

\[ \mathrm{pass@}k = \mathbb{E}\left[1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}\right] \]

其中 \( n \) 为每个题目采样的总候选解数量，\( c \) 为其中正确解的数量，\( k \le n \)。

4. 代码与软件工程：从 HumanEval/MBPP 到 SWE-bench

代码生成评测的最大优势在于其绝对可验证性（Objective Verifiability）。代码不存在模糊的语言修辞争议，只需在沙箱中运行预置的单元测试用例（Unit Test Cases），通过断言判断逻辑的绝对正确性。

4.1 HumanEval 与 MBPP：经典的单函数评测基准

HumanEval 是 OpenAI 在发布 Codex 模型时提出的经典函数合成测试集，包含 164 个手工编写的 Python 编程题目。每个样本包含函数签名、Docstring 说明文档、函数体提示以及 3~10 个私有测试断言。

MBPP（Mostly Basic Python Problems）由 Google 团队构建，包含 974 个面向初学者的 Python 短任务，强调基础语法、列表推导、字典处理与标准库应用。MBPP 通常使用 3-shot 设置。

然而，HumanEval 与 MBPP 的局限性在当今后训练中越发突出：题目规模过小（仅百题量级）、严重依赖合成语法练习，且未涉及外部三方依赖、环境依赖与多文件交互。最严重的是，由于代码公开在 GitHub 多年，几乎所有大模型的预训练语料都严重“背过”了这些答案，导致 pass@1 指标出现严重虚高。

4.2 SWE-bench：仓库级真实软件工程的终极试炼

为了终结“函数级刷题”的虚假繁荣，普林斯顿大学与芝加哥大学团队于 2023 年联合推出了 SWE-bench（Software Engineering Benchmark）。该基准直接从 12 个广受欢迎的开源 Python 软件仓库（如 Django、SymPy、Sphinx、scikit-learn、Matplotlib 等）中提取了 2294 个真实的 GitHub Pull Request 与对应的 Issue 描述。

在 SWE-bench 评测中，大模型必须扮演全功能的软件工程师智能体（Software Engineering Agent）：

  • 全仓库上下文理解：模型面对的是成千上万行代码的真实仓库，必须通过 grep、find 或目录树浏览定位涉事代码行。
  • 生成 Git 补丁（Unified Diff）：模型不能仅生成单个代码片段，而必须输出标准补丁，精确修改多个文件并保持语法规范。
  • 双向单元测试验证（FAIL_TO_PASS & PASS_TO_PASS）：测试用例包含两组：原来失败的测试在打入模型补丁后必须全部通过（FAIL_TO_PASS）；原本正常的系统回归测试必须依然保持全绿（PASS_TO_PASS），严禁引入回归缺陷。

由于完整版 SWE-bench 评测极其庞大且包含不严谨的偶发失败用例，社区进一步衍生出 SWE-bench Lite（300 题精选）与 SWE-bench Verified（经由人类专家手工核实确保题目自洽、环境百分百可复现的 500 题子集）。当前即便是顶尖的前沿大模型，在 SWE-bench Verified 上的独立解决率（Resolve Rate）也仅在 40%~55% 左右，展现出对模型长程规划、环境交互与调试排错能力的终极区分度。

5. 精准控制与真实交互：IFEval 与 MT-Bench / Arena-Hard

5.1 IFEval：可量化验证的指令遵循测试

很多大模型在学术基准上能写出高深论文，但在执行具体业务指令时却屡屡犯错。例如业务方要求“输出不得包含字母 e”、“必须包含不少于 3 个段落且首段必须以指定短语开头”、“以纯 JSON 格式输出且不得添加反引号”。这类指令属于可验证指令遵循（Verifiable Instruction Following）。

由 Google 团队推出的 IFEval（Instruction Following Evaluation）是评测这一能力的行业金标准。IFEval 包含 541 个精巧构造的 Prompt，涵盖 25 种严格的形式化指令约束：

  • 格式约束：纯 JSON 输出、包含特定数量的高亮标记、带有指定数量的 Markdown 标题等。
  • 长度与数量约束：字数严格介于特定区间、段落数量恰好为 N、句子数量必须大于某阈值等。
  • 词汇与语言约束：必须出现/不得出现特定关键词、全篇采用全大写或全小写、使用特定语言回答等。
  • 引用与特定句式：结尾必须包含指定免责声明、开头必须复述用户提问等。

IFEval 的所有指标均通过 Python 规则脚本严格自动化断言，完全剥离了 LLM 裁判的主观偏好。其统计结果分为四个维度：Loose Accuracy（宽松准确率）与 Strict Accuracy（严格准确率），并在提示词级别（Prompt-level）与指令原子级（Instruction-level）分别统计。

5.2 MT-Bench 与 Arena-Hard：多轮与开放域交互的试金石

对于开放域对话，人工评估成本昂贵且难以自动化回归。以 LMSYS 推出的基准为代表：

MT-Bench（Multi-Turn Benchmark）：精心设计了 80 个多轮对话任务，覆盖 8 大领域（写作、角色扮演、抽取、推理、数学、代码、知识问答、STEM）。评测重点在于第一轮模型给出初始回答后，第二轮评测系统会提出追问或要求修改。通过 GPT-4 裁判在 1 到 10 分尺度上展开评分，能够敏感地检测出模型在多轮交互中的上下文遗忘与指令漂移。

Arena-Hard：为了克服 MT-Bench 题目过于简单、模型区分度衰减的困境，LMSYS 团队从 Chatbot Arena 真实人类交互海量日志中筛选出 500 道最高频、最严苛、最具挑战性的提示词构建了 Arena-Hard-Auto。其测试结果与真实人类竞技场排名的斯皮尔曼等级相关系数（Spearman's \( \rho \)）高达 0.95 以上，被公认为最敏锐反映模型对人类偏好拟合度的主观基准之一。

7.1 IFEval 可验证指令判决器实现

以下代码实现了 IFEval 中最关键的五种可验证原子约束（包含指定高频词、禁止出现特定词、特定最小字数、段落数严格匹配、纯 JSON 格式包装）的严格判定逻辑。

eval_ifeval_verifier.py 
import json
import re
from typing import Dict, Any, List, Tuple

class IFEvalVerifier:
    """IFEval 核心形式化指令判决器"""

    @staticmethod
    def verify_word_count(text: str, min_words: int = None, max_words: int = None) -> bool:
        """检查英文单词数量是否处于区间 [min_words, max_words]"""
        words = re.findall(r"\b\w+\b", text)
        count = len(words)
        if min_words is not None and count < min_words:
            return False
        if max_words is not None and count > max_words:
            return False
        return True

    @staticmethod
    def verify_forbidden_words(text: str, forbidden_words: List[str]) -> bool:
        """检查是否严格未包含禁止词汇（不区分大小写）"""
        lowered = text.lower()
        for word in forbidden_words:
            pattern = rf"\b{re.escape(word.lower())}\b"
            if re.search(pattern, lowered):
                return False
        return True

    @staticmethod
    def verify_paragraph_count(text: str, expected_paragraphs: int) -> bool:
        """检查段落数量是否完全符合预期（由连续双换行隔开）"""
        paragraphs = [p.strip() for p in text.strip().split("\n\n") if p.strip()]
        return len(paragraphs) == expected_paragraphs

    @staticmethod
    def verify_json_format(text: str) -> bool:
        """检查文本是否为纯 JSON 对象，不得混杂任何多余修饰文本或代码块标记"""
        stripped = text.strip()
        # 若包含 markdown ```json 标记，视为未能纯粹遵循 JSON 输出约束
        if stripped.startswith("```") or stripped.endswith("```"):
            return False
        try:
            json.loads(stripped)
            return True
        except Exception:
            return False

    def evaluate_response(self, response: str, criteria: Dict[str, Any]) -> Tuple[bool, Dict[str, bool]]:
        """综合评估单条响应是否满足全部声明的指令约束"""
        results = {}
        
        # 1. 词数校验
        if "word_count" in criteria:
            cfg = criteria["word_count"]
            passed = self.verify_word_count(response, cfg.get("min"), cfg.get("max"))
            results["word_count"] = passed
            
        # 2. 禁用词校验
        if "forbidden_words" in criteria:
            passed = self.verify_forbidden_words(response, criteria["forbidden_words"])
            results["forbidden_words"] = passed
            
        # 3. 段落数校验
        if "paragraph_count" in criteria:
            passed = self.verify_paragraph_count(response, criteria["paragraph_count"])
            results["paragraph_count"] = passed

        # 4. JSON 纯粹性校验
        if criteria.get("require_pure_json", False):
            passed = self.verify_json_format(response)
            results["require_pure_json"] = passed

        overall = all(results.values()) if results else True
        return overall, results

# ================= 单元测试示例 =================
if __name__ == "__main__":
    verifier = IFEvalVerifier()
    
    sample_text_1 = (
        "Artificial intelligence is transforming industries.\n\n"
        "Machine learning models are becoming increasingly efficient and helpful."
    )
    
    spec_1 = {
        "word_count": {"min": 10, "max": 30},
        "forbidden_words": ["bad", "wrong"],
        "paragraph_count": 2
    }
    
    passed_1, details_1 = verifier.evaluate_response(sample_text_1, spec_1)
    print(f"用例 1 评估结果: {passed_1}, 详细分项: {details_1}")

    sample_json = '{"name": "Alice", "role": "researcher", "active": true}'
    spec_json = {"require_pure_json": True}
    passed_2, details_2 = verifier.evaluate_response(sample_json, spec_json)
    print(f"用例 2 (纯 JSON) 评估结果: {passed_2}")

7.2 数学推理答案提取与符号等价化验引擎

在 MATH 基准测试中，由于 LaTeX 排版差异，如 \frac{1}{2} 与 0.5，或 x^2 - 1 与 (x+1)(x-1) 语义完全等价但字符串截然不同。以下模块实现了严苛的 LaTeX 盒体抽取与基于 SymPy 的代数化简等价比对。

eval_math_extractor.py 
import re
import sympy
from typing import Optional

class MathAnswerExtractor:
    """数学答案提取器与符号等价判别器"""

    @staticmethod
    def extract_boxed_content(text: str) -> Optional[str]:
        """递归解析文本中最深层或最后一个 \\boxed{...} 内的答案"""
        idx = text.rfind("\\boxed{")
        if idx == -1:
            return None
        start = idx + len("\\boxed{")
        depth = 1
        i = start
        while i < len(text) and depth > 0:
            if text[i] == '{':
                depth += 1
            elif text[i] == '}':
                depth -= 1
            i += 1
        if depth == 0:
            return text[start:i-1].strip()
        return None

    @staticmethod
    def normalize_latex(expr: str) -> str:
        """规范化 LaTeX 数学表达式字符串"""
        if not expr:
            return ""
        s = expr.strip()
        # 移除货币符号与空格
        s = s.replace("$", "").replace(" ", "").replace("\n", "")
        # 标准化常见乘号与除号
        s = s.replace("\\times", "*").replace("\\cdot", "*").replace("\\div", "/")
        # 处理常见分数 \frac{a}{b} -> (a)/(b)
        frac_pattern = re.compile(r"\\frac\{([^{}]+)\}\{([^{}]+)\}")
        while frac_pattern.search(s):
            s = frac_pattern.sub(r"((\1)/(\2))", s)
        return s

    def is_equiv(self, pred_raw: str, gold_raw: str, tolerance: float = 1e-5) -> bool:
        """判断模型预测答案与标准答案是否在代数上等价或浮点误差内一致"""
        pred = self.extract_boxed_content(pred_raw) or pred_raw
        gold = self.extract_boxed_content(gold_raw) or gold_raw
        
        # 快速完全字符串精确匹配
        if pred.strip() == gold.strip():
            return True

        norm_pred = self.normalize_latex(pred)
        norm_gold = self.normalize_latex(gold)
        if norm_pred == norm_gold:
            return True

        # 尝试数值直接对比
        try:
            val_pred = float(norm_pred)
            val_gold = float(norm_gold)
            return abs(val_pred - val_gold) < tolerance
        except ValueError:
            pass

        # 借助 SymPy 展开代数等价性化简验证
        try:
            sym_pred = sympy.sympify(norm_pred)
            sym_gold = sympy.sympify(norm_gold)
            diff = sympy.simplify(sym_pred - sym_gold)
            if diff == 0:
                return True
        except Exception:
            pass

        return False

# ================= 单元测试验证 =================
if __name__ == "__main__":
    extractor = MathAnswerExtractor()
    
    # 测试用例 1: 复杂分数与小数等价
    gold_ans = "The final result is \\boxed{\\frac{3}{4}}."
    model_ans_1 = "After calculating, we find \\boxed{0.75}"
    print(f"分数与小数等价性: {extractor.is_equiv(model_ans_1, gold_ans)}")  # True

    # 测试用例 2: 代数多项式因式分解等价
    gold_poly = "\\boxed{(x + 1)(x - 1)}"
    model_poly = "\\boxed{x^2 - 1}"
    print(f"多项式化简等价性: {extractor.is_equiv(model_poly, gold_poly)}")  # True

7.3 统一轻量级多基准评测自动化运行流水线

为了降低后训练团队对接基准的工程门槛，下面的脚本封装了一个轻量统一的多基准测试流水线。该脚本定义了通用的 Dataset Loader、批处理推理推理引擎接口与 Metrics 汇总报表导出模块。

unified_benchmark_runner.py 
import json
import argparse
from typing import List, Dict, Any

class MockLLMEngine:
    """用于流水线演示的模型推理模拟器（真实场景下替换为 vLLM 或 SGLang）"""
    def generate(self, prompts: List[str], max_tokens: int = 1024) -> List[str]:
        responses = []
        for p in prompts:
            if "GSM8K" in p:
                responses.append("Let's calculate step by step.\n10 * 2 = 20.\n#### 20")
            elif "IFEval" in p:
                responses.append('{"status": "success", "result": "valid json response"}')
            else:
                responses.append("The answer is \\boxed{42}")
        return responses

class UnifiedBenchmarkRunner:
    """统一评测驱动器"""
    def __init__(self, engine: Any):
        self.engine = engine

    def run_gsm8k_eval(self, test_data: List[Dict[str, str]]) -> float:
        """执行 GSM8K 批处理评测"""
        prompts = [f"GSM8K Problem: {item['question']}\nPlease reason step by step." for item in test_data]
        outputs = self.engine.generate(prompts)
        
        correct = 0
        for out, item in zip(outputs, test_data):
            # 提取 #### 后的最终答案
            match = re.search(r"####\s*(-?[\d,]+)", out)
            pred = match.group(1).replace(",", "").strip() if match else ""
            gold = item["answer"].split("####")[-1].strip().replace(",", "")
            if pred == gold:
                correct += 1
        acc = (correct / len(test_data)) * 100.0 if test_data else 0.0
        return acc

    def run_ifeval_eval(self, test_data: List[Dict[str, Any]]) -> float:
        """执行简易 IFEval 纯 JSON 格式遵循评测"""
        prompts = [f"IFEval Prompt: {item['prompt']}" for item in test_data]
        outputs = self.engine.generate(prompts)
        
        passed_count = 0
        for out in outputs:
            try:
                json.loads(out.strip())
                passed_count += 1
            except Exception:
                pass
        return (passed_count / len(test_data)) * 100.0 if test_data else 0.0

if __name__ == "__main__":
    engine = MockLLMEngine()
    runner = UnifiedBenchmarkRunner(engine)

    # 模拟 GSM8K 测试数据
    gsm_samples = [
        {"question": "What is 10 times 2?", "answer": "10 * 2 = 20 #### 20"},
        {"question": "What is 5 plus 5?", "answer": "5 + 5 = 10 #### 10"}
    ]
    gsm_acc = runner.run_gsm8k_eval(gsm_samples)
    print(f"[Benchmark] GSM8K pass@1: {gsm_acc:.2f}%")

    # 模拟 IFEval 测试数据
    ifeval_samples = [
        {"prompt": "Output a greeting in strictly valid JSON format."}
    ]
    ifeval_acc = runner.run_ifeval_eval(ifeval_samples)
    print(f"[Benchmark] IFEval Strict JSON Accuracy: {ifeval_acc:.2f}%")

8. 评测指标防虚标实战经验与踩坑排查

在后训练算法开发中，工程人员往往会遭遇“评测数字很光鲜，实测体验一团糟”的尴尬境地。这种现象的根源在于评测协议的不对齐与评测黑客行为。以下梳理在评测基准测试时必须规避的典型陷阱：

⚠️ 常见误区：评测环境的“蝴蝶效应”

1. 对数似然选项打分 vs 生成式自由解码：MMLU 的官方评测存在两种流派。部分团队在报告分数时使用限制在 A/B/C/D 四个 Token 上的 Log-likelihood 概率；而另一些团队使用生成式 CoT 并正则提取。两者在相同模型上的差距可高达 5%~10%。不可在对比报告中混淆两者的分数。

2. Chat Template 特殊标记被吃掉：在评测 SFT 或 RLHF 模型时，若未正确应用模型的 tokenizer.apply_chat_template，导致 <|im_start|>、<|im_end|> 标记丢失，模型可能会退化为续写模式，引发格式判定断崖式下跌。

3. 截断长度（max_tokens）设置过小：对于 MATH 或 AIME 这类长链推理基准，模型可能需要 8192 乃至 16384 个 Token 展开反思。若 max_tokens 粗暴设为 1024，模型尚未输出 \boxed{} 答案即被强制截断，导致大量“假阴性（False Negative）”未通过判罚。

🚨 重要警告：SWE-bench 评测环境隔离要求

SWE-bench 会在本地执行模型生成的代码修补补丁并运行仓库的单元测试脚本。严禁在没有 Docker 容器沙箱隔离的宿主机上裸跑 SWE-bench！部分测试用例或恶意模型生成可能包含 rm -rf、破坏性端口占用或系统配置篡改，轻则破坏评测环境一致性导致评分不可复现，重则导致服务器核心文件丢失。

9. 本章小结

  • 评测矩阵的纵深演进：基准测试从早期的多项选择事实记忆（MMLU、CMMLU）全面向抗饱和强推理（MMLU-Pro）、奥赛级数学（AIME 2024）、可验证指令遵循（IFEval）和仓库级代码工程（SWE-bench）跃升。
  • 机制决定公正性：代码沙箱执行与代数符号化验（SymPy）具备最高的客观性与复现性；规则校验能高效约束格式行为；而开放对话必须依赖模型裁判与人类偏好基准（MT-Bench、Arena-Hard）。
  • 度量协议的统一至关重要：脱离提示词模板（0-shot vs Few-shot CoT）、生成超参（贪婪 vs 采样）与判别提取方式的单纯分数对比没有任何学术与工业意义。规范化自动化流水线是研发闭环的基石。
🧠 自测题（点击展开答案）
问题 1：为什么 MMLU-Pro 将题目选项从 MMLU 的 4 选 1 扩展至 10 选 1？其核心数学机理是什么？

核心机理是大幅压缩盲猜期望得分，提升区分度。在 4 选 1 机制下，随机猜测即可获得 25% 的底线得分，当模型能力达到一定高度后，由于误差区间与猜测概率重叠，模型优劣的统计显著性降低。扩展到 10 选 1 后，随机猜测底线骤降至 10%，显著放大了顶尖推理模型与中庸模型在真实知识提取上的方差，同时有效对抗了针对少量候选项选项分布规律的“作弊微调”。

问题 2：在评测 MATH 数据集时，为什么不能直接使用字符串精确匹配（Exact Match），而必须引入 SymPy 或规范化解析引擎？

因为数学表达具有天然的多形式语义同构性。例如模型可能输出 \frac{2}{4}、\frac{1}{2} 或 0.5；在代数式中，(x+1)^2 与 x^2 + 2x + 1 在字符串维度上差异巨大，但数学本质完全等价。直接使用精确字符串匹配会导致大量数学推导完全正确但排版风格不同的样本被误判为错误，严重低估模型的真实逻辑能力。

问题 3：在 SWE-bench 评测中，什么是 FAIL_TO_PASS 和 PASS_TO_PASS 测试用例？为什么两者必须同时满足？

FAIL_TO_PASS 是与当前 Issue 缺陷直接绑定的测试用例，在修补前必然运行失败；模型生成的补丁必须让这部分用例转为全部通过，证明缺陷已被修复。PASS_TO_PASS 则是软件仓库中原有的大量历史回归测试，在修补前处于正常通过状态；打入补丁后它们必须依然保持全绿。两者同时满足才能证明补丁不仅成功修复了特定问题，而且没有破坏既有软件功能的向后兼容性（Zero Regression）。
