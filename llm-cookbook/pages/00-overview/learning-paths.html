学习路径指南

这本手册有十六篇、一百余页，但没人需要全部读完。你的角色决定了哪条路径效率最高——全栈交付从模型接入走到部署，算法路线深入训练和推理，系统路线聚焦性能与运维，研究路线追踪原理与前沿。选错路径浪费的不只是时间，也会消耗信心。这一页给出四条完整路线、每条路线的验收标准，以及一份「卡住了怎么办」的排障指南。

一图看懂

四条路径不是难度递增的关系，而是目标不同。应用与检索主题不需要学数学，原理与前沿主题不必精通部署。找到你的象限，只走那条路。这本手册的正确用法不是「从第一页读到最后一页」，而是「拿着你的问题，沿一条路径走进去，遇到不懂的名词再横向查」。

论文原图：为什么训练与系统主题从 Transformer 开始

学习路径不是把章节排成一条漂亮的目录，而是要尊重知识之间的依赖。训练与系统主题一开始就会遇到「为什么要量化」「为什么显存会爆」「为什么某个推理引擎更快」这些问题；如果不知道模型内部的张量从哪里来，后面的系统优化就只能背结论。下面复用 Transformer 原论文的总架构图，把这条路径的第一个验收点落到一个可观察对象上：你要能指出输入、注意力、前馈网络、残差连接和输出投影分别在哪里。

新手读图先不要试图记住所有箭头：左侧编码器把输入加工成上下文表示，右侧解码器在掩码注意力约束下逐步生成输出；每个色块都可以看成一门后续课程的入口。读到 03 篇时，你应能解释「多头注意力」怎样让不同位置交换信息；读到 05 篇时，你应能指出这些矩阵运算为什么会受到显存层级影响；读到 08-09 篇时，你应能把右侧逐 token 生成和 KV Cache、批处理联系起来。

这张图也解释了为什么本页坚持「阶段验收」而不是只报阅读页数：如果你读完架构却不能从图上讲出一个 token 如何流经网络，那么继续读训练和部署只会把不牢固的概念叠起来。反过来，只要你能用自己的话复述一次数据流，再用一个小模型打印张量形状，后续章节就有了可验证的落脚点。

先做一次技术定位：三个问题

很多人一上来就问「大模型该从哪学起」，这个问题没有通解，因为它缺了最关键的前提：你打算交付什么。同样是「学会大模型」，一个要上线客服机器人的后端工程师和一个要发论文的研究生，需要的知识集合重叠不到三成。

下面三个问题能在五分钟内把你定位到一条路径上。回答时请按未来三个月真实要做的事来选，而不是按「我想成为什么样的人」来选——路径可以之后再换，但走错三个月的成本很高。

定位问题你的回答指向的路径
① 三个月后你要交付什么？一个能用的产品功能（问答、摘要、客服）应用与检索主题
一套稳定、可回归的提示与评测流程提示与上下文主题
一个上线的模型服务（微调过的、自托管的）训练与系统主题
一篇可复现的实验、报告或论文原理与前沿主题
② 你能接受的学习周期？一周以内，越快越好应用与检索主题

三个答案不一致怎么办 很常见，说明你处在两条路径的过渡带。此时的经验法则是：按「算力」这一问选路径，按「交付物」这一问选深度。没有 GPU 却想学分布式训练，读完也没法验证，知识会很快忘掉；反过来，有卡却只学提示工程，是浪费了最稀缺的资源。

还有一类读者不属于任何一条：技术管理者与产品经理。你们不需要走完整路径，但需要看懂四条路径各自要花多少人、多少时间、卡在哪。建议只读每条路径的「目标与时长」卡片、本页的「四条路径对比」表，再加上 技术全景图 与 服务化与推理经济学 两页，就足以做资源决策。

路线一：应用与检索——从 API 到可引用答案

目标与时长

目标：能独立用 LLM API 搭建一个可用的业务功能（客服、摘要、文档问答）。
预计时长：3-5 天。
背景要求：会写基础 Python，不需要数学。

不需要学什么

不需要学 Transformer 架构、不需要学训练、不需要学 CUDA。把模型当黑盒——输入 prompt，输出结果，中间不需要你管。

阅读路线

  1. 什么是大模型 — 建立基本概念，理解能力边界
  2. 模型家族与选型 — 知道该用哪个模型，为什么
  3. 提示工程 — 最核心的技能，学会怎么跟模型说话
  4. 结构化输出与约束解码 — 让模型返回你能直接解析的 JSON，而不是散文
  5. RAG 检索增强生成 — 让模型基于你的文档回答
  6. 实战：搭建 RAG 系统 — 跟着代码做一遍

第一天就应该跑通的那 20 行

应用与检索主题最容易犯的错，是花三天读文档却一行代码都没跑。正确顺序是先跑通再理解：拿到 API key 的第一个小时，就应该有一个能返回文本的函数。下面这段骨架不依赖任何 SDK，只用 HTTP 请求，因此换任何一家 OpenAI 兼容服务商都能用——具体的鉴权头、字段名与模型名以你所选服务商的官方文档为准。

# 应用与检索主题的第一个程序:把模型当成一个普通函数来用
# 端点路径、字段名、鉴权方式以你所选服务商的官方文档为准
import os
import requests

API_BASE = os.environ["LLM_API_BASE"]   # 形如 https://.../v1/chat/completions
API_KEY  = os.environ["LLM_API_KEY"]
MODEL    = os.environ.get("LLM_MODEL", "your-model-name")

def ask(question, system="你是一个严谨的技术助手,不确定的地方要明确说不确定。"):
    payload = {
        "model": MODEL,
        "messages": [
            {"role": "system", "content": system},
            {"role": "user",   "content": question},
        ],
        "temperature": 0.2,   # 业务场景通常要低温度,保证可复现
    }
    resp = requests.post(
        API_BASE,
        headers={"Authorization": "Bearer " + API_KEY},
        json=payload,
        timeout=60,
    )
    resp.raise_for_status()
    return resp.json()["choices"][0]["message"]["content"]

if __name__ == "__main__":
    print(ask("用三句话解释什么是向量数据库"))

跑通之后，把它改造成三个练习，你的第一天就没白过：① 把 temperature 从 0.2 调到 1.2，同一个问题连问五次，观察输出的稳定性差异，这会让你对 解码策略 有第一手体感；② 在 system 里加一句「只输出 JSON，不要任何解释」，看模型多久违规一次，这是 结构化输出 存在的理由；③ 故意问一个它不可能知道的内部信息，观察它是否编造，这是 幻觉 的现场演示。

应用与检索主题的核心技能 不是写代码——是拆解问题。LLM 擅长什么不擅长什么，哪些步骤该交给它，哪些该用传统代码。这个判断力比任何 prompt 技巧都重要。一个成熟的判断标准是：凡是有确定算法的（排序、计算、查库、权限校验），一律交给传统代码；只有需要「理解语义」「组织语言」「模糊匹配」的环节才交给模型。

用一张体验图看应用与检索主题的第一周长什么样。注意第 3 天那个明显的低谷——几乎所有人都会在「demo 能跑但结果不稳定」这一步掉进去，这不是你的问题，是这条路径的固有形状。

路线二：提示与上下文——理解输入如何改变行为

目标与时长

目标：精通 prompt 设计、few-shot、思维链、结构化输出，能把一个任务的准确率从 60% 优化到 90%。
预计时长：1-2 周。
背景要求：扎实的编程基础，对 LLM 有基本使用经验。

关键区别

提示与上下文主题和应用与检索主题的区别在于系统性：不是试到能用就停，而是建立可评估、可回归、可迭代的 prompt 管理流程。

阅读路线

  1. 提示工程 — 核心技术：few-shot、CoT、self-consistency
  2. 结构化输出与约束解码 — 格式合法性的技术底座，工具调用的前置知识
  3. RAG 检索增强生成 — prompt + 检索的组合技
  4. 上下文工程 — 管理有限的上下文窗口
  5. Agent 基础范式 — 让模型自主规划和使用工具
  6. 评估方法论 — 怎么量化 prompt 效果
  7. Prompt 版本管理与评估门禁 — 工程化你的 prompt

这条路径真正的分水岭：有没有评测集

判断一个人是「会写提示词」还是「提示与上下文主题」，只需要问一个问题：你怎么知道新版 prompt 比旧版好？

如果答案是「我试了几个例子感觉更好了」，那还停留在手工阶段。这种做法在样本量小于几十的时候几乎必然误判——模型输出本身带随机性，两版 prompt 的真实差距如果只有几个百分点，靠肉眼看十条样本根本区分不出来，你看到的差异大部分来自采样噪声。

提示与上下文主题的标准动作是：先固定一个 golden set（几十到几百条带标准答案的样本，覆盖典型场景和已知的失败案例），每次改 prompt 都跑一遍全集，看聚合指标而不是个别样例。这套流程的细节在 Prompt 版本管理与评估门禁，评分方法的偏差来源在 评估方法论。

提示与上下文主题最常见的自我欺骗 用同一批样例既做优化又做验证。你在这十条上反复调 prompt，最后在这十条上得了满分——这和在训练集上测试没有区别。golden set 必须在优化开始前就冻结，并且留一部分「从未用于调优」的样本作为最终验收。这个问题的严肃版本叫数据污染，见 数据污染与评估可信度。

路线三：训练与系统——从目标函数到服务性能

目标与时长

目标：能独立完成模型微调、量化部署、推理优化、线上运维。
预计时长：4-8 周。
背景要求：Python + PyTorch 基础，了解深度学习。

这是手册的主干

训练与系统主题是这本 Cookbook 的核心受众。手册从第三篇到第十二篇主要为你服务——架构、训练、推理、效率、运维。

阅读路线

  1. Transformer 完整架构 — 理解你训练的模型长什么样
  2. 注意力机制 — 最核心的组件，必须吃透
  3. 训练理论（06-07 篇）：预训练目标 → Scaling Laws → 推理强化学习 → 免奖励模型对齐
  4. 前沿探索（04 篇 + 08 篇）：线性与混合注意力 → 推理模型 → 推理时扩展
  5. 可解释性（13 篇）：机制可解释性基础 → 稀疏自编码器与电路分析
  6. 从零实现：从零实现 miniGPT — 亲手搭建一个可训练的模型

原理与前沿主题路径有一个和其他三条完全不同的特点：它不是线性的，而是「深度优先 + 频繁回溯」。读一篇论文时你会不断遇到不熟悉的前置概念，正确做法是当场跳回手册对应页把它补上，而不是硬着头皮读完再说。这也是为什么手册对原理与前沿主题而言更像索引而不是教材——你需要的是「按名词快速定位到解释」的能力。

另一个提醒：复现比阅读更重要。读懂一篇论文的标志不是能复述它的方法，而是能说清它的实验在什么条件下会失效。这个判断力只能从亲手跑实验里来。手册第 15 篇的六条实战路线，每一条都对应前面某一篇的理论，是最便宜的动手入口。

卡住了怎么办：一份排障流程

自学过程中最消耗人的不是难度，而是卡住却不知道自己卡在哪。把常见的卡点归类，会发现只有四种，而且每种的解法完全不同——用错解法（比如对着「前置知识缺失」硬读原文）会让人误以为自己不适合这个方向。

卡点类型典型表现错误做法正确做法
前置知识缺失 一段话里有三个没听过的名词 硬读，或者去搜更难的原始论文 回查手册对应的基础页，补完再回来。手册的交叉链接就是为此设计的

跨路径的共同必修

不管走哪条路，以下几个页面所有人都应该看。它们不属于任何一条路径的专属知识，而是「不看就会在别处反复吃亏」的公共地基：

  • 什么是大模型 — 理解能力边界，避免不切实际的期望。所有失败的 LLM 项目里，有相当一部分死于一开始就把它用在了它做不了的事上。
  • 技术全景图 — 知道整个技术栈长什么样，不迷路。也标出了具身智能、世界模型这些相邻但不在手册范围内的领域，避免你搜错方向。
  • 模型家族与选型 — 知道用哪个模型，这是所有项目的起点，也是最容易被授权条款和数据合规反噬的一步。
  • 幻觉与事实性 — 无论你做应用还是做训练，都躲不开「它一本正经地编」这个问题，早点建立心理预期。
  • 评估方法论 — 没有评估就没有改进。这一页对四条路径都成立，只是每条路径关心的指标不同。
深入：如何把「读完一页」变成可执行的阶段验收

阶段验收的核心不是考试，而是让知识变成一个可以观察的动作。以「理解注意力」为例，低质量目标是「看完 attention.html」；高质量目标是「给定一个长度为 3 的 token 序列，能手算 QKᵀ 的形状、说明 softmax 的作用，并解释为什么长序列会带来更高的内存压力」。后一个目标同时检查概念、公式和工程后果。

执行时采用三步闭环：先用自己的话画一张不看资料的数据流图，再运行一个最小代码实验，最后用一组新例子解释失败原因。只完成第一步，容易停留在会复述；只完成第二步，容易变成会调用库但不懂机制；三步都完成，才说明知识已经能迁移到具体问题。

每个阶段都应该留下一个可复用产物：应用与检索主题留下 API demo 和 30 条评测集，提示与上下文主题留下 prompt 版本与回归报告，训练与系统主题留下显存账本和部署基准，原理与前沿主题留下复现实验与误差分析。产物比勾选章节更可靠，因为它能在下一阶段继续作为输入。

深入：为什么按角色分路径，比按难度分层更有效

大多数技术教程默认「从简单到复杂」的线性组织：先讲基础，再讲进阶，最后讲高级。这种组织方式在知识体系较小、依赖链较短时很好用，但在大模型这种横向极宽、纵向极深的领域会失效，原因有三个。

第一，依赖关系不是一条线，是一张有向图。做 RAG 需要知道嵌入向量，但完全不需要知道反向传播；做量化需要知道数值精度，但不需要知道 PPO。如果强行排成一条线，每个人都要为自己用不到的知识付出时间成本，而这个成本大到足以让大多数人在中途放弃。

第二，动机会在没有反馈的阶段耗尽。按难度分层意味着一个想做应用的人要先学两周数学才能碰到第一个能跑的东西。人类的学习动机高度依赖短周期反馈，两周无反馈几乎必然导致放弃。按角色分路径的核心价值，就是让每条路径在前三天内就产生一个可见成果。

第三，「难」是相对于目标而言的。对原理与前沿主题来说，规模律的推导是核心内容；对应用与检索主题来说，它是完全无关的细节——不是「太难所以以后再学」，而是「这辈子都不需要」。把它标成「高级」会误导应用与检索主题认为自己缺了什么，从而产生不必要的焦虑。

这也是本手册同时保留「难度标签」和「主题路径」两套导航的原因：难度标签描述的是单页内容的密度，路径描述的是页与页之间的推荐顺序。两者不冲突——一个应用与检索主题完全可以跳过所有标着「高级」的页，同时读完所有标着「入门」的页，仍然是一条完整的路径。反过来，原理与前沿主题也会需要读一些标着「入门」的页来快速建立某个陌生子领域的直觉。

最后一个实践建议：路径不是终身契约。绝大多数人的真实轨迹是先走应用与检索主题路径拿到手感，再按需要横向补提示工程或纵向补算法工程。先窄后宽，比先宽后窄的成功率高得多。

要点速查

  • 选路径比走路径重要：四条路径目标不同，不是难度递增。选错路径浪费的是信心。
  • 三个定位问题：三个月后交付什么、能接受多长周期、手上有什么算力。答案不一致时，按算力选路径、按交付物选深度。
  • 应用与检索主题：不需要数学，核心是问题拆解。3-5 天上手。第一天就要跑通代码，第 3 天的幻灭期靠「结构化输出 + 低温度 + 检索接地」渡过。
  • 提示与上下文主题：核心是系统化——可评估、可回归、可迭代。1-2 周。分水岭是有没有冻结的 golden set，而不是提示词写得漂不漂亮。
  • 训练与系统主题：手册核心受众，从架构到运维形成闭环。4-8 周，每两周必须有一个能跑的产物。最大的弯路是跳过架构直接学微调。
  • 原理与前沿主题：从底层往上读，数学是地基。手册是索引不是教材，读懂的标志是能说清方法的失效边界。
  • 验收看产物不看进度：「读完了」不是标准，「能做出什么」才是。每条路径都有三个可验证的里程碑。
  • 卡住先分类：前置缺失、缺例子、缺目标、纯疲劳——四种卡点解法完全不同，用错解法会加深挫败感。
  • 共同必修：what-is-llm、tech-map、model-families、hallucination、eval-methods——所有人都该看。
  • 路径可以换：先窄后宽的成功率远高于先宽后窄。绝大多数人的真实轨迹都是先做应用再按需补深度。
