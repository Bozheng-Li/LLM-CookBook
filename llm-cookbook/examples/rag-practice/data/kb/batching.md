# 连续批处理与吞吐

静态批处理要等一个批次里所有请求都生成完才能返回，最慢的那条决定整批的延迟。生成长度差异越大，GPU 空转越严重。

连续批处理（continuous batching，也叫 in-flight batching）在每个解码步之后检查：谁生成完了就立刻返回并释放槽位，队列里的新请求马上补进来。同样的硬件，吞吐通常能提升数倍。

这带来一个调度上的取舍。新请求需要先做 prefill（处理整个 prompt），而 prefill 是计算密集的；正在解码的请求是访存密集的。把一个长 prompt 的 prefill 插进来，会让所有正在解码的请求卡一下，表现为 TPOT（每 token 输出时间）尖刺。

Chunked prefill 是应对办法：把长 prompt 的 prefill 切成小块，每步只做一块，和解码请求混合在同一个批次里。这样 prefill 的计算填满了解码留下的算力空隙，TPOT 也不再有尖刺。

评估服务性能要分开看两个指标：TTFT（首 token 时间）主要由 prefill 和排队决定，TPOT 由解码步的批大小和访存决定。只报平均延迟会掩盖问题，至少要看 P95。
