# 评测大语言模型

评测设计的第一原则：别在你自己觉得简单的问题上让模型自证。测试集必须和训练数据隔离，而且要用外部公开基准，不能只靠模型内部一致性。

经典基准各测一面。MMLU 测多学科知识，HellaSwag 测常识推理，GSM8K 测数学解题，HumanEval 测代码生成。这些基准的真实分数和纸面分数差一个实现细节：采样与解码参数。同一个模型，温度 0 与温度 0.7、单次采样与多次采样再投票，GSM8K 可以差出十个点。

评测运行时的陷阱同样致命。参考实现的短路逻辑、越界访问、结果解析的容错性，都会让分数虚高。GSM8K 的经典教训是解析答案只认"答案是 X"格式，模型输出变体就判错——这测的是格式服从，不是数学。

框架的价值在于标准化这些细节。lm-eval-harness 提供统一的模板、采样和解析逻辑，报告分数时应该带上框架版本，否则不同实现之间的分数不可比。OpenRouter 的排名榜和 Chatbot Arena 的 Elo 是另一类——它们测的是人类偏好，与基准分数相关性有限，但反映真实使用体验。

评估一次性的成本下不去，就做子集抽测加分档：小模型抽 1% 测，中模型抽 10%，只有大模型和候选上线版本跑全量。
